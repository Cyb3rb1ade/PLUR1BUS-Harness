# Hermes host mode: PLUR1BUS as the memory provider of an existing Hermes

**Status:** HM2 implemented on `feat/hm2-hermes` (harness PR #55, installer in `Cyb3rb1ade/PLUR1BUS-Host-Addons`, add-on version 0.1.0, unreleased) · **Plan:** `docs/superpowers/plans/2026-09-29-hm2-hermes-host-mode-adapter.md` · **Spec:** `docs/superpowers/specs/2026-09-28-plugin-distribution-and-migration-design.md` §A.6 · **Decision:** D88 · **Companion:** `docs/host-adapters.md` (tier 1), `docs/hermes/hermes-host-facts.md` (what was observed on Hermes), `docs/rpc.md`.

Host mode lets a person who runs Hermes and nothing else use PLUR1BUS as Hermes' long-term memory. There is no PLUR1BUS web UI, no channels and no bundled modules: a local **sidecar** (the supervisor and the core, nothing more) holds the memory, and a small **directory provider** inside the Hermes home forwards Hermes' memory hooks to it over the core RPC. Rulings are cited by id (`HM2-R*` from the plan, `HM2-P`/`F*` from the pre-flight ledger).

OpenClaw host mode and the Harness keep separate memory stores. The Harness refuses a configured store path inside an OpenClaw state directory; `plur1bus 1staid check` reports the separate memories as an informational notice when the OpenClaw plugin is configured. To consolidate, migrate with `plur1bus import` or switch the OpenClaw plugin to thin-client mode. The guard does not inspect the plugin store or migrate it automatically.

## Architecture

```
Hermes  --hooks-->  plugins/plur1bus/  (directory provider, Python, no engine)
                       |  vendored plur1bus-memory-client (stdlib only)
                       |  NDJSON JSON-RPC over  <home>/run/core.sock  |  \\.\pipe\plur1bus-<hash>-core
                       v
              plur1bus core  <--  plur1bus supervisor     ("setup --profile host": supervisor + core only)
                       v
              engine store under the PLUR1BUS home (memories, journal, agents)
```

| Part | Where | What it is |
|---|---|---|
| Python client | `clients/python/plur1bus-memory-client/` | Stdlib-only Python 3.11+ client: socket and Windows named-pipe transport (overlapped I/O with deadlines, HM2-R11), the address, token and pid rules of `paths.rs`/`paths.ts`, the server-identity check before the token is sent (S11, HM2-R7), capability discovery from `core.auth`. `_schema.py` and the address vectors are generated by `scripts/gen-python-client.mjs` (HM2-R3). |
| Provider | `hosts/hermes/plur1bus/` | `plugin.yaml`, `__init__.py` (`MemoryProvider` and `register`), `binding.py`, `mapping.py`, `journal.py`, `cli.py`, `_filelock.py`, `_client.py` (imports the vendored client), `config_schema.py` and `README.md`. It vendors the client under `_vendor/` at build time and declares no Python dependency (HM2-R4); it holds no engine, store or model. |
| Sidecar | `plur1bus setup --profile host` | The supervisor and the core, installed under the PLUR1BUS home, started by the OS service (or by setup itself with `--no-service`). Skills and bundled modules are skipped. |
| Installer | `Cyb3rb1ade/PLUR1BUS-Host-Addons` `install-plugin.sh --host hermes` / `install-plugin.ps1 -Host hermes` (add-on version 0.1.0, unreleased) | Detects Hermes (including WSL delegation), installs the pinned sidecar binary and the provider tarball, writes the binding, sets `memory.provider`. Not part of this repository; see the plugin repository's documentation and `docs/manual-release.md` §7. |
| CI | `.github/workflows/hermes-host.yml`, job `python-host` in `.github/workflows/ci.yml` | Real Hermes turns on disposable runners; client and provider tests on Linux, macOS and Windows. |

The provider imports Hermes' `agent.memory_provider` and nothing else from Hermes; `cli.py` imports no Hermes module at all, because Hermes loads it on its own for `hermes plur1bus ...` (`docs/hermes/hermes-host-facts.md` (e)).

## RPC surface and stability

The turn path uses **stable** methods only (HM2-R5): `core.auth`, `memory.recall`, `memory.capture`. In the RPC schema (1.4.0 at merge) `agent.*`, `memory.checkpoint` and the D21 operations (`memory.list`, `memory.show`, `memory.forget`, `memory.correct`, `memory.share`) are not yet stable (ADR-016). The provider calls them only when `core.auth` lists them in its capabilities; their absence switches off that hook or tool, never the provider. Promotion to stable is open (plan Q3). This corrects the plugin-distribution spec's note (F12) that called them stable. HM2 made no RPC change (HM2-R6): the client needs rpc major 1 with minor 3 or later (`E_RPC_VERSION` otherwise); the schema is 1.4.0 at merge.

## Hook to RPC table (as implemented)

| Hermes hook | Behaviour | RPC | Ruling |
|---|---|---|---|
| `is_available()` | True when the binding file parses and `<home>/run/core.token` is readable. Never connects (a probe would consume a pipe instance). | none | HM2-R12 |
| `initialize` | Reads the binding (absent or invalid: provider inert, one warning naming `hermes plur1bus bind`), builds the caller and session key, opens two clients (read side and capture side), warms up within 1 s. | `core.auth`, `agent.open` when advertised (failure ignored) | HM2-R5 |
| `system_prompt_block()` | A fixed one-paragraph note, no RPC, so Hermes' cached system prompt stays stable. | none | HM2-R14 |
| `prefetch(query)` | Trivial prompts (`is_trivial_prompt`) return `""` without a call. Otherwise recalls with `budget.hardMs = recallHardMs` (default 600) and a transport deadline of `hardMs + 400 ms`, and returns `result.joined.text`. Any failure returns `""`. `queue_prefetch` is not implemented. | `memory.recall` | HM2-R14 |
| `sync_turn(user, assistant)` | Queues the completed turn (user and assistant text only, at most 64 messages, request kept 64 KiB under the 4 MiB line limit, over-long content cut and marked `[truncated]`) for **one ordered background worker**; the hook itself does no I/O. Skipped when `agent_context` is not `primary` (cron, subagent) or the binding has `capture: false`. Each turn gets its own `runId`. | `memory.capture` | HM2-R13, F5 |
| `on_pre_compress` | Checkpoint API **v1**: waits up to 2 s for pending captures, then writes a checkpoint when advertised; returns `""`. Hermes' fail-closed checkpoint API v2 is not advertised (plan Q5). | `memory.checkpoint` (`reason: "compaction"`) | HM2-R15 |
| `on_session_end` | Within 2 s: waits for pending captures, then a `session-end` checkpoint and `agent.close`, each only when advertised. | `memory.checkpoint`, `agent.close` | HM2-R5, R15 |
| `shutdown` | Within 2 s: delivers what the worker can, journals every undelivered turn, counts any it could not write as `lost`, closes the clients. | none | HM2-R13 |
| `get_tool_schemas` / `handle_tool_call` | The `plur1bus_memory_list`, `_show`, `_forget`, `_correct`, `_share` tools, offered only for methods the core advertises, except that before `initialize` all five schemas are returned (Hermes builds its tool routing table before `initialize` and before any connection); after `initialize` the list holds only advertised methods. Results are the JSON result, or `{"error": "<E_* code>"}`. Hermes asks for the tool list once right after the provider starts, so a core that is down at session start means no memory tools for that session. | `memory.list/show/forget/correct/share` | HM2-R5 |
| `get_config_schema` / `save_config` | Empty and a no-op: the installer writes the binding. | none | |

Hermes' own message text reaches PLUR1BUS only through `memory.capture`; the recalled block is wrapped by the core in a `<memory-record>` fence, which the real-Hermes CI test checks on the second turn.

## Identity mapping and its limits

The RPC's `CallerIdentity` is closed (`{ channel: "cli", accountId, userId }`), and the engine keeps a proved principal only for channels in its route vocabulary. With no RPC change (HM2-R6) the provider sends:

| Field | Value |
|---|---|
| `channel` | `"cli"` |
| `accountId` | `"hermes:<platform>"`, the platform lower-cased and folded to `[a-z0-9_-]{1,32}`; missing becomes `local` |
| `userId` | Hermes `user_id`, else `chat_id`, else `"local"`; control characters stripped, at most 128 characters |
| session key | the gateway session key when Hermes has one, else the session id; over 256 characters it is cut and ends with `#<16 hex of sha256>` |

The engine derives a distinct user principal per platform and user, with trust `proved` (the same OS user holds the core token). Limits:

- **No group/private setting (plan Q4, accepted).** Hermes turns carry no D22 setting, and the engine does not filter by setting today either; it lands with E7 and a later RPC minor. Until then a memory captured in a group chat is recalled for that user everywhere the same `accountId`/`userId` pair appears. The alternative (disable capture for gateway chats whose `chat_id` differs from `user_id`) was rejected because it loses memories in groups.
- When a later RPC minor adds a host channel, the user-principal hash changes; the engine's user aliases (D24/E7) are for that.
- The provider holds a full-surface core token (HM2-R7): a scoped per-agent client token is HM4/M3.

## Binding file and agent naming

`$HERMES_HOME/plur1bus.json` (schema `plur1bus.hermes-binding/1`, mode 0600) is written by the installer or `hermes plur1bus bind` and only read by the provider.

| Field | Meaning |
|---|---|
| `home` | absolute PLUR1BUS home the sidecar runs with |
| `bin` | the `plur1bus` binary (used by `bind`), or `null` |
| `agentId` | the PLUR1BUS agent this Hermes home uses |
| `recallHardMs` | recall budget, default 600, allowed 50 to 10000 |
| `capture` | default `true`; `false` turns capture off |
| `installedBy`, `version` | provenance, informational |

**One agent per Hermes home** (HM2-R8, amended by HM2-R8a). Hermes reports the profile `default` for every home outside `~/.hermes`, so a profile-name rule would collide. The id is keyed on `realpath(HERMES_HOME)`:

| Home | Agent id |
|---|---|
| the default root (`~/.hermes`; on Windows `%LOCALAPPDATA%\hermes` when `HERMES_HOME` is unset) | `hermes-default` |
| `<default root>/profiles/<p>` | `hermes-<fold(p)>`: ASCII letters lower-cased, every other character outside `[a-z0-9_-]` becomes `-`, 64 characters in total |
| any other home | `hermes-home-<first 8 hex of sha256(realpath)>` |

The default root is `~/.hermes` on POSIX and `%LOCALAPPDATA%\hermes` on Windows (falling back to `%USERPROFILE%\AppData\Local\hermes`), matching the importer's `defaultHermesHome`. Windows paths compare case-insensitively; the hash is over the exact resolved string, so **moving a Hermes home changes its agent id** (a re-bind creates a new agent; the old agent and its memories stay). The JavaScript installer implements the same rules; both are checked against the shared vectors in `hosts/hermes/tests/fixtures/binding-vectors.json` and `hermes-home-vectors.json`.

The agent is created with `plur1bus agent create <id>` (only the supervisor's `config.set` can add one; the provider never writes config). `<plur1bus home>/hosts/hermes-bindings.json` (schema `plur1bus.hermes-bindings/1`) records `{agentId: hermesHome}`; an agent id already bound to a different Hermes home is refused naming both.

### The shared registry lock

The installer (Node) and the provider (Python, `hermes plur1bus bind`) both read-modify-write `hermes-bindings.json`, and Node has no `flock`. Both therefore take the same lock **file**, `<plur1bus home>/hosts/.hermes-bindings.lock`, by existence (details in `docs/hermes/hermes-host-facts.md` (k)):

- create with `O_CREAT|O_EXCL`, mode 0600, content `<pid> <hostname> <ms> <nonce>` (128-bit hex nonce, new for every hold);
- stale after 60 s, or when it names a dead pid of this host and is at least 1 s old (POSIX `kill(pid, 0)`, Windows `OpenProcess`/`GetExitCodeProcess`; the installer uses an equivalent probe, libuv's `process.kill(pid, 0)`: where they differ (libuv's wider `OpenProcess` access rights, pid 0, an exit code of 259) one side judges the pid alive, so a difference only delays a break to the 60 s rule, never breaks a live lock); breaking renames it to `<lock>.break-<nonce>`, compares device/inode and content with what was judged stale, and puts it back with `link` if another process got there first; the lock path is never unlinked directly;
- release renames to `<lock>.rel-<nonce>` and unlinks only if the content holds this holder's nonce; on Windows a sharing or access error on that rename (a reader holding the file open) is retried for up to 2 s, and if the lock is missing because a waiter moved it aside, the holder waits for the put-back and then releases it;
- before writing, the holder re-reads the lock and writes nothing if its nonce is gone (`LockLost`);
- wait at most 10 s, then fail (`LockTimeout`).

The capture journal uses a different, in-process-and-`flock` lock (`_filelock.FileLock`) and is never shared with the installer.

## Degrade and journal rules

Host-adapter rule 1 applies: the provider reports degraded and drops nothing silently (HM2-R13, with F5, F6, F28).

- **Recall** failure or timeout returns `""` and logs one warning per session; the turn continues.
- **Capture** runs on the one worker and is never retried inline. A transport-class failure (`E_TRANSPORT`, `E_TIMEOUT`, `E_CORE_UNAVAILABLE`, `E_SERVER_IDENTITY`, `E_AGENT_UNKNOWN`) appends the entry to `$HERMES_HOME/plur1bus/journal.ndjson`. A permanent refusal drops that entry and counts it as `rejected`, so one bad turn never blocks the queue (F5).
- The journal is mode 0600 (directory 0700), holds at most 1 000 entries and 4 MiB (the oldest are dropped and counted), and is replayed in order, in batches of 50, before the worker's next capture and after a successful recall; replay stops at the first transport-class failure. Replay is at-least-once per batch; duplicates are absorbed by the engine's turn replay guard because every entry carries its `runId`, while two genuinely identical turns get different ids and are both kept.
- No hook touches the journal except `shutdown`, with a bounded lock; message text is written only to the journal (F6): log records, `status` and `selftest` output carry codes and counts. The core token is never logged or stored.
- `E_AGENT_UNKNOWN` degrades and names `hermes plur1bus bind`.
- `lost` in `status` counts turns that could not be written even to the journal.

## Commands: `hermes plur1bus status | selftest | bind`

The commands exist only while `memory.provider` is `plur1bus` (Hermes registers a provider's CLI only for the active provider). Each takes `--json` (one document on stdout) and `--hermes-home <dir>`; `bind` additionally takes `--home <plur1bus home>` and `--bin <plur1bus binary>`. Output carries codes, counts and paths, never message text or the token.

| Command | Does | JSON schema id | Exit |
|---|---|---|---|
| `status` | Binding, core reachability (`rpc`, `contract`, `instanceId`), journal counts (queued, dropped, rejected, lost), last error code. | `plur1bus.hermes-status/1` | 0 |
| `selftest` | Read-only: `connect`, `core.status`, `agent.status` (when advertised), one `memory.recall`. | `plur1bus.hermes-selftest/1` (`checks[]` with `id`, `ok`, `detail`) | 0 when ok, 1 otherwise |
| `bind` | Derives the agent id, runs `<bin> --home <home> --json agent create <id>` (an existing agent is fine), registers it under the registry lock, writes the binding. | `plur1bus.hermes-bind/1` (`ok`, `hermesHome`, `home`, `agentId`, `created`, `error?`) | 0 / 1 |

### Known limitation: the 300 ms core.auth budget of `plur1bus memory ...`

The CLI's own memory commands (`plur1bus memory list`, `recall`, ..., `crates/plur1bus/src/commands/memory.rs`) allow **300 ms** for the `core.auth` handshake. A core that is busy (for example right after replaying a journalled capture, or blocked in a synchronous engine call) can answer later and the command fails with `E_CORE_UNAVAILABLE` and a handshake timeout. The provider is not affected (its client has its own deadlines), but `plur1bus memory ...` users and scripts see this budget; the live tests retry such a transient failure for up to 15 s. What holds the Windows core for more than 300 ms after a replay was not measured (candidates: first-capture lazy module loads, synchronous `node:sqlite` writes); it is tracked with the engine's synchronous-I/O follow-up. A related engine effect: on Windows a `memory.share` can block the core up to 30 s on an ACL read, long enough for the supervisor's hang threshold to restart it; the client live-test stack (`clients/python/plur1bus-memory-client/tests/live/stack.py`) works around it with a 20 s supervisor health interval on `win32` only.

## Install-side behaviour that shapes this guide

These are the sidecar's rules (the installer's own are in PLUR1BUS-Host-Addons):

- **`plur1bus setup --profile host|full`** (HM2-R9). `host` installs the supervisor and the core only; `modules.bundled` and `skills` finish `skipped` with reason `profile-host`, and `config` creates no first agent unless `--agent` is given. The install manifest records `profile` (absent reads as `full`). Without `--profile`, setup keeps the recorded profile, so re-running the harness one-liner never upgrades a host home silently. Do not assume `config.json` exists after a host setup.
- **Refusals** (HB16 vocabulary, `state-root` step; nothing is changed): `profile-invalid` (a value other than `host` or `full`), `profile-change-unsupported` (the requested profile differs from the recorded one; host to full arrives with HM4, and Hermes on an existing full home is also HM4, HM2-R10), `manifest-invalid` (`manifest.json` exists but cannot be read; failing closed so a full install never overwrites a broken host manifest, HM2-R27).
- **Installer facts** (PLUR1BUS-Host-Addons): the sidecar binary is the pinned one named by the signed install feed, not the harness's latest (HM2-R17); `memory.provider` is edited with a minimal line edit, never `hermes config set`, on Hermes 0.21.4 and on any unparsable version (HM2-R24, R24a); the provider directory exists before `memory.provider` is set, and the previous value is restored before the directory is removed on rollback and uninstall (HM2-R17a); another active provider is replaced only with `--replace-provider`; an existing full harness exits 3 `harness-present` (HM2-R10); the minimum Hermes is the `v2026.9.21` line, 0.21.4 = `743ee72` (HM2-R22a); native Windows is labelled beta (plan Q7).

## Files written

| Path | By | What |
|---|---|---|
| `$HERMES_HOME/plugins/plur1bus/` | installer | the provider directory, with `MANIFEST.json` (SHA-256 per file) and `_vendor/plur1bus_memory_client/` |
| `$HERMES_HOME/plur1bus.json` | installer, `bind` | the binding (0600) |
| `$HERMES_HOME/plur1bus/journal.ndjson`, `state.json`, `.lock` | provider | the capture journal, its counters and last error code, its lock |
| `$HERMES_HOME/.plur1bus-installer.json` | installer | rollback state (previous provider, whether the sidecar was fresh) |
| `$HERMES_HOME/config.yaml` | installer only | the `memory.provider` key, with a backup; the provider never writes config |
| `<plur1bus home>/hosts/hermes-bindings.json`, `.hermes-bindings.lock` | installer, `bind` | agent-to-Hermes-home registry and its lock |
| `<plur1bus home>/` (`manifest.json`, `runtime/`, `run/`, `state/`, logs) | `setup --profile host` | the sidecar as for any harness install |
| `~/.local/bin/plur1bus`, `%LOCALAPPDATA%\PLUR1BUS\bin\plur1bus.exe` | installer | the pinned sidecar binary |

`HERMES_HOME` is Hermes' own variable; when it is unset the Hermes home is `~/.hermes`, and on Windows `%LOCALAPPDATA%\hermes`.

## Running the tests locally

From the repository root, Python 3.11 or later (a venv with `clients/python/plur1bus-memory-client/requirements-dev.txt`, hash-pinned, adds the `jsonschema` conformance tests):

```bash
# client, offline (Linux, macOS, Windows; the real named-pipe tests run only on Windows)
python3 -m unittest discover -s clients/python/plur1bus-memory-client/tests -t clients/python/plur1bus-memory-client
# provider, offline (Hermes stubs under hosts/hermes/tests/stubs)
python3 -m unittest discover -s hosts/hermes/tests -t hosts/hermes
```

Live suites need a built core (`pnpm install --frozen-lockfile && pnpm gen && pnpm build && cargo build --release -p plur1bus`) and run against a flat-embedder test core, so nothing is downloaded:

```bash
export PLUR1BUS_BIN="$PWD/target/release/plur1bus" PLUR1BUS_CORE_JS="$PWD/packages/core/dist/core.js"
PLUR1BUS_LIVE_REQUIRED=1 python3 -m unittest discover -s clients/python/plur1bus-memory-client/tests/live -t clients/python/plur1bus-memory-client
PLUR1BUS_LIVE_REQUIRED=1 python3 -m unittest discover -s hosts/hermes/tests/e2e -t hosts/hermes
```

CI runs the same four commands through `hosts/hermes/tests/run_with_timeout.py` (same arguments, same tests) so a hung test fails with its id and all thread stacks after 120 s instead of holding the job: `python3 hosts/hermes/tests/run_with_timeout.py discover -v -s hosts/hermes/tests -t hosts/hermes`. `PLUR1BUS_TEST_TIMEOUT` (seconds) changes the per-test limit, `PLUR1BUS_FIXTURE_TIMEOUT` the limit for class/module fixtures; a test that needs longer takes `@timeout(seconds)` from that module.

`PLUR1BUS_LIVE_REQUIRED=1` makes a live suite that cannot run fail instead of skipping. Also relevant: `node --test scripts/build-hermes-provider.test.mjs` (the release tarball), `cargo test -p plur1bus --test setup_profile` (the profile rules), and `node scripts/lint-hygiene.mjs`.

Tests never touch a real service manager, a real Hermes or a real home: every test uses temporary `HOME`, `USERPROFILE`, `LOCALAPPDATA`, `XDG_*`, `HERMES_HOME` and `PLUR1BUS_HOME`, and setup runs with `--no-service` (HM2-R19). A real Hermes runs only in `hermes-host.yml` on ephemeral GitHub-hosted runners, guarded by `hosts/hermes/tests/e2e/assert_disposable.py`; do not run it on a machine whose Hermes or home you care about.

## Release and artefacts

A harness release carries `plur1bus-hermes-provider-<version>.tar.gz` (deterministic ustar with `MANIFEST.json`, HM2-R21), the client wheel and sdist (attached, not uploaded to PyPI; plan Q2), and `hermes-sidecar.lock.json`, all in `SHA256SUMS` and attested. Provider and client carry the harness version (HM2-R22). The plugin feed's `hosts.hermes` is generated from the lock after a harness release; the order of steps is in `docs/manual-release.md` §7.
