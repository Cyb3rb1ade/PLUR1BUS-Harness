### Policy — is third-party use of ChatGPT/Codex OAuth permitted?
**Unresolved / not officially clarified.** A public GitHub discussion (`openai/codex` Discussion #8338) asked directly whether forking/modifying Codex CLI while using "Sign in with ChatGPT" violates OpenAI's ToS. An OpenAI maintainer (`etraut-openai`, response dated 2025-12-19) confirmed the Codex CLI code itself is Apache-2.0 (fork/modify permitted) but pointed to OpenAI's general Terms of Use rather than giving a definitive answer on OAuth-authenticated third-party harnesses; follow-up questions on commercial wrapper distribution and server-side ChatGPT-OAuth integrations went unanswered as of the discussion's most recent activity. Community tooling (e.g., `opencode-openai-device-auth`, a third-party device-code shim for "ChatGPT Plus/Pro OAuth in headless environments") exists and functions, but this is not the same as OpenAI endorsement. **Verdict for the matrix: "ambiguous / not officially authorized for third-party harnesses"** — treat as restricted pending explicit OpenAI guidance. Sources: [openai/codex Discussion #8338](https://github.com/openai/codex/discussions/8338), [tumf/opencode-openai-device-auth](https://github.com/tumf/opencode-openai-device-auth).

### Policy — Claude subscription OAuth in third-party harnesses (verified, explicit)
**Prohibited**, and this has been restated/clarified as of February 2026. Anthropic's own "Legal and compliance" doc states verbatim (fetched 2026-09-22):

> "OAuth authentication is intended exclusively for purchasers of Claude Free, Pro, Max, Team, and Enterprise subscription plans and is designed to support ordinary use of Claude Code and other native Anthropic applications... Anthropic does not permit third-party developers to offer Claude.ai login into their own applications, or to route requests through Free, Pro, or Max plan credentials on behalf of their users. Moreover, developers may not collect, store, or intermediate Claude.ai credentials or session tokens — sign-in to a Claude account must complete through Anthropic's own flow."

> "The Claude Code binary must not be modified... customers may not remove, disable, or restrict any authentication method built into it."

Independent reporting corroborates a February 2026 clarification event: Anthropic updated legal-compliance language explicitly banning use of Claude Free/Pro/Max OAuth tokens "in any other product, tool, or service — including the Agent SDK." An Anthropic engineer (Thariq Shihipar, per reporting) explained the rationale as unauthorized harnesses generating "unusual traffic patterns without any of the usual telemetry," complicating rate-limit support. Anthropic frames this as a clarification of pre-existing Consumer ToS restrictions rather than a new rule, but multiple outlets describe practical effect as a new enforcement crackdown in Feb 2026. Sources: [Claude Code Legal and compliance](https://code.claude.com/docs/en/legal-and-compliance) (primary, current as fetched), [The Register, 2026-02-20](https://www.theregister.com/2026/02/20/anthropic_clarifies_ban_third_party_claude_access/), [VentureBeat](https://venturebeat.com/technology/anthropic-cracks-down-on-unauthorized-claude-usage-by-third-party-harnesses), [Winbuzzer](https://winbuzzer.com/2026/02/19/anthropic-bans-claude-subscription-oauth-in-third-party-apps-xcxwbn/). **API-key auth remains fully permitted** for third-party harnesses per the same doc, including customer-provisioned keys in dev environments/secrets managers, provided usage is billed to the key owner and not resold/intermediated.

**ADR-005 implication:** the harness must not implement or offer a Claude subscription OAuth login path; it should support Anthropic API-key auth only for Claude, and clearly document this as a policy constraint, not a technical one.

### Policy — Gemini subscription logins in third-party harnesses (verified, explicit)
**Prohibited.** Gemini CLI's (now Antigravity CLI `agy`, D40) own terms/privacy documentation states verbatim (fetched 2026-09-22):

> "Directly accessing the services powering Gemini CLI (for example, the Gemini Code Assist service) using third-party software, tools, or services (for example, using OpenClaw with Gemini CLI OAuth) is a violation of applicable terms and policies."

Violations may lead to account suspension/termination. Note also a related, narrower report of client deprecation: a `google-gemini/gemini-cli` GitHub issue (#28229) shows OAuth failing for some Google AI Pro users with the message "This client is no longer supported for Gemini Code Assist for individuals," suggesting client-ID-level enforcement is already occurring, consistent with the stated policy. Separately, the same source notes Gemini CLI's own unpaid/Google-One-tier access was superseded by **Antigravity CLI on 2026-06-18**; no separate third-party-use carve-out for Antigravity was found in the fetched doc — treat Antigravity OAuth as **the same prohibited category** absent contrary evidence (gap: no direct Antigravity ToS page fetched this session). Community repos (`opencode-antigravity-auth`, `opencode-gemini-auth`) implement unofficial OAuth bridges into these Google consumer flows; a related community-tracked issue (`can1357/oh-my-pi` #12487) explicitly frames such Gemini-CLI/Antigravity OAuth bridging in third-party harnesses as a policy violation. Sources: [Gemini CLI ToS & Privacy](https://geminicli.com/docs/resources/tos-privacy/), [gemini-cli #28229](https://github.com/google-gemini/gemini-cli/issues/28229), [oh-my-pi #12487](https://github.com/can1357/oh-my-pi/issues/12487).

**ADR-005 implication:** same posture as Anthropic — no Gemini-subscription OAuth login path in the harness; Gemini access should go through the AI Studio API key or Vertex ADC/service-account path only.

### Policy — SuperGrok / X Premium+ subscription device-code login
**Exists, but is an unofficial/community integration, not an xAI-documented public client flow, and is tier-gated.** Third-party agent-harness docs (Nous Research's Hermes Agent) describe implementing a browser-based OAuth device-code login against `accounts.x.ai` for users with SuperGrok/X Premium+ subscriptions, explicitly stating no official xAI documentation confirms or endorses this path. The same docs report that **xAI's backend enforces an allowlist on this OAuth API surface and has been observed returning HTTP 403 to standard SuperGrok subscribers** despite active subscriptions (tracked as a known issue), and recommend falling back to the documented API-key path since it is "not subject to the same gating." No xAI policy statement (permitting or prohibiting third-party use of this flow) was found. **Verdict: unverified/undocumented by the vendor, and functionally unreliable due to entitlement gating (403s) — do not treat as a supported flow in the harness; ADR-005 should record it as "unofficial, not recommended."** Source: [Hermes Agent: xAI Grok OAuth (SuperGrok / X Premium+)](https://hermes-agent.nousresearch.com/docs/guides/xai-grok-oauth).

## Prompt caching (cross-provider)

| Provider | Mechanism | Min tokens | TTL | Pricing | Client layout rules | Source |

## Summary of gaps / unverified items (for the report writer and ADR authors)

- **xAI**: model-discovery endpoint, SSE/tool-call/reasoning deviations, and vision support were not deep-dived this session (docs.x.ai/overview gave base URL and auth only). Needs a follow-up fetch of xAI's chat-completions and tool-use reference pages.
- **Google Gemini context caching**: TTL and explicit per-token cache pricing were not found on Google's own `ai.google.dev/gemini-api/docs/caching` page as fetched; the only TTL/pricing figures available come from OpenRouter's secondary characterization and should not be treated as Google-confirmed until cross-checked directly.
- **Vertex AI (ADC)**: the `gcloud auth application-default login` mechanics, required IAM roles, and model-discovery endpoint were not confirmed from a fully-rendered Google Cloud page this session (two fetch attempts hit redirect/nav-only content). The endpoint URL *pattern* (`{region}-aiplatform.googleapis.com/.../publishers/google/models/{model}:generateContent`) is confirmed from Google's REST reference pages, but full ADC setup detail is a gap.
- **vLLM**: the Automatic Prefix Caching feature page fetched this session returned only navigation chrome; default port, default-on/off state, block-size minimum, and prompt-layout guidance are unverified and need a re-fetch (or a read of the vLLM GitHub source directly) before ADR-010 finalizes vLLM-specific caching guidance.
- **Ollama (local and cloud)**: tool-calling support, prompt-caching behavior, and the cloud-vs-local model-discovery endpoint parity were not deep-dived.
- **LM Studio**: whether it performs any cross-request KV/prefix caching, and its health-check endpoint, were not found in the fetched excerpt.
- **mlx-lm (`mlx_lm.server`)**: tool-calling support, caching, and health endpoint are undocumented in `SERVER.md` as fetched — likely genuinely absent (the doc explicitly flags the server as not production-hardened) rather than merely unresearched, but this is an inference, not confirmed.
- **oMLX**: provenance is a community GitHub project (`tbro0815/omlx`, forked at `jundot/omlx`), not a first-party Apple/vendor tool — matches the task's description well but should be treated as lower-authority/community-maintained software when cited in the harness's provider matrix.
- **OpenAI Codex OAuth/device-code technical parameters** (authorization/token endpoint URLs, client_id, scopes, PKCE parameters, device-authorization endpoint, polling interval, loopback port convention): **not publicly documented** by OpenAI as of this check. Per the task's constraint against reverse-engineering private client IDs, these were not pursued further; the harness's OpenAI-subscription auth design (if attempted at all, which is not recommended given the ambiguous policy above) would need to either wait for official documentation or treat this as out of scope.
- **OpenCode Go**: details were sourced from a secondary aggregator (DeepWiki) rather than opencode.ai's own docs; the $10/month subscription framing and shared-infrastructure claim should be re-verified against opencode.ai primary docs before being treated as authoritative in the provider matrix.
