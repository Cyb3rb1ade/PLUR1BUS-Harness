## PART A — Design Learnings

### A1. Agent loop and context/compaction

Hermes runs a **synchronous, single-threaded per-turn loop** (`AIAgent` in `run_agent.py`, called out in `website/docs/developer-guide/architecture.md`, fetched 2026-09-22) that owns provider selection, prompt construction, tool execution, retries/fallback, compression and persistence for one turn at a time; concurrency comes from running many `AIAgent` instances (one per session/subagent/cron job), not from an async loop inside one agent. The turn pipeline is decomposed into many single-purpose modules under `agent/turn_*.py` (`turn_preflight.py`, `turn_context.py`, `turn_context_compaction.py`, `turn_iteration_prep.py`, `turn_request_assembly.py`, `turn_finalizer.py`, `turn_recovery.py`, `turn_overflow.py`) rather than one monolithic loop function.

Compaction/compression is layered, not a single algorithm:

| Mechanism | file:line | Idea worth adopting | Weakness |
|---|---|---|---|
| Three-pass turn-start compaction: idle-triggered (wall-clock gap, opt-in) → preflight token-threshold compression → overflow-warning re-arm, orchestrated by `run_turn_start_compaction` | `agent/turn_context_compaction.py:1-37` | Separating *when to compact* (idle/threshold/overflow) from *how to compact* (below) lets a harness swap summarization strategy without touching turn-loop control flow. `CompactionOutcome` dataclass cleanly reports whether compression ran and whether it was a no-op ("blocked") back to the caller. | Three independent trigger paths sharing one mutable `agent` object is easy to get subtly wrong on ordering; Hermes needed a dedicated `blocked` flag (a compression attempt that "proved... ineffective") — i.e. they hit and patched real bugs here (see `turn_iteration_prep.py`, `test_compression_stall_fallback.py`). |
| Local (client-side) compression: LLM-summarize the old tail into a synthetic "compaction summary" message, huge dedicated module | `agent/context_compressor.py` (5,367 lines total) | Splitting summary-generation prompts by *cause* (manual `/compact`, automatic threshold, post-tool overflow) with distinct prompt templates (`context_compressor.py:231,537,553,569,584`) rather than one generic "summarize this" prompt — each template explicitly re-asserts that persistent memory (their MEMORY.md/USER.md equivalent) remains authoritative post-compaction, which is the right instinct: a harness's own long-term-memory file must survive summarization. | The file is 5,367 lines — a strong signal this concern accreted incrementally and was never re-architected; a from-scratch harness should design one composable compaction pipeline (trigger → selector → summarizer → splice) instead of growing one file per edge case. |
| Native server-side compaction passthrough for OpenAI Responses routes that support it (`context_management=[{"type":"compaction","compact_threshold":N}]`), narrowly scoped to specific model/backend combos, local compressor stays armed as a fallback below the native threshold | `agent/native_compaction.py:1-24` | Prefer the *provider's own* compaction primitive when the wire protocol offers one, and keep it strictly a fallback-arming problem (`LOCAL_TRIGGER_SAFETY_MARGIN = 8_192`) rather than an either/or — avoids re-implementing summarization for backends that already do it server-side, while never trusting a single provider's availability. | Eligibility is done by literal model-name substring matching (`_ELIGIBLE_MODEL_MARKER = "gpt-5.6"`) and official-host URL sniffing (`is_official_codex_base_url`) — brittle string/host heuristics baked into runtime logic; a harness should prefer an explicit provider-capability flag over sniffing. |
| A distinct lightweight "micro-compaction" path (`agent/micro_compaction.py`) alongside the heavyweight compressor | `agent/micro_compaction.py` | Two tiers (cheap incremental trims vs full LLM summarization) avoids paying full-summary cost on every trigger. | Two different compaction subsystems plus a native passthrough is three code paths to keep consistent; not verified how much logic is actually shared vs. duplicated (unverified — would need a deeper diff to confirm overlap).|
| Post-compression session lineage: parent/child session id chain, `session_persistence.py`, `hermes_state_sessions.py` — a compacted session gets a **new** session id with `parent_session_id` pointing at the pre-compaction session (see sessions table below) | `hermes_state_common.py:353,398-399` | Treating compaction as "fork a new session, carry a synthetic handoff message" rather than mutating history in place gives free undo/audit (`hermes sessions` can show lineage) and sidesteps concurrent-writer races on the same row. | Requires a `compression_locks` table (`hermes_state_common.py:517-522`) and a `session_turn_leases` table (`:524-529`) to prevent two compaction attempts or two turns racing on the same conversation — real distributed-lock complexity for what is conceptually a single-process concern; a harness that keeps one agent-loop-per-session in a single process may not need this at all. |

**What NOT to copy:** the file-per-micro-concern explosion (`turn_*.py` × 20, `agent/*.py` × 380 total files) is a Hermes-specific consequence of years of incremental patching under test-driven regression fixes (many files reference specific issue numbers, e.g. `#9948`, `#82154`, `#96811`); a fresh harness should design the turn loop as a small number of clearly-staged functions and resist the urge to spin out a new file per edge case.

### A2. Provider runtime and the three wire modes

`providers/base.py` (415 lines) defines a **declarative** `ProviderProfile` dataclass — one profile per provider, holding auth type, base URL, model catalog, and a set of *hook* methods (`prepare_messages`, `build_extra_body`, `build_api_kwargs_extras`, `create_client`, `fetch_models`, `resolve_aux_model`, `supported_reasoning_efforts`, `default_reasoning_config`) that the transport calls at fixed points. The profile explicitly documents that it is data + hooks only — it "does NOT own client construction, credential rotation, or streaming"; that stays on the agent (`providers/base.py:7-10`).

| Mechanism | file:line | Idea worth adopting | Weakness |
|---|---|---|---|
| `ProviderProfile` as single source of truth, consumed by 7+ independent subsystems (auth, model listing, doctor health-check, config wizard, runtime routing, hostname→provider mapping, aux-model routing) | `providers/README.md:29-54` | This is the single strongest idea to adopt: one declarative record per provider prevents the "add a provider" tax from touching 7 files by hand. A TS harness should define an equivalent `ProviderProfile` interface with hook methods returning plain data, and have every subsystem read from a registry instead of hardcoding provider names. | `providers/base.py:308-331` documents `create_client()` as the *escape hatch* for non-HTTP providers (ACP subprocess shim) returning `Any` — i.e. the abstraction leaks for exotic providers; the "clean" declarative model above still bottoms out in an untyped object for anything that isn't OpenAI-shaped HTTP. |
| Wire-mode dispatch — three modes (`chat_completions`, `codex_responses`, `anthropic_messages`, plus a fourth `bedrock_converse` not requested but present) selected via `agent.api_mode` string, branched throughout the runtime rather than via polymorphism | `agent/chat_completion_helpers.py:724-732,1500-1507,1770-1820`, `agent/agent_init.py:368,380-393` | Enumerating the small, closed set of wire *shapes* as a constant set (`agent/agent_init.py:368`: `"chat_completions", "codex_responses", "anthropic_messages", "bedrock_converse"`) and having every layer (client construction, kwargs building, streaming, error summaries, reasoning normalization) switch on the same string keeps behavior traceable via grep — good for auditability even if not idiomatically OO. | Every call site re-checks `agent.api_mode == "..."` as a string (dozens of occurrences across `chat_completion_helpers.py` alone) instead of dispatching through a `WireAdapter` interface; a TS harness should implement one `WireAdapter` per mode (methods: `buildRequest`, `parseStream`, `normalizeToolCalls`, `normalizeUsage`) selected once, not re-branched at every call site. |
| Reasoning-content normalization: `reasoning` / `reasoning_content` fields flattened to one shape "before string operations in the main stream, Relay recording, synchronous and asynchronous auxiliary streams" (per `developer-guide/provider-runtime.md`, fetched 2026-09-22) | `agent/reasoning_params.py`, doc: provider-runtime.md | Normalize reasoning/thinking content to one internal shape immediately at the stream-parsing boundary, before it touches any downstream consumer (display, persistence, compaction) — avoids N different consumers each re-implementing "is this Anthropic-style `thinking` or OpenAI-style `reasoning_content`". | Per-provider vocabularies for reasoning effort are clamped via a *tri-state* contract (`None`/`()`/tuple) on `supported_reasoning_efforts()` (`providers/base.py:279-306`) that callers must special-case correctly — a subtle three-way boolean-like contract that is easy to get backwards (the docstring itself needs 15 lines to explain it). |
| ACP as a **provider transport**, not just an agent-side protocol: `copilot-acp` profile drives an external ACP subprocess over stdio as if it were an inference API, via `create_client()` returning a `CopilotACPClient` | `plugins/model-providers/copilot-acp/__init__.py:1-60` | Treating "drive another agent CLI via ACP" as just another `ProviderProfile.create_client()` implementation is elegant — it reuses the entire provider-selection, retry, and tool-normalization pipeline for a fundamentally different transport (stdio JSON-RPC instead of HTTP) with zero core changes. | `fetch_models()` here spins up a short-lived ACP session (`session/new`) just to list models because "the CLI may keep its login in an OS credential store with no token Hermes can reuse" — i.e. the abstraction still has to special-case one provider's opaque auth, undermining the "profiles are declarative" claim for this whole class of providers. |
| Tool-call normalization is one of many concerns folded into `agent/chat_completion_helpers.py` (found via wire-mode branch grep) rather than a small isolated module | `agent/chat_completion_helpers.py` (large file, exact line count not captured — treat as unverified single-purpose boundary) | N/A (documents an anti-pattern) | This file is the load-bearing junction for streaming, non-streaming, kwargs building, retry, and summary-attempt building for *all three* wire modes at once (see `_SUMMARY_ATTEMPT_BUILDERS = {"codex_responses": ..., "anthropic_messages": ...}` at `agent/chat_completion_helpers.py:2272`) — a single very large file doing wire-mode-specific work for every mode is exactly the coupling a TS harness's `WireAdapter` split should avoid. |

**What NOT to copy:** string-typed `api_mode` branching sprinkled across dozens of call sites; the file naming convention that puts unrelated per-mode logic into one shared `chat_completion_helpers.py`; the untyped `Any` escape hatch for non-HTTP providers as the *primary* mechanism rather than a documented exception.

### A3. OAuth / device-code flows and credential pools with failover

| Mechanism | file:line | Idea worth adopting | Weakness |
|---|---|---|---|
| Device-code / loopback-PKCE / browser OAuth helpers extracted into one shared module used by every OAuth provider, with environment detection to avoid opening a browser somewhere it can't be reached (SSH, GCP Cloud Shell, Codespaces, Gitpod, Replit, StackBlitz) | `hermes_cli/auth_device_flow.py:1-108` | Centralizing "can we open a graphical browser here?" (`_can_open_graphical_browser`, `:68-88`) and "are we in a remote/headless session?" (`_is_remote_session`, `:49-60`) as shared predicates, consulted by every OAuth flow, is directly reusable: a harness with any OAuth login should ship one `canOpenBrowser()`/`isRemoteSession()` pair instead of duplicating heuristics per provider. | The remote-IDE detection list is a hardcoded set of env var names (`CLOUD_SHELL`, `CODESPACES`, `GITPOD_WORKSPACE_ID`, `REPL_ID`, `STACKBLITZ`, `hermes_cli/auth_device_flow.py:40-46`) that will need continual manual updates as new cloud IDEs appear — an enumeration-of-the-world approach with no fallback signal. |
| `CredentialPool` (3,057-line module) — persistent, multi-credential, same-provider pool supporting several selection strategies (`fill_first`, `round_robin`, `random`, `least_used`) and per-model cooldowns distinct from whole-credential cooldowns | `agent/credential_pool.py:118-127` (strategy constants), `:230-238` (`model_cooldowns` field on `PooledCredential`) | The **per-model cooldown separate from per-credential status** is the standout idea: "a provider may rate-limit one model while the same credential remains usable for its sibling models" (`agent/credential_pool.py:228-230`) — keep that as a first-class concept in a TS credential pool rather than treating a credential as globally up/down. | The pool persists a large amount of provider-specific metadata as an untyped `extra: Dict[str, Any]` bag with an explicit allow-list of ~15 keys (`_EXTRA_KEYS`, `agent/credential_pool.py:164-172`) that must be manually kept in sync with every provider's OAuth response shape — a stringly-typed side-channel that will accrete forever; a harness should model provider-specific OAuth extras as a discriminated union instead. |
| Failure-classified cooldowns: HTTP status alone can't size the cooldown (401 vs 429 vs ambiguous-billing-400), so classification is persisted (`failure_reason`, `FAILURE_REASON_BILLING`, `FAILURE_REASON_BILLING_UNVERIFIED`) and the *sole remaining credential* gets a much shorter cooldown than one of several (`EXHAUSTED_TTL_SOLE_CREDENTIAL_SECONDS = 60` vs `EXHAUSTED_TTL_429_SECONDS = 60*60`) | `agent/credential_pool.py:130-148,175-180` | Distinguishing "this failure is ambiguous and might be a transient content-filter reject, not real billing exhaustion" (`FAILURE_REASON_BILLING_UNVERIFIED`, referencing bug `#82154`: "Anthropic's 'out of extra usage' 400 is returned both for genuine overage and for a server-side content-filter rejection") and giving *unverified* billing failures a short cooldown while *confirmed* depletion re-latches is a sound design a harness should copy conceptually: never treat an ambiguous signal as a certain one. | This required a real production incident (`#82154`) to discover; a harness building this from scratch should assume ambiguous status codes will recur per-provider and design the classifier to be provider-extensible from day one rather than retrofitted. |
| Single-use refresh-token race handling: rotating a single-use OAuth refresh token across multiple cooperating processes sharing one pool, with an explicit "first profile to rotate commits the new value" comment and `CREDENTIAL_PERSIST_FAILED_REASON` for the case where a rotation succeeded upstream but failed to persist locally | `agent/credential_pool.py:100-105,908-926` | The recognition that single-use refresh tokens plus multiple processes is an inherent race, and that a "rotated but not yet visible everywhere" state must be a distinguishable, locally-generated terminal reason (not conflated with a real 400 from the provider) is a good defensive pattern for any multi-process TS harness sharing credentials across workers. | This is a genuinely hard distributed-systems problem the code works around with file-based locking + a `_write_through_provider_state_to_global_root` reconciliation helper (`:788-820`) rather than solving cleanly — a harness that can avoid multiple processes sharing one OAuth credential (e.g. by having exactly one credential-refresh owner process) sidesteps this entire class of bug. |

**What NOT to copy:** the sprawling untyped `extra` dict for provider-specific OAuth metadata; conflating "billing exhausted" and "billing ambiguous" would have been the natural first design and Hermes had to learn the hard way (via `#82154`) to split them — a harness should design that split in up front rather than as a retrofit, but should not copy Hermes's exact string-key vocabulary (`billing`, `billing_unverified`) verbatim; invent its own.

### A4. MemoryProvider ABC lifecycle and disabling the built-in memory loop

`agent/memory_provider.py` (192 lines, fully read) is a clean, small ABC — a good direct reference. Key lifecycle, in order: `initialize()` once at startup → per-turn `prefetch()`/`queue_prefetch()` (recall) → tool dispatch (`get_tool_schemas()`/`handle_tool_call()`) → `sync_turn()` (persist) → `shutdown()`. Optional hooks: `on_turn_start`, `on_session_end`, `on_session_switch`, `on_pre_compress`, `on_delegation`, `on_memory_write`, `identity_signature`, `backup_paths`.

| Mechanism | file:line | Idea worth adopting | Weakness |
|---|---|---|---|
| Exactly one external memory provider allowed at a time, builtin always coexists; enforced at registration (`add_provider`) with a clear warning naming the already-registered provider | `agent/memory_manager.py:326-336` | Simple, auditable invariant — avoids N-provider fan-out ambiguity (whose recall wins?) for the common case, while still letting the file-backed "builtin" memory run alongside any one external provider. A harness can adopt "one pluggable long-term-memory backend, plus always-on local notes" as its default posture. | Schema/tool registration happens *before* the provider is marked active specifically to avoid a provider whose schema load raises blocking every later external provider in the process (`agent/memory_manager.py:338-341`, referencing bug `#9948`) — again, a real bug fix, meaning the naive order (register then load) is a trap a harness should avoid from the start rather than discover via incident. |
| Reserved core tool names: a memory-provider tool schema that collides with a built-in tool name (e.g. `clarify`, `delegate_tool`) is rejected "at the door" before entering the routing table | `agent/memory_manager.py:349-358`, referencing bug `#40466` | Defending the built-in tool namespace against plugin shadowing at registration time, not at dispatch time, is the right layering — dispatch-time shadowing bugs are hard to reason about. | N/A — this is a straightforwardly good pattern. |
| `is_trivial_prompt()` gate — skips memory recall entirely for bare greetings/acks (`"ok"`, `"thanks"`, `"lgtm"`, etc.) via a carefully anchored regex, to avoid "a round-trip and... stale context... derailing one-word replies" | `agent/memory_provider.py:54-72` | A cheap, provider-agnostic short-circuit for the common "no semantic content" turn is worth adopting verbatim as a *concept* (not the regex) — recall/compaction work is wasted on `"ok"`/`"👍"` turns. | The regex is hand-maintained and locale/emoji-specific (explicit Unicode punctuation ranges, `agent/memory_provider.py:61`); a harness might prefer a length + stopword-ratio heuristic that generalizes better across languages. |
| `pre_compress_checkpoint_api_version`: v1 = best-effort `on_pre_compress()` with the raw message list, v2 = opt-in **fail-closed** checkpoint with normalized evidence handoff | `agent/memory_provider.py:35-37,78-80` | Versioning a lifecycle hook's *contract* (not just its signature) so providers can opt into stricter guarantees (fail-closed vs best-effort) without breaking existing providers is a mature plugin-evolution pattern worth copying for any ABC a harness exposes to third parties. | Only two providers reaching v2 is plausible but unverified from the files read; the value of the versioning scheme depends on adoption, which this research did not measure. |
| **Disabling the built-in memory loop** entirely (no MEMORY.md/USER.md system-prompt injection, no nudges) via two independent config flags, `memory.memory_enabled: false` and `memory.user_profile_enabled: false`, resolved by `get_builtin_memory_store_flags()` | `tools/memory_tool.py:229-232`; enforced in `agent/agent_init.py:1254-1289`; regression-tested in `tests/agent/test_builtin_memory_disabled_surface.py:1-13` | This is the direct answer to "how is the builtin loop disabled": two boolean config keys under a `memory:` section, defaulting to `true` (`is_truthy_value(..., default=True)`). A harness should expose an equivalent explicit two-flag (memory vs. profile) disable, not a single "memory: off" switch, since Hermes found users running a third-party provider (Hindsight, Mem0) still paid for the built-in prompt text and tool schema unless *both* were separately turned off (test docstring explains a real bug: listing `memory` under `disabled_toolsets` also disabled the *external* provider's tools, which is the wrong scope). | The toolset-vs-config-flag distinction is confusing: `disabled_toolsets: [memory]` removes tool *schemas* for both builtin and external providers, while `memory_enabled`/`user_profile_enabled` only stops the builtin *store*/prompt injection — two overlapping mechanisms controlling adjacent but different things is a design smell a harness should flatten into one coherent on/off surface per concern. |

**What NOT to copy:** two overlapping disable mechanisms (toolset-based vs. config-flag-based) for what is conceptually one feature; the hand-tuned trivial-prompt regex.

### A5. Platform adapters — maturity and design

Bundled as plugins under `plugins/platforms/<name>/` (22 directories at HEAD): `a2a, buzz, dingtalk, discord, email, feishu, google_chat, homeassistant, irc, line, matrix, mattermost, ntfy, photon, raft, simplex, slack, sms, teams, telegram, wecom, whatsapp`. All inherit `BasePlatformAdapter` (`gateway/platforms/base.py`, 4,678 lines).

| Mechanism | file:line | Idea worth adopting | Weakness |
|---|---|---|---|
| Adapter maturity signal: line count as a rough proxy for feature depth — `discord/adapter.py` 7,359 lines, `telegram/adapter.py` 7,225 lines, `matrix/adapter.py` 3,190 lines, `buzz/adapter.py` 2,004 lines | `plugins/platforms/{discord,telegram,matrix,buzz}/adapter.py` (line counts captured directly) | Telegram and Discord are clearly the most mature/battle-tested (largest, most auxiliary files: Discord alone has `adapter_media.py`, `ffmpeg_utils.py`, `recovery.py`, `voice_mixer.py` — voice-channel support). Matrix and Buzz are comparatively thin. A harness prioritizing platform coverage should treat Telegram/Discord as reference implementations and Matrix/Buzz as "works but less polished." | Line count is a crude proxy — no direct evidence of relative bug-density or test coverage was gathered per adapter (unverified beyond size). |
| Matrix E2EE is a **three-state config** (off / optional / required) requiring `mautrix[encryption]` + system `libolm`, with `required` mode failing closed if crypto deps can't initialize | Per `website/docs/user-guide/messaging/matrix.md` (fetched 2026-09-22); adapter at `plugins/platforms/matrix/adapter.py` | The off/optional/required tri-state for an optional native-dependency feature (rather than a boolean) is a good pattern: it lets an operator explicitly demand encryption and fail loudly, rather than silently degrading to plaintext. | Documented limitations (per the same doc): E2EE "doesn't compile natively on macOS ARM64" (proxy-mode workaround needed), older messages are inaccessible after the bot joins an encrypted room, and upgrades need explicit migration steps — i.e. E2EE is real but operationally fragile; a harness should not assume native crypto libs are trivially portable across host architectures. |
| Buzz platform: relays over a Nostr-based community protocol by **shelling out to an external `buzz` CLI binary** (JSON in/out) rather than embedding a Nostr client library, with `nostr_auth.py` for key-based auth | `plugins/platforms/buzz/plugin.yaml:1-20`, `plugins/platforms/buzz/nostr_auth.py` (177 lines) | Shelling out to a vendor-maintained CLI for a young/niche protocol (rather than vendoring a Nostr client) minimizes maintenance surface for a protocol Hermes doesn't want to own; a harness integrating with an immature external protocol could use the same "process, not library" boundary. | Process-based integration means the adapter's reliability is bounded by an external binary's availability/version drift, and JSON-over-subprocess has no streaming/backpressure story evidenced in the files read (unverified whether Buzz supports live/streamed messages or only request/response). |
| Sibling adapters sharing a behavior mixin for one platform with two transport modes (WhatsApp: unofficial "Baileys bridge" vs official "Cloud API"), mixin listed *first* in MRO so its `format_message` wins | `gateway/platforms/ADDING_A_PLATFORM.md:63-77` | Explicit multiple-inheritance-order documentation ("the mixin must come first... so the mixin's format_message overrides BasePlatformAdapter's generic default") for a real, working dual-transport platform is a directly reusable pattern for any harness that needs to support both an official and unofficial API for the same chat platform. | Python MRO-order-dependent correctness is inherently fragile and undocumented-by-the-language; a TS harness has no exact equivalent (no MRO) and should instead use explicit composition/delegation rather than trying to replicate mixin-ordering semantics. |
| Plugin-first platform integration path requires **zero core changes**: `ctx.register_platform()` plus optional hooks (`env_enablement_fn`, `apply_yaml_config_fn`, `is_connected`, `cron_deliver_env_var`, `standalone_sender_fn`) cover cron delivery, env-var wiring, and status display without touching `cron/scheduler.py`'s hardcoded platform sets | `gateway/platforms/ADDING_A_PLATFORM.md:1-51` | This is the single best idea in this section: a platform plugin can wire itself into cron delivery via a *declared* `cron_deliver_env_var` instead of the core cron scheduler needing a hardcoded per-platform branch. A harness's cron-delivery-to-chat feature should be built plugin-first this way from day one. | The doc itself admits the built-in path still has hardcoded platform sets in `cron/scheduler.py` that a plugin must route around — i.e. the "zero core changes" promise is true for *new* platforms but the core still carries historical special-casing for built-in ones; a from-scratch harness has the chance to never introduce that special-casing at all. |

**What NOT to copy:** MRO-order-dependent mixin composition (no TS equivalent, and it's fragile even in Python); using raw line count as your only maturity signal when actually evaluating adapters to port — verify with tests/issue history too.

### A6. Profiles as isolated instances

| Mechanism | file:line | Idea worth adopting | Weakness |
|---|---|---|---|
| `hermes -p <name>` gives a profile its own `HERMES_HOME`, config, memory, sessions DB, and gateway PID; multiple profiles run concurrently | `hermes_cli/profiles.py` (2,190 lines); per `developer-guide/architecture.md` (fetched 2026-09-22) | Full filesystem-level isolation (one directory tree per profile, `~/.hermes/profiles/<name>/`) rather than a shared DB with a `profile_id` column is the simplest possible isolation model and trivially supports "back up/restore/delete one profile = one directory op." Directly adoptable. | 2,190 lines for profile management alone signals this grew organically; a harness should scope what "profile" needs to control (paths, env, secrets, active session) tightly from the start rather than let it accrete config-migration and CLI-wiring concerns. |
| Context-local `HERMES_HOME` override (`ContextVar`) rather than a global mutable — lets one process serve multiple profiles concurrently on different worker threads/coroutines, each with `copy_context()` | `hermes_constants.py:18-42` (pattern implied, exact override fn read), also `agent/memory_provider.py:21-33` (`ctx_bound`) | Using a context-local (not a global or a passed-everywhere parameter) for "which profile's home directory is active" is the mechanism that makes gateway multiplexing (A11) possible at all — a TS harness with worker-thread or async-local support (Node's `AsyncLocalStorage`) should use the direct equivalent for the same reason. | Every background thread/executor must remember to propagate context explicitly (`ctx_bound`/`spawn_context_thread`, `agent/memory_provider.py:21-33`) — "a worker started with an empty context silently lands on the default profile" is called out as a real failure mode in the docstring itself; this is easy to get wrong at every new call site that spawns a thread. |

### A7. Cron with delivery to chat targets

| Mechanism | file:line | Idea worth adopting | Weakness |

## What our harness must explicitly NOT copy (Hermes-specific idioms to avoid)

1. **File-per-micro-concern proliferation.** `agent/` has ~380 files and many 3,000–7,000-line single files (`context_compressor.py` 5,367 lines, `chat_completion_helpers.py`, `gateway/platforms/base.py` 4,678 lines, `agent/credential_pool.py` 3,057 lines). This is a multi-year incremental-patch signature, not a designed architecture. A fresh harness should design fewer, more cohesive modules with clear interfaces from the start.
2. **String-typed mode dispatch sprinkled across call sites** (`agent.api_mode == "codex_responses"` repeated dozens of times) instead of polymorphic wire adapters. Adopt the *concept* of a small closed set of wire modes; do not adopt the *implementation pattern* of re-branching on a string everywhere it's needed.
3. **Untyped `extra: Dict[str, Any]` escape hatches** for provider-specific state (credential pool OAuth extras, tool-schema metadata). These are stringly-typed side-channels that accrete forever and lose type safety exactly where correctness matters most (auth). A TypeScript harness has no excuse to repeat this — use discriminated unions.
4. **Two overlapping "disable this feature" mechanisms for one concern** (memory: `disabled_toolsets` vs. `memory_enabled`/`user_profile_enabled` config flags controlling adjacent-but-different scopes). Design one coherent on/off surface per feature.
5. **Python-MRO-order-dependent mixin composition** for platform adapters (`class WhatsAppAdapter(Mixin, BasePlatformAdapter)`, order-significant). TypeScript has no MRO; do not attempt to replicate multiple-inheritance-order semantics — use explicit composition/delegation instead.
6. **Incident-driven hardening as the primary Windows-support strategy** (multiple fixes explicitly reference specific bug numbers like `#87134`, `#58265`, `#77579` discovered in production). Budget explicit Windows testing up front instead.
7. **Claiming full isolation for a partial mechanism.** Hermes's own docs admit gateway multiplexing leaves the tool registry, MCP discovery, and terminal/sandbox env vars process-global despite the multiplexing feature's framing as profile isolation. Don't market/design a feature as providing guarantees it only partially provides — say explicitly what remains shared.
8. **Conflating ambiguous and confirmed failure states** as a first design (the billing-vs-billing_unverified split in credential pooling was a retrofit after a real incident, `#82154`). Design the ambiguous/confirmed distinction into any failure-classification system from day one.
9. **Hardcoded, manually-maintained environment-detection allowlists** (the remote-IDE env-var list for OAuth browser-launch detection) as the *sole* signal, with no fallback heuristic — this style of enumeration-of-the-world will always lag reality.
10. Do not reproduce Hermes's exact naming vocabulary (`SOUL.md`, `MEMORY.md`, `USER.md`, `HERMES_HOME`, config key names, tool names) verbatim in a competing product — these are Nous Research/Hermes-specific product identity, not just technical mechanism, and copying them risks both confusion with the Hermes product and plagiarism concerns beyond the technical-design learnings this dossier is scoped to.

### B3. What `hermes claw migrate` does (OpenClaw → Hermes), and reusable source mappings

`hermes claw migrate` (CLI wrapper: `hermes_cli/claw.py`, 526 lines, read in full; actual mapping logic: `optional-skills/migration/openclaw-migration/scripts/openclaw_to_hermes.py`, 3,246 lines, partially read) does the following, in order: (1) locate an OpenClaw source directory (`--source`, else first existing of `~/.openclaw`, `~/.clawdbot`, `~/.moltbot`, else default to `~/.openclaw`); (2) warn if OpenClaw or the Hermes gateway is currently running (token-conflict risk on Telegram/Discord/Slack, which allow only one active session per bot token); (3) **always preview first** (dry-run) regardless of flags; (4) refuse to apply if the plan has unresolved conflicts unless `--overwrite`; (5) take a pre-migration zip backup of the target `~/.hermes/` (unless `--no-backup`), restorable via `hermes import`; (6) execute via `Migrator.migrate()`; (7) never touches/deletes the OpenClaw source directory itself — that's the separate `hermes claw cleanup` command, which renames (archives) it to `<name>.pre-migration[-<date>]`.

**Two presets**, both defined as explicit sets of "migration option" kinds (`MIGRATION_PRESETS`, `openclaw_to_hermes.py:189-226`):
- `user-data` (30 of 31 total option kinds — excludes `secret-settings`, which additionally requires `--migrate-secrets` regardless of preset)
- `full` (all option kinds in `MIGRATION_OPTION_METADATA`, i.e. every row in the table below)

**Secrets are never migrated implicitly** under either preset — `--migrate-secrets` is a separate, explicit flag required in addition to `--preset full`, and only an allow-listed set of secret env vars is eligible even then: `SUPPORTED_SECRET_TARGETS = {TELEGRAM_BOT_TOKEN, OPENROUTER_API_KEY, OPENAI_API_KEY, ANTHROPIC_API_KEY, ELEVENLABS_API_KEY, VOICE_TOOLS_OPENAI_KEY}` (`openclaw_to_hermes.py:38-45`).
