### Pin recommendation & risk for M6
- **MCP**: pin the spec to `2026-07-28` and `@modelcontextprotocol/sdk@1.30.0` (or the `^1.30` range). **Risk — spec churn**: the same release that is "current" also deprecates Sampling, Roots, and Logging, so any ADR-008 design that leans on MCP sampling for model calls or MCP logging for observability should be treated as building on a feature with a removal clock (earliest 2027-07-28) — prefer direct provider APIs / OpenTelemetry for those needs from day one rather than the deprecated MCP utilities. Streamable HTTP is stable and SSE-two-endpoint is already deprecated, so build only Streamable HTTP + stdio.
- **ACP**: pin `@agentclientprotocol/sdk` (schema v1 line) rather than the v2 alpha — v2 is unstable and can break wire compatibility pre-release. **Risk — SDK maturity**: the TS SDK's primary API (`agent()`/`client()`) is fairly new (older class-based API already deprecated once), so expect ADR-level notes on the churn rate of this SDK; the protocol itself, however, has a large and fast-growing ecosystem (registry, many agents/clients) which de-risks betting on it for M6.
- **A2A**: pin `@a2a-js/sdk@1.2.0` against spec `1.0.0`. **Risk — SDK maturity**: 1.2.0 is a young major-version SDK (the protocol itself just reached 1.0 too), so budget for breaking SDK updates; mitigate by running our A2A client/server against `a2a-tck` in CI once integrated.

### Minimum-viable adapter strategy for M6
- **ACP-first, PTY/JSON-fallback second.** Given the ACP ecosystem is both officially maintained (npm `@agentclientprotocol/sdk`) and already has multiple CLIs with *native* support (Gemini CLI (now Antigravity CLI `agy`, D40), Kimi Code, Qwen Code, Copilot CLI, Goose) plus adapter-wrapped support for the two highest-value CLIs (Claude Code via `claude-agent-acp`, Codex CLI via `codex-acp`), a single ACP-client implementation in the harness (using `@agentclientprotocol/sdk`'s `client()` API) covers the majority of target CLIs with one code path.
- **Realistically usable at M6, ranked by confidence:**
  1. **Claude Code** (via `claude-agent-acp`) and **Codex CLI** (via `codex-acp`) — both are already proven end-to-end in a comparable harness (`buzz-acp`), and both also have a non-ACP JSON-streaming headless mode (`claude -p --output-format stream-json`, `codex exec --json`) as a fallback path if the ACP adapter proves brittle.
  2. **Goose** — native ACP (`goose acp`), also proven in `buzz-acp` today.
  3. **Gemini CLI** (now Antigravity CLI `agy`, D40) — native ACP (`gemini --acp`), called out by the ACP project itself as a reference-quality implementation, though not yet cross-validated by a third-party harness the way Claude/Codex/Goose are via buzz-acp.
  4. **Qwen Code, Kimi Code, GitHub Copilot CLI** — all native ACP per their own docs, but none were found cross-validated by an existing third-party harness in this research pass; treat as "should work, budget an integration-test spike before committing."
  5. Everything else in the assignment's list (Grok CLI, OpenCode, pi, agy/Antigravity, Aider, Cline, Cursor CLI) has enough open gaps (see table) that M6 should not depend on them without a dedicated verification spike; for CLIs without confirmed ACP support, the fallback is a **PTY-driven adapter that shells out to the CLI's own non-interactive/JSON mode** where one exists (confirmed to exist for Aider-adjacent tools generally, Cursor CLI headless, Antigravity CLI headless) and otherwise a raw PTY scrape as the last resort.
- **Login/secret reuse pattern**: for Claude Code and Codex CLI specifically, the harness can avoid ever handling raw secrets by reading the CLI's own on-disk credential file (`~/.claude/.credentials.json`, `~/.codex/auth.json`) or by using the CLI's dedicated CI-token mechanism (`claude setup-token` → `CLAUDE_CODE_OAUTH_TOKEN`; Codex's `CODEX_API_KEY`/GitHub Action). This generalizes: **prefer "read the CLI's own credential store" or "use the CLI's documented CI-token flow" over asking the user to hand the harness a raw API key**, wherever a CLI documents one (Qwen Code explicitly recommends env-var/API-key auth for headless use once OAuth is unavailable in CI, which is the same pattern).

## Buzz architecture (from the repo)

Buzz (`block/buzz`, Apache-2.0, Rust monorepo) is a self-hosted team-communication platform built directly on the Nostr wire protocol (NIP-01), where **agents and humans are structurally equal** — every action (message, reaction, workflow step, canvas update) is a signed Nostr event dispatched purely by its `kind` integer, so new features are new kind numbers rather than protocol changes. [file:/home/claude/refs/buzz/ARCHITECTURE.md]

- **Relay is the single source of truth.** All reads/writes go through one relay (`buzz-relay`, built on Axum) per connection — no P2P gossip, no replication. The relay does NIP-42 WebSocket auth, the EVENT/REQ pipeline, and also exposes an HTTP bridge (`/events`, `/query`, `/count`, `/hooks/{id}`, `/media/*`, `/git/*`). Postgres holds events/channels/tokens/workflows/audit; Redis handles presence, typing indicators, and cross-node pub/sub fan-out. [ARCHITECTURE.md system-architecture diagram]
- **Kind ranges**: 0–9999 standard NIP-01..NIP-XX kinds; 10000–19999 replaceable (NIP-16); 20000–29999 ephemeral (not stored/audited, e.g. presence heartbeats); 30000–39999 parameterized replaceable; **40000–49999 Buzz custom kinds** (stream messages/edits, forum posts, workflow execution steps, canvas). `buzz-core::kind.rs` is the single source of truth, with 127 kinds registered at the time of writing. [ARCHITECTURE.md "Kind Ranges"/"Buzz Custom Kinds" tables]
- **Agent identity & auth**: every agent gets its **own Nostr keypair** (generated via `buzz-admin generate-key`, an `nsec1...`), registered as a relay member (a kind:13534 membership event). Agents authenticate over the CLI/HTTP path via **NIP-98** (Schnorr-signed HTTP requests) and over the relay WebSocket via **NIP-42**. This is a deliberately separate identity model from human users — "mint a separate keypair for each" agent. [crates/buzz-acp/README.md "Generating Keys"; crates/buzz-cli/README.md auth table]
- **Channels/threads/DMs/reactions**: `buzz channels {list,create,join,topic}`, `buzz messages {send,get,thread,search,edit,delete,send-diff}` (with `--reply-to`/`--broadcast` for threading), `buzz reactions {add,get}` (NIP-25-based), `buzz dms {open,list}`. All `buzz-cli` I/O is **JSON in, JSON out** on stdout, JSON errors on stderr, with a documented exit-code contract (0 ok / 1 user error / 2 network / 3 auth / 4 other / 5 write conflict) — this is exactly the shape a Node harness would shell out to. [crates/buzz-cli/README.md]
- **`buzz-acp`**: the bridge from Buzz's relay to any ACP-speaking coding agent. It listens for @mentions over the relay's WebSocket, spawns the target agent as an ACP-over-stdio subprocess, and lets the agent reply via `buzz-cli`. It has concretely validated **three** agents: **goose** (native `goose acp`), **codex** (via the `codex-acp` npm adapter), and **claude code** (via `claude-agent-acp`). Configuration is fully env-var/flag driven (`BUZZ_ACP_AGENT_COMMAND`, `--agents` for a pool of 1–32 subprocesses, `--heartbeat-interval`, an inbound "author gate" of `owner-only`/`allowlist`/`anyone`/`nobody` for who can trigger the agent). [crates/buzz-acp/README.md]
- **Crate dependency hierarchy**: `buzz-core` (zero-I/O types/verification) → `buzz-db`/`buzz-auth`/`buzz-pubsub`/`buzz-search`/`buzz-audit`/`buzz-workflow` (all isolated from each other, coordinated only by `buzz-relay`) → `buzz-relay`. Separately: `buzz-acp` (agent harness), `buzz-sdk` (typed Nostr event builders shared by `buzz-acp`/`buzz-cli`), `buzz-media` (Blossom/S3), `buzz-cli`, `buzz-admin` (relay-membership/key-gen ops CLI). [ARCHITECTURE.md "Crate Dependency Hierarchy"]
- **Multi-tenancy note**: Buzz supports a "community" concept — a tenant-visible workspace resolved from the request host (`req.community = resolve_host(connection.host)`) before any auth/event/REQ/REST/media/git/search/workflow handling; unknown hosts fail closed. Relevant if our harness ever needs to address multiple Buzz communities from one deployment. [ARCHITECTURE.md executive summary]

**Gap**: I did not find, in this pass, a canonical Node/TS client library published by the Buzz project itself (`buzz-sdk` is Rust); a Node harness talking to Buzz would either shell out to `buzz-cli` (JSON-in/JSON-out, matches the task's own suggested approach) or hand-roll NIP-01/NIP-42/NIP-98 event construction with `nostr-tools` — both are viable, and this note doesn't pick one for the ADR, it just confirms both are grounded in what the repo actually offers.
