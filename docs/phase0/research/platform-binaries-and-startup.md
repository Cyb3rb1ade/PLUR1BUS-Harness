### Weakest target and degradation options

**Windows arm64 is confirmed as the weakest target**, but not uniformly — several packages (better-sqlite3, @napi-rs/keyring, @lancedb/lancedb, onnxruntime-node/DirectML) actually have *good* win32-arm64 coverage. The concrete risk concentrates in **node-pty** (PTY adapter for coding-CLI shells) and, secondarily, in **whatever ships for @matrix-org/matrix-sdk-crypto-nodejs** if the native NAPI package turns out not to cover win32-arm64 cleanly. Degradation options if a target lacks a prebuild:
1. **node-pty on win32-arm64**: fall back to `node-pty-prebuilt-multiarch` or `@lydell/node-pty`; if both fail, degrade the PTY-backed CLI adapter to a non-PTY (spawn + pipe) mode with reduced fidelity (no real TTY control sequences) as a documented feature-flagged degradation, or require Visual Studio Build Tools for an on-machine `node-gyp` build (re-introduces a native toolchain requirement, conflicts with "Python-free" goal only if VS's own gyp path shells to Python — see item 5).
2. **@lancedb/lancedb on darwin-x64**: either build from source (Rust + cargo, not node-gyp/Python) or accept Rosetta 2 emulation as the "best-effort" fallback explicitly permitted by the objective's framing of darwin-x64.
3. **Matrix E2EE crypto**: prefer `@matrix-org/matrix-sdk-crypto-wasm` universally to eliminate the native-prebuild risk on the weakest target altogether, at a modest crypto-throughput cost that is unlikely to matter for E2EE session/key operations (not a hot path).

### Python-free check (item 5)

None of the packages above declare a hard Python dependency for their **prebuilt** install path. Python only re-enters if a prebuild is missing and the fallback reaches classic `node-gyp` (`node-gyp` itself no longer bundles/requires `gyp`'s Python 2 dependency in current versions — modern node-gyp uses a JS-based build config on most platforms, but on some Windows toolchains and older node-gyp majors, Python 3 can still be invoked as part of `node-gyp configure`). Concretely, the packages most likely to hit this are: **@lancedb/lancedb on darwin-x64** (source build needs Rust/cargo, not Python), **node-pty on win32-arm64** if no prebuild is found (source build via `node-gyp rebuild` — this is the one genuine node-gyp/Python exposure in the matrix), and **better-sqlite3**/**sharp** only in the very unlikely case their bundled prebuilds don't match a future/unusual platform variant. This is a **gap**: this session did not verify the exact node-gyp version pinned by node-pty 1.1.0 or whether it invokes Python on any of the 6 targets — recommend a hands-on CI check (build on a clean machine with no Python installed) as the authoritative test.

- **node:sqlite**: Stability **1.2 – Release Candidate** per `nodejs.org/api/sqlite.html` (fetched 2026-09-22). Timeline: experimental behind `--experimental-sqlite` from v22.5.0 → default-on experimental at v22.13.0/v23.4.0 → RC at v25.7.0. **FTS5 availability is unconfirmed** (not mentioned in the fetched docs excerpt; needs a hands-on `CREATE VIRTUAL TABLE ... USING fts5(...)` smoke test on the actual Node 24/26 builds you intend to ship, since this is the single most consequential unresolved fact for a search-heavy harness). Source: [nodejs.org/api/sqlite.html](https://nodejs.org/api/sqlite.html).
- **TypeScript type stripping (`--experimental-strip-types`)**: **On by default since Node v22.18.0** — running `node file.ts` directly requires no flag on v22.18.0+ (so also true for Node 24 and 26). Node performs **no type-checking**, only syntax stripping (still need `tsc --noEmit` separately for type safety). Unsupported/erasable-only: `enum`, parameter properties, namespaces with runtime code, and import aliases require a real transpile step; everything else (type annotations, interfaces, type aliases, `import type`) runs natively. The stripper is Node's own "Amaro" loader and does not read `tsconfig.json`. This directly answers "can we run TS without a build step?" — **yes, for a subset of TS syntax**, which is likely sufficient for a modern strict-mode codebase that avoids enums/namespaces. Source: [nodejs.org/learn/typescript/run-natively](https://nodejs.org/learn/typescript/run-natively) (official docs, fetched 2026-09-22).
- **Node SEA (Single Executable Applications)**: Core feature stability **1.1 – Active development**; a newer Virtual File System (VFS) asset feature (added v26.9.0) is **1.0 – Early development**, i.e. explicitly not stable. **Native addons are supported** but must be bundled as SEA "assets" and loaded manually via `process.dlopen()` after writing them to a temp file (cannot `dlopen` straight out of the VFS). Cross-platform/cross-compiled SEAs must disable `useCodeCache` and `useSnapshot`. SEA is CI-tested on: **Windows** (unspecified arch breakdown), **macOS arm64 only (not x64)**, and **Linux (all supported distros except Alpine; all arches except s390x)** — this leaves macOS x64 SEA support explicitly unconfirmed/untested by Node's own CI, which matters given this project treats darwin-x64 as best-effort anyway. There is also a **known critical bug**: an SEA built by `postject` on a **Linux arm64 Docker container** produces an ELF binary with a broken hash table that **crashes on `process.dlopen()`** — i.e. any native-addon-bundling SEA build pipeline must build Linux arm64 SEAs on bare-metal/VM arm64, not inside Docker-on-arm64, or on a different host arch entirely. Source: [nodejs.org/api/single-executable-applications.html](https://nodejs.org/api/single-executable-applications.html) (fetched 2026-09-22).
- **`node --snapshot-blob` (startup snapshots)**: not independently re-verified this session beyond general awareness that it exists and interacts with SEA (`useSnapshot`) — **gap**, no fresh primary-source numbers found; the SEA docs do confirm it's mutually exclusive with VFS and with cross-platform SEA builds.
- **`module.enableCompileCache()` / `NODE_COMPILE_CACHE`**: Real-world adoption evidence: npm's own CLI merged a PR enabling it for performance ([npm/cli#7901](https://github.com/npm/cli/pull/7901)) — a strong primary signal this is considered production-ready and worth using. A blog benchmark (secondary source, not an official Node benchmark) reports: general expectation of "**20–30% boost in server start-up time**" attributed to Node 25's compile-cache work; the author's own measurement went from a median **290ms → 238ms** (~20% faster) for their app, and in a Cloud Run cold-start scenario, bundling + prewarming brought first-render time from **1.64s → 1.4s**. Treat these specific numbers as one blog's measurement, not a controlled/official benchmark. Source: [ben3d.ca/blog/introducing-node-prewarm](https://ben3d.ca/blog/introducing-node-prewarm).
- **ESM loading cost**: not independently benchmarked this session — **gap**. General industry consensus (not specifically re-verified here) is that ESM's mandatory resolution/loader hooks add measurable per-module overhead versus CJS `require`, which is one reason ecosystem discussion around compile caching and bundling (below) is active; no specific ms numbers were found and cited this session.

### CLI cold-start technique comparison

| Technique | What it does | Evidence found this session |
|---|---|---|
| Lazy dynamic `import()` for heavy deps | Defers loading onnxruntime/lancedb/sharp until the code path that needs them actually runs, so a CLI's `--help`/simple-subcommand paths stay fast | No specific ms numbers found this session (gap); mechanism is well-established Node/ESM behavior, not independently benchmarked here |
| Avoiding heavy deps at top-level module scope | Prevents eager `require`/`import` graph traversal from paying for native-module load + init cost on every invocation | Same as above — mechanistically sound, no fresh numbers cited |
| Bundling with esbuild/rolldown | Collapses the module graph into fewer files, reducing filesystem/resolution overhead, which the compile-cache blog above notes matters *"particularly for serverless platforms where filesystem I/O costs can offset compilation savings"* — implying bundling and compile-cache are complementary, not redundant | [ben3d.ca](https://ben3d.ca/blog/introducing-node-prewarm) explicitly calls out that bundling-first was necessary to see the Cloud Run improvement |
| V8 code cache / `module.enableCompileCache` | Skips re-parsing/re-compiling JS on repeated cold starts by caching V8 bytecode | ~20–30% startup improvement per the same blog + npm CLI's own adoption ([npm/cli#7901](https://github.com/npm/cli/pull/7901)) |
| Node SEA + snapshot/code-cache | Ships a single binary with an optional startup snapshot | Cannot combine `useVfs` with `useSnapshot`/`useCodeCache`; cross-platform SEA builds must disable both — meaning SEA's startup-snapshot benefit is only available for same-platform, non-VFS builds. Source: [nodejs.org SEA docs](https://nodejs.org/api/single-executable-applications.html) |

**Bun as an alternative runtime (documentation only, per instructions — not a decision input):**

## Service management (per OS, without admin rights)

**Caveat on verification:** two direct fetches this session (Arch Wiki `systemd/User`, freedesktop.org `user@.service` man page) either failed (bot-blocked) or didn't contain the specific non-root/`loginctl enable-linger` confirmation, and a Microsoft Learn Task Scheduler overview page fetched did not contain the non-admin-task-creation detail either. The statements below reflect this session's general technical knowledge of these well-documented OS mechanisms, **not a freshly fetched primary-source quote**, and should be spot-checked against `man systemd.user`, `man loginctl`, and `docs.microsoft.com`'s Task Scheduler security-context docs before being asserted as verified rows in the platform matrix.

- **macOS — launchd user agents**: A non-admin user can place a plist in `~/Library/LaunchAgents/` and `launchctl bootstrap gui/$(id -u) <plist>` (or the older `launchctl load`) to run a per-user background process at login, with no `sudo`/admin rights required. This is the standard, long-established mechanism for user-level services on macOS (distinct from admin-only `/Library/LaunchDaemons` system daemons). **Unverified this session against a fresh Apple primary source — gap.**
- **Linux — systemd user units**: A non-root user can write unit files to `~/.config/systemd/user/` and manage them with `systemctl --user enable|start`. By default, `--user` units only run while that user has an active login session; `loginctl enable-linger <user>` allows the user's systemd instance (and thus their `--user` units) to start at boot and persist without an active login session — `enable-linger` for one's **own** account typically does not require root (policy-dependent via polkit), though some distros restrict it to admins. This is the standard non-root path referenced generically by community write-ups such as [Non-Root Systemd Scripts (brandonrozek.com)](https://brandonrozek.com/blog/non-root-systemd-scripts/) and [ArchWiki: systemd/User](https://wiki.archlinux.org/title/Systemd/User) (the latter could not be fetched this session — blocked by anti-bot protection — so treat as a pointer, not a confirmed quote). **Distro-level `enable-linger` permission policy is a gap** that should be tested on the actual target distros (Ubuntu 22.04/24.04) rather than assumed.
- **Windows — Task Scheduler / per-user**: A standard (non-admin) user can create a scheduled task that runs under their own account without elevation via `schtasks /create /sc onlogon /tn <name> /tr <path>` (or the Task Scheduler UI), as long as the task's run level is not set to "Run with highest privileges" and it targets the current user rather than SYSTEM/another account — this is standard, widely-documented Windows behavior. The per-user Startup folder (`shell:startup`, i.e. `%APPDATA%\Microsoft\Windows\Start Menu\Programs\Startup`) is an even simpler no-admin autostart mechanism. **This session's fetch of the Microsoft Learn Task Scheduler overview page did not contain an explicit non-admin confirmation — flag as a gap needing a direct check of the Task Scheduler security-context / "Task Actions" documentation**, e.g. `learn.microsoft.com/windows/win32/taskschd/task-scheduler-schema` or the "Configure a task's run level" documentation, before this row is marked "verified" in the platform matrix.
- **Cross-cutting implication for a non-admin installer**: all three OSes support a genuinely admin-free path to "start my CLI's background component at login," but the *persistence-without-active-session* guarantee differs: launchd user agents and Windows per-user scheduled tasks with an "at logon" trigger both effectively require a session to have started at least once; systemd's `loginctl enable-linger` is the one mechanism that can make a background component survive **without** any interactive login at all (useful for a headless/server-like use of the harness), and its exact non-root permission story per-distro is the piece most worth testing directly rather than assuming.
