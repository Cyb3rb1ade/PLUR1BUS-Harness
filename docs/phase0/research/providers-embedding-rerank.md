## Key Question 1: In-process (Transformers.js + onnxruntime-node) — package versions, ONNX availability, licenses, and embedding-identity fields

### Takeaway
`@huggingface/transformers` (v4.x) bundles both `onnxruntime-web` and `onnxruntime-node` as dependencies, with `onnxruntime-node` prebuilt for Windows/Linux/macOS on both x64 and arm64 (CPU EP only on Linux arm64 — WebGPU is not yet prebuilt there). Of the requested models, `intfloat/multilingual-e5-small/base/large` (MIT) and `BAAI/bge-reranker-v2-m3` (Apache-2.0) are the only ones with clearly free-for-commercial licenses; the two Jina models (`jina-embeddings-v3`, `jina-embeddings-v5-text-nano`) and `jina-reranker-v2-base-multilingual` are all **CC BY-NC-4.0** (non-commercial, contact sales@jina.ai for commercial use). Strong permissively-licensed 2025–2026 alternatives with ONNX mirrors exist: Qwen3-Embedding/Reranker-0.6B (Apache-2.0, via `onnx-community/*-ONNX`), Alibaba `gte-multilingual-base`/reranker (Apache-2.0, via `onnx-community/gte-multilingual-base`), and `nomic-ai/nomic-embed-text-v2-moe` (Apache-2.0, MoE, Matryoshka).

### Cited Findings

**Package versions (checked 2026-09-22):**
- `@huggingface/transformers` latest published version is **4.3.0**; its `package.json` lists dependencies `onnxruntime-web@1.31.0-dev.20260914-8d85527a0` and `onnxruntime-node@1.30.0` — [registry.npmjs.org/@huggingface/transformers/latest](https://registry.npmjs.org/@huggingface/transformers/latest), checked 2026-09-22.

### Inferences
- Given multilingual-e5-small/base/large, Qwen3-Embedding/Reranker-0.6B, and gte-multilingual-base/reranker all have `onnx-community/*` mirrors, the practical in-process default stack for a permissively-licensed setup is: **multilingual-e5-small (MIT) for a small/cheap default**, **Qwen3-Embedding-0.6B (Apache-2.0) for a stronger general-purpose option with Matryoshka + long context**, and **Qwen3-Reranker-0.6B or BAAI/bge-reranker-v2-m3 (both Apache-2.0) for reranking** — avoiding the Jina family entirely if the product needs unrestricted commercial redistribution, since all three Jina models checked here are CC BY-NC-4.0.
- The onnxruntime-node README's platform matrix implies that a memory engine targeting Windows arm64 and Linux arm64 in-process should stick to the **CPU execution provider** on Linux arm64 (no prebuilt WebGPU there), and can consider DirectML or WebGPU on Windows arm64.

### Gaps
- Exact embedding dimension, Matryoshka support, and max-token cap for `intfloat/multilingual-e5-base` and `multilingual-e5-large` were not independently re-fetched from their own model cards this pass (inferred by convention from the e5-small card and search snippets only) — a follow-up fetch of those two cards is needed for exact figures.
- The full `jinaai/jina-embeddings-v3` README was too large to render in the fetch tool; dimension, Matryoshka granularity, and exact max-token figure for v3 specifically were not independently re-confirmed (only v5-text-nano was fully confirmed).
- `Alibaba-NLP/gte-multilingual-base`'s embedding dimension, Matryoshka support, max tokens, and prefix scheme were not returned by the fetch (only license and language list came through) — needs a direct re-check.
- Whether `nomic-embed-text-v2-moe` has an official ONNX conversion (vs. only GGUF) was not confirmed.
- Approximate RAM at int8 vs fp32 for each of the above models was **not researched this pass** — no source was fetched for memory footprint figures; this is a full gap across the entire in-process table and should be sourced separately (e.g., from HF model card "safetensors" file sizes times a quantization multiplier, or from `@huggingface/transformers` quantization docs).
- Revision/commit-hash pinning fields (the "embedding identity" `revision` field) were not captured — only branch/`main` was used for all citations above; production spec should pin exact commit SHAs per HF's model versioning, and this pass didn't record them.

## Key Question 2: Remote embedding APIs

### Takeaway
OpenAI, Google Gemini, Cohere, Jina, Voyage, and Mistral all offer hosted embedding APIs with `dimensions`/Matryoshka-style truncation support (except Cohere, not independently confirmed this pass) and per-provider `task_type`/`input_type` parameters for asymmetric query/document embedding. OpenRouter has added an embeddings API (OpenAI-compatible `/v1/embeddings`) that routes to upstream providers. Anthropic explicitly does **not** offer an embeddings API and its own docs recommend Voyage AI instead. xAI, Nous Portal, and OpenCode Zen show no evidence of offering embedding APIs in the sources checked.

### Inferences
- For a Node.js memory engine needing a single "remote fallback" embedding provider with Matryoshka-style dimension control, OpenAI `text-embedding-3-small`/`-large` and Google `gemini-embedding-2`/`-001` are the most mature choices given confirmed `dimensions`/output-dimensionality controls; Voyage's `voyage-4` family is the strongest domain-specialized alternative (finance/law/code) and is also Anthropic's own recommended pairing for Claude-based stacks.
- OpenRouter's embeddings API being framed as routing to upstream models under one interface suggests it should be modeled in a provider matrix as a **pass-through/proxy provider** whose actual "embedding identity" (model id, dimension, revision) is whatever the pinned upstream model reports — this needs explicit upstream-model pinning in the adapter's embedding-identity record, exactly as the objective's key question anticipates.

- No exact $/M-token pricing figures were captured for OpenAI, Google Gemini, Voyage, Mistral in this pass (only relative/illustrative figures or "not confirmed") — a dedicated pricing-page fetch per provider is needed for the provider-matrix's cost column.

## Key Question 3: Remote rerank APIs

### Takeaway
Cohere, Jina, and Voyage all expose a `{query, documents[], top_n|top_k} → {results: [{index, relevance_score}]}` shaped rerank endpoint with scores in [0,1], but scores are **not comparable across providers/models** — at least one major hosted rerank API documents that its relevance scores are only meaningful within a single request (i.e., against the same query/document set), not as an absolute, cross-model quality measure.

### Cited Findings
- Cohere Rerank request: `{model, query, documents: [string...], top_n?}`; response: `{results: [{index, relevance_score}], id, meta}`. Current models include `rerank-v4.0-pro` and `rerank-v3.5`. Scores are floats in [0,1] (examples shown: 0.999071, 0.7867867, 0.32713068) — [docs.cohere.com/reference/rerank](https://docs.cohere.com/reference/rerank), checked 2026-09-22.
- Jina Reranker request: `{model, query, documents: [string...], top_n, return_documents}`; current models: `jina-reranker-v3.5` (0.6B, listwise, 131K context, hybrid attention + self-distillation), `jina-reranker-v3` (listwise, 131K context), `jina-reranker-m0` (multimodal/visual documents), `jina-reranker-v2-base-multilingual` (cross-encoder, 100+ languages), `jina-colbert-v2` (late-interaction, 89 languages). Pricing shares Jina's token-tiered plan (Free 100RPM/100K TPM, Paid 500RPM/2M TPM, Premium 5,000RPM/50M TPM) — [jina.ai/reranker](https://jina.ai/reranker/), checked 2026-09-22.
- Voyage Rerank request: `{query, documents: [string...], model, top_k, truncation}`; response: `{results: [{index, document, relevance_score}], total_tokens}`. Current models: `rerank-3` (preview, highest accuracy), `rerank-3-lite` (preview), `rerank-2.5` (generalist, instruction-following), `rerank-2.5-lite`. Max 1,000 documents/request; context 32K tokens for rerank-2.5; scores are floats in [0,1] — [docs.voyageai.com/docs/reranker](https://docs.voyageai.com/docs/reranker), checked 2026-09-22.
- HF Text Embeddings Inference (TEI) `/rerank` request: `{query, texts: [string...], raw_scores: bool}` — [huggingface.co/docs/text-embeddings-inference quick tour](https://huggingface.co/docs/text-embeddings-inference/en/quick_tour), checked 2026-09-22 (exact response shape not captured — see Gaps and Local Servers section).
- vLLM documents both a `Score API` and a `Cohere Rerank API` (i.e. an endpoint compatible with Cohere's `/v1/rerank` request/response shape) under its pooling-models docs, but the exact JSON examples were not rendered by the fetch tool this pass — [docs.vllm.ai/en/latest/models/pooling_models/scoring](https://docs.vllm.ai/en/latest/models/pooling_models/scoring/), checked 2026-09-22.
- llama.cpp's server README documents a `--rerank`/`--reranking` flag ("enable reranking endpoint on server, default: disabled") and both `/v1/rerank` and `/rerank` endpoints (added per PR #9510), referencing `query, documents, top_n` parameters, but the exact JSON request/response examples were not rendered by the fetch tool this pass — [github.com/ggml-org/llama.cpp tools/server/README.md](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md), checked 2026-09-22.
- oMLX exposes `POST /v1/rerank` alongside `POST /v1/embeddings`, described as a "drop-in replacement for OpenAI and Anthropic APIs," supporting reranker models like ModernBERT and XLM-RoBERTa — but exact JSON schema was not documented in the fetched excerpt — [github.com/jundot/omlx](https://github.com/jundot/omlx), checked 2026-09-22.
- On score comparability: a technical article on cross-encoder reranker score calibration states "at least one major hosted rerank API states in its docs that relevance scores are only meaningful within a single request," directly supporting the "scores not comparable across rerankers" premise — [dev.to: Cross-Encoder Reranker Score Calibration — Why 0.5 Cutoffs Fail](https://dev.to/ji_ai/cross-encoder-reranker-score-calibration-why-05-cutoffs-fail-1k9b), checked 2026-09-22.

### Inferences
- A normalized `rerank(query, documents[], top_n) → [{index, score}]` adapter is directly achievable for Cohere, Jina, and Voyage since all three already return `{results: [{index, relevance_score}]}` (or `{index, document, relevance_score}` for Voyage) — the adapter mainly needs to (a) map each provider's field name (`relevance_score` in all three) to a common `score` field, and (b) never mix scores from different reranker models/providers in a single downstream ranking without re-normalizing per the calibration-article citation above.
- TEI, vLLM, llama.cpp, and oMLX likely follow the same `query`/`documents-or-texts`/`top_n` request convention (TEI uses `texts` instead of `documents`; vLLM explicitly documents Cohere-compatible rerank semantics) — but exact response field names for TEI, vLLM, llama.cpp, and oMLX rerank endpoints need direct verification (see Gaps) before finalizing the adapter's field-mapping table.

### Gaps
- TEI's `/rerank` **response** JSON shape (does it return `{index, score}` pairs, sorted or unsorted, and under what field name?) was not captured — the fetch only returned the request shape.
- vLLM's exact `/v1/score` and Cohere-compatible `/v1/rerank` request/response JSON examples were not rendered (page structure confirmed, examples not shown) — needs a direct fetch of `vllm/examples/pooling/score/rerank_api_online.py` on GitHub for a concrete example.
- llama.cpp's exact `/v1/rerank` and `/rerank` request/response JSON (field names, whether it nests under `results`, whether score key is `score` vs `relevance_score`) was not captured — needs a direct read of PR #9510 or a runtime test against a live `llama-server --reranking` instance.
- oMLX's exact rerank JSON schema (request/response field names) was not captured, only the endpoint's existence and OpenAI-compatibility framing.
- BAAI/bge-reranker-v2-m3 and Qwen3-Reranker-0.6B were not found behind any of the checked hosted rerank APIs (Cohere/Jina/Voyage) — they are local/self-hosted-only among the models reviewed here, served via TEI/vLLM/llama.cpp/oMLX/Infinity rather than a first-party hosted API.

## Key Question 5: Rerank wire formats (for a normalized adapter)

### Takeaway
All hosted rerank APIs reviewed (Cohere, Jina, Voyage) converge on the same request shape (`query`, `documents`/`texts`, `top_n`/`top_k`) and response shape (`results: [{index, ...relevance_score}]`), making a normalized `rerank(query, documents[], top_n) → [{index, score}]` adapter straightforward for those three; local/self-hosted servers (TEI, vLLM, llama.cpp, oMLX) appear to follow similar conventions but their exact JSON shapes need direct confirmation (see Gaps in Key Q3/Q4) before being hard-coded into the adapter spec.

### Cited Findings — request/response shapes by provider

**Cohere** (`docs.cohere.com/reference/rerank`, checked 2026-09-22):
```json
// Request
{ "model": "rerank-v3.5", "query": "...", "documents": ["...", "..."], "top_n": 3 }
// Response
{ "results": [ { "index": 0, "relevance_score": 0.999071 } ], "id": "...", "meta": { } }
```

**Jina** (`jina.ai/reranker`, checked 2026-09-22):
```json
// Request
{ "model": "jina-reranker-v3.5", "query": "...", "documents": ["...", "..."], "top_n": 3, "return_documents": false }
// Response shape not fully captured — response is expected to mirror Cohere's {results:[{index, relevance_score}]} pattern per Jina's Cohere-API-compatibility positioning, but this was NOT independently confirmed with an exact JSON example this pass (Gap)
```

**Voyage** (`docs.voyageai.com/docs/reranker`, checked 2026-09-22):
```json
// Request
{ "query": "...", "documents": ["...", "..."], "model": "rerank-2.5", "top_k": 3, "truncation": true }
// Response
{ "results": [ { "index": 0, "document": "...", "relevance_score": 0.94140625 } ], "total_tokens": 1000 }
```

**HF TEI** (`huggingface.co/docs/text-embeddings-inference`, checked 2026-09-22):
```json
// Request
{ "query": "...", "texts": ["...", "..."], "raw_scores": false }
// Response: NOT captured in this pass (Gap) — field returns "ranking scores for each text" per docs prose, exact JSON not shown
```

**vLLM, llama.cpp, oMLX**: endpoints and flags confirmed to exist (see Key Q3/Q4 tables and citations) but exact request/response JSON was **not captured** in this research pass for any of the three — treat all three as Gaps requiring a follow-up fetch or a live smoke-test against a running instance.

**Score comparability across rerankers**: NOT comparable. Cited support: "at least one major hosted rerank API states in its docs that relevance scores are only meaningful within a single request" — [dev.to: Cross-Encoder Reranker Score Calibration](https://dev.to/ji_ai/cross-encoder-reranker-score-calibration-why-05-cutoffs-fail-1k9b), checked 2026-09-22. This directly implies a normalized adapter must not blend or threshold scores across different rerank models/providers without re-calibration (e.g., re-normalizing to a rank rather than an absolute score when combining outputs from multiple rerankers).

### Inferences
- A minimal normalized adapter interface is: `rerank(query: string, documents: string[], topN?: number, model: string) => Promise<{index: number, score: number}[]>`, where the adapter's per-provider mapping layer renames each provider's `documents`/`texts` request field and `relevance_score`/`score` response field into this common shape. Given Cohere and Voyage both return `results: [{index, relevance_score}]` almost identically, that pairing can be implemented and tested first; Jina, TEI, vLLM, llama.cpp, and oMLX need their exact response shapes confirmed before the adapter can be considered complete for those five.

### Gaps
- Exact JSON response shapes for Jina, TEI, vLLM, llama.cpp, and oMLX rerank endpoints were not captured (only request shapes or endpoint existence, in each case) — this is the single largest remaining gap for finishing the ADR-006 adapter spec and should be the first follow-up (either via a second research pass fetching raw GitHub file content / API reference pages, or via a live integration smoke test against each running server).
- Whether Jina's rerank endpoint response is truly Cohere-compatible (same `results: [{index, relevance_score}]` shape) is an inference, not a confirmed fact.
