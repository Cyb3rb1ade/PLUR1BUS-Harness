## (1) Feature crons and dreaming

### Takeaway

PLUR1BUS ships **11 shipped cron specs** in one table (`lib/setup/feature-cron-plan.js:25-170`) plus **6 more features reachable only by RPC/CLI**, all dispatched through a single model-free path `openclaw cron` → `scripts/run-feature-cron.mjs` → Gateway RPC `plur1bus.feature.run` → the `/plur1bus internal <feature>` handler in `index.js:7498-8272`. Provisioning is *not* done by the plugin at runtime: it is a best-effort external script (`scripts/setup-feature-crons.mjs`) that is **contractually forbidden from ever failing** and returns exit 0 from at least nine distinct silent-skip branches. Observability is a single `api.logger.info` line per run plus a JSON `ReplyPayload` printed to the cron job's stdout; there is **no per-job status file, no last-run/next-run surface, no per-run log file, and no counters** — the only persisted run state is `runs.json` `completed[runKey]` for rem-dream/reflection/compaction and a 20-hour bootstrap throttle marker.

### Inferences

- The "never ran / unclear whether it ran" report is over-determined: at least four independent mechanisms produce a silent no-op (setup script exit-0 contract, fail-closed native probe that *disables* jobs, `sourceConfig`-only feature selection, and the `no_llm_config`/`too_few_memories` early returns), and none of them writes durable state a human or a doctor command can inspect afterwards.
- A new host contract should invert the default: every job run should append one record to a per-agent run ledger (job, partition, startedAt, durationMs, outcome, reason, counts) *before* any early return, so that "skipped because X" is as visible as "completed".
- The `singleton: true` flag on `gc-run` is the only job-level concurrency declaration; every other job is provisioned per agent with hand-tuned staggering encoded in comments (`staggerPersonaEvolveSchedule`, `staggerAutoAcceptStaleSchedule`, `staggerEmbeddingDrainSchedule` referenced at `feature-cron-plan.js:34,75,90`). A scheduler ADR should make staggering declarative.

### Gaps

- The stagger functions themselves (`staggerPersonaEvolveSchedule` etc.) are referenced in comments in `feature-cron-plan.js` but I only read lines 1-600 of that 1377-line file; their exact offsets per agent were not verified.
- Whether REM trend output actually influences recall ranking is not established — I found the writers (`appendPatterns`, `analyzeTrends`) but did not trace a reader in `lib/recall-pipeline.js`.
- `MEMORY.md` as a promotion target: **not found** in this repo. The diary target is `DREAMS.md`.
- No status/metrics HTTP or gateway surface for job runs was found; `lib/control-plane-health.js` exists but I did not open it, so I cannot say it lacks one — treat as unverified.

## (2) Embedding and reranking

### Takeaway

Two embedding providers (OpenAI SDK, local ONNX via `@huggingface/transformers`) and two rerankers (Cohere HTTP, local ONNX) behind a small factory; the brief's **15 s embed / 5 s rerank defaults are confirmed** (`config-normalize.js:63`, `:158`). Local models are pinned by revision **and SHA-256 per artifact** and downloaded from `https://huggingface.co/{repo}/resolve/{revision}/{path}`. Two of the five pinned models are **CC BY-NC 4.0** and require an explicit `acceptNonCommercialLicense` flag. A single scalar `vectorDim` is threaded through every pool, so **one uniform embedding dimension is assumed across all recall tables**.

### Inferences

- ADR-006 can treat the scoped-embedding IPC as the natural service boundary: its envelope is already model/dimension/fingerprint-bound and transport-agnostic apart from the socket path and the Linux abstract-socket election. Swapping the transport is a ~30-line change; the protocol needs none.
- The dual 5 s rerank timers (provider-internal + pipeline `Promise.race`) mean a Cohere rerank can be abandoned by the pipeline while the HTTP request is still in flight; a single owner for the timeout is cleaner.
- Because the artifact hashes are per-file and the Jina v3 weights come from a third-party re-export repo (`ldwformat/…`) pinned by revision, the supply-chain story is stronger than "trust HF" but depends on that third-party repo staying online — a mirror/offline bundle is worth an ADR line.

### Gaps

- I did not measure or find a configured **batch size** for the local provider; `MAX_EMBED_TEXTS = 64` (IPC) and `MAX_EMBED_CHARS = 10_000` (host adapter) are the only caps I verified. A `batchSize` config key was **not found**.
- Local-provider request timeout: I found no per-call timeout inside `embedding-local-transformers.js` (the 15 s default is on the OpenAI path via `requestTimeoutMs`); the local path appears to be bounded only by the caller's scheduler timeout. Unverified beyond the greps I ran.
- I read `lib/providers/local-transformers-shared-pool.js` only via grep; its eviction/idle policy is not fully established.
- The Jina v5 nano and BGE reranker model cards were not fetched — only the v3 card was checked externally. Their licenses are asserted here from the code's own metadata (`local-model-artifacts.js:79-80` for v5 nano; BGE's profile carries **no** license field).

## (3) ACL, principal, scopes

### Takeaway

Three scopes — `agent-private` (default), `workspace`, `user` — enforced by one pure function `checkAccess(ctx, memory)` over a validated ownership tuple. "User" is identified by a **hash of `[channel, accountId, userId]`**, not by a raw user id. `/share` is genuinely copy-never-move, idempotent, and it **re-embeds** the text rather than copying the stored vector. Input validation is centralised in `lib/sql-safety.js` + `lib/input-limits.js`; the ACL audit log is JSONL and best-effort.

## (4) Windows portability

### Takeaway

The plugin already has *some* platform awareness (a non-Linux TCP fallback for owner election, a `win32` branch for executable names, and an explicit "unavailable on win32" capability gate), but it is not runnable on Windows today. ### Inferences

- The port splits cleanly into two tiers. **Tier 1 (must):** IPC transport, `securePath`, `HOME`→`homedir()`, case/separator normalization before principal hashing, and Node ports of the four shell scripts. **Tier 2 (degrade gracefully):** fd-based directory routing already self-disables with a clear message, so named-namespace routing can ship as "POSIX only" in the first Windows release without new code.
- The byte-exact `commandArgv` comparison (`feature-cron-native.js:68-77`) is the subtlest Windows risk in the whole set: it is not a crash, it is an idempotency break that would make `setup-feature-crons.mjs` rewrite every job on every gateway start.
- `process.kill(pid, 0)` plus PID reuse is the second subtle one: it fails *open* (treats a dead holder as alive), which on Windows means a stuck Neo lock rather than a corrupted store — safe but operationally annoying.

### Gaps

- `lib/registry-lock.js` and `lib/fsync-atomic.js` / `lib/atomic-file.js` were not opened; `renameSync`-over-existing-file is legal on Windows but `rename` onto an *open* file is not, and the atomic-write helpers (`dream-diary.js:128-138` uses `mkdtempSync` + `writeFileSync` + `renameSync`) may hit `EPERM`/`EBUSY` there. Unverified.
- LanceDB's own Windows support (the `@lancedb/lancedb` native addon) was not investigated and is a prerequisite the code cannot answer.
- `scripts/lib/openclaw-cli.mjs` (how the `openclaw` child process is spawned) was not read; shell-quoting differences on Windows may matter.
- No CI matrix or Windows test was found in `.github/`; not verified beyond noting the directory exists.
