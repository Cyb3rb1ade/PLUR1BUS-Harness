# RE-08 T1/T3 implementation hand-off

T1 adds RPC 1.7.0 and the engine transport contract. T3 adds the Core-side client,
selection, independent engine identity and guarded reverse-RPC handlers. The Node
implementation remains the default. Selecting the experimental Rust implementation
does not start a process in this package; an absent engine leaves the Core serving,
and recall reports `E_NOT_AVAILABLE` with `reason: engine-unavailable`.

## Compatibility details

- RE-01 remains unchanged. `packages/rpc-schema/src/engine-contract.mjs` derives
  `EngineContract*Data` definitions and operation signatures from that contract;
  the schema tests compare the checked-in projection and check regeneration is
  idempotent. Runtime signals, callbacks and `capture.done` use transport lifecycle
  handling and notifications.
- The existing deprecated Core `engine.event` keeps its payload, metadata and
  opt-in delivery. Its additive `x-engine-notification` annotation describes the
  engine emitter; the generated `EngineTransportEvent` type represents that
  payload. Capability builders and notification validation use the serving role.
- `systemSupplement` returns the contract's `string[]`, and model status uses
  `ModelsStatus`. The brief's other shapes do not match the existing contract.
  Synchronous client readers use values hydrated during connection bootstrap.
- `engine.open` and `engine.agent.close` carry the existing `AgentStore` lifecycle.
  Closing the Core's client closes its connection, not the separately owned engine
  process. `engine.shutdown` is available to the future process supervisor.
- Re-embedding's optional `request`/`id` wire adapters preserve the runtime arguments
  already documented in `packages/core/src/embedding-migrate/engine-port.ts`.
  RE-01's parameterless declarations do not describe these existing arguments.
- Address vectors retain their independent, checked-in provenance. The Python
  generator verifies the added engine addresses and does not generate vectors.
  `Layout::engine_endpoints` supplies the future T4 `RoleKind::Engine` match arm
  without adding the supervisor slot here.

## Open integration gate: LLM attribution

`createHarnessHost` does not currently bind `HostServices.llm`. Its `LlmParams`
contract contains messages, model, temperature and maximum tokens, but no agent or
principal. The existing provider composition requires this attribution for budgets,
privacy and the D109 tool policy. A reverse connection authenticated as the engine
cannot infer which of several agents owns a concurrent completion.

`host.llm.complete` therefore guards the principal and supports injection of the
normal composed completion service, but the production Core does not provide that
callback yet. It returns `E_NOT_AVAILABLE` with `reason: llm-unavailable`. Calling a
provider directly or inventing an agent would bypass an existing control and is
explicitly a stop condition in package L.

The controller must settle the cross-process attribution before T3 can be marked
complete. One compatible option is an additional outer `agentId` argument on
`host.llm.complete`, verified against registered agents, with a derived internal
background principal and the existing composed provider/budget path. T2 would need
to supply that field; RE-01's `LlmParams` could remain unchanged. That extension has
not been silently added.
