# V1 outbound A2A and the Rust CLI handoff

V1 follows the TypeScript R-2b PR #835 because both change the RPC schema and budget surface. The outbound protocol uses the existing `consult_agent` and `delegate_task` tools and one `DelegationTarget` with `kind: external` and `origin: a2a`. Rust CLI implementation belongs to Claude; this PR adds no CLI command.

## Owner workflow and RPC signatures

The experimental Core methods were added in RPC **1.12.0**. The initial allocation reserved 1.10.0 for #820; main now uses 1.10.0 for cache telemetry #837. R-2b allocated 1.11.0, and V1 uses 1.12.0. All four methods require an authenticated Owner **person**, including listing. Agent principals and Admins are denied. The methods are excluded from WebMCP.

| Planned CLI command | Core RPC and input | Result / schema names |
| --- | --- | --- |
| `plur1bus a2a peer add --id ID --card-url URL --kid KID --public-key-file PATH [--credential-secret NAME]` | `a2a.peer.add({ id, cardUrl, kid, publicKey, credentialSecret? })` | Pending `A2APeer`; `A2aPeerAddParams`, `A2aPeerAddResult` aliases. |
| `plur1bus a2a peer list` | `a2a.peer.list({})` | `{ peers: A2APeer[] }`; `A2aPeerListParams`, `A2aPeerListResult`. |
| `plur1bus a2a peer remove ID` | `a2a.peer.remove({ id })` | `{ id, removed }`; `A2aPeerRemoveParams`, `A2aPeerRemoveResult`. |
| `plur1bus a2a peer trust ID --fingerprint SHA256 --revision REVISION` | `a2a.peer.trust({ id, fingerprint, revision })` | Verified, trusted `A2APeer`; `A2aPeerTrustParams`, `A2aPeerTrustResult`. |

These command spellings/options are a handoff proposal, not installed commands. Shared definitions are `A2APeerId`, `A2APublicKey`, `A2AFingerprint` and `DelegationTargetId`. The public key is the closed public JWK `{ kty: "OKP", crv: "Ed25519", x: "<32-byte unpadded base64url>" }`. Private JWK fields are rejected. `fingerprint` is the RFC 7638 thumbprint, `sha256:` followed by unpadded base64url. `revision` is an opaque compare-and-swap identity, not a timestamp.

The Owner supplies the public JWK and key id through a trusted channel. `add` performs no network request and never trusts a peer. Display the pending fingerprint and require the person's explicit decision before calling `trust`. Trust fetches and verifies the signed A2A 1.0 card through D109. There is no automatic `jku`/JWKS discovery, key rotation or replacement. A changed key needs remove/add/trust; a changed endpoint needs explicit trust again. Removal is idempotent, aborts in-flight requests and prevents stale trust operations from recreating the peer.

An Owner can assign a trusted target `a2a:<id>` with `project.agent.add`; local `AgentId` remains unchanged. Collaboration still requires project assignment and `agent.use` rights. The remote target runs without local `AgentScope` authority and opens no local agent memory/session store. D104 delegation requests a real receiver acknowledgement before work. Responses remain untrusted data.

## Output and errors

Human output should show the peer id, target id, card URL, key id, fingerprint, revision, pending/trusted state and whether a credential reference exists. Never display a leased credential or foreign card text. Every command should offer `--json`, print the raw RPC result using the existing output helper, and add only the CLI document discriminator: `a2a.peer.add/1`, `a2a.peer.list/1`, `a2a.peer.remove/1` or `a2a.peer.trust/1`. Failures use `error/1` and the existing structured RPC error.

Use the existing exit mapping: 0 success; 2 invalid input, `E_NOT_AVAILABLE`, approval-required or cancellation; 3 only the existing `E_LOCKED` case; 1 for authentication/authorization refusal, conflict, storage or other RPC/protocol failures. Missing/invalid key files and missing trust arguments fail locally before any RPC. Do not add a new interpretation of these global exit codes.

`reason` is a fixed code, including `invalid-peer`, `invalid-key`, `peer-exists`, `peer-not-found`, `peer-untrusted`, `peer-revoked`, `card-signature`, `approval-required`, `egress-denied`, `local-only`, `budget-exceeded`, `too-large`, `aborted` and `unavailable`. No remote status/error text, URLs with credentials, message/card content or key bytes are interpolated into errors. The trust RPC may wait for the existing `approval.*` flow; it does not silently approve its own network request. The normal approval/OS-attestation flow works without a new UI.

## Transport and accounting

`a2aClient.*` is live, advanced, Owner-writable and disabled by default. Every HTTP request, including card discovery and each same-origin GET redirect, is an internal `peer.a2a_http` tool call with effect/capability `network.a2a`. It has the external approval floor and taint restrictions. A headless ask is denied immediately. Approval arguments contain ids, hashes and byte counts; credentials and message bodies remain private to the adapter.

Every hop rechecks the live egress host/port policy and pins the socket to its approved IP. HTTP is limited to explicitly admitted loopback; other peers use HTTPS with normal certificate checks. The A2A-specific egress purpose permits explicitly listed Tailnet addresses while ordinary egress retains its private-address restriction. LAN, metadata and mixed private DNS answers remain denied, including the metadata address inside 100.64/10. `privacy.localOnly` additionally requires the actual pin to be loopback or Tailnet (100.64/10 or fd7a:115c:a1e0::/48). `privacy.localEndpoints` cannot allow a WAN A2A peer. Cross-origin redirects and all POST redirects are refused. Each response has a byte cap and deadline; compression is refused. Abort/disconnect closes the socket.

Signed cards must identify exactly one same-origin JSON-RPC 1.0 endpoint and verify under the approved Ed25519 key id. The adapter requests blocking `SendMessage`, accepts completed tasks or agent messages with text, and fails safely on remote errors, interrupted/nonterminal tasks or malformed replies. It does not install remote tools or process remote file URLs.

The budget module atomically reserves per-peer and shared-turn HTTP-call and token capacity, persisted across connections and Core restarts. Helpers cannot reset a shared turn's budget. Existing global/user/project/agent/session/turn token limits also apply. A2A has no authoritative billing-token field: communicated UTF-8 request/reply bytes are a conservative token upper bound. This does **not** meter hidden model work performed by a peer. Card reads consume calls but no message tokens. Unknown usage after a write consumes the reserved bound; only a proven unused request is refunded. One content-free `a2a.call` admission audit is written before each outgoing request; normal D109 decision/outcome entries remain separate. An unavailable audit or budget refuses I/O.

Optional bearer credentials are named secret-store references, leased only after policy/egress/privacy admission, registered for redaction and revoked after the request. No credential is stored in peer config or the peer database.

Successful reply and acknowledgement text is redacted before it crosses the target port or reaches transcripts/results. The operation retains its exact leased values until decoding finishes, including rotated and short credentials; known encoded forms are masked as well. Signed card verification and token accounting continue to use the original bytes.

## Required CLI tests

- Exercise all four RPC methods through a fake Core and assert exact closed parameters and method/schema names.
- Check raw `--json` preservation, including additive unknown result fields and each CLI schema discriminator.
- Verify pending-first registration, explicit fingerprint/revision trust, changed-key refusal and idempotent removal; no implicit network approval.
- Reject private/malformed JWK files, credential-bearing URLs, invalid ids and incomplete trust options before RPC.
- Cover the shared exit mappings and fixed errors for denied roles, unavailable Core/peer, approval-required, stale revision and invalid signature.
- Scan human/JSON/error output for private key bytes, bearer markers, foreign card/message text and remote error markers.

Core regressions live in `packages/core/test/a2a/` (`protocol-leak.test.ts`, `secret-leak.test.ts`, cards and pins), `test/budget/peer.test.ts`, `test/egress/a2a.test.ts`, schema tests and the mechanical Rust RPC fixture roundtrips.
