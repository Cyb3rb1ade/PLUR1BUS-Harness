# PR #820: Variant B and the Linux coding-turn grant

Variant B keeps ACP agents, ACP terminal callbacks and connector probes unavailable
on macOS and Windows. They refuse with `sandbox-unavailable` before launching a
process. A platform override cannot enable ACP on an unsupported host. Installed
connector discovery may still report executable and login-file metadata, but it
reports the protocol as `unprobed` and never opens credential contents.

Linux retains the existing bubblewrap opt-in for exactly one Harness-provisioned
worktree under `state/worktrees`. The opaque grant pins a live database row,
canonical path, directory identity and Git metadata. Every sandbox preparation
rechecks the row, symlink-free ancestry, exact writable root and hardlink scan.
Git metadata stays read-only. Other writable Linux policies remain refused.
The existing real connector argv gate remains closed pending credential-bind
acceptance; this change does not enable vendor CLI processes.

## K2, TM3 and PS integration

Use the existing provisioner and its trusted worktree port. The port provisions
root/card checkouts through `GitWorktreeProvisioner` and returns an optional opaque
mount for a live repository-bound checkout. Workspace fallbacks and legacy rows
without pinned Git/directory metadata grant no opt-in; their file tools remain
available.

```ts
const worktrees = provisionedWorktreePort(store, () => null, stateDir);
const codingWorktree = worktrees.root(agentId, projectId, cardId);
const codingWorktreeMount = worktrees.mount?.(agentId, projectId, cardId);
if (!codingWorktree || !codingWorktreeMount) throw new Error('worktree unavailable');
// Trusted in-process ChatRequest, delivered to the normal composed provider:
const request = { ...baseRequest, codingWorktree, codingWorktreeMount };
```

Production local delegation performs this handoff automatically:
`ProjectWorktreePort.mount` → `ChatRequest.codingWorktreeMount` → `composeTools` →
`SandboxPortsOptions.acpWorktree` → `SandboxPolicy.acpWorktree`. Both `exec.run`
and sandboxed host execution use that policy on Linux only. macOS coding turns
do not acquire the grant, and process-port policy construction excludes it on
unsupported hosts even if trusted code supplies one. D109 dispatch and process permission
checks remain in place. Read-only reviews never acquire a writable grant.

These are internal TypeScript values. They add no RPC or tool parameter, schema
version, migration or second Git implementation. Serializing a grant destroys its
authority. A checkout path alone, a forged grant, an additional writable root or
a removed/replaced database binding cannot enable a writable process.

## Verification

The external-agent suite, production coding bridge and worktree process-port
regressions pass on macOS and in a separate Linux arm64 VM container with Node
24.21.0. The Linux run uses the normal `node` user and `CI=1`, with no unavailable
backend skip. Its native helper is built from the unchanged production Rust
source using Rust 1.95.0 and the lockfile's exact libc 0.2.189.

The Linux production bridge checks that path-only and serialized grants launch
no process, then executes a real write through ordinary `exec.run` with the
trusted card-worktree grant. Existing isolation, credential, Git metadata,
hardlink and lifecycle assertions remain active on Linux. macOS assertions
exercise the explicit platform refusal without starting an ACP process.

The VM evidence verifies containment and composition. K2's owner-operated Linux
live baseline and nightly model/credential acceptance remain separate gates.
No further native macOS containment or watchdog investigation is included.
