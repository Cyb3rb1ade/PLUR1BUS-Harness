# Großpaket 3 A3 — Deep dreaming and confirmed promotion

## Delivered

Issues #606 and #607 are addressed in the Harness scheduler and its real candidate producer. Deep maintenance (`consolidate-daily`, `auto-accept-stale`, `gc-run`) no longer depends on a promotable shortlist. Minimum corpus, circuit breaker, idempotency, LLM routing and concurrency guards remain in force. A failed/truncated candidate read permits independent deep maintenance, then records `failed/engine_error`; it cannot authorize promotion.

The producer preserves currently visible agent-private source ids and creation timestamps. The optional public Engine **1.17.0** A1 adapter joins `memory.stats(ids, principal, context)` by those ids. Foreign agents, duplicate/out-of-request ids and invalid counters are refused. Missing stats are never inferred from search scores, scheduler pulls or ledger history.

Fallback shortlist evidence is explicit: `DEFAULT_FALLBACK_GATES` in `candidates.ts` requires age ≥ 24 hours plus either publicly reported importance ≥ 0.75 or at least two distinct private source cards with identical normalized content. The current pinned `MemoryCard` has no importance field: production therefore uses its creation time and actual distinct source cards. A fallback decision does **not** authorize promotion. With actual stats, ≥ 3 recalls and ≥ 3 distinct queries are required; the similarity threshold applies only when the public source reports a score. A public `since` listing has no similarity score; `score = null` passes the existing optional score gate.

After successful jobs, eligible actual source ids go to `memory.promote({ ids }, principal, context)`. The ledger advances only after a matching same-agent Engine receipt. `promoted/integrated` confirms the write. A1 explicitly defines `skipped/already-promoted` as confirmation of its durable agent/id/content marker, allowing reconciliation after a crash between Engine write and ledger update. Other skips and omitted receipts stay shortlisted with their Engine decision; malformed/foreign receipts fail the run without advancing any ledger row. Cancellation after submission also leaves the ledger closed for reconciliation next time.

No ledger migration is needed. Every run must reacquire the actual source id from the Engine; persistent content hashes alone never reconstruct authority. Existing candidate dedupe/expiry and gate records remain in the same store.
