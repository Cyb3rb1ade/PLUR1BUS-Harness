# Demo guide: M7 importers (OpenClaw and Hermes)

How to show the M7 acceptance criteria (`docs/milestones.md` §M7, `docs/import.md` §6.3 and §11) to someone in about fifteen minutes. Everything here uses a throw-away home and a **copy** of a source tree, never a real installation. The same steps run as tests, which is the proof; the commands below are for showing it.

Status of what you can show: the OpenClaw store take-over and the re-embedding routing come with PR #543, the provenance, leak-sweep and back-fill work with the branch `agy/m7-p2-provenance-backfill` (builds on #543). Both are built from the same checkout, so the demo needs that branch. Rollback of imported cards, cron import and the trigger for the identity back-fill are **not** part of the demo because they do not exist yet (`docs/import.md` §11.3); say so out loud.

## 0. Setup

```sh
export DEMO=$(mktemp -d)                 # the harness home (empty)
cp -R <your-synthetic-source> $DEMO/src  # a COPY; the importer never writes to it, the demo proves that in step 2
plur1bus --home $DEMO import openclaw --detect --source $DEMO/src   # read-only look at what is there
```

Use a hand-written synthetic tree. The test fixtures (`packages/core/test/import/fixtures.ts`, `buildM7OpenclawFixture` and `buildM7HermesFixture`) show the shape; no real data, no real tokens.

## 1. Dry run (criterion 1)

```sh
plur1bus --home $DEMO import openclaw --source $DEMO/src
```

The default is a dry run. Show: the plan (agents, files, stores, cron), the counts, and that `$DEMO` is still empty (`ls -A $DEMO`). The JSON form (`--json`) matches `docs/import.md` §5.7. Test: `openclaw-import.test.ts` "dry-run is default: returns complete plan and writes zero files to source or target".

## 2. Apply with store take-over (criteria 2 and 4)

```sh
( cd $DEMO/src && find . -type f | sort | xargs sha256sum ) > $DEMO/before.sha
plur1bus --home $DEMO import openclaw --source $DEMO/src --apply
( cd $DEMO/src && find . -type f | sort | xargs sha256sum ) | diff - $DEMO/before.sha && echo "source unchanged"
```

Show in the report section "PLUR1BUS stores": a store whose embedding identity matches the harness is `taken-over` with no re-embedding. Then ask the agent what it remembers (any recall command or the web UI): the old memories come back. Run the same `--apply` again: every entity is `matched-existing` and nothing outside `imports/` changes. Tests: `openclaw-store-takeover.test.ts` "P1.1: …" and "P1.4: …".

## 3. A store that does not fit (criterion 5)

Put a store with another model or another dimension into the source (a 768-dimension store, or the same dimension from another model). Run the dry run: the store is `re-embedding-migration`, with the reason (`dimension-mismatch` or `identity-mismatch`) and the next step `plur1bus memory reembed`. Show that `$DEMO/state/lancedb` does not contain it. It is never mixed into the matching store's vector space. Test: "P1.2: …".

## 4. Hermes: soul, skills, cards with origin (criterion 3)

```sh
plur1bus --home $DEMO import hermes --source <hermes-copy> --apply
plur1bus --home $DEMO import hermes --source <hermes-copy> --skills --apply
```

Show: each profile's `SOUL.md` in its agent workspace, the skills (disabled until enabled), and the memory cards. Every card says where it came from. Through the web UI or `plur1bus memory show <id>`: provenance `imported`, source `hermes:<profile>:memories/MEMORY.md#2`, and the import run (`;run=<runId>`) and time. `USER.md` is not imported unless a user is linked on purpose (ADR-007 Q4); the report says `unresolved-user-scope`. Cron is listed as `deferred` (known gap, step 7). Tests: `hermes-acceptance3.test.ts`, `provenance-imported.test.ts`.

## 5. Rollback (criterion 6)

```sh
plur1bus --home $DEMO import hermes --rollback $DEMO/imports/<runId>/report.json --apply
```

Files, config and agents are back to the pre-import state. **The memory cards stay**: the report says `not-reverted (engine has no undo)` and gives the number. This is a known gap, not a bug; the reason is in `docs/import.md` §11.3 (removing a card would block importing it again). Test: "rollback reports exactly this run's cards as not reverted …".

## 6. No leaks (criterion 7)

```sh
grep -rIl -e '<a token from your fixture>' $DEMO/imports $DEMO/state 2>/dev/null   # prints nothing
```

Reports, ledgers and logs contain counts and fingerprints, no secret values, no card text, no plain channel ids. The test scans everything a run leaves or prints: `leak-sweep.test.ts`.

## 7. What is not there (say it before you are asked)

| Not built | Why | Where |
|---|---|---|
| Cron import | needs a decision on who the imported job runs as and whether it starts disabled | `docs/import.md` §11.3 |
| Removing imported cards on rollback | the engine has no undo | §11.3 |
| `imported` marker after editing a card | needs an engine change | §11.3 |
| Trigger for the identity back-fill | the engine port is built and proven (`test/identity/engine-rebind.test.ts`), no CLI or RPC calls it yet | §11.3 |
| Secret import | no secret store yet, refused on purpose | checklist 8 |

## 8. Identity back-fill, as far as it goes

After a person is linked to a channel identity on purpose (owner action, confirmed), the memories of that identity can be attached to their user: a preview counts the cards, the apply changes the owner of exactly those cards and nothing else (same rows, same vectors, no copy, no `/share`), and the step is reversible through the engine's own record. A second user cannot take over a bound identity. This is shown by the four tests in `packages/core/test/identity/engine-rebind.test.ts`; there is nothing to click yet.
