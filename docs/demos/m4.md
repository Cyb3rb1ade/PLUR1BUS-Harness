# M4 review demo — 15 October 2026

This is a review guide for the five stacked Draft PRs, not a production-readiness or all-platform claim. Use an isolated Harness home and test accounts. Matrix persistence remains blocked; see [the spike report](../handoff/2026-10-15-m4-p2-matrix.md).

## 1. One agent on four channels

Configure one agent and its persona. In Settings → Switchboard enable Telegram, Discord, Matrix and Buzz with their SecretStore references and explicit allowlists. Buzz needs configured wss relays permitted through Egress and a signed recipient kind-10050 DM relay list. [Buzz setup](../channels/buzz.md) describes the exact text-only NIP-17 scope.

Send the same question in each DM. The same agent receives it; inspect the effective direct/group profile and each contributing layer in Switchboard. In a group, send an unmentioned message: silence. Mention the bot: the shipped group profile allows a reply but only content-free provenance capture. A later layer cannot widen an earlier restriction.

Automated evidence: `packages/core/test/channels/cross-channel-persona.test.ts` uses four host fakes with the actual composition prompt/router; existing hosted real-adapter suites exercise their own wire protocols. `packages/channels-buzz/test/socket.test.ts` uses the real pinned WebSocket transport and real crypto against loopback.

## 2. Pair one person twice

In My identities, generate a code for the first channel. Send `/link <code>` in the person's DM and approve the claim. Repeat for a second channel under the same person. Codes remain eight characters, one hour and at most three pending per channel; pending codes are never exported.

Verify that the linked person has the same private recall through both channels. Another, unlinked account receives a pairing notice and cannot start a turn. Automated evidence: `packages/core/test/delivery/cross-channel-memory.test.ts`, including genuine start → claim → confirm and actual pinned-engine recall through Matrix/Buzz.

## 3. Confirm recurring delivery

Recurring → Delivery destinations: select one of the signed-in person's linked direct identities and add it. Read the confirmation in that exact DM and reply with the displayed `/delivery` command. Refresh validation, then select that destination in a user-job editor.

Before confirmation, attempting to save/use it is refused. Run the job: its assistant result arrives only at the validated target. Remove the destination and run again: no delivery and no new model call. System and Dreams status subscriptions are explicitly configured through `delivery.target.subscribe`; they send fixed completion status, never raw private diary/system detail.

Automated evidence: `packages/core/test/channel-handoff/core.test.ts` runs the actual Core/RPC/user-job/identity pipeline with a fake adapter; destination and job authorization/race tests cover foreign runAs, expiry and revocation during resolution. DE/EN destination selection has browser/axe coverage.

## 4. Continue in Web

The API currently may choose a dynamic listening port. Set `core.webHandoffBaseUrl` to the actual Web UI URL reported by your API, with HTTPS or loopback HTTP. Never put credentials, query parameters or fragments in this setting. Leave it empty until the address is known.

As the paired person, send `/web` in a DM, including as the first command after pairing. Open the returned ten-minute link and sign in as that same person. It creates a separate private direct chat with a quoted, untrusted context preamble (prepared summaries and bounded recent excerpts). The channel session remains active. Try the link again, use it as another person, or after expiry: refusal. Opening the URL alone does not authenticate anyone.

In Web chat history, open an own Channel direct message. It has no composer. Use **Continue in Web** to create a separate chat. Groups never appear; a session once observed as a group stays excluded even if later classified direct. Old sessions without trusted DM provenance are not migrated by guessing; start a new channel session with `/new` if needed.

Evidence: `packages/core/test/channel-handoff`, `packages/api/test/channel-handoff.test.ts`, `packages/web/test/channel-handoff.test.ts` (DE/EN + axe, failed-link → fresh-link regression), and the real Telegram adapter `/web` regression.

## 5. Matrix experimental verification — blocked persistence acceptance

Memory crypto is off by default. Only for an explicit experiment, select `channels.matrix.e2ee.mode: memory`; keep unverified-device rejection. The UI warns that keys are not persistent and verification is required after restart. Use an existing compatible cross-signed peer, request SAS from the owner/admin Web control, inspect emoji/decimals on both devices and explicitly acknowledge equality before confirming.

Restart and observe the warning/changed memory identity. This is the authorized fallback, not a persistent E2EE demo. The default remains off. Cross-signing bootstrap, recovery backup and actual WASM key/ratchet persistence remain open, as does running verification on all five required targets. SQLite's kill-during-write fixture test proves the SQLite primitive only. No extra/native crypto-store package was installed.
