## 4. Node runtime facts

- **Node 24 ("Krypton")**: Active LTS as of 2026-09-22. First released ~April/May 2025. Exact Active→Maintenance and EOL dates: **unverified** (gap — the fetched `nodejs.org/en/about/previous-releases` excerpt conflated a page-updated timestamp with an LTS-end date). Source: [nodejs.org/en/about/previous-releases](https://nodejs.org/en/about/previous-releases).
- **Node 26**: "Current" (not LTS) as of 2026-09-22, first released ~May 2026; would not become Active LTS until ~October 2026 under Node's normal cadence. A cadence change ("one major release per year, starting with Node 27") is reported by [InfoQ](https://www.infoq.com/news/2026/06/nodejs-release-changes/) and an official [nodejs.org blog post](https://nodejs.org/en/blog/announcements/evolving-the-nodejs-release-schedule) — **neither fetched in full this session; implications for Node 26's LTS timeline are unverified.**
- **TypeScript type stripping**: on by default since **Node v22.18.0** (`node file.ts` needs no flag on 22.18+, hence also 24 and 26). Node's stripper ("Amaro") does **syntax stripping only, no type-checking** (`tsc --noEmit` still required for type safety) and does not read `tsconfig.json`. Erasable-only limits: `enum`, parameter properties, namespaces with runtime code, and import-equals aliases are **not supported** and need a real transpile step; plain type annotations, interfaces, type aliases and `import type` run natively. Source: [nodejs.org/learn/typescript/run-natively](https://nodejs.org/learn/typescript/run-natively), fetched 2026-09-22. **Design consequence:** the harness/engine TypeScript must avoid `enum`/namespaces/parameter properties on any code path meant to run un-transpiled, or must always transpile — decide explicitly in ADR-001/002 rather than defaulting silently.
- **Node SEA**: core feature stability **1.1 – Active development**; the newer Virtual File System (VFS) asset feature (v26.9.0+) is **1.0 – Early development**. Native addons must be bundled as SEA assets and `process.dlopen()`'d from a temp file, not straight from the VFS. Cross-platform/cross-compiled SEAs must disable `useCodeCache` and `useSnapshot`. **CI-tested on:** Windows (arch breakdown unspecified), **macOS arm64 only**, Linux (all supported distros except Alpine, all arches except s390x) — macOS x64 SEA is explicitly untested by Node's own CI (feeds §3). Known Linux-arm64-in-Docker `dlopen` crash bug, see §3. Source: [nodejs.org/api/single-executable-applications.html](https://nodejs.org/api/single-executable-applications.html), fetched 2026-09-22.
- **`module.enableCompileCache()` / `NODE_COMPILE_CACHE`**: production-adopted (npm CLI merged support, [npm/cli#7901](https://github.com/npm/cli/pull/7901)). See §5 for the specific measured numbers.
- **`--snapshot-blob`**: exists, mutually exclusive with SEA's VFS and with cross-platform SEA builds; no fresh primary-source performance numbers found this session (**gap**).
- **Bun**: documented-risk-only, not a build target. Bun's Node-API layer states "**most** existing Node-API extensions work... out of the box" ([bun.com/docs/runtime/node-api](https://bun.com/docs/runtime/node-api)) — the hedge is the finding. No tested confirmation exists for `onnxruntime-node`, `@lancedb/lancedb`, `sharp`, `better-sqlite3`, or `node-pty` under Bun; given this stack is unusually native-module-heavy (Rust NAPI + multiple C++ addons), any one of them failing under Bun's N-API shim late in the project would be expensive. Keep Bun as a documented alternative only, per `docs/phase0/research/platform-binaries-and-startup.md`; not a Phase-0 decision input.

## 5. Startup-latency techniques

Measured numbers, with source per row (per D6):

| Technique | Measured effect | Source |
|---|---|---|
| `module.enableCompileCache()` / V8 code cache | **290 ms → 238 ms** median startup (~20% faster), one app's own before/after measurement; general blog claim of "20–30% boost" for Node's compile-cache work | `docs/phase0/research/platform-binaries-and-startup.md` §Node runtime facts, citing [ben3d.ca/blog/introducing-node-prewarm](https://ben3d.ca/blog/introducing-node-prewarm) (secondary, one blog's benchmark, not an official Node number) |
| Bundling + prewarming (Cloud Run cold start) | **1.64 s → 1.4 s** first-render time | same source, same blog |
| Removing blocking probes from the prompt-build critical path (Hermes) | CLI submit → request dispatch **~4.3 s → ~0.9 s**; AIAgent init 1.0–3.3 s → 0.36–0.64 s; first system-prompt build 0.93 s → 0.32 s. Removed: Discord capability probe over HTTPS (~2.0 s), Ollama `/api/show` probe against non-Ollama providers (~0.3 s), python3/pip subprocess probes during first-prompt build (~0.5 s), MCP package import on every between-turn refresh (~0.4 s) | `docs/phase0/research/harness-engineering-state-of-the-art.md` §4 Latency, citing [NousResearch/hermes-agent PR #59332](https://github.com/NousResearch/hermes-agent/pull/59332) — measured, cold process, OpenRouter |
| Cold daemon-less CLI spawn (counter-example, motivates the daemon) | 13.13 s / 13.88 s / 13.00 s per query, no improvement across repeated calls; ~75% of wall-clock is reusable overhead (process spawn 4–5 s, CLI init 3–4 s, model load 2–3 s, LLM call 2–3 s) | `docs/phase0/research/harness-engineering-state-of-the-art.md` §4, citing [claude-agent-sdk-typescript#33](https://github.com/anthropics/claude-agent-sdk-typescript/issues/33), 2025-10-18 |

**Resulting rules for the CLI (D6):**
1. Bundle with esbuild or rolldown — collapses the module graph, and per the ben3d.ca finding bundling is a *prerequisite* for the compile-cache win to show up on cold-start-sensitive platforms (filesystem I/O otherwise offsets compilation savings).
2. Lazy `import()` for every heavy/native dependency (`onnxruntime-node`, `@lancedb/lancedb`, `sharp`, `node-pty`, provider SDKs) — never at top-level module scope, so `--help` and trivial subcommands never pay their load cost.
3. Turn on `module.enableCompileCache()` / `NODE_COMPILE_CACHE` unconditionally.
4. **No network probes and no subprocess spawns on the prompt-build / command-dispatch critical path** — this is the single most transferable rule from the Hermes measurement; any capability detection goes memory-cache → 24h disk-cache → permissive default + background refresh, never a synchronous probe.
5. Run a resident core daemon; the CLI is a thin client. Retrofitting a daemon later is hard, per the same daemon-mode issue; start with one.
6. Target **< 100 ms cold `--help`** (brief D6) — achievable only via 1–5 together; no single technique here gets there alone (the best single number cited, 238 ms compile-cache-only, is still 2.4× the target).

## 6. PLUR1BUS Windows port — work package summary

Source: `docs/phase0/research/plur1bus-crons-embedding-portability.md` §4, all citations at commit **`89148f9`** (`89148f9f604a27149094efbc7cd910a7d362a94a`, 2026-09-21) in `@cyb3rb1ade/plur1bus-memory` 7.15.4. Per brief D3, these are PRs against the PLUR1BUS repo, not harness workarounds.

Five blocker clusters:

1. **Unix domain socket (embedding-IPC owner)** — `lib/providers/scoped-embedding-ipc.js:284,434-435`: `socketPath` under `<stateRoot>/control/embedding-ipc/owner.sock`, `chmodSync(…, 0o600)`. **Proposed:** named pipe `\\.\pipe\plur1bus-embedding-<sha256(stateRoot)[0:32]>` secured with a pipe ACL at creation, `chmod` dropped on that path. Socket-type assertions (`lstatSync().isSocket()`/`isSymbolicLink()`, `:165-172,406-415`) have no named-pipe equivalent — replace with the connect-probe already implemented at `:174-195`. The macOS path-length guard (`:270-276`, darwin > 103 bytes) is the precedent pattern for adding a `win32` branch in the same function. The existing non-Linux fallback (loopback TCP `127.0.0.1:49152+(digest%16384)`, `:207-216`) already works on Windows but a named pipe avoids a firewall prompt.
2. **`securePath()` with ACLs replacing `chmod 0o600/0o700`** — 8 call sites (`scoped-embedding-ipc.js:153,279,435`; `lib/shared-memory-migration.js:216`; `lib/workspace-policy.js:98`; `lib/model-preparation/state-store.js:130`; `lib/reembedding/lance-backend.js:126`; `lib/reembedding/state-store.js:179`). On Windows, `chmod` only ever touches the read-only bit — a single `securePath(path)` helper (POSIX: `chmod`; Windows: ACL restricted to the current user SID, e.g. via `icacls` or a native binding) becomes the one call site to port.
3. **PID-reuse-unsafe lock plus O_DIRECTORY route already self-disabling:**
   - `lib/job-lock.js:15-38`: atomic `openSync(path,"wx")` lock, staleness by `mtimeMs` > 10 min. `"wx"` is atomic on Windows too; the gap is a crashed holder surviving until the 10-minute window with no OS-level liveness check. **Proposed:** keep the lock file open for the run's duration (Windows releases mandatory locks on process death) or shorten `staleMs`.
   - `lib/neo-arch.js:296-305`: `neoLockHolderAlive(pid)` via `process.kill(pid,0)` works on Windows (signal 0 = existence check) but Windows recycles PIDs more aggressively, so a recycled PID reads as a live holder — a **PID-reuse bug**, not a crash. **Proposed:** store `{pid, startedAtHrTime}` and compare both, or use a named mutex.
   - `lib/directory-capability.js:29-46`: `stableDirectoryCapabilitiesSupported()` **already returns `false` on win32** (`O_DIRECTORY`/`O_NOFOLLOW` absent), throwing a clear "unavailable on \<platform\>" error at `:21-27` — **this route needs no Windows work**, it self-disables; ship as a documented "named-namespace routing: POSIX only" Tier-2 degradation.
4. **Four bash scripts on the install/ops path** — `scripts/install-memory-system.sh` (local + remote-via-SSH install, `--dry-run`), `scripts/backup-snapshot.sh`, `scripts/restore-snapshot.sh`, `scripts/protect-plur1bus-deploy.sh` (runs on a `*/15` cron from `/root/.openclaw/scripts/`, has an untracked production twin). All POSIX-only (`bash`, `set -euo pipefail`, `rsync`/`ssh`, `$HOME`). **Proposed:** port each to a Node `.mjs` (the repo already has 27 `.mjs` scripts — established pattern); the `protect-plur1bus-deploy.sh` port also removes its production-twin drift risk.
5. **Byte-exact `commandArgv` comparison and `workspace-dir:v1` path hashing** (the two subtlest correctness risks, not crashes):
   - `lib/setup/feature-cron-native.js:49-55,68-77`: cron argv is `[process.execPath, FEATURE_CRON_RUNNER_PATH, "--agent", …]`, portable as data — but `isNativeFeatureCommandPayload`'s comparison is **byte-exact**, so a Windows path (`C:\...\node.exe`, backslashes, drive-letter case) must round-trip identically or every feature-cron job is silently re-planned as a migration on every gateway start. This is an idempotency break, not a crash — the subtlest item in the whole set.
   - `memory-request-context.js:173` (`workspace-dir:v1:<canonicalDir>`) plus `lib/dreaming/dream-diary.js:27` case-handling: workspace principals are hashed from a directory string. `C:\Users\X` vs `c:\users\x` hash differently on Windows/NTFS (case-insensitive filesystem, case-sensitive string), silently splitting one workspace's memories into two principals. **Proposed:** normalize case and path separators before hashing on win32.
   - `lib/providers/openclaw-memory-embedding-adapters.js:56-57`: `process.env.OPENCLAW_HOME || join(process.env.HOME || ".", ".openclaw")` — **`HOME` is not set on Windows** by default. **Proposed:** one-line fix to `os.homedir()`, matching the pattern already used in `lib/db-adapter.js:38`, `lib/critical-push-state.js:18`, `lib/neo-arch.js:428-429`, `lib/obsidian/safe-paths.js:9-10`, `lib/setup/feature-profiles.js:453,570`, `lib/telegram-commands/status-data.js:30`, `lib/telegram-commands/feature-toggle.js:148`.

Also noted, lower-priority: symlink refusal at 17+ sites uses `isSymbolicLink()`, which is true for NTFS symlinks but not junctions/most reparse points (needs an `isUnsafeLink()` helper); `PATH` scan for the host CLI (`feature-cron-plugin-runtime.js:169-191`) is already Windows-aware (`.cmd`/`.exe` variants); `~` expansion is hand-rolled in five places and doesn't handle `~\`. Not investigated (gaps, per the source doc): `lib/registry-lock.js`, `lib/fsync-atomic.js`/`lib/atomic-file.js` (rename-onto-open-file semantics differ on Windows), `scripts/lib/openclaw-cli.mjs` shell-quoting, and no CI/Windows test was found in `.github/` at commit `89148f9`.

**Tiering (per the source doc's own inference):** Tier 1 (must-fix before Windows is usable at all): IPC transport, `securePath()`, `HOME`→`homedir()`, case/separator normalization before principal hashing, the four script ports. Tier 2 (ship degraded, documented): fd-based directory-capability routing stays POSIX-only.

## 7. Service management without admin rights, per OS

| OS | Mechanism | Persists without active login? | Source |
|---|---|---|---|
| macOS | `launchd` user agent: plist in `~/Library/LaunchAgents/`, `launchctl bootstrap gui/$(id -u) <plist>` (or `launchctl load`). No `sudo` needed — distinct from admin-only `/Library/LaunchDaemons`. | Effectively requires one interactive login to have started the agent (GUI-session scoped). | Background knowledge; **not re-verified against a fresh Apple primary source this session — unverified**, per `platform-binaries-and-startup.md`. |
| Linux | `systemd --user`: unit files in `~/.config/systemd/user/`, managed with `systemctl --user enable\|start`. | Only with `loginctl enable-linger <user>` — the one mechanism of the three that survives with **no** interactive login at all. Own-account `enable-linger` is typically polkit-gated and not admin-only, but distro policy varies. | Background knowledge; **distro-level linger policy on Ubuntu 22.04/24.04 is an explicit gap, unverified**, per `platform-binaries-and-startup.md`. |
| Windows | Task Scheduler: `schtasks /create /sc onlogon /tn <name> /tr <path>` (or UI) targeting the current user, run level not "highest privileges" — no elevation needed. Simpler alternative: per-user Startup folder (`shell:startup`). | Effectively requires one interactive logon (an "at logon" trigger). | Background knowledge; **Microsoft Learn Task Scheduler fetch this session did not contain an explicit non-admin confirmation — unverified**, per `platform-binaries-and-startup.md`. |

**Installer implications (`install.sh` / `install.ps1`):**
- No admin rights on any OS for the service-registration step itself (table above); Node provisioning is the one place a package manager might otherwise want elevation — avoid that by installing Node into a user-writable location (e.g. via a portable/embedded Node fetch or `nvm`-style user install) rather than a system package manager requiring `sudo`/admin.
- **Python-free goal**: confirmed feasible for the *prebuilt* install path of every package in §2 — none declares a hard Python dependency for its prebuild. The one genuine exposure is **node-pty on Linux** (both x64 and arm64), which per the corrected finding in §2 always falls back to `node-gyp rebuild` there (no bundled Linux prebuild exists in 1.1.0 at all) — the installer's Linux path must guarantee a C/C++ toolchain (gcc/build-essential) and should treat "does `node-gyp configure` invoke Python on this box" as a hands-on CI check (**gap**, not yet run) rather than an assumption, since modern node-gyp majors vary here.
- Only place persistence-without-login matters structurally: a headless/server-style harness deployment on Linux should document `loginctl enable-linger` as a setup step; macOS and Windows don't have an admin-free equivalent for that specific case (both need at least one interactive login to arm the autostart).
