## 1. Übersicht und Abnahmekriterien

D106 soll die Ausführung von Host-Werkzeugen und Prozessen in einer restriktiven Sandbox (Fail-Closed) kapseln.
Phase 1 (#523) implementierte die Richtlinienerstellung (`preparePolicy`), Pfadprüfung und OS-Probes.
Phase 2 (#525) verdrahtet die Sandbox mit `exec.run` und setzt einen Vorab-Riegel (`processSandbox`) im `ToolDispatcher` für ungesandboxte `hostctl`-Aufrufe.

### Abnahmekriterien & Prüfpunkte:
1. **Windows Pfad-Kanonisierung:**
   - 8.3 Aliase: `lexicalSpelling` filtert nicht vorschnell, sondern lässt `realpath` den langen NTFS-Pfad auflösen; danach greift `checkSyntax`. (Erfüllt)
   - UNC-Pfade: `\\?\UNC\` wird auf `\\` normalisiert und anschließend von `checkSyntax` via `unc-not-allowed` abgewiesen. (Erfüllt)
   - `\\?\`: Normalisiert auf DOS-Laufwerkspfad; Win32-Gerätenamespaces (`\\.\`, `\??\`, etc.) werden abgewiesen. (Erfüllt)
   - Groß-/Kleinschreibung: Bei Root- und Launcher-Vergleichen auf Windows wird `within(..., true)` mit Case-Folding (`toLowerCase()`) verwendet. (Erfüllt)
2. **Launcher in beschreibbarem Root:** `preparePolicy` prüft `writeRoots.some(r => within(limitsHelper, r.path, true))` und wirft `SandboxFailure`. (Erfüllt)
3. **Hard-Link-Erkennung:** `preparePolicy` scannt Verzeichnisse mittels `lstat` und lehnt Dateien mit `nlink > 1` ab. (Erfüllt, aber mit 20k-Cap, siehe m2)
4. **Dispatcher-Riegel (`processSandbox`):** Werkzeuge mit `processSandbox.required !== false` werden vor der Ausführung mit `tool-denied` abgewiesen. (Erfüllt)
5. **Bypass-Audit:** Gibt es noch Wege, `hostctl` ungesandboxt auszuführen? (Stichproben-Ergebnis: dispatch-intern weitgehend dicht, aber Lücken bei `kill_foreign`, siehe m1)

## 3. Befunde

### Blocker
Keine.

### Major

#### M1 — Fehlende Plattform-Parität: Windows fehlt vollständig, Linux verweigert beschreibbare Verzeichnisse (`packages/core/src/tools/sandbox/backends.ts:23, 58`)
- **Datei:Zeile:** `packages/core/src/tools/sandbox/backends.ts:23`, `backends.ts:58`
- **Begründung:**
  - Unter Windows liefert `detectSandbox` stets `available: false` ("No restricted-token/AppContainer launcher is installed"). Windows-Installationen können daher keine sandbox-pflichtigen Tools ausführen.
  - Unter Linux liefert `backendArgv` bei vorhandenen `p.writeRoots` sofort einen Fehler:
    ```ts
    if (p.writeRoots.length) throw new SandboxFailure('bubblewrap writable roots require dynamic credential-name enforcement; backend refused');
    ```
    Das bedeutet: Jedes Tool, das Schreibzugriff auf den Workspace benötigt (wie `exec.run` mit Compiler- oder Datei-Ausgaben), schlägt unter Linux in der Sandbox fehl.
  - Eine produktive Nutzung der Sandbox ist somit derzeit faktisch auf macOS (Seatbelt) beschränkt.
- **Hinweis:** Dies deckt sich mit dem Draft-Status von PR #523 und #525 ("No D106 acceptance claim"), verhindert jedoch die finale Abnahme des Meilensteins.

### Minor / Nit

#### m1 (Minor) — `hostctl.proc.kill_foreign` wird vom Sandbox-Riegel nicht erfasst (`packages/core/src/composition/tools.ts:31`)
- **Datei:Zeile:** `packages/core/src/composition/tools.ts:31`, `packages/hostctl/src/index.ts:88`
- **Begründung:**
  In `composition/tools.ts` lautet der reguläre Ausdruck zur Markierung ungesandboxter Tools:
  ```ts
  const HOSTCTL_UNSANDBOXED = /^hostctl\.(?:proc\.(?:exec|start|shell)|app\.open|clipboard\.|notify|fs\.(?:search|trash))/;
  ```
  `hostctl.proc.kill_foreign` matcht hierauf **nicht** (da `proc\.(?:exec|start|shell)` nur drei Unterbefehle einschließt).
  `hostctl.proc.kill_foreign` sendet jedoch über `process.kill(pid, 'SIGTERM')` Signale an beliebige PIDs auf dem Hostsystem. Zwar greift die D109-Approval-Prüfung, aber der Sandbox-Vorabriegel `processSandbox` wird für dieses Tool nicht registriert.
- **Abhilfe:** `HOSTCTL_UNSANDBOXED` sollte `hostctl.proc.kill_foreign` einschließen oder `proc\.` generell matchen.

#### m2 (Minor) — Hard-Link- und Mask-Scan scheitert bei Verzeichnissen mit mehr als 20.000 Einträgen (`packages/core/src/tools/sandbox/policy.ts:86`)
- **Datei:Zeile:** `packages/core/src/tools/sandbox/policy.ts:86`, `backends.ts:41`
- **Begründung:**
  Der rekursive Scan zur Erkennung von Hard-Links bricht ab, wenn mehr als 20.000 Dateien besucht werden:
  ```ts
  if (++visited > 20000) throw new SandboxFailure('sandbox root alias scan exceeds safety cap');
  ```
  In Projekten mit großen Workspaces (z. B. vielen Assets oder tiefen Builds) führt dies dazu, dass `exec.run` den Start mit `sandbox root alias scan exceeds safety cap` verweigert.

#### m3 (Nit) — Toter Code `createSandboxHostExec` in `ports.ts` (`packages/core/src/tools/sandbox/ports.ts:45`)
- **Datei:Zeile:** `packages/core/src/tools/sandbox/ports.ts:45`
- **Begründung:** Die Funktion `createSandboxHostExec` wird exportiert, aber im gesamten Repository nirgends importiert oder instanziiert. `hostctl` greift weiterhin auf `createNodeHostContext()` zu.
