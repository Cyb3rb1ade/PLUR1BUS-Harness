## Summary and recommendation

**M8: not acceptable.** No criterion is fully met on this commit, criterion 7 (release checklist, tag) has not started, and
two defects sit under the two criteria the reconciliation calls best evidenced. The native `update` rollback does not
cover the SQLite stores the new core migrates during the health gate, so a minor release with a schema step can leave a
"rolled back" installation that does not start (M8-M1). The round-trip test cited for backup and restore fails on `main`
and no workflow runs it (M8-M2). Both need fixing before the owner reads acceptance 3 and 4 as "teilweise".

**D1: not acceptable.** This is expected at this stage. WP12 and WP13 (deep links, packaging, installers, uninstall, CLI
shim, signing channels) are not on `main`. The harness half of the upgrade (D1 plan Task 3) does not exist either: the
controller runs `plur1bus state snapshot|verify|restore` and `admin smoke`, which the real CLI does not have (D1-M1). The
shell code read well in the focus samples: the bridge, `host.keyUnlock` and the approvals frame. I could not execute any
of its Rust tests here.

**X1: acceptable with conditions.** All eight §12 criteria have real tests that pass locally, and the ZIP audit is
strict. Conditions: the owner records the three scope moves against §12 (`ext lint` to X5, pinned first-party keys empty
until X5, only the inspect path fuzzed), and the nightly 600 s fuzz run is shown green at least once (x1-m1).

**HM2, harness side: acceptable with conditions.** The client, provider, `setup --profile host` and the live conformance
suites pass on Linux. Conditions: Windows named-pipe tests (Task 3 gate F20) and the `hermes-host.yml` real-Hermes run
need a recorded green on Windows and macOS, which I could not produce. The installer half lives in PLUR1BUS-Host-Addons
and is not reviewed here.

**HM3: acceptable with conditions.** G1–G4 and G7–G12 have tests that pass, but 13 recorded KNOWN GAPs remain. Three of
them are in the G3 path mapper, among them a WSL-source path that maps outside the source root (hm3-m1). The 14.10
wording "HM3 is done" should name them.

## Findings

### Major

**M8-M1 — `plur1bus update` rollback cannot undo the store migrations the new core runs.** The snapshot holds the
binary, `config.json`, `manifest.json` and `runtime/core` only, "never `state/`" (`crates/plur1bus/src/update/snapshot.rs:1`–`3`,
plan R3). The health gate starts the new binary and waits for a `ready` core (`crates/plur1bus/src/update/host.rs:175`).
On open, the core migrates its SQLite stores forward by `PRAGMA user_version`, without a separate migration step: sessions
(`packages/core/src/session/migrations.ts:127`), identity (`identity/store.ts:73`), approvals, budget, collab and dreams.
Each store refuses a file "newer than this core supports" (`session/migrations.ts:130`, `identity/store.ts:74`). If the
gate then fails, or the person runs `update --rollback` later, the old core comes back on stores the new core already
migrated. It refuses to open them, so the rollback ends in "the previous version was restored but did not start"
(`update/mod.rs:428`). This breaks D78 / §6.3 item 4 ("snapshot → migrate → health gate → automatic rollback") for
every minor release that adds a SQLite step. The update plan lists migrations only from the signed manifest text
(`update/plan.rs:239`), so a release author has to remember them. `tests/update_apply.rs` cannot see this because its
fake core touches no store. The probe below shows the refusal. Fix direction: snapshot the SQLite files under `state/`
(they are small next to the LanceDB store), or let the gate start the new core on a copy. Alternatively, refuse to apply
a release whose core raises any `SCHEMA_VERSION` unless the person accepts an irreversible update. The desktop path
(WP11) does not have this defect: it snapshots the whole state volume (§6.15.8 step 3).

**M8-M2 — The backup round-trip test is red on `main` and no workflow runs it.** `tests/system/backup.test.ts:75`
expects exit 1 from `backup verify` of a byte-flipped archive. Since the CLI-wide exit table (`e5178f29`,
`crates/plur1bus/src/output.rs:134`), `archive-corrupt` and `truncated` are `E_INVALID_PARAMS` and exit 2. The test
failed in three runs out of three against a debug build of this commit (`2 !== 1` at the `flipped.tar.gz` step). It
appears in no workflow: the `system` job lists its files explicitly (`.github/workflows/ci.yml:158`) without
`backup.test.ts`, and `nightly.yml` does not name it either. The 14.10 status cites exactly this test for M8
acceptance 4. The restore half below line 75 (dry run, the restore itself, identical recall) has not run green on this
commit. The Rust tests `backup.rs` and `backup_archives.rs` pass but use hand-built archives and no core.

**D1-M1 — The harness side of the desktop upgrade does not exist.** `apps/desktop/src-tauri/src/controller/upgrade.rs:219`
runs `plur1bus state snapshot --src /src --dst /dst --json`, and `:305` runs `plur1bus admin smoke --json`, inside the
container. The real CLI on this commit has neither (`unrecognized subcommand 'state'`, `… 'smoke'`). There is also no
core `admin.smoke` RPC and no `__smoke` agent in `packages/core/src`. Every WP11 test therefore runs against
`fake-plur1bus` and the stub image. `docs/desktop.md:514` says so ("real harness integration is D1 Task 3"). The 14.10
status lists WP11 as "on `main`" and puts only "real harness image and store-migration acceptance" under open. That
understates it: until Task 3 is built, a real bundled harness cannot be upgraded or rolled back at all, and
desktop spec §8 acceptance 5 cannot even be attempted.

### Minor

**m1 (M8) — The dry-run comparison of acceptance 4 is not tested.** "Dry-run reports the same plan" is checked only as
`dry.dryRun === true` (`tests/system/backup.test.ts:90`); nothing compares the dry-run plan with what the real restore
then did.

**m2 (M8) — §6.3 item 4 and the native gate disagree.** `docs/milestones.md` §6.3 item 4 says every update, the native
one included, gates on `admin smoke`. The native gate is `--version`, a ready core and `1staid check` (`cli.rs:158`,
plan line 49), and `admin smoke` does not exist (D1-M1). One of the two texts is wrong.

**m3 (M8, backup) — "Vault encrypted?" is answered "not archived".** Neither the Obsidian vault nor the encrypted
secret-fallback file is in the archive. The archive itself is a plain `tar.gz` with mode 0600 (`backup/archive.rs:128`).
It contains the memory store and every `state/**/*.sqlite` in clear: sessions, identity, approvals, budget. All of this
is recorded as "not built" in the status, so I count it as confirmation, not as a new defect. One consequence I did not
run: the approval chain key lives in the secret store (`approvals/keys.ts:8`), which is never archived. A restore onto
another machine therefore brings `approvals.sqlite` without the key its HMAC chain needs. I expect the store to fail
closed there, which has not been verified.

**m4 (D1) — The host bridge trusts whatever listens on the bundled port once `/meta` matches.** `start_bridge`
(`apps/desktop/src-tauri/src/host_commands.rs:143`–`146`) compares the unauthenticated `/api/v1/meta` `installationId`
and then opens `ws://127.0.0.1:<port>/ws` with the device token as Bearer. On a `bridge.call get` it answers with the
secret-store key (`bridge.rs:190`–`197`). A same-user process that binds the freed port while the harness container is
stopped can echo the public `installationId`, receive the device token and ask for the key. On macOS this hands out what
the keychain ACL otherwise guards. I did not reproduce it; it needs a local same-user attacker and a timing window. The
bridge itself is narrow (one capability, `args` must be empty, 64 KiB frames, generation fencing).

**x1-m1 (X1) — Acceptance 8 is only half covered.** The fuzz target exercises `inspect_reader` and `audit_zip`
(`crates/plur1bus-ext/tests/fuzz.rs:1`–`7`). It never extracts, so "no out-of-staging write" is not what the fuzzer
checks. Extraction safety rests on the audit, then `install::archive::extract`, then `stage::check_tree`. That chain is
tested by examples, not fuzzed. The nightly 600 s job (`nightly.yml:83`) exists; I did not see a run.

**hm3-m1 (HM3) — The path mapper still has three recorded escapes or misreads.**
`packages/core/test/import/paths-mapper.test.ts:188` (todo): a WSL source read from Windows joins `..\..\..\.ssh\id_rsa`
with `\` and maps it to `\\wsl.localhost\Ubuntu\.ssh\id_rsa`, outside the source root. At `:198`, `../../etc/passwd` is
silently re-rooted to `<root>/etc/passwd` instead of being unmapped. At `:203`, `${constructor}` expands to an
`Object.prototype` member. The first one is a containment gap of G3 that the importer's safe-read deny-list may or may not
catch; I did not trace it further. The remaining ten todos are parser leniencies (`docs/import.md` §12.4).

## Cross-check: the `apps.open` approval bypass of Phase 1 (#544, B1) and the desktop

The desktop is **not affected as a second bypass path**:
- The host bridge serves exactly one capability, `host.keyUnlock`. It refuses any other capability and any non-empty
  `args` (`bridge.rs:181`–`194`), so it has no route by which the harness could make the desktop open a file, app or URL.
- The shell's own external opener (WP5) serves the SPA's links (`https:`, `http:`, `mailto:` only, classified in Rust),
  not agent tools.
- The approvals frame cannot approve in a release build.

It is **affected indirectly**. B1's root cause is the classification in `packages/core/src/composition/tools.ts:68`
together with `host-tools/apps.ts:126`, which makes `decide()` return `allow`. No `approval.requested` event is ever
emitted for `apps.open`, so the desktop frame, like the web SPA, never shows the person that an agent opened something.
The fix belongs in the core (see #544); the desktop needs nothing for it.

## Probe code (run locally, not committed)

```ts
// probe-rollback-schema.test.ts — M8-M1. WT = this worktree.
import { test } from "node:test";
import assert from "node:assert/strict";
import { DatabaseSync } from "node:sqlite";
import { mkdtempSync } from "node:fs";
import { tmpdir } from "node:os";
import { join } from "node:path";
const W = process.env.WT!;
const { migrate, MIGRATIONS } = await import(`${W}/packages/core/src/session/migrations.ts`);

test("a store migrated by the next core (one more migration) is refused by the current core", () => {
  const file = join(mkdtempSync(join(tmpdir(), "p6-sess-")), "sessions.sqlite");
  const db = new DatabaseSync(file);
  migrate(db, [...MIGRATIONS, "CREATE TABLE p6_next_release (x INTEGER);"]); // the new core during the gate
  // the gate fails -> rollback restores binary, config, manifest and runtime/core, never state/; the old core opens:
  assert.throws(() => migrate(db), (e: any) => e.reason === "schema-too-new" || /newer than this core/.test(String(e.message)));
  db.close();
});
```

Result: passes, so the old core refuses the migrated store.

## Focus samples

**Update and rollback (injected failure).** Native: `update/mod.rs` is a persistent state machine. A gate failure,
a crash after the swap and a crash after the gate are each tested and settle correctly for binary, config, manifest and
core. The defect is in scope, not in mechanics (M8-M1). Desktop (read only): `upgrade.rs` injects every failure §8
names: `new_image_never_ready`, `migration_fails`, `firstaid_fails_after_upgrade`, `smoke_fails`, `gate_times_out`,
`corrupted_snapshot_before_restore_is_recovery_failed_and_deletes_nothing`, `snapshot_disk_full_…`, plus create/start
failures for both runtimes. All of it runs against fakes (D1-M1).

**Backup and restore.** The archive format is tight: the manifest is the first entry, then regular files only, each
name and size matched against the manifest. `..` and stray entries are refused (`archive.rs:426`), the output is
written once with mode 0600, and the restore swaps by rename and keeps a pre-restore copy. On the vault question, see
m3: nothing is encrypted, and the vault and secret file are not included.

**ZIP parser of `plur1bus-ext`.** Read `zipaudit.rs` in full. It accepts exactly one EOCD at the end, with no comment,
no ZIP64, no multi-disk and no encryption. It refuses Info-ZIP Unicode Path and Comment extra fields (no parser
differential to the `zip` crate used for extraction). Local headers must equal their central entries and be contiguous.
Names must be UTF-8 and NFC, with no `..`, absolute path, drive letter, backslash, control or bidi character, Windows
device name or trailing dot or space, at most 16 segments and 240 bytes. Case and NFC folding catches file-against-file
and file-against-directory collisions. Only regular files pass; symlinks, hard links and devices are refused. Caps:
256 MiB per package, 128 MiB per entry, 20 000 entries, ratio 100:1, the summed declared size, and streamed decoding
bounded to `uncompressed + 1` with a CRC check. Extraction re-checks the tree (`stage::check_tree`). No defect found;
one probe disproved a suspected gap.

**Host-bridge approvals in the desktop.** See WP9, m4 and the #544 cross-check.
