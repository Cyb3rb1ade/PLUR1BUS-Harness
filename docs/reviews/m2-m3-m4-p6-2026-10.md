## Summary and recommendation

**M2: not acceptable.** Eleven of nineteen items are partial and two are open because they need engine PR-10 (5, 11); that
matches the reconciliation's "M2 is not done". What the review adds: the voice path drops model usage that already
happened once it crosses a hard limit, so the L8 ledger under-counts and the next call passes (M1); a value that the D111
writer misses (#544 M1, M2) comes back unredacted through `logs.query`, which Admin may call over `/rpc` although Admin has
no secret reveal (M2); and two end-to-end system tests that the status cites or depends on fail on this commit and are not
in CI (M3). Criteria 10 and 18 move from *erfüllt* to *teilweise*.

**M3: not acceptable.** The reconciliation's decisive gap is out of date: `/rpc` and `/events` are served since #468
(`37ad8d62`) and durable API accounts since #490, both merged after `823c0a58`, with a real API → real core test. What is
still missing: `/ws`, chat REST routes, OIDC, WebAuthn, the TLS listener, the licence record (F35), the create saga,
a CI job with Chromium for the a11y and responsive suites. The deny-by-default claim (5) holds at the guard, but there is no sweep of
Viewer writes through the now-served `/rpc`, and the RBAC matrix carries 120 recorded deviations (m2, m3). A long message
blocks the core for up to a minute on every turn path (M4). With a Chromium present, seven browser tests of `packages/web`
fail on this commit; CI installs no Chromium for that job, so it never sees them (M6). The a11y and responsive suites
pass locally, which is new evidence for 7 and 9, but not a CI gate.

**M4: not acceptable.** Buzz, E2EE and the behaviour merge are absent (as recorded). Two recorded KNOWN GAPs that the status
does not mention are privacy defects: after a channel handle is unlinked from one person and linked to another, the new
person's turns run in the old person's session and see its conversation, and channel inbound ignores a disabled person (M5).

## Findings

Findings already reported in the M1 review (#544) are not repeated; where they reach M2/M3 surfaces, the consequence is
reported here with a cross-reference.

### Blocker

None.

### Major

**M1 — The voice budget drops usage that already happened, and books a repeated event twice (M2 criterion 10).**
`packages/core/src/voice/budget.ts:25`–`29`: for a usage event with tokens, `record()` books the *actual* usage through
`checkBeforeCall` (a pre-call admission) and then `settle`. When the actual usage would cross a hard limit, the admission
refuses, `record()` returns `false` (the session is closed), and the tokens are never written to the ledger. The provider
has already consumed them, so `used` stays low and the next text or voice call is admitted (probe: limit 1 000, 900 booked,
a 500-token event refused and dropped, a following 90-token call allowed; real spend 1 400). L8 says a breach refuses
rather than truncates silently; here the accounting is silently truncated. Second defect in the same function: the port
contract says "record is idempotent by eventId" (`voice/ports.ts:12`), but only the seconds row is deduplicated
(`INSERT OR IGNORE`); the token booking runs again for a repeated `eventId` (probe: one 200-token event reported twice books
400). The broker deduplicates with a set, but it checks before and adds after an `await` (`voice/broker.ts:143`–`150`,
`:166`–`169`), so a re-delivered event that arrives while the first is being recorded passes too. The over-count direction is
conservative for the limit but wrong for cost reporting and shared global limits. The text-provider path
(`composition/provider.ts:222`–`250`) settles actual usage without refusing and is correct; `l8.test.ts` "concurrent
reservations through separate connections cannot overbook" covers it and passes. `voice/budget-ledger.test.ts` stubs the call
budget, so neither defect can show there.

**M2 — Secrets the D111 writer misses come back through `logs.query` to Owner and Admin over `/rpc` (M2 criterion 8,
M3 RBAC).** `logs.query`/`logs.tail` are in `WEB_CORE_METHODS` (`packages/api/src/rpc-route.ts:7`) and allowed to Owner and
Admin (`packages/core/src/rbac/policy.ts:66`). They re-redact on read with `createRedactor()` without any registered secret
(`packages/core/src/logs/methods.ts:53`). So the two writer defects of #544 (M1: no secret-store value is ever registered;
M2: `word: key=value` is not redacted) are not caught on the way out either: the probe writes `request failed: password=<v>`
and `upstream answered with secret <v>` through `writeLegacy` and gets both back verbatim from `logs.query`. Admin is denied
`secrets.reveal` by design (ADR-004, `policy.ts:126`–`130`), so this is a path to secret values for a role that must not have
them, and it is an "API response" in the sense of criterion 8, which `packages/api/test/secrets-never-leave.test.ts` does not
cover (it sweeps the REST routes, not `/rpc`). Contrast: `agent.export` does register the secret-store values before
redacting (`agents/signing.ts:28`, `core.ts:668`), which shows the intended pattern. Fix direction: as in #544 M1/M2, and
the read path should register the same values.

**M3 — Two end-to-end system tests fail on this commit and are not run by CI (M2 criteria 18 and secret store).**
`tests/system/model-discovery.test.ts` fails at its first step: `model scan` refuses the local mock provider with
`failed:invalid` / `egress_scheme` (the egress guard was tightened after the test was written). The reconciliation cites this
test as evidence for criterion 18. `tests/system/secrets.test.ts:101` expects exit 1 for `E_INVALID_PARAMS`, but the CLI's
single exit table maps it to 2 (`crates/plur1bus/src/output.rs:134`, commit `e5178f29`). Neither file is in
`.github/workflows/ci.yml` (`:158` lists the system tests CI runs; `identity`, `sessions`, `reembed`, `dreams`, `backup` are
missing too), so both have rotted unnoticed. The unit and contract tests under `test/discovery/` and `test/secrets/` pass.
Caveat: the debug binary was not rebuilt by me; the second failure follows from the source either way, the first is a
core-side refusal and independent of the binary.

**M4 — One long message blocks the core for up to a minute on every turn (recorded KNOWN GAP, not in the status).**
`test/triage/rules.test.ts:297` records that the triage segmentation regex is quadratic in a run of whitespace: 30 000 spaces
about 1.2 s, 100 000 about 14 s, 200 000 about a minute, while `session.submit` accepts 200 000 characters. `triage()` runs on
every provider turn (`composition/provider.ts:138`) and in role routing (`session/role-routing.ts:40`). Since #468 any person
who may submit a session over `/rpc` (Member upward) can stall the single core process. It is a todo test, not part of the
M2 or M3 status or open points.

**M5 — Channel identity: a re-linked handle sees the previous person's conversation; a disabled person still gets turns
(recorded KNOWN GAPs, not in the M4 status).** `test/identity/identity-port.test.ts:183` records that after a channel handle is
unlinked from person A and linked to person B, B's turn runs in A's active session ("the chat's active session is found by
chat key alone"), so the model prompt contains A's earlier message and reply. A second todo records that channel inbound
ignores `person.disabled`. Both bear on criterion 2 ("a linked user is remembered as the same principal … fail-closed").
Neither is in the M4 status paragraph or the §8 open items.

**M6 — Seven web browser tests fail on this commit; CI cannot see them (M3).** `packages/web/test/harness.ts:17` skips every
browser test when no Chromium is found, and `.github/workflows/ci.yml` installs none for the web job (only `desktop.yml` does),
so the browser half of `packages/web` is not a CI gate. Here, with Chromium present, these fail, each also when run alone:
`doctor.test.ts:239` (auto refresh every 30 s: 1 call instead of 2), `models-states.test.ts:225` (detail hint never
rendered), `recurring-audit.test.ts:16` and `:29` (history date, localized run error), `skills-approvals-jobs.test.ts:195`
and `:211` (Run now dialog, history tab), `user-jobs.test.ts:10` (create with timezone preview). Most are timeouts waiting for
an element on the Recurring/Jobs pages. I did not analyse the cause (product regression, mock drift or an environment
assumption such as time zone); either way the UI pages behind M3 criteria 1 and 2 have red tests that no gate reports.
`inbox-page.test.ts:123` and `palette-e2e.test.ts:182` failed under load and passed alone.

### Minor

**m1 — Channel redaction catalogue: known misses reach `channel.test` answers.** The Telegram catalogue records as todo that
a percent-encoded token, the part after the bot id, and the webhook `secret_token` echoed in an error description survive
into `err.message` (`channels-telegram` redaction-catalogue KNOWN GAPs); Discord records that `resolveIntents` and
`splitOptions` echo the first 40 characters of a rejected entry. The core's own `scrub` (`rpc/channel-surface.ts:73`) does not
catch these forms either (probe), and `channel.test` returns the scrubbed text as `detail` (`channel-surface.ts:388`), which
Owner/Admin get over `/rpc`. Not recorded: a base64 form of a Discord token passes the Discord scrubber. Each needs a
vendor answer that echoes the credential oddly; the catalogue is otherwise thorough.

**m2 — The RBAC matrix carries 120 recorded deviations; the status reads it as green.** `packages/webmcp/test/rbac-matrix.test.ts`
passes with 120 todo cases: about 50 human-only actions WebMCP does not forbid (two of them default tools), about 40 writes
neither forbidden nor on the exposure list, about 30 core methods without an `RPC_RULES` entry. The reconciliation says
criterion 5 is *erfüllt* "for every RPC method at the guard (`rbac-matrix.test.ts`)". Mitigation the matrix does not model:
for API-delegated callers every unruled method is owner-only (`packages/core/src/rpc/api-admission.ts:24`), so the text
"only the local token protects it" is out of date for the web path, and WebMCP is not wired into `packages/web` today, so
the WebMCP cases are latent.

**m3 — No Viewer-write sweep through `/rpc`.** The served transport exposes 115 core and 4 supervisor methods
(`rpc-route.ts:7`). `web-transport-e2e.test.ts` calls five of them as a Viewer (`inbox.count|list|markRead|dismiss`
allowed, `approval.list` and `secret.status` refused). Criterion 5 ("every endpoint rejects a Viewer write") is proven at the guard, not over the transport, and
no test pins `WEB_CORE_METHODS` against the guard and `apiAdmission` together.

**m4 — Per-user, per-project, per-turn and per-session budget limits cannot be set.** The call budget enforces six scopes
(`budget/calls.ts:7`), but the only writer in production is `budget.set`, which writes the legacy global/agent table
(`rpc/methods.ts:342`); nothing writes `budget_call_limit` outside tests, and `budget.status` shows only legacy limits. The
M2 scope names budgets "per agent / project / user" (ADR-010 §4).

**m5 — Recorded latent defects in the `toolcall` library.** `executeBatch` derives its idempotency key and cache by joining
scope and operation id with `:`, so a cached approved result of one scope can be served to another
(`test/toolcall/results.test.ts:536`, todo). Nothing in `src` outside `toolcall/` calls `executeBatch`, so it is latent.

**m6 — Criterion 17 test is weaker than its name.** `openai-auth/auth.test.ts:37` ("Acceptance 17") stubs the deny-list
(`denied: async () => true`), so it proves only that the port refuses when the list says so; the source scan covers
`src/openai-auth` and `src/voice` only and one known client ID. The deny-list entries themselves exist
(`host-tools/denylist.ts:37`–`42`) and `host-tools/denylist.test.ts` covers the Codex path on Linux.

**m7 — M4 criterion 6: "logged" is not asserted.** `channels/router.test.ts:25`–`50` asserts that an unknown sender creates no
session and its content is never submitted; no assertion checks that the drop is logged.

### Nit

- `identity.pair.start` issues 60-minute codes; `rpc.schema.json` says 10 minutes and `docs/identity.md` says one hour
  (recorded todo).
- The OAuth loopback listener can be consumed by a forged callback (login DoS, no credential exposure; recorded todo).
- The voice seconds ceiling is check-then-act (`voice/budget.ts:9`–`13`): two sessions opened at the same moment both pass
  the last second; the session ceiling then closes them.

### Observed outside the scope

`packages/core/src/mcp/auth.ts:55`–`63` (`PkceAuthProvider.accessToken`) refreshes without a single flight: two concurrent
MCP calls with an expired token both spend the same refresh token, and with a rotating issuer the loser drops the token set.
For the M6 review. The core's provider refresh owner (`auth/refresh.ts`) is a single owner per credential, shared with
discovery (`composition/auth.ts:48`–`52`), and its race tests pass.

## Focus samples

**Secret store and redaction across API answers.** `secrets/store.ts` gates every operation to `owner` (status and leases
also to `core`), audits before it acts, and revokes leases on rotation; values leave only through `reveal`. Over the web,
`secret.get` is not exposed at all (`rpc-route.ts:5`–`17`), `secret.set|delete|list|status` reach the store, whose principal
mapping admits only a person with role owner (`core.ts:728`–`731`); the e2e test shows a Viewer refused. The REST sweep in
`secrets-never-leave.test.ts` is strong (every route, five ways, every secret in nine encodings). The gap is the read side of
the diagnostic log (M2) and the channel error text (m1). `agent.export` registers the store's values before it redacts.

**Auth flows (refresh race).** `auth/refresh.ts` keeps one flight per credential reference, re-reads the record inside the
flight, persists the rotated token before releasing waiters and keeps an unpersisted rotation in memory instead of spending
the old token again. Discovery reuses the composition's provider and so the same owner (`composition/auth.ts:48`–`52`,
`core.ts:457`). The ChatGPT-plan path marks the refresh token spent durably before the exchange and serialises per account
(`openai-auth/plan.ts:64`–`79`). I found no race on the M2 paths; `invalidate` writes without compare-and-swap, but with
uniform store latency a concurrent flight cannot finish inside its window, so it is not reported. The MCP client is the
exception (outside the scope).

**RBAC and surface matrix.** Unruled methods are owner-only for API callers (`api-admission.ts`), `/rpc` is session-only with
CSRF on every call and strips `principal`/`actAs`; web callers get surface T1 (`rbac/connection-surface.ts`), so they decide
only low-risk approvals. Gaps: m2, m3.

**Telegram/Discord redaction catalogue.** Both catalogues drive the real channel against an in-process fake with scripted
faults and scan every surface (message, stack, cause, JSON, inspect); recorded misses and the core-side consequence are m1.

**Budgets with reservations.** The call budget reserves inside one `BEGIN IMMEDIATE` transaction (check, insert), counts live
reservations across period rollover, expires orphans after a TTL and settles idempotently; `l8.test.ts` runs concurrent
reservations from separate connections and passes. No double booking on the text-provider path; the voice ledger is the
exception (M1). Scope gap: m4.
