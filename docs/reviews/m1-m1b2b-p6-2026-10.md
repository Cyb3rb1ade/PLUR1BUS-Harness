## Summary and recommendation

**M1 (harness share): acceptable with conditions.** Ten of the twelve criteria have a real, green test on this commit; I
could not run the engine side (criterion 12), the real-model rerank leg (criterion 1), Windows or macOS. Conditions: a T7
handle test (5), an L12 order test (10), a Windows B1 figure and O6 (11), and `docs/embedding-identity.md`, which the M1
exit list names and which does not exist (m6).

**M1b-2b additions: not acceptable.** The four D109 tests exist and pass, but they run against a synthetic tool registry.
The tool composition that a running core actually uses lets an agent launch any file, app or URL with the OS default
handler, outside every root and without approval (B1). Together with the D106 sandbox and `tool-eval` gaps, ADR-014 still
*Proposed*, and three redaction defects in the D111 writer (M1–M3), the block is not ready for the owner's sign-off.

## Findings

### Blocker

**B1 — `apps.open` runs without approval, outside every root, from any surface.**
`packages/core/src/host-tools/apps.ts:126` registers `apps.open` with capability `sys.read` (class `allowed` inside and
outside roots, no surface floor). `packages/core/src/composition/tools.ts:68` registers every `HOST_TOOLS` entry with
`effect: cap.intrinsicEffect` (here `read`), so no effect floor applies either. `decide()` therefore returns `allow`. The
tool then runs `xdg-open` / `open` / `explorer.exe` on any path (deny-list checked lexically only) or http(s)/mailto URL.
On Windows `explorer.exe <file.bat>` executes the file; together with `file.write`, which is allowed without approval inside
the workspace, an agent can write a script and run it while `shell.exec` (approval class, `exec.run` mode `deny` by default)
would have refused. The probe below shows the decision path (`meta.decision: "allow"`, approval port never called, surface
T0, target outside the root). What the default handler then does on Windows or macOS I did **not** run. The authors know it:
`packages/core/test/host-tools/audit-b07.test.ts:66` is a todo "KNOWN GAP"; it is not in the milestone status, not in
`docs/approvals.md` §9, and `composition/tools.test.ts` and `catalog.test.ts` pin the current mapping. The hostctl variant
`hostctl.app.open` uses `os.script` (approval), which shows the core mapping is the outlier. D106 lists `apps.open` as
"allowed", but D109 (which refines D106) makes executing or opening something a separate approval (`net.submit` row) and
requires zero escapes; `permission-eval` cannot see this escape because it never uses the production composition (m2).
Fix direction: an approval-class capability for `apps.open` (at least for `kind: file|app`), the tool's own effect in the
composition, and a `permission-eval` row over `composeTools`.

### Major

**M1 — The diagnostic writer never learns the secret values (D111 §4 rule 1 not wired).** `createWriter` has
`registerSecret` (`packages/core/src/logs/writer.ts:134`), but nothing in `src` calls it: the core log is created in
`packages/core/src/logs/bootstrap.ts:6` and the composition keeps its own `registered` set
(`packages/core/src/composition/index.ts:118`) for tool-error details only. Spec §4 rule 1 ("each process registers the
exact secret-store values and leases it holds … any occurrence is replaced") is therefore inactive in `logs/core.log`.
A provider key in free text that matches none of the patterns (probe: `failed with secret <canary>`) is written in clear.

**M2 — `key=value` after a `Name:` prefix is not redacted (D111 §4 rule 2).** The free-text rule in
`packages/core/src/logs/redact.ts:124` consumes `Error: token=<v>` as the pair `Error` → `token=<v>`, so the secret key
is never examined. The same holds for any `word: key=value` (`request failed: password=<v>` leaks, probe below). The first
case is a todo KNOWN GAP in `packages/core/test/logger.test.ts:92`; the general form is not recorded. Through `writeLegacy`
the leak reaches `logs/core.log` (probe: canary found in the file).

**M3 — Redaction is quadratic and runs before truncation, on the core's event loop.** Measured with
`createRedactor().text("m".repeat(n))`: 1 KiB 5 ms, 4 KiB 74 ms, 8 KiB 242 ms, 32 KiB 4256 ms. `writer.ts:76` and
`writer.ts:122`/`125` redact the full attributes and message before `fit()`/`cap()` shorten them, so a single 16 KiB
message took 1033 ms in `writeLegacy`. Any log call carrying a long unbroken foreign string (an upstream error body, a
foreign stderr line) blocks the core for seconds. Recorded as a todo KNOWN GAP at `logger.test.ts:97` (4 KiB only); the
real cost at the line limits is higher than the note says. I did not trace which remote inputs reach the writer unbounded.

### Minor

**m1 — `clipboard.write` is gated as `clipboard.read`.** `packages/core/src/host-tools/clipboard.ts:49` and
`packages/hostctl/src/index.ts:55` map the write to `clipboard.read`; in the core composition its effect is recorded as
`read`. A T1 (editor) surface may therefore decide a clipboard write (`surfaceMayDecide` admits T1 for low-risk
`clipboard.read`), the person is shown a read capability, and the audit line says `effect: read`.

**m2 — `permission-eval` does not exercise the production tool composition.** Both halves register synthetic tools
(`packages/core/test/policy/permission-eval-e2e.fixtures.ts:170`, `:175`). The "zero escapes" result is real for the
evaluator, stores and dispatcher, but it says nothing about the capability and classify choices in
`composition/tools.ts`, which is where B1 lives.

**m3 — Host tools can never use a standing grant.** Every `HOST_TOOLS` entry classifies as `outsideRoots: true`
(`composition/tools.ts:68`), and a capability grant never applies outside roots (`decide.ts:432`). So the D106 rule
"clipboard read: approval per session" cannot hold: every read asks again (probe: a session grant on `clipboard.read` was
ignored). Fail-closed, but it trains the person to click through prompts.

**m4 — Kill soak is not stable in this sandbox.** Of four 200-turn runs with the debug binary, two failed: one with
`TypeError: The "pid" argument must be of type number. Received null` from `supervisorPid(h)!`
(`tests/system/kill-soak.test.ts:195`; the helper reads the supervisor pid from `daemon status` while it is being
restarted), one on the 1000 ms recall budget (1031 ms). The seed of the first failure passed on a rerun. CI uses its own
runners and binary; I cannot say whether CI is affected.

**m5 — Production roots carry no identity.** The spec stores each root with its identity and suspends a replaced root.
`canonicalisePath` supports `PathRoot.identity`, but the composition builds roots as `{ id, path }` only
(`packages/core/src/composition/index.ts:164`). A workspace directory replaced by a link to another (non-home, non-system)
directory is accepted silently as the new root.

**m6 — Stale or missing documents.** `docs/embedding-identity.md` (M1 exit list) does not exist. `docs/approvals.md:455`
(§9 item 1) still says the core constructs no dispatcher and host tools are not built, which is false since #293.
`docs/milestones.md:127` says the dreaming leftovers are "on this branch, not on `main`", but they are on `main` since #521.
ADR-014 §Context (line 7) still says the turn loop and the D109 chokepoint do not exist.

**m7 — Licence audit fails and is not in CI.** `node scripts/audit-deps.mjs` exits 1 with 11 `NOT-LISTED` transitive cargo
licences (Zlib, MIT-0, CDLA-Permissive-2.0 in `foldhash`, `zlib-rs`, `borrow-or-share`, `webpki-roots`, `webpki-root-certs`);
its pnpm half was incomplete in this sandbox. No workflow runs it. `npm audit` (vulnerabilities) needs the registry and was
not run.

**m8 — Canonicalisation deviations from the D109 spec (low risk).** 8.3 names are refused by shape
(`packages/core/src/policy/paths.ts:157`), not expanded with `GetLongPathNameW`, so legitimate names such as `backup~1.txt`
are refused on Windows; bind mounts are compared by string, not by identity (spec: "bind mounts are compared by identity");
the POSIX system-tree list omits `/var`, `/lib`, `/opt`, `/root` as forbidden roots.

## Focus samples

**Dispatcher chokepoint.** `call-paths.test.ts` keeps `tool.execute` inside `ToolDispatcher`; outside it only
`callWithRepair` (`tools/repair.ts:128`) calls `execute`, and nothing in `src` uses it. The per-turn registry
(`composition/tools.ts`) is the only producer of executable tools; every turn tool goes through `#decide`, a throwing
`classify`, `policyContext` or evaluator is a refusal, and a decision that cannot be audited refuses the call. Direct
`decide()` calls outside the dispatcher (`exec.run` inner gate, media and voice policies) are additional gates, not bypasses:
`exec.run`'s outer dispatcher decision is always approval-class because it has no `classify` (outside roots by default).
The escape found is not a bypass of `decide()` but a wrong classification fed into it (B1, m1).

**Path canonicalisation.** Read `policy/paths.ts` in full. `..` is refused before normalisation; symlinks are resolved with
`realpath` and judged on the target, dangling links and loops refused; hard links are checked by identity against the
deny-list; `openVerified` re-checks identity and parent after open, with `O_NOFOLLOW` and `O_EXCL`, plus `/proc/self/fd` on
Linux. The `permission-eval-e2e` path rows (symlink out of root, link to `~/.ssh`, hard links, NFC/NFD) pass on Linux.
Junctions, 8.3 names, alternate streams and the Windows reparse-point path are covered only by syntax tests here; the real
Windows behaviour was not checked. Deviations: m5, m8.

**Redaction in the diagnostic writer.** Writer-side redaction runs on every attribute and message, depth-bounded, keys by
name, deny-list paths hashed. Defects: M1, M2, M3.

**Audit hash chain.** `audit/chain.ts`: unkeyed SHA-256 chain plus a separate anchor, fail-closed append when the anchor
disagrees, torn tails kept as evidence, rotation carries `seq` and `prev`. Policy decisions reach it: the composition's
policy audit writes to the RBAC sink, which tees `audit.log` and the chain (`core.ts:573`, `:593`). The limits are stated in
`docs/audit-chain.md` (someone who can write chain and anchor can rewrite both). One todo KNOWN GAP: secrets inside `detail`
are written as given (`test/audit/chain-hardening.test.ts:47`); producers redact. `audit.verify` reads every chain file
synchronously under the lock inside the core (no size bound on the number of rotated files), which blocks the core while it
runs; not rated, worth a note in the doc. The approval store's HMAC chain (`approvals/chain.ts`) was skimmed: keyed MACs, a
keyed head row, constant-time comparison, binding tuple; tests pass.
