# ADR-005: Authentication policy and secret storage

**Status:** Accepted (2026-09-22, with amendments D12–D13) · **Date:** 2026-09-22 · **Deciders:** Christian (owner) · **Inputs:** `docs/phase0/brief.md` D1, D5, D10, D12, D13 · `docs/phase0/auftrag-original-2026-09-21.md` §6, §6.1, §6.3, §8, §11, §13 Q3 · `docs/phase0/research/providers-chat-auth-caching.md` (§1–§4 and the subscription-login policy table) · `docs/phase0/research/hermes-learnings-and-import.md` A3 · `docs/phase0/research/platform-binaries-and-startup.md` (binaries table)

## Context

§6.3 fixes the auth engine's shape: four auth kinds, declarative auth profiles, headless-capable flows, a token lifecycle with pools and failover, an OS-keychain secret store with an encrypted file fallback, and a per-profile `policy_status ∈ {allowed, restricted, prohibited}` with source and check date, under one absolute rule — **`prohibited` is never shipped** — and one default that §13 Q3 leaves open: `restricted` as opt-in with a visible risk notice. §6.3 also instructs: *"Stand bei Anthropic, Google, OpenAI und xAI zum Implementierungszeitpunkt prüfen — die Regeln haben sich 2026 mehrfach geändert."* That check was performed on 2026-09-22 and its results change what §6.1's provider table can deliver.

Three further constraints apply. No client impersonation: foreign client IDs, or user-agent / system-prompt fingerprints of official CLIs, are forbidden without the vendor's explicit permission (§6.3). Subscription logins are person-bound: usable only for agents whose owner is the login holder, never shareable with other harness users (§6.3). And the documented escape hatch when a subscription cannot be used directly is the vendor's official CLI attached as an external agent over ACP (§6.3 → §8; brief D5, ADR-011).

## Decision

**Ship four auth kinds driven by declarative profiles, plus one delegated-binary pattern for vendor CLIs that manage their own login; store every secret in the OS keychain via `@napi-rs/keyring` with an encrypted file fallback, hand the engine only short-lived leases — and ship no subscription-OAuth login whose current vendor policy reads `prohibited`.** Concretely at v0.1, amended 2026-09-22 after a fresh check of Anthropic's compliance page: **Anthropic Claude subscription use is shipped**, but only through the provider profile **"Anthropic via Claude Code / Agent SDK"** — the harness spawns the unmodified Claude Code binary (or the official `@anthropic-ai/claude-agent-sdk`, which drives that binary) under the user's own existing login, and never implements a harness-native OAuth/PKCE/device-code flow against Claude.ai and never reads `~/.claude/.credentials.json` or its Keychain equivalent, either of which would be the "collect, store, or intermediate" a Claude.ai credential that Anthropic's own compliance page forbids (§"Auth policy per profile" below). A harness-native Claude.ai login stays **not implemented**. Google Gemini CLI (now Antigravity CLI `agy`, D40) / Code Assist / Antigravity OAuth stays **not implemented** (`prohibited`, unchanged); whether an analogous "run the unmodified Gemini CLI as a backend" pattern is itself permitted is **unverified** and is carried as an open item to re-check, not assumed. OpenAI ChatGPT/Codex OAuth is **not implemented** either, because its status is ambiguous *and* its endpoints are undocumented, and implementing it would require reverse-engineering; xAI's SuperGrok device-code path is **not implemented** (unofficial, tier-gated). OpenRouter PKCE, Nous Portal OAuth, Vertex ADC and API keys everywhere are shipped. Anthropic's own policy in this area changed three times within 2026 — an April ban of third-party subscription use, a May-13 announcement of a monthly "Agent SDK credit," and a June-16 pause of that announcement — so the 90-day re-check (Action item 1) applies to the new Anthropic profile as much as to any `prohibited` one.

**Amended 2026-09-22 (owner decision D12).** The Anthropic profile above is now the *default* of three shipped routes, not the only one. Owner instruction, verbatim: *"Also drei Wege: API, Restricted und Claude Code."* (1) **Anthropic via Claude Code (headless backend)** — default, `policy_status: allowed`, unchanged in substance but now specified precisely (see the D12 amendment section below for the exact CLI invocation and the open M2 spike). (2) **Anthropic setup-token (OpenClaw-style)** — new, `policy_status: restricted`, opt-in with a visible risk notice: the harness stores the token the user obtained themselves via `claude setup-token` and calls the Anthropic Messages API directly with the request shape Claude Code uses. This narrows original §6.3's no-client-imitation rule; the narrowing is recorded as the D12 amendment below. (3) **Anthropic API key** — unchanged, `allowed`. See "### Amendment D12" below for the full evidence.

**Further amended 2026-09-22 (owner decision D13, same day).** D12's own draft went on to say OpenAI ChatGPT/Codex OAuth and xAI's device-code OAuth simply move from "not shipped" to flat `restricted` opt-in. The owner's actual A2 answer is more specific and **supersedes that clause**: OpenAI and xAI each get the **same three-route pattern as Anthropic**, not a single OAuth toggle. Verbatim: *"API (auch für Embeddings) Zusätzlich so wie bei Anthropic über die CLI / also grok und codex. Codex als 3. via oauth auf eigenes Risiko."* (1) API key, `allowed`, default — OpenAI's key also serves embeddings (D9, ADR-006). (2) The vendor's own CLI as a headless backend — **Codex CLI** (`codex exec --json` / `codex-acp`) for OpenAI, **Grok CLI** ("Grok Build") for xAI — `allowed`, spawned unmodified under the user's own login, exactly the Claude-Code-backend pattern. (3) **For OpenAI/Codex only**, ChatGPT/Codex OAuth as a third route, `restricted`, opt-in, risk notice "at your own risk" (the owner's own phrase). **xAI gets no OAuth route at all** — the xAI device-code profile is **not shipped**, imported from OpenClaw only as a visible, disabled profile, the same treatment as Google's. See "### Amendment D13" below.

### Declarative auth profiles (data, not code)

One JSON/YAML record per profile, versioned in config, never containing a secret:

`id` · `display_name` · `kind` (`api_key|oauth_pkce|device_code|adc`) · `capabilities` (`chat|embedding|rerank`) · `base_url` · `auth_header_scheme` (e.g. `Authorization: Bearer {token}`, `x-api-key: {token}`) · `extra_headers` · `authorization_endpoint` · `token_endpoint` · `device_authorization_endpoint` · `revocation_endpoint` · `scopes` · `client_registration` (`none|static|dynamic`) · `client_id` (only where the vendor publishes one for third parties) · `redirect` (`loopback` + port policy) · `pkce` (`S256`) · `refresh` (`rotating|static`, `refresh_skew_seconds`) · `discovery` (`/v1/models` or manual list) · `policy_status` · `policy_source` (URL) · `policy_checked` (date) · `person_bound` (bool) · `secret_ref` (keychain handle, never the value).

Adding a vendor that fits an existing kind must require no code — §6.1's "generic OpenAI-compatible / Anthropic-compatible templates" and §6.2's embedding/rerank equivalents are the same mechanism applied to profiles.

### Headless / SSH

Preference order, decided per environment probe, not per provider: (1) **device code** where the vendor documents one; (2) **loopback PKCE with a configurable port** plus an explicit `ssh -L <port>:localhost:<port>` hint in the CLI output; (3) **paste-callback fallback** — print the authorization URL, let the user complete it anywhere, paste the full callback URL back. OpenRouter's documented conventions support all three, including omitting the callback for headless apps (`research/providers-chat-auth-caching.md` §4).

Ship **one** pair of shared predicates — `canOpenGraphicalBrowser()` and `isRemoteSession()` — consulted by every flow, rather than per-provider heuristics; this is Hermes' `auth_device_flow.py` idea (`research/hermes-learnings-and-import.md` A3, citing `hermes_cli/auth_device_flow.py:49-88`). Its documented weakness is that the remote-IDE detection is a hard-coded env-var allowlist (`:40-46`) that always lags reality, so the harness adds a fallback signal (no `DISPLAY`/`WAYLAND_DISPLAY`, an `SSH_CONNECTION` present, or a non-TTY stdout) and always offers the paste fallback manually via `--paste-callback`.

A login can be started from the **web UI** (device-code dialog and QR/URL display, §9), the **CLI** (`plur1bus-harness login <profile>`) and a **chat channel** (§6.3) — in the channel case only for the identity-linked owner of the profile, with the code delivered in a DM, never in a group.

### Token lifecycle and credential pools

- Refresh proactively before expiry (`refresh_skew_seconds`, default 120 s), not on 401.
- Handle rotating refresh tokens as single-use; exactly **one** process owns refresh (the core), so the multi-process rotation race Hermes solves with file locks and reconciliation (`research/hermes-learnings-and-import.md` A3, `agent/credential_pool.py:100-105,908-926`) is designed out rather than worked around.
- Revoke/logout calls the profile's `revocation_endpoint` where present, then deletes the keychain entry and writes an audit record.
- **Multi-account credential pools** per profile with selection strategy (`fill_first|round_robin|least_used`) and **failure-classified cooldowns**: HTTP status alone cannot size a cooldown, so persist a classification and distinguish *confirmed* from *ambiguous* exhaustion; give the sole remaining credential a much shorter cooldown than one of several. This is Hermes' design idea, adopted conceptually and not verbatim — its own vocabulary (`billing`, `billing_unverified`, `EXHAUSTED_TTL_429_SECONDS = 3600` vs `EXHAUSTED_TTL_SOLE_CREDENTIAL_SECONDS = 60`) was a retrofit after a production incident (`research/hermes-learnings-and-import.md` A3, `agent/credential_pool.py:130-148,175-180`); we design the ambiguous/confirmed split in from day one and invent our own codes. Also adopted: **per-model cooldowns separate from per-credential status** (`:228-238`).
- Exactly one cooldown authority. Hermes runs a second, independent backoff in cron (`cron/quota_hold.py`, A7) and the note flags the disagreement risk; the harness routes cron and interactive turns through the same pool.
- **UI status per credential:** valid until, plan/tier if the provider reports it, last error with its classification, cooldown remaining, and the profile's `policy_status` badge with source link and check date (§6.3, §9).

Rules attached to the field: `prohibited` profiles are absent from the shipped catalogue — not hidden behind a flag, not loadable from user config. `restricted` profiles ship only when a **documented** flow exists; a status is never upgraded by reverse-engineering an official client. Every row carries `policy_source` + `policy_checked` and is re-checked on a schedule (Action item 1). The one exception to "no subscription profile ships" is the delegated-binary pattern: it is `allowed`, not `prohibited`, precisely because the harness performs no login of its own — it spawns an already-authenticated vendor process. That distinction (harness-native login vs. spawning the vendor's own authenticated binary) is now the load-bearing line in this table, not "subscription vs. API key."

**No client impersonation, narrowed by D12 (2026-09-22).** The harness never sends another product's client ID, never spoofs an official CLI's user agent, and never reproduces an official CLI's system prompt to look like it (§6.3) — that rule stands for any credential the harness itself obtains. It is narrowed, not repealed, for a token the user obtained through the vendor's own official flow: **"Client-compatible request shaping is permitted only for tokens the user obtained themselves through the vendor's official flow; the harness never re-implements a vendor login, never reads another client's credential store, never refreshes another client's tokens."** (D12, verbatim, amending original §6.3.) This is what makes the Anthropic setup-token profile possible without reopening the door to harvesting `~/.claude/.credentials.json` or any other client's stored credential. **Person-bound.** A subscription-derived credential is usable only by agents owned by the login holder and cannot be granted to other harness users (§6.3); RBAC enforces this in the same policy layer as everything else (ADR-004).

### Amendment D12 (2026-09-22): three Anthropic routes; OpenAI/xAI restricted; Google stays prohibited but importable

Owner decision, verbatim intent: *"Also drei Wege: API, Restricted und Claude Code."* Anthropic now ships three provider profiles instead of two:

1. **Anthropic via Claude Code (headless backend) — DEFAULT.** The harness spawns the unmodified `claude` binary (`--bare -p --input-format stream-json --output-format stream-json --system-prompt <ours> --mcp-config <ours> --strict-mcp-config`), or the official `@anthropic-ai/claude-agent-sdk`, which drives that same binary — one resident process per agent session, harness never holds a credential. `policy_status: allowed` (the compliance page permits an end user signing in to the unmodified binary, already cited above). Headless/SSH: the user runs `claude setup-token` or Claude Code's own login themselves; the token reaches the binary via `CLAUDE_CODE_OAUTH_TOKEN`, never used by the harness itself. Verified against the CLI docs 2026-09-22: `--bare` exists ("Minimal mode: skip auto-discovery of hooks, skills, custom commands, subagents, plugins, MCP servers, auto memory, and CLAUDE.md so scripted calls start faster"); `--system-prompt` replaces the default prompt entirely; `--input-format stream-json`/`--output-format stream-json`; `--mcp-config`/`--strict-mcp-config`; `--tools`/`--disallowedTools`; `--permission-mode`. SDK `Options`: `permissionMode`, `canUseTool`, `maxBudgetUsd`, `effort`, `fallbackModel`, `resume`; result field `total_cost_usd` (source: [code.claude.com/docs/en/cli-reference](https://code.claude.com/docs/en/cli-reference) and [code.claude.com/docs/en/agent-sdk/typescript](https://code.claude.com/docs/en/agent-sdk/typescript), checked 2026-09-22). **Open for an M2 spike:** whether Claude Code's built-in tools (Bash/Read/Edit) can be fully disabled in `--bare` via `--tools ""` — the SDK docs say built-ins "cannot be disabled entirely" via allowed/disallowed, the CLI docs say `--tools` restricts access, and the two statements contradict each other, unresolved as of this check — and the TTFT overhead of the resident process (target < 300 ms vs. direct API).
2. **Anthropic setup-token (OpenClaw-style)** — `policy_status: restricted`, opt-in with a visible risk notice. The user runs `claude setup-token` (Anthropic's own OAuth flow) and pastes the long-lived token; the harness stores it in the OS keychain and calls the Anthropic Messages API directly with the request shape Claude Code uses (required for the token to be accepted), billed against the user's subscription. **Evidence:** the owner's production OpenClaw 2026.9.5 installation runs Anthropic in `"mode": "token"` (`~/.openclaw/openclaw.json`, profile `anthropic:cyb3rb1ade-me.com`, inspected 2026-09-22 structure-only; `research/verification-log.md` V9) and bills against the subscription; Anthropic's June-2026 statement says third-party applications "continue drawing from regular subscription limits" (V7), while the compliance page still says developers "may not collect, store, or intermediate Claude.ai credentials or session tokens" (V5). Hence **restricted, not allowed**: it may stop working without notice; person-bound (only for agents owned by the token holder); never refreshed or re-minted by the harness; a dead token surfaces a typed re-auth message pointing to `claude setup-token`. This is the profile that required amending original §6.3's no-client-imitation rule, recorded above as D12. The Hermes route (reading `~/.claude/.credentials.json`/Keychain and refreshing it) stays excluded — cite `hermes-agent/agent/anthropic_credentials.py:5-7,46-49,217-357 @ 743ee72` and `website/docs/integrations/providers.md:142-177 @ 743ee72` (Max + extra usage credits only, Pro excluded) as the reason it is inferior anyway, on top of being the exact pattern §6.3 forbids (reading and refreshing another client's credential store).
3. **Anthropic API key** — `allowed`, pay-per-token, fallback and the shared-production recommendation. Unchanged.

**OpenAI and xAI OAuth, changed by D12, then superseded by D13.** The owner runs all three of OpenAI ChatGPT/Codex OAuth, xAI Grok OAuth and Google Gemini-CLI (now Antigravity CLI `agy`, D40) OAuth in production OpenClaw today (profiles `openai:chatgpt-default`, `openai:christian@…` mode `oauth`; `xai:…` mode `oauth`; `google-gemini-cli:…` mode `oauth` — V9). D12's draft plan was: **OpenAI and xAI OAuth become `restricted` opt-in with a risk notice**, both, imported from OpenClaw as disabled-until-opted-in profiles rather than omitted. **D13 (below) replaces this** with the three-route pattern. **Google Gemini-CLI (now Antigravity CLI `agy`, D40) OAuth stays `prohibited`** (Gemini CLI ToS names third-party harness use explicitly) unless the 90-day re-check finds the ToS changed; it is imported as a **disabled profile with the prohibition explanation**, not silently dropped. Where earlier drafts of this ADR and `provider-matrix.md` said "OpenAI and xAI not shipped at v0.1," that is superseded by D12 and then refined by D13.

### Amendment D13 (2026-09-22, same day as D12): OpenAI and xAI each get Anthropic's three-route pattern; xAI OAuth dropped

Owner answer to A2, verbatim: *"API (auch für Embeddings) Zusätzlich so wie bei Anthropic über die CLI / also grok und codex. Codex als 3. via oauth auf eigenes Risiko."* Read plainly: the owner wants OpenAI and xAI to mirror Anthropic's three-tier shape (API / CLI-backend / restricted-OAuth), not the flat "OAuth restricted for both" D12 first sketched. Concretely:

1. **API key — `allowed`, default, for both vendors.** Unchanged from the original table. For OpenAI, the same key also serves the embedding API (D9, ADR-006) — no separate embedding credential is needed.
2. **Vendor CLI as a headless backend — `allowed`, for both vendors.** The harness spawns the unmodified **Codex CLI** (`codex exec --json`, or over `codex-acp`) for OpenAI, and the unmodified **Grok CLI** ("Grok Build") for xAI, under the user's own existing login — exactly the "Anthropic via Claude Code" shape from D12, generalised. The harness never performs, brokers, stores or reads either login; discovery reuses ADR-011's existence-only probe.
3. **OpenAI only — ChatGPT/Codex OAuth as a third route, `restricted`, opt-in, "at your own risk."** This is the owner's own qualifier ("auf eigenes Risiko"), read as the risk-notice wording for this profile specifically, on top of the standard `restricted` opt-in disclosure. It still requires the user's own official ChatGPT/Codex login; the harness stores only the resulting token (§"Client-compatible request shaping" above).
4. **xAI does not get an OAuth route.** The owner named "grok und codex" for the CLI-backend route (item 2) but did not extend the third, OAuth route to xAI — only "Codex als 3." So xAI ships two routes (API key, Grok-CLI backend), and its existing production OAuth profile (`xai:…` mode `oauth`, V9) is imported as a **visible, disabled** profile, not opted into `restricted` — the same treatment already given to Google's prohibited profile, though xAI's own status is "not shipped by owner choice" rather than "prohibited by the vendor."

This does not change anything about Google, which stays `prohibited` and unshipped per D12/the original resolution.

## Options considered

### Option A: Ship every flow that technically works, gate the risky ones behind opt-in
| Dimension | Assessment |
|---|---|
| Complexity | High — three bespoke, undocumented flows to reverse-engineer and then maintain against silent vendor changes |
| Fit with brief | **Violates §6.3** ("`prohibited` wird nie ausgeliefert") and its no-impersonation clause |
| Cross-platform risk | Low technically |
| Maintenance burden | Very high: undocumented endpoints break without notice; xAI's surface already 403s legitimate subscribers |
| Latency / token cost | n/a |

**Pros:** users could use subscriptions they already pay for. **Cons:** knowingly ships terms violations in an MIT-licensed public repo under the owner's name; exposes users to account suspension (Gemini ToS states this explicitly); requires impersonating client IDs the vendors do not publish.

### Option B: API keys only; no subscription OAuth at all
| Dimension | Assessment |
|---|---|
| Complexity | Lowest |
| Fit with brief | Conflicts with §6.1's provider table, which lists OpenRouter PKCE and Nous Portal OAuth as intended — and Nous Portal has **no** API-key path at all |
| Maintenance burden | Lowest |

**Pros:** no policy exposure. **Cons:** drops two vendors that explicitly invite third-party OAuth, and loses the whole OAuth machinery §6.3 requires.

### Option C: Full auth engine; per-profile policy gate; no `prohibited` profile ships — **recommended**
| Dimension | Assessment |
|---|---|
| Complexity | Medium — one OAuth/device-code engine, driven by data |
| Fit with brief D1–D11 | Full: §6.3 as written, D5's ACP escape hatch as the compliant subscription path |
| Cross-platform risk | Keyring prebuilds confirmed on all six targets (`@napi-rs/keyring`) |
| Maintenance burden | The recurring cost is a dated policy re-check, not code |
| Latency / token cost | Proactive refresh keeps auth off the hot path (D6) |

**Pros:** every shipped flow is vendor-documented; policy changes are config-data changes; users keep a compliant route to their subscriptions via ADR-011. **Cons:** users who expected "log in with my Claude Max / Gemini subscription" must either use an API key or run the vendor CLI as an external agent; the harness looks less capable than tools that ignore the rules.

## Trade-off analysis

The only genuinely contested axis is user convenience versus enforceable compliance. Two of the four frontier vendors state the prohibition in their own words, one naming a competing harness by name; a public MIT repo under the owner's name that shipped those flows would be documenting its own violation. The technical argument points the same way: all three unavailable flows rest on undocumented endpoints, and one (xAI) is already observed failing for paying subscribers — so the maintenance cost is high and the reliability low even setting policy aside. The escape hatch costs the user little: the official CLI attached over ACP keeps the login inside the unmodified vendor binary, which is exactly the shape the vendors permit, and the harness already needs that subsystem for D5.

## Consequences

- **Easier:** auth becomes data — adding a vendor is a profile record, not a code path; one refresh owner removes a whole class of distributed race; one cooldown authority removes the Hermes cron-vs-pool disagreement; secrets have exactly one storage API with confirmed prebuilds on every target; the policy field makes the reason for an absent login visible in the UI instead of a mystery.
- **Harder:** "why can't I log in with my Claude subscription?" becomes a support question the docs must answer; the ACP path (ADR-011) is now load-bearing for subscription users, so its M6 timing matters more; an encrypted-file fallback needs its own key-management story on headless servers; the policy table needs a dated re-check forever, and a stale row is a compliance risk rather than a cosmetic one.
- **Revisit when:** any vendor publishes a third-party OAuth path (Anthropic, Google, OpenAI, xAI), the OpenAI ambiguity is resolved in either direction, or xAI documents the `accounts.x.ai` flow. Each is a config change plus an ADR amendment, not a rewrite.

## Conflicts with the brief

**Finding.** §6.1's provider table lists "Anthropic Claude-Abo — nur gemäß Auth-Policy (6.3)" and "Google-Gemini-Abo-Logins (Gemini CLI / Code Assist / Antigravity) — nur gemäß Auth-Policy (6.3)" (Gemini CLI is now Antigravity CLI `agy`, D40), i.e. it anticipates that those logins might ship under the policy. For Google, they do not: the 2026-09-22 check confirms Gemini CLI / Code Assist / Antigravity OAuth is **prohibited** in the vendor's own current wording, unchanged, and §6.3's rule that `prohibited` is never shipped applies without qualification. For Anthropic, a fresh 2026-09-22 re-read of the vendor's compliance page shows the prohibition is narrower than the original reading treated it: what is forbidden is a **harness-native** Claude.ai login — a harness-implemented OAuth/PKCE/device-code flow, or reading `~/.claude/.credentials.json`/Keychain, either of which is "collecting, storing or intermediating" the credential. The same page's "Can customers offer Claude Code in their products?" section explicitly permits a platform to host the unmodified Claude Code binary (or the Agent SDK that drives it) so each end user signs in with their own subscription through Anthropic's own flow — a documented, compliant route to "use my existing subscription" that the original reading did not distinguish from the prohibited one. Additionally, the owner's earlier default for `restricted` profiles (opt-in with a visible risk notice, §13 Q3) still has nothing to apply to at v0.1 for OpenAI and xAI: OpenAI's subscription flow is at best `restricted` but has no documented endpoints, and xAI's is unverified and tier-gated, so neither can be implemented without reverse-engineering, which §6.3 forbids.

**Source.** §6.1 and §6.3 vs. [code.claude.com/docs/en/legal-and-compliance](https://code.claude.com/docs/en/legal-and-compliance) ("Authentication and credential use" and "Can customers offer Claude Code in their products?", re-fetched 2026-09-22) and [geminicli.com/docs/resources/tos-privacy/](https://geminicli.com/docs/resources/tos-privacy/) (fetched 2026-09-22), the Feb-2026 clarification reporting ([The Register 2026-02-20](https://www.theregister.com/2026/02/20/anthropic_clarifies_ban_third_party_claude_access/)), [openai/codex discussion #8338](https://github.com/openai/codex/discussions/8338), [Hermes: xAI Grok OAuth](https://hermes-agent.nousresearch.com/docs/guides/xai-grok-oauth), plus [support.claude.com/en/articles/15036540](https://support.claude.com/en/articles/15036540-use-the-claude-agent-sdk-with-your-claude-plan) (published 2026-06-16), [the-decoder.com 2026-06-16](https://the-decoder.com/anthropic-backs-off-unpopular-billing-overhaul-as-price-war-with-openai-looms/), [VentureBeat 2026-05-13](https://venturebeat.com/technology/anthropic-reinstates-openclaw-and-third-party-agent-usage-on-claude-subscriptions-with-a-catch) and [docs.openclaw.ai/providers/anthropic](https://docs.openclaw.ai/providers/anthropic) — all as recorded in `research/providers-chat-auth-caching.md` §1–§4 and its subscription-login policy table, and re-verified in this 2026-09-22 amendment (see `research/verification-log.md` V5–V8).

**Options.** (i) Ship the flows anyway behind an opt-in warning (Option A above). (ii) Ship nothing for those vendors and say nothing. (iii) Ship no prohibited flow for Google/OpenAI/xAI, but ship the compliant substitutes (API key, vendor CLI over ACP) and explain the gap in the UI at the point of use. (iv) For Anthropic specifically, ship the delegated **"Anthropic via Claude Code / Agent SDK"** backend profile as `allowed` — spawning the unmodified binary/SDK under the user's own login — while keeping a harness-native Claude.ai OAuth `prohibited`.

**Recommended resolution: (iii) for Google/OpenAI/xAI, (iv) for Anthropic, stated for the record:**

> **Google, OpenAI and xAI subscription logins are not shipped — not as an opt-in, not behind a risk notice, not behind a hidden flag.** The rule "`prohibited` is never shipped" (§6.3) decides Google's case on the vendor's own current wording; OpenAI's subscription flow is ambiguous *and* undocumented, and xAI's is unofficial and tier-gated, so shipping either would require reverse-engineering an official client, which §6.3 forbids. Compliant substitutes are shipped in their place: **API keys**, which Google's AI Studio/Vertex paths and the OpenAI Platform explicitly permit, and **the vendor's own official CLI attached as an external ACP agent (ADR-011)**. Each affected profile stays in the catalogue as a **visible, disabled entry** carrying its `policy_status`, the source URL, the check date and the recommended alternative.
>
> **Anthropic subscription use is shipped, via a provider profile "Anthropic via Claude Code / Agent SDK."** The harness spawns the unmodified Claude Code binary (or the official `@anthropic-ai/claude-agent-sdk`, which drives it) under the user's own existing Claude login; it never implements a harness-native Claude.ai OAuth/PKCE/device-code flow and never reads `~/.claude/.credentials.json` or the Keychain equivalent, since Anthropic's compliance page forbids exactly that — *"developers may not collect, store, or intermediate Claude.ai credentials or session tokens"* — while explicitly adding, verbatim, that this *"does not prevent an end user from signing in to the unmodified Claude Code binary with their own Claude subscription, including where a platform hosts Claude Code as described under Can customers offer Claude Code in their products? above,"* whose conditions are: the binary must not be modified, no authentication method may be removed or disabled, no usage may be paid for/resold/intermediated, and each end user authenticates with their own credentials ([code.claude.com/docs/en/legal-and-compliance](https://code.claude.com/docs/en/legal-and-compliance), checked 2026-09-22). `policy_status = allowed`, sourced to that page together with Anthropic's June-2026 "Nothing changes for now" confirmation that the Agent SDK, `claude -p` and third-party applications keep drawing from regular subscription limits, and the monthly Agent SDK credit it announced 2026-05-13 and then paused, which the profile would draw from instead if reactivated. This profile is an ordinary chat-turn inference backend, not only an ADR-011 external coding agent — the same shape as OpenClaw's own "Claude CLI" route (which reuses the installed executable's login, does not persist or refresh it, and recommends an API key for shared production automation) and Hermes' `copilot-acp` provider. Google's, OpenAI's and xAI's subscription logins are unaffected and stay unshipped as above; whether an analogous Gemini-CLI (now Antigravity CLI `agy`, D40)-as-backend pattern is itself permitted by Google is **unverified** and is carried as an open re-check item, not an assumption. Anthropic's policy in this exact area moved three times within 2026 — an April ban of third-party subscription use, a May-13 credit announcement, and a June-16 pause of that announcement — so the 90-day re-check (Action item 1) applies to this profile as much as to any `prohibited` one.
>
> A dated re-check task re-verifies Anthropic, Google, OpenAI and xAI every 90 days and on any vendor announcement; a change to any vendor's status is then a profile-data change plus an ADR-005 amendment, not new architecture.

## Open questions for the owner

1. **§13 Q3 — owner confirmed 2026-09-22, then extended by D12 the same day:** *"Anthropic new terms allow OAuth for OpenClaw/Hermes and others."* This is accurate for the **mechanism** — the delegated "Anthropic via Claude Code / Agent SDK" profile above is exactly that OpenClaw/Hermes-style route, and it now ships as `allowed`, `default`. 2. Should disabled subscription profiles be **visible with an explanation** (recommended) or hidden entirely from the catalogue?
3. Encrypted-file fallback: operator passphrase prompted at daemon start (safer, blocks unattended restart) or a machine-bound key file with restrictive ACLs (survives reboot, weaker)? A hybrid with an optional TPM/Secure-Enclave-backed key is a later option.
4. Re-check cadence: 90 days proposed. Shorter (30) given how often 2026 policies moved, or event-driven only?
5. Do we support **per-user** provider credentials (Member brings their own key) in v0.1, or Owner/Admin-provisioned credentials only? This changes the pool and RBAC model, not the flows.
