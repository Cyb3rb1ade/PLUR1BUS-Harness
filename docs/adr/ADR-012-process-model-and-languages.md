**Amends ADR-001.** ADR-001 Option B describes the harness as "single-stack" ("one language, one toolchain"). D7 replaces that: the harness has two languages (Rust and TypeScript) joined by JSON Schema as the single source of every cross-language type. The rest of ADR-001 (standalone monorepo, engine in-process in a resident core, thin client) stands.

## Context

D3 asks for modules behind versioned, typed interfaces, an updater that replaces units without touching foreign internals, and restarts limited to what a change requires. D2/ADR-002 put the PLUR1BUS engine in-process in one resident core that is the only holder of the LanceDB and ONNX handles (T7). M1 acceptance 3 requires that a killed core or supervisor never blocks a command, and acceptance 11 requires `--help` p95 < 100 ms. Three forces follow:

1. Something must survive the failure of the process that holds the engine, and restart it: that cannot be the same process.
2. The command users type most (`plur1bus …`) must start fast and must not load Node, the engine or native modules.
3. Two processes in two languages must agree on every request, result, error and notification without hand-kept duplicates.

The owner asked for the process-model trade-off explicitly (D6) and accepted the language recommendation (D7) on 2026-09-24.

## Decision

**Process model B: a small Rust supervisor, one TypeScript core process per installation that holds the engine, and add-on modules as separate processes; a thin Rust CLI talks to the core over a local socket with JSON-RPC 2.0 (NDJSON), authenticated by a per-start token; the core excludes a second core with an OS-held lock taken through `node:sqlite`. Rust is used for the CLI, supervisor, installer and updater; TypeScript for the core and every module bound to a Node SDK; JSON Schema is the single source of RPC and configuration types, generated into both languages.**

### 1. Process model

```
OS service manager (launchd / systemd --user / Task Scheduler)      ← not ours
  └─ plur1bus supervise            Rust, tiny, always alive          ← H2
       ├─ core                     Node: engine, stores, models, JSON-RPC server
       └─ modules (none in 2a)     own processes, clients of the core
plur1bus <cmd>                     Rust CLI, thin client of core and supervisor
```

- **Core** (`packages/core`, `@plur1bus/core`): builds the engine once with `createEngine(host, config)` on the harness's own `HostServices` (`packages/core/src/engine.ts`, `host.ts`; `routing`, `pathOverrides`, `mutateConfig` absent, `runtime: null`), registers channel `cli`, replays the capture journal, then serves RPC. It is the only process that opens LanceDB or ONNX.
- **Supervisor (built in 2a-H3a, `crates/plur1bus/src/supervisor/`):** a Rust binary (`plur1bus supervise`, hidden subcommand) spawns the core (or adopts one already running), monitors it, restarts it with backoff, and answers `supervisor.auth`/`daemon.*` over its own socket/pipe (§10). It does **not** yet own `config.json` — that stays the CLI's job through 2a-H3b (§8; ADR-013 §5 is unchanged by this plan).
- **Modules** (2a defines the manifest shape, ships none): separate processes that are clients of the core through `@plur1bus/module-api`.
- **CLI** (`crates/plur1bus`): never loads Node for a command; connects to the core, and, since 2a-H3a, to the supervisor (`daemon`, `service`, `1staid check`). It never spawns the core implicitly — `daemon start` spawns the *supervisor* (directly, or through a registered OS service), never the core.

#### Why B — the A/B/C trade-off (D6)

| Dimension | A: one process, hot reload | **B: supervisor + core + module processes** | C: one process, worker threads |
|---|---|---|---|
| Restart one unit | Not real: ESM modules cannot be unloaded, so a "restart" re-imports next to the old instance and leaves its timers, listeners and native handles behind. | Real: a module restart is a process restart; the core keeps running. | Partial: a worker can be terminated, but native handles opened through the main thread's addons stay. |
| Fault isolation | None: a faulty add-on (throw in a timer, OOM, native crash) takes the engine down. | Per process: an add-on crash is a module crash; the supervisor restarts it with backoff. | JS heaps are isolated, but a native crash or process-level OOM kills every worker at once. |
| Secret isolation | None: add-ons share the heap that later holds provider keys. | OS process boundary; a module sees only what the RPC surface gives it. | Workers share the process address space with the secrets. |
| Updater / third-party add-ons | Replacing a unit means restarting everything. | Replacing a unit is stop, swap, start; first- and third-party modules have one shape. | Same restart caveat as A for native parts. |
| RAM | Lowest (one Node heap). | 30–50 MB baseline per Node process. | Low (one process, several isolates). |
| Complexity | Low at first, rising with every add-on. | Supervisor, lifelines and adoption are new code (spec §6.4). | Medium; worker messaging plus the native-crash gap. |

B's only structural cost is RAM per process. It is mitigated by starting modules lazily (none run in 2a) and, later, by a first-party "module host" that runs trusted small modules as workers *inside* one B process — a C-style optimisation layered on B, never replacing the process boundary for third-party code.

### 2. Languages and the single source of types (D7)

- **Rust** for the CLI, supervisor, installer and updater: a static binary with no runtime to install, fast cold start for `--help` (B1), and process/service handling (lifelines, Job Objects, `launchd`/`systemd`/Task Scheduler) without a Node dependency on the recovery path.
- **TypeScript** for the core and every module bound to a Node SDK: the engine is Node, and MCP/ACP/A2A SDKs are TypeScript (ADR-001, ADR-008).
- **JSON Schema 2020-12 is the single source.** `packages/rpc-schema/schema/rpc.schema.json` defines every method's `params`/`result`, every notification, the error enum, the envelopes and the capture-journal line. TypeScript types are generated by `json-schema-to-typescript` (`packages/rpc-schema/src/build.mjs` → `generated/types.ts`, `generated/names.json`); Rust types by `typify` 0.8 in `crates/plur1bus-rpc/build.rs` (into `OUT_DIR`, `$defs` rewritten to `definitions` for schemars 0.8). The TypeScript server validates params with ajv, and **also validates every result** before sending it (`rpc/server.ts`: a result that violates the schema is logged and answered with `E_INTERNAL reason=result-schema`). `packages/config-schema/schema/config.schema.json` plays the same role for configuration (ADR-013).
- **Contract fixtures** (`packages/rpc-schema/fixtures/`): one valid request/response pair per method, every error code once, every notification once; the TypeScript server tests and the Rust client tests (`crates/plur1bus-rpc`) read the same files.
- **Workspace package resolution** (rulings R12, R14): `rpc-schema`, `config-schema` and `module-api` export `{ "source": "./src/index.ts", "types": "./src/index.ts", "default": "./dist/index.js" }`; `scripts/test-package.mjs` runs Node with `--conditions=source`, so cross-package tests always run against source, never a stale `dist/`. Production resolution (`default`) is unchanged.
- **CLI `--json`** (ruling R13) prints the raw `serde_json::Value` returned by the RPC call, never a re-serialised typed struct: `typify` drops unknown keys on open result types and drops empty optionals, so a typed round trip would silently change the documented shape. Typed structs are used only to read fields. **R13 amended (2a-H2, ADR-016 §8):** every `--json` document now has exactly one key spliced on top of that raw value, `"schema": "<command>/<major>"` (dotted command path, e.g. `memory.list/1`, `memory.proposals.accept/1`; every failure document is `error/1`), inserted by a single `document()` helper (`crates/plur1bus/src/output.rs`) so `Out::ok`/`Out::fail` are the only call sites that touch the envelope. No RPC method result may declare a top-level `schema` property (enforced by a schema test) so the two can never collide; `config schema --json`'s value is `{ schema, tier, jsonSchema }` rather than splicing into the JSON Schema value itself, since a JSON Schema must not carry a foreign top-level key (ruling G15). `core run`'s ready line is the core process's own output, not a CLI document, and is exempt.

### 3. RPC transport and protocol

- **JSON-RPC 2.0, NDJSON**: one UTF-8 JSON value per line, at most 4 MiB per line (`MAX_LINE_BYTES` in `packages/module-api/src/framing.ts`, `MAX_LINE` in `crates/plur1bus-rpc/src/client.rs`, the Rust read is bounded to `MAX_LINE + 1` bytes). An over-long line is answered with `E_INVALID_PARAMS reason=line-too-long` and the connection is closed. One connection per client; notifications arrive on the same connection after `events.subscribe`.
- **Address**: POSIX `run/core.sock`; Windows `\\.\pipe\plur1bus-<first 16 hex of sha256(lower-cased home)>-core` (`packages/core/src/paths.ts` `coreAddress`; the Rust CLI derives the identical name, T11 ruling: `--home`/`PLUR1BUS_HOME` are absolutised and lexically normalised like Node's `path.resolve` on both sides).
- **Handshake `core.auth`**: the first request on every connection is `core.auth { token }`. Its result is `{ contract, rpc, instanceId, pid, capabilities? }`: the engine contract version (`1.6.0` at the pinned commit, `d32771c5`) and the RPC schema version (`x-rpc-version`, `1.1.0`, plan 2a-H2). Any other method before a successful `core.auth` is answered `E_UNAUTHORIZED reason=auth-required`; a wrong token or malformed `core.auth` params get an error and the connection is closed; a connection that has not authenticated within 30 s is closed (`authIdleMs`). `core.status` repeats `contract` and `rpc`. **2a-H2 (ADR-016 §3, ruling G2):** `capabilities` (`buildCapabilities`, `packages/rpc-schema/src/index.ts`) is now attached to the `core.auth` result — `{ methods, notifications, extensionPoints: {}, features }`, `methods`/`notifications` derived from the schema's own `x-stability`/`x-since`/`x-deprecated` annotations, never a hand-kept list; `features` is `CORE_FEATURES` (`packages/core/src/capabilities.ts`) sorted, currently `["events.harness", "memory.ops", "memory.proposals"]`. Both clients' `supports(method)` (`crates/plur1bus-rpc/src/client.rs`, `packages/module-api/src/client.ts`) answer `true` when `capabilities` is absent (an older core) and otherwise check `capabilities.methods` — this is how the CLI answers `E_NOT_AVAILABLE reason=core-lacks-method` against an old core instead of crashing (Review Focus 5). G2 also records that the supervisor handshake gets the same `Capabilities` `$def` only when the supervisor exists (2a-H3); H2 has no second handshake to extend.
- **Version check** is the client's job: both clients (`crates/plur1bus-rpc` `SUPPORTED_RPC_MAJOR = 1`, `packages/module-api/src/client.ts`) read `rpc` from the `core.auth` result, compare the major **before** deserialising the rest (a future major may have a shape this client cannot read), and refuse with `E_RPC_VERSION reason=major-mismatch`.
- **Closed error enum** (`$defs/ErrorCode`), now 15 codes: `E_UNAUTHORIZED`, `E_RPC_VERSION`, `E_NOT_AVAILABLE`, `E_CORE_UNAVAILABLE`, `E_INVALID_PARAMS`, `E_AGENT_UNKNOWN`, `E_CONFIG_INVALID`, `E_MODULE_UNKNOWN`, `E_INTERNAL`, `E_LOCKED`, and, added in 2a-H2 for the memory-op surface (ruling G7): **`E_NOT_FOUND`, `E_DENIED`, `E_APPROVAL_REQUIRED`, `E_CONFLICT`, `E_STORAGE`**. The code travels in `error.data.error` with optional `reason` and `detail`; the numeric JSON-RPC `code` is `-32602` for invalid params, `-32600` for an invalid request, `-32700` for a parse error, `-32601` for an unknown method (reported as `E_INTERNAL reason=method-not-found`) and `-32000` otherwise for every other code including the five new ones (`packages/core/src/rpc/errors.ts`). `RpcError` refuses to construct a code outside the enum, so no method can invent one without a schema change. `error.data` also gained an optional `ids: { [k]: string }` (2a-H2): the engine's non-secret `MemoryOpError.detail` map, copied onto the error only when it has at least one string-valued entry (`mapMemoryOpError`, `packages/core/src/memory-ops.ts`), and threaded through to `RpcError::ids()` (`crates/plur1bus-rpc/src/error.rs`) and the CLI's `--json` error document (`rpc_error_extra`, `crates/plur1bus/src/output.rs`) — this is how a half-failed shared-copy refresh's `sourceId`/`sharedId`/`staleSharedId` reach the person who has to finish it by hand (Review Focus 3).
- **RPC 1.2.0 adds a second server (2a-H3a, ruling S2).** The schema's single method/notification namespace now carries `x-server: "core" | "supervisor"` on every entry (`packages/rpc-schema/schema/rpc.schema.json`); `buildCapabilities(features, server)` (TS, `packages/rpc-schema/src/index.ts`) and `capabilities(server, features)` (Rust, `crates/plur1bus-rpc/src/capabilities.rs`) filter by it, so `core.auth`'s `capabilities` lists only core methods/notifications and the new `supervisor.auth`'s lists only the supervisor's. The supervisor serves `supervisor.auth` (token → `{rpc, instanceId, pid, capabilities}`, `SUPERVISOR_FEATURES = ["adoption", "lifelines"]`), `daemon.status` (`{supervisor: ProcessState, children: ChildStatus[]}`), `daemon.start` and `daemon.stop`; the core additionally serves **`core.adopt { nonce }`** (`x-server: "core"`, per S2 — the call a supervisor makes *on* the core, not `daemon.adopt` as the design spec's prose named it), which authenticates against `run/supervisor.token` (`timingSafeEqual`, case-insensitive hex) and, on success, makes the calling connection the core's lifeline (`packages/core/src/core.ts` `adopt()`, `orphan-watch.ts` `watchConnection`). `core.status`'s result became the shared, named `$defs/CoreStatus` (also returned by `core.adopt`), and gained three optional fields this plan adds: **`deprecationsUsed: string[]`** (ADR-016 §5, `RpcServer.deprecationsUsed()`, sorted, populated the first time a deprecated method or notification name is used, surfaced by `1staid check`'s `api.deprecations`); **`models: { embedder, reranker }`** (`$defs/ModelStatus`, Task 13, E4 contract 1.8.0 — see the warm-up deviation below); and **`sharedMemory: SharedMemoryStatus`** (Task 14, E4). A child's own shape, `$defs/ChildStatus`, is new: `{ role, process: ProcessState, instanceId, pid, adopted, restarts, lastExit, nextRestartAt }`, rendered by the Rust `ChildState::to_json()` (`crates/plur1bus/src/supervisor/state.rs`) and validated against the schema by both `crates/plur1bus`'s and `packages/rpc-schema`'s test suites. Both clients' `supports(method)` now check membership against the handshake's own `x-server`-filtered `capabilities.methods`, so a CLI command against an old or capability-less peer answers `E_NOT_AVAILABLE` for that one method (ADR-016 §3 restated for the second server).
- **Memory ops are served, not stubbed (2a-H2).** The paragraph this replaces described `memory.list|show|forget|correct|share|state` answering `E_NOT_AVAILABLE reason=engine-pr-E1` until engine PR E1 landed; that PR is in at the pinned commit, and `packages/core/src/memory-ops.ts`'s `buildMemoryOpMethods` now serves all ten MemoryOps methods (the original six plus `memory.propose`, `memory.proposals.list|accept|reject`, D31) from `Engine.memory`, spread into the RPC method table in place of the old stub. Every handler runs the same `op()` wrapper in order: refuse if the core `isStopping()` (`E_CORE_UNAVAILABLE reason=core-stopping`); `requireAgent` (`E_AGENT_UNKNOWN reason=not-registered`, moved here from `rpc/methods.ts` so the two modules don't import each other); derive the principal with `callerToPrincipal` and, on a degraded identity, refuse writes with `E_DENIED reason=principal-invalid` before the engine is called while reads proceed and carry `degraded` (ruling G8, extending the recall-only rule of R18 in §4 to the whole memory-op surface); for `memory.list`, refuse `topic` and `since` both present or both absent, or `until` without `since`, with `E_INVALID_PARAMS reason=topic-xor-since` (ruling G9) before the engine is called; call the engine under `AGENT_CONTEXT_CLI`; project the result onto exactly the schema's keys (`projectCard`/`projectProposal`), copying optional `score`/`sharedBy`/`sourceId` only when the engine sets them so a foreign `sharedBy` such as `"Anna.Main"` still validates (Review Focus 1); on a throw, `mapMemoryOpError` runs the G7 table (recognising a `MemoryOpError` by `name` and a known `code`, never by importing an engine internal) and, if it returns null, the error is rethrown as `E_INTERNAL handler-threw`. Accepting a proposal is worth naming here too: the engine refreshes the recipient's shared copy under a **new id** (the accept result's `id`, which also becomes the proposal's `resultId`), so a copy id taken before an accept is stale afterward — confirmed end to end by the 2a-H2 system test (`tests/system/memory-ops.test.ts`).
- **Back-pressure**: if a connection's pending writes exceed 16 MiB (`MAX_PENDING_BYTES`), the core logs a warning and destroys that connection — a stalled local client cannot exhaust the core's memory (T6 ruling).
- **Client timeouts** (`crates/plur1bus-rpc/src/client.rs`): socket connect and the whole `core.auth` handshake run under `connect_timeout` (300 ms); later calls under `call_timeout` (an idle read timeout; default 30 s, set per command by the CLI, e.g. `core.recall.hardBudgetMs` + 400 ms for `memory recall`). After a timeout, an I/O error, an over-long line or EOF the client marks itself **poisoned** and refuses further calls until reconnected, because the stream position is unknown. A missing socket fails at once (ENOENT), which is how the CLI answers "core absent" in well under 300 ms.
- **Shutdown drains memory ops before closing sockets (2a-H2, ruling G17).** `stop()`'s order is now: set state `stopping` → abort the shutdown signal → `engine.close({ budgetMs })` → `RpcServer.drain({ methods: MEMORY_OP_METHODS, budgetMs })`, which tracks every in-flight dispatch of a listed method and resolves once each has written its reply or the remaining budget runs out → `server.close({ graceMs: 1000 })`, which stops accepting, `end()`s every connection (never `destroy()` right after a `write()` — the PR #2 Windows rule) and arms an unref'd `destroy()` timer for the grace period → lock release → run files (`packages/core/src/core.ts`, `packages/core/src/rpc/server.ts`). A memory op already dispatched when `stop()` begins gets its result; one sent after `isStopping()` flips answers `E_CORE_UNAVAILABLE reason=core-stopping` at once.

**Notifications (2a-H2 replaces the H1 verbatim-forward model, ADR-016 §6).** `$defs/notifications` is now harness-owned: `core.state { process }` (unchanged), `agent.activity { agentId, activity }` (unchanged), and nine new schemas the core maps engine events onto (`packages/core/src/events-map.ts` `mapEngineEvent`) — `recall.completed`, `recall.degraded`, `recall.block-clipped`, `recall.block-dropped`, `job.run`, `memory.proposal`, plus the not-yet-emitted-by-the-engine `dream.completed`, `acl.denied`, `embedding.identity.changed` (ruling G11: minimal, experimental schemas, mapped when the engine starts emitting them, no invented payload fields). `mapEngineEvent` returns `null` — logged at debug and never sent — for an unknown name, a non-object payload, a missing or wrongly typed required field, or an `agentId`/`sharerAgentId`/`sharedBy` combination the schema rejects; `memory.proposal` sets `agentId` to the sharer and an `audience: [sharerAgentId, proposerAgentId]` so both sides of a proposal see it under an `events.subscribe { agentId }` filter (ruling G12). The old verbatim `engine.event { name, agentId?, payload }` notification still exists, unchanged in shape, but is now `deprecated` (`x-deprecated { since: "1.1.0", removeAfter: "2027-03-26", replacement: "harness event notifications: recall.completed, recall.degraded, recall.block-clipped, recall.block-dropped, job.run, memory.proposal (ADR-016 §6)" }`) and delivered **only** to a subscription that names it explicitly in `events.subscribe { names }` (ruling G13 — opt-in, so a no-filter subscriber gets the mapped notifications and never the raw engine payload); subscribing to it, or calling any deprecated method, logs one warning per process. `events.subscribe { names?, agentId? }` still filters by notification method name and, for an audience-bearing notification, by membership in the audience instead of the `params.agentId` match; one delivery per connection.

### 4. Authentication and transport security

- **Token**: 32 random bytes (`crypto.randomBytes(32)`), hex-encoded (64 characters; the schema enforces the length on `core.auth`), generated fresh at every core start and written to `run/core.token` with mode `0600`. The core compares it with `crypto.timingSafeEqual` after an equal-length check (`rpc/server.ts` `tokenMatches`). Socket permissions plus the token make the caller `trust: "proved"`.
- **POSIX**: `run/` is created `0700` and re-`chmod`ed `0700` at listen; the socket is `chmod 0600` after `listen`. An existing socket file is probed first: if something answers, the core refuses (`address in use`); only a dead (stale) socket is unlinked.
- **Windows, as built in 2a-H3a (Task 10; ruling S11).** The **supervisor's** pipe is created in Rust (`crates/plur1bus/src/supervisor/pipe_windows.rs`) with an explicit security descriptor `D:P(A;;GA;;;<user SID>)(A;;GA;;;SY)` (`crates/plur1bus-rpc/src/win.rs` `SecurityDescriptor::from_sddl`), `FILE_FLAG_FIRST_PIPE_INSTANCE` on the first instance, and every instance overlapped; closing a connection runs `CancelIoEx` before `DisconnectNamedPipe`, and `daemon.stop`'s drain (`FlushFileBuffers`) is bounded at 2 s before it cancels. The **core's** Node-created pipe deliberately keeps Node's default DACL (full control for SYSTEM/Administrators/creator-owner, read-only for Everyone/Anonymous) — deviation C2 below — mitigated two ways: (1) `securePath` (`packages/core/src/platform.ts` `createPlatformCapabilities`) now runs `icacls <p> /inheritance:r /grant:r *<SID>:(F) *S-1-5-18:(F)` (directories get `(OI)(CI)(F)` so files created later inherit it, ruling H3-R15) on `run/`, `run/core.token` and `run/core.pid`, returning `mechanism: "acl"` (the engine contract's closed union has no `"icacls"` value) or `{ applied: false, reason: "acl-tool-unavailable" }` on failure; (2) every RPC client (Rust and, via the supervisor's own connect calls, the health/adoption code) refuses a pipe whose `GetNamedPipeServerProcessId()` differs from the `run/{core,supervisor}.pid` it expects, before the token is even sent (`Client::handshake`'s `check_server_pid`, `E_UNAUTHORIZED reason="pipe-server-mismatch"`; client opens also carry `SECURITY_IDENTIFICATION` so a squatting pipe cannot impersonate the real server first). `1staid check`'s `windows.pipe-acl` row runs the same DACL walk (`win::pipe_dacl_report`/`writable_by_others`) read-only, and `crates/plur1bus-rpc/src/acl.rs` (`writable_by_others`, `run_writable_by_others`) implements the platform-neutral decision logic, unit-tested on every OS. Reads on every Windows `Client`/pipe now carry a real deadline via overlapped I/O (`win::overlapped_op`, `OverlappedPipe`) instead of the H1/2a-H2 "no deadline yet" gap. **Still true from H1/2a-H2:** the supervisor's own writes to a client have no deadline (`INFINITE`; documented limit, unchanged by this plan). **Not verified in this plan** (no Windows runner in the implementer's environment; verified only by `windows-2025` CI once the branch runs there): the exact interaction of `GetSecurityInfo` on a read-only pipe client handle, `FlushFileBuffers` cancellation on an overlapped pipe, and whether Task Scheduler's `RestartOnFailure` restarts a non-zero *exit code* or only a launch failure (§10 below).
- **Principal on the CLI path**: the CLI sends only `CallerIdentity { channel: "cli", accountId: <hostname>, userId: <OS user> }` (`crates/plur1bus/src/identity.rs`); every params object is closed (`additionalProperties: false`), so a client cannot supply `trust`, `origin`, `background` or `incognito`. The core derives the engine `Principal` (`packages/core/src/principal.ts`): `user:v1:sha256(JSON.stringify([channel, accountId, userId]))`, `workspace-dir:v1:<realpath of agents/<id>/workspace>`, `trust: "proved"`, `AgentContext { origin: "user", background: false }`, and `incognito: false` set explicitly on captures. **Identity degrade (ruling R18):** an identity that is empty, longer than 128 characters or contains control characters does not fail the call; the core uses `trust: "inferred"` without a user principal (agent-private memory) and reports `degraded { reason: "principal-invalid", capability: "identity" }` on recall. The schema therefore carries no `maxLength` on `accountId`/`userId`; the 128 limit (the engine's `INPUT_LIMITS`) lives in the core only.

### 5. The core lock: `node:sqlite` `BEGIN EXCLUSIVE`, not `flock`

The core holds `state/core.lock` for its lifetime (`packages/core/src/lock.ts`). The file is a SQLite database: the core opens it with `node:sqlite` (`DatabaseSync`), sets `PRAGMA busy_timeout=0; PRAGMA locking_mode=EXCLUSIVE`, runs `BEGIN EXCLUSIVE`, and records `{ pid, instance, at }` in a `holder` table inside the open transaction. An open EXCLUSIVE transaction is an `fcntl` (POSIX) / `LockFileEx` (Windows) lock held by the kernel for the process: a second core's `BEGIN EXCLUSIVE` fails immediately (busy timeout 0) and becomes `E_LOCKED reason=core-lock-held`; when the holder dies — including `SIGKILL` — the OS releases the lock. `release()` rolls back and closes. Verified: Node 24.21 during the plan's H1 pre-check, and permanently by `packages/core/test/lock.test.ts` ("refuses a second holder in another process and frees on SIGKILL") and `core.test.ts` (a second `createCore().start()` on the same home rejects with `E_LOCKED`).

Why not `flock`, as the spec says: Node has no `flock` API; the options were a native addon (a new prebuild matrix on five targets for one system call) or shelling out to a helper whose lifetime is not the core's. `node:sqlite` ships inside Node ≥ 24, already on the harness's dependency floor, and gives the same property — the lock dies with the process, "two cores on one LanceDB" is excluded by the OS, not by discipline.

**`E_LOCKED` (H1 addition to the spec's error enum).** The spec's closed enum had no code for "another core already holds this installation". Reusing `E_CORE_UNAVAILABLE` would have said the opposite of the truth (a core *is* running), and `E_INTERNAL` would have hidden an expected, user-actionable state. `E_LOCKED` is added to `$defs/ErrorCode`; the core process exits with code 3 when it is refused (`packages/core/src/bin.ts`), and the CLI maps `E_LOCKED` to exit code 3 too (`crates/plur1bus/src/output.rs`). A refused core never touches the running core's `run/core.token` or `run/core.pid`.

**Engine contract major is enforced, not just read (2a-H2).** `SUPPORTED_CONTRACT_MAJOR = 1` and `assertEngineContract` (`packages/core/src/engine.ts`) run immediately after the engine binds, inside `core.ts`'s start `try` block, so an unsupported major goes through the same start-failure cleanup as any other start error. A contract whose major isn't 1, or whose string doesn't parse as semver, throws `E_RPC_VERSION reason=engine-contract-major`; `bin.ts` maps that to process exit code **4** (ruling G20) — a fourth, distinct exit code alongside `E_LOCKED`'s 3, because "the engine moved to a contract this core cannot speak" is a different, non-retryable condition from "another core holds the lock".

### 6. Why `contract`/`rpc` travel in `core.auth`, not in every response envelope

The spec (§6.2) says every response envelope carries `contract` and `rpc`. JSON-RPC 2.0 defines the response object's members exactly (`jsonrpc`, `result` or `error`, `id`); strict clients reject extra members, and the harness's own `$defs/Response` is closed (`additionalProperties: false`) so that the schema stays a faithful JSON-RPC 2.0 description. Putting the versions inside every `result` would pollute every method's result type. The purpose — a client learns both versions before it relies on any shape and refuses an unknown major — is met by the mandatory first call: `core.auth` returns `contract` and `rpc`, `core.status` repeats them, and a connection cannot issue any other call before `core.auth`.

### 7. Captures under core loss (the journal)

When the core cannot be reached, `memory add` does not fail: the CLI appends a `JournalLine` (schema `$defs/JournalLine`: `v`, `id`, `at`, `agentId`, `sessionKey`, `caller`, `messages` — the caller identity, not a principal; the core derives the principal at replay exactly as for a live call) to `state/journal/<agentId>.jsonl` and reports `degraded { reason: "core-unavailable", capability: "capture" }` with `journaled: true`; `memory recall` answers `degraded { reason: "core-unavailable", capability: "recall" }` with exit code 0 — missing memory is a visible state, not a command failure. The core replays the journal at start, before it opens the socket:

- **Ruling R20**: a line leaves the journal only if its capture resolved without a `reason` and `stored + skipped > 0`; any reason, zero counts or a rejected `done` keeps it (logged, retried next start, counted as `journalBacklog` in `core.status`). Replay first renames `<agent>.jsonl` to `<agent>.jsonl.replaying-<pid>`, so a concurrent CLI append lands in a fresh file; kept lines are appended back, each with its own newline, so a later append can never glue onto a kept torn tail; leftover `*.replaying-*` files from a crashed replay are processed first; each file is processed in isolation (a failed rename skips that file for this start). Criterion: "no journal line lost". Cost: a poison line is retried every start until fixed by hand, and a crash between append-back and delete gives at-least-once reprocessing, which the engine's capture dedup absorbs.
- **Ruling R19** (capture semantics): a capture's abort signal is the core's own shutdown signal only — never the client connection and never the `waitMs` timer. `memory.capture` with `wait: true` races `done` against `waitMs` (default 60 s, `core.capture.waitMs`) and answers `{ id, acceptedAt, pending: true }` if the timer wins; the capture keeps running. A client disconnect never aborts a capture. Cost: a capture can outlive its request until core shutdown.

Plan H1 built everything below the supervisor as two interims, because the supervisor did not exist yet. **2a-H3a builds the supervisor** (`crates/plur1bus/src/supervisor/`: `mod.rs` the state machine and restart scheduler, `server.rs` the RPC server, `child.rs` spawn/health/hang-kill, `adopt.rs` peer-credentialed adoption, `pipe_windows.rs` the Windows ACL'd pipe, `service/{systemd,launchd,schtasks}.rs` OS registration) and the RPC, `daemon`, `service` and `1staid check` surfaces built on it (§3, §10). ### 10. Supervision (2a-H3a)

This section records how the supervisor built in 2a-H3a resolves the spec §6.4 gaps the plan's rulings S3–S9, S14 and S17 were written against, plus the durability bugs the plan's kill soak found and the model warm-up it shipped.

#### 10.1 Identity, the token, and lifelines (S3, S4)

`run/supervisor.token` is both "the nonce a fresh start writes" (spec) and the supervisor's own RPC bearer token: 32 random bytes as lower-case hex, written fresh at every `supervise` start with mode `0600` (`crates/plur1bus/src/supervisor/mod.rs`, `fresh_token`, `getrandom` 0.3). A spawned child's lifeline is its **stdin pipe**, held open by the supervisor's `Monitor` (`supervisor::child::Monitor`, `Lifeline::Stdin`); an adopted child's lifeline is **the authenticated connection `core.adopt` succeeded on** (`Lifeline::Connection`). Losing either — stdin EOF/error, or that connection closing — orphans the core (`packages/core/src/orphan-watch.ts` on the core side); a later successful `core.adopt` replaces the previous source (`orphan-watch.ts` `watchConnection`).

#### 10.2 Health, hangs and termination (S6, S8)

The health thread polls `core.status` every `healthIntervalMs × scale` with a 2 s deadline; three consecutive failures mark the child `degraded("unresponsive")`, and one success restores whatever state the core itself reports (`process.state`). "Hung" is defined as no successful poll for `max(30 s, 3 × healthInterval) × scale` of monotonic time (`Instant`, never wall time) — the `3 ×` floor is a 2a-H3a addition beyond the spec's bare "30 s", because a literal 30 s would make every healthy core between polls look hung whenever `healthIntervalMs` is configured above 10 s. A hung child is escalated: `core.shutdown` on a fresh connection (any OS), `SIGTERM` after 2 s × scale (unix only), `SIGKILL`/`TerminateProcess` after 10 s × scale more (`supervisor::child::Monitor`'s waiter thread). The supervisor never signals a PID it has not confirmed is the actual peer at that moment: on unix this is `SO_PEERCRED`/`LOCAL_PEERPID` (`plur1bus-rpc::transport::Stream::peer_pid`) checked via a fresh connect immediately before each signal (macOS and other unix, per-signal re-check), or pinned once through a `pidfd` opened at probe time (Linux, `crates/plur1bus/src/supervisor/adopt.rs` `Peer::open`, no re-check needed — a pidfd cannot be reused for a different process); on Windows it is a process handle opened with `OpenProcess` while the pid was known to be the pipe's server (`Peer`, `TerminateProcess`), with "cannot tell" (treated as alive) when `OpenProcess` itself fails. `run/core.pid` is `<pid> <instanceId>\n`; a mismatch on either field marks a found process `Foreign`, never signalled by the socket-server pid alone.

#### 10.3 Exit classification, crash reasons and backoff (S9, ruling H3-R3)

`crates/plur1bus/src/supervisor/state.rs`'s `CrashReason` enum is the vocabulary the whole plan uses for "why did the core stop", both in `daemon.status`'s `lastExit.reason` and in `1staid check`'s `core.state`/`supervisor.state`: **`lock-held`**, **`config-invalid`**, **`engine-contract`**, **`ready-timeout`**, **`adopted-exit`**, and **`none`** (a clean, requested stop). `classify_exit(code, signal, requested)` maps: a requested stop always wins → `stopped` with reason `none`; otherwise exit 2 → fatal `config-invalid` (an invalid `config.json`, never retried without `daemon start`); exit 4 → fatal `engine-contract` (the pinned engine's contract major, or since Task 13 minor, is unsupported by this core — S18 below — never retried without `daemon start`); exit 3 (`E_LOCKED`) → retryable `lock-held`; anything else (including a bare signal) → retryable with no specific reason, except that the supervisor itself assigns `ready-timeout` when its own 60 s × scale readiness wait is what killed the child, and `adopted-exit` when an *adopted* core (one the supervisor did not spawn) goes away on its own with no lifeline loss recorded as the cause.

`Backoff` (`state.rs`) is the exit → next-restart-delay/give-up policy: delays double 1, 2, 4, 8, 16, 32, 60, 60… seconds (× scale), reset to 1 s once the child has been `ready` for a full `600 s × scale` window with no new exit. **Ruling H3-R13** (a fix-round finding, not the plan's original text): a `lock-held` exit backs off exactly like any other exit **but never counts toward the 5-exits-in-10-minutes give-up rule** (`Backoff::on_lock_held_exit`, distinct from `on_exit`). Without this, a core that is simply slow to listen (still holding `state/core.lock` from a prior generation, or racing a hand-started `core run`) would exhaust the sticky give-up budget — reached in about 1 s at scale 0.02 — before the supervisor's next start-up probe (`probe_and_adopt`) ever got a chance to find it `Serving` and adopt it instead of respawning. The cost accepted: a lock holder that never listens and never dies causes one spawn (which exits 3) at most every 60 s × scale, forever, each logged — cheaper than a supervisor that gives up on a core still coming up. A real crash still gives up permanently after 5 exits within the window (sticky, cleared only by `daemon start`'s `Backoff::reset()`), pinned by `crates/plur1bus/tests/system/kill-soak.test.ts`'s `S16` subtest and `state.rs`'s property tests.

#### 10.4 A missing `core.js` keeps the supervisor up (ruling H3-R11)

Spec §6.4 does not say what happens if the thing the supervisor is told to spawn does not exist (for example, before `setup`/2a-H3b-4 has installed a runtime). The first cut of Task 6 had the supervisor exit 1 in that case; the fix round reversed this, because under a service manager with `Restart=on-failure` that just loops the exit every second, which is worse than the alternative: `run_inner` builds the `Monitor` lazily (`supervisor::child::mark_unspawnable`), and a missing `core.js` shows the child as `Crashed { reason: "config-invalid" }` with `restart_at` cleared and `nextRestartAt`/`pid` both `null` — visible and quiet, not retried, until a `daemon start` (which re-runs `core_spec` and spawns as soon as the file exists) or the file simply appears and the next `daemon start`/restart finds it.

#### 10.5 Run files: `run/supervisor.lock`, stale files, and `*.tmp` (ruling H3-R9)

Beyond the spec's "probe the address, then write the token, then bind" sequence, 2a-H3a added an exclusive `run/supervisor.lock` (`std::fs::File::try_lock`, no new dependency) taken *before* the address probe, closing a real race: two processes starting at once can both find a dead address and each proceed to overwrite the other's fresh token or unlink the other's fresh socket. The loser of the lock probes the winner (up to 3 s) for its pid, prints `supervisor already running (pid N)` to stderr, and exits 3 (Review Focus 1, `a_second_supervisor_on_the_same_home_exits_3`). **The lock file is never removed** — removing it would reopen the same race on the next start — so `1staid check`'s `run.stale-files` row must treat `run/supervisor.lock` as expected, not stale, and never reports it. The same expectation extends to any `*.tmp` file a rename-based atomic write leaves behind after a crash mid-write (config, tokens); `1staid check` does not flag those either. What `run.stale-files` *does* flag: `core.pid`/`supervisor.pid` present but naming a dead pid, and `core.sock`/`supervisor.sock` present but nothing answering — both expected after a power loss, both cleared automatically by the next `supervise` start (a stale socket file is unlinked once probing confirms nothing is listening on it), and both reported `warn` before that start and `ok` after (Review Focus 3).

#### 10.6 Stop: a hard deadline, and the OS service unit values (S16 hand-off, Task 8)

`daemon.stop { budgetMs? }` (default 10 s, range 0–120 000 ms, S16's soak uses this to bound outages) is a **hard deadline** from the moment the stop request is accepted, not a sequence of independent waits: `Monitor::stop` computes `deadline = now + budget + stop_grace` once, and every subsequent wait (for `core.shutdown` delivery, for the process to exit, for a post-kill reap) is clamped to what remains of that deadline, not to its own fixed timeout — this is what makes `daemon.stop`'s advertised budget an upper bound on wall time rather than an aspiration (`crates/plur1bus/tests/supervisor_children.rs` `daemon_stop_is_bounded_by_the_budget_for_a_hung_core`). This deadline is why the OS service units' own stop-timeout values are set well above the RPC-level maximum: `TimeoutStopSec` (systemd) and `ExitTimeOut` (launchd) are **150 s** — the 120 s maximum `daemon.stop budgetMs` plus a further hard-stop grace plus a 25 s margin — so the OS never forcibly kills the supervisor mid-graceful-stop while it is still legitimately draining a child within a budget the RPC caller itself chose. Task Scheduler has no equivalent graceful-stop setting; its `/End` terminates directly, which is why `service uninstall` on Windows now calls `daemon.stop` first and falls back to `/End` only if that does not answer (Task 10).

#### 10.7 Deviations accepted for this plan (beyond the table below)

- **No `PR_SET_PDEATHSIG` / Job Object `KILL_ON_JOB_CLOSE` (ruling S5, controller ruling C1).** The spec names both as backstops that kill an orphaned child when the supervisor dies. Both were rejected outright: they contradict D11 and acceptance criterion 3 ("the core survives a supervisor crash and is adopted by the next one") by definition — a backstop that kills the child on supervisor death makes adoption impossible. The core's own grace timer (`supervisor.graceMs`) is the backstop for an orphan whose new supervisor never arrives in time; a hung orphan (accepts a connection but never answers) is caught by the *next* supervisor's start-up probe, which terminates it before adopting or spawning fresh (§10.2). Recorded as a permanent ADR-012 deviation, not merely deferred.
- **`KillMode=process` (systemd) / `AbandonProcessGroup=true` (launchd), Task 8's own addition beyond the plan's literal service-unit values, for the same D11/C1 reason:** the default `KillMode=control-group` (systemd) would have systemd kill the core *together with* a crashed or stopped supervisor, since both share a process group by default — again making adoption impossible. `RestartPreventExitStatus=2 3` (systemd) stops the OS from looping a restart on a usage error (2) or "another supervisor already owns this home" (3, the single-instance-lock refusal of §10.5) — those are not transient failures a restart would fix.
- **launchd has no "don't restart on this exit status" equivalent to systemd's `RestartPreventExitStatus`.** `KeepAlive = { SuccessfulExit = false }` restarts on *any* non-zero exit, including exit 1 (a usage error) and exit 3 (lost the single-instance race) — unbounded restart, throttled only by `ThrottleInterval = 5`. This is a known, accepted gap on macOS: a misconfigured `plur1bus.plist` invocation (for example a corrupted binary path surviving a bad update) restarts every 5 s indefinitely until `service uninstall` or manual intervention, with no equivalent of systemd's exit-code allowlist. Left to a human or to 2a-H3b's `update`/`1staid repair` to notice and fix, not solved in this plan.
- **Windows Task Scheduler's `RestartOnFailure` semantics are unverified** for a process that exits with a non-zero *code* versus one that simply fails to *launch* — sources disagree, and the implementer's environment has no Windows runner. The CI system job (`windows-2025`, gated `service_real::the_os_restarts_a_killed_supervisor`) is the empirical answer; as of this record it had not yet been observed to run. If it turns out `RestartOnFailure` only covers launch failures, 2a-H3b needs either a wrapper task or a second, repetition-based trigger.
- **A Windows console window can flash briefly at Task Scheduler logon** even with `release_own_console()`'s `FreeConsole()` call (Task 10, checkpoint 5c) — that call only closes a console the supervisor does not share with an interactive shell; it cannot prevent one being briefly created at process start. Not fixable from user-mode without hiding the whole process, which is out of scope.
- **A `%` in the binary path or `--home` is refused outright for Task Scheduler** (`ServiceError::PathHasPercent`, reason `path-percent`) rather than escaped: Task Scheduler expands `%VAR%` in both the command and its arguments with no literal-percent escape, so a path containing one cannot be represented safely.
- **`PLUR1BUS_NODE` must name `node.exe`/`node` directly, never a shell shim (`.cmd`, a wrapper script).** With a shim, the OS-reported child pid is the shim's, not the eventual `node.exe`'s; the supervisor's identity checks (§10.2: hello `pid` must equal both the socket-server pid and, for a spawned child, the OS process handle it holds) then never match, and the child never becomes `ready`. This is a documented operational constraint, not a bug to fix — the same requirement already existed for `core run` before 2a-H3a, and the Windows pipe-server-pid check (§4) now catches the mismatch even earlier, before the token is sent.
- **The supervisor's own writes to a connected client have no deadline** (`INFINITE` on Windows, unbounded on unix) — a client that stops reading its socket/pipe can hold one server-side connection thread open indefinitely. This predates 2a-H3a (present since the H1 RPC server) and is recorded here as a known limit still not addressed, tracked for a future plan if it becomes a real problem (the supervisor's own connections are all short-lived RPC calls in practice).

#### 10.8 Two data-loss bugs the kill soak (criterion 2, Task 12) found and fixed

1. **A dead supervisor's stdio pipes crashed the core's own graceful stop (EPIPE).** An orphaned core's grace-expiry stop path logs through `console.error`, which after a `SIGKILL`ed supervisor writes to a now-reader-less pipe and throws `EPIPE`; the resulting unhandled `error` event on the stream crashed the process mid-stop, leaving `run/core.sock`, `core.pid` and `core.token` behind with no "core stopped" line ever written. Fixed in `packages/core/src/bin.ts`: every stdio stream's `error` event is now swallowed (`stream.on("error", () => {})`) for both `stdout` and `stderr`, on the reasoning that losing a log sink must never be allowed to abort a shutdown — the core's own log file remains the record of what happened.
2. **A capture the core's own stop aborted was answered as if it had succeeded, and the fact was silently lost.** `memory.capture` accepted just before the core began stopping was cancelled by the stop's abort signal, but the engine's own "not captured" outcome (`{ stored: 0, skipped: 1, reason: "not_captured" }`, or `{ stored: 0, skipped: 0 }`) was returned to the caller as a normal (non-error) result — so the CLI printed it as a plain, non-degraded reply and never journaled it (the journal fallback only triggers on an RPC *error*). Fixed in `packages/core/src/rpc/methods.ts`: `memory.capture` now throws `E_CORE_UNAVAILABLE reason=core-stopping` in every case where the stop's abort touched the call before anything was actually stored — arriving after `isStopping()` is already true, aborted before `stored > 0`, or a post-abort rejection — and the CLI (`crates/plur1bus/src/commands/memory.rs`) journals that error exactly as it already journals an unreachable core. **Ruling H3-R21** extends the same refusal to `memory.recall` on a stopping core (previously it could answer `degraded { reason: "engine-closed" }`, a shape a caller could mistake for a normal, if degraded, answer): a stopping core now refuses both memory ops the same way, `core-stopping`, so "the core is going away" is never confused with "the core answered, just imperfectly."

#### 10.9 Engine pin, contract-minor enforcement, and E4 (S18, ruling C8)

The engine pin moved twice within this plan: `3a4426a5` (contract 1.7.0, Task 1, Tasks 2–12's baseline) and then, once engine PR E4 merged (ruling C8: Tasks 13–15 waited for that merge and then followed E4's *actual* shipped interface rather than the plan's copy of it), `d0842424` (contract **1.8.0**, Task 13). `assertEngineContract` (`packages/core/src/engine.ts`) was extended beyond the existing major-only check to also refuse any `1.x` contract below `1.8.0` — `E_RPC_VERSION reason=engine-contract-minor`, mapped to the same process exit code 4 as a major mismatch (§10.3's `engine-contract` crash reason) — because the model-warm-up and shared-memory-status surfaces this plan built (§10.10, ADR-016's `memory.shared` check) depend on E4 members (`Engine.models`, `EngineStatus.sharedMemory`) that do not exist below 1.8.0. No feature-detection fallback was needed in the final code: Tasks 2–12 never referenced any E4 member, so there was nothing to detect around once the pin moved.

#### 10.10 Model warm-up, its measured numbers, and where it lives (spec §6.3, ruling C4)

The core now calls `engine.models.warm({ signal })` once, right after it becomes ready (`packages/core/src/warmup.ts` `startWarmup`), in the background — `process` stays `ready` throughout (ruling S7/C4: the design spec's own `core.status.degraded = { reason: "models-warming" }` does not exist as a top-level field; the model-derived degraded state lives at `core.status.engine.degraded`, distinct from process health, exactly as ADR-012 §3 already separated "is the socket serving" from "is the engine's own state fully healthy"). `engine.ready` is `true` only once `engine.degraded` is `null`; `engine.models` (`$defs/ModelStatus`, §3 above) reports the embedder's and reranker's own `state`/`warming`/`checkedAt`/`error` independently, so a client can show partial readiness rather than a single boolean. `1staid check`'s `models.warm` row (inserted right after `core.state`, ruling H3-R5's fixed check-id ordering) is `ok` when nothing is degraded, `warn` (with `detail.capability`) while `models-warming`, and `fail` (with `detail = { capability, error }` and a hint pointing at `logs/core.log`) on `model-failed`.

Measured numbers (Task 13, this 2-core sandbox unless noted):
- **B8 (core ready, flat embedder, no real models):** ~563–599 ms from `core run`/`supervise` start to the socket serving; the flat-embedder path never has a model to warm, so "models warm" reports 75–77 ms after ready (there is nothing real to wait for).
- **B11 (`core.status` p95, the health-poll-cost bound):** 0.32 ms, well inside the 5 ms budget.
- **Real-model nightly** (`nightly.yml`, real embedder + reranker): models warm **4.5–4.9 s** after the core reports ready; the **first real recall** answered in **292 ms (ubuntu)** / **314 ms (macOS)**, both inside the 400 ms soft budget and both with `exceededBudget: false`. As of this record the nightly run on this plan's branch was **still red**, on a `degraded { capability: "recall", reason: "aborted" }` flag the first recall carried despite its latency being within budget — under investigation as a follow-up, read-only at the time of writing, expected to land after this plan's docs commit (one writer at a time, per this plan's own rule).

Engine-side follow-up recorded for the next engine plan (not fixed in this plan, and not a 2a-H3a/2a-H3b bug): **capture latency grows roughly linearly with the number of LanceDB fragments** a table accumulates, because every `memory add` writes one fragment and a query scans all of them; compaction (`table.optimize()`/equivalent) currently runs only inside the engine's own `consolidate-daily` job, never opportunistically. This was found by the kill soak's own latency measurements (Task 12: `memory add`/`memory recall` grew past their per-call budgets at roughly 100–150 facts on one agent with the flat embedder) and is why the soak spreads its facts round-robin across several agents rather than one (ruling H3-R19) instead of the design spec's implied single-agent load. Measuring this with the real embedder, and periodic compaction outside `consolidate-daily`, are both open items for a future engine plan (tentatively "E5").

#### 10.11 Journal replay runs before the socket listens — a design question left for 2a-H3b

The core's journal replay (ADR-012 §7, unchanged in mechanism by this plan) still runs to completion **before** the RPC socket starts serving. Task 15 made replay durable against a kill mid-replay — every replayed line now carries a stable `runId` (`journal:<line id>`, unchanged across restarts and across a partially-replayed `.jsonl.replaying-<pid>` file), and the engine's own `duplicate-turn` capture outcome removes a line that a previous, interrupted replay had already stored, closing the at-least-once-replay gap the kill soak surfaced (§10.8's data loss was a different bug; this is the "same fact captured twice" symptom the soak also measured, down to 0 duplicates across the runs recorded in Task 15's report). What Task 15 did **not** change, and what the plan's own progress ledger flags explicitly for 2a-H3b: while a large journal backlog is being replayed, the core is simply unreachable for that whole window (`daemon status`/`1staid check` correctly show it as not-yet-ready, and callers correctly journal or degrade), which can be tens of seconds after a long outage under load. Whether the core should instead start serving RPC (or at least `core.status`/`memory.recall` against already-consolidated data) while replay continues in the background is an open design question for 2a-H3b, not resolved here.

| §6.2 notifications `config.changed`, `module.state` | Not in the 2a-H2 schema | Supervisor notifications; added with the supervisor methods in 2a-H3 (ruling G1). |

## Consequences

- **Easier:** restarting or replacing a module without touching the core; third-party add-ons with the same shape as first-party ones; a CLI that answers in milliseconds and stays useful when the core is down; one schema edit changes both languages, and the fixtures fail the build on drift; a second core on the same home is impossible, not merely discouraged.
- **Harder:** two toolchains in CI (Cargo and pnpm) and two failure surfaces; every new method needs a schema edit, `pnpm gen`, fixtures and `pnpm docs:gen`; RAM grows by 30–50 MB per running module process; the supervisor's lifeline/adoption/backoff code (2a-H3a, §10) is new code in a process that must not fail, verified so far only by the Linux sandbox plus compile-checks on Windows and macOS pending their CI legs.
- **Revisit when:** RAM per module becomes a user complaint (build the in-process module host for trusted modules); the engine publishes the npm prerelease (switch the pin); 2a-H3b lands (supervisor ownership of `config.json`, `config.changed`, the module loader, `setup`, `update`, `1staid repair`, admin ops over RPC); a client needs versions on every response (it does not today — they are per connection); the engine adds LanceDB compaction outside `consolidate-daily` (§10.10) or the nightly's `degraded {capability:"recall", reason:"aborted"}` investigation lands; the design question of serving RPC during journal replay (§10.11) gets an answer.

## Alternatives considered

- **Process model A (single process, hot reload)** and **C (worker threads)**: rejected, see the table in §1.
- **One language (TypeScript for the CLI too)**: rejected by D7 — a Node CLI pays Node start-up on every command (B1 < 100 ms p95 is not reliably reachable) and puts Node on the recovery path of a broken Node installation.
- **Hand-written types on both sides**: rejected; drift between the Rust client and the TypeScript server is the most likely class of bug in a two-language system.
- **`contract`/`rpc` in every result**: rejected, pollutes every result type (§6).
- **`flock` through a native addon, or a PID file**: the addon adds a prebuild matrix for one call; a PID file is discipline, not exclusion (stale PIDs, PID reuse).
- **HTTP on loopback instead of a Unix socket / named pipe**: rejected for the local control path — a port is reachable by every local user and needs its own auth story; filesystem permissions on the socket are free on POSIX.
