**Amends ADR-001.** ADR-001 Option B describes the harness as "single-stack" ("one language, one toolchain"). D7 replaces that: the harness has two languages (Rust and TypeScript) joined by JSON Schema as the single source of every cross-language type. ## Context

D3 asks for modules behind versioned, typed interfaces, an updater that replaces units without touching foreign internals, and restarts limited to what a change requires. D2/ADR-002 put the PLUR1BUS engine in-process in one resident core that is the only holder of the LanceDB and ONNX handles (T7). M1 acceptance 3 requires that a killed core or supervisor never blocks a command, and acceptance 11 requires `--help` p95 < 100 ms. Three forces follow:

1. Something must survive the failure of the process that holds the engine, and restart it: that cannot be the same process.
2. The command users type most (`plur1bus …`) must start fast and must not load Node, the engine or native modules.
3. Two processes in two languages must agree on every request, result, error and notification without hand-kept duplicates.

The owner asked for the process-model trade-off explicitly (D6) and accepted the language recommendation (D7) on 2026-09-24.

## Decision

**Process model B: a small Rust supervisor, one TypeScript core process per installation that holds the engine, and add-on modules as separate processes; a thin Rust CLI talks to the core over a local socket with JSON-RPC 2.0 (NDJSON), authenticated by a per-start token; the core excludes a second core with an OS-held lock taken through `node:sqlite`. Rust is used for the CLI, supervisor, installer and updater; TypeScript for the core and every module bound to a Node SDK; JSON Schema is the single source of RPC and configuration types, generated into both languages.**

### 1. Process model

```
OS service manager (launchd / systemd --user / Task Scheduler)      ← not ours
  └─ plur1bus supervise            Rust, tiny, always alive          ← H2
       ├─ core                     Node: engine, stores, models, JSON-RPC server
       └─ modules (none in 2a)     own processes, clients of the core
plur1bus <cmd>                     Rust CLI, thin client of core and supervisor
```

- **Core** (`packages/core`, `@plur1bus/core`): builds the engine once with `createEngine(host, config)` on the harness's own `HostServices` (`packages/core/src/engine.ts`, `host.ts`; `routing`, `pathOverrides`, `mutateConfig` absent, `runtime: null`), registers channel `cli`, replays the capture journal, then serves RPC. It is the only process that opens LanceDB or ONNX.
- **Supervisor (built in 2a-H3a, `crates/plur1bus/src/supervisor/`):** a Rust binary (`plur1bus supervise`, hidden subcommand) spawns the core (or adopts one already running), monitors it, restarts it with backoff, and answers `supervisor.auth`/`daemon.*` over its own socket/pipe (§10). It does **not** yet own `config.json` — that stays the CLI's job through 2a-H3b (§8; ADR-013 §5 is unchanged by this plan).
- **Modules** (2a defines the manifest shape, ships none): separate processes that are clients of the core through `@plur1bus/module-api`.
- **CLI** (`crates/plur1bus`): never loads Node for a command; connects to the core, and, since 2a-H3a, to the supervisor (`daemon`, `service`, `1staid check`). It never spawns the core implicitly — `daemon start` spawns the *supervisor* (directly, or through a registered OS service), never the core.

#### Why B — the A/B/C trade-off (D6)

| Dimension | A: one process, hot reload | **B: supervisor + core + module processes** | C: one process, worker threads |
|---|---|---|---|
| Restart one unit | Not real: ESM modules cannot be unloaded, so a "restart" re-imports next to the old instance and leaves its timers, listeners and native handles behind. | Real: a module restart is a process restart; the core keeps running. | Partial: a worker can be terminated, but native handles opened through the main thread's addons stay. |
| Fault isolation | None: a faulty add-on (throw in a timer, OOM, native crash) takes the engine down. | Per process: an add-on crash is a module crash; the supervisor restarts it with backoff. | JS heaps are isolated, but a native crash or process-level OOM kills every worker at once. |
| Secret isolation | None: add-ons share the heap that later holds provider keys. | OS process boundary; a module sees only what the RPC surface gives it. | Workers share the process address space with the secrets. |
| Updater / third-party add-ons | Replacing a unit means restarting everything. | Replacing a unit is stop, swap, start; first- and third-party modules have one shape. | Same restart caveat as A for native parts. |
| RAM | Lowest (one Node heap). | 30–50 MB baseline per Node process. | Low (one process, several isolates). |
| Complexity | Low at first, rising with every add-on. | Supervisor, lifelines and adoption are new code (spec §6.4). | Medium; worker messaging plus the native-crash gap. |

B's only structural cost is RAM per process. It is mitigated by starting modules lazily (none run in 2a) and, later, by a first-party "module host" that runs trusted small modules as workers *inside* one B process — a C-style optimisation layered on B, never replacing the process boundary for third-party code.

### 2. Languages and the single source of types (D7)

- **Rust** for the CLI, supervisor, installer and updater: a static binary with no runtime to install, fast cold start for `--help` (B1), and process/service handling (lifelines, Job Objects, `launchd`/`systemd`/Task Scheduler) without a Node dependency on the recovery path.
- **TypeScript** for the core and every module bound to a Node SDK: the engine is Node, and MCP/ACP/A2A SDKs are TypeScript (ADR-001, ADR-008).
- **JSON Schema 2020-12 is the single source.** `packages/rpc-schema/schema/rpc.schema.json` defines every method's `params`/`result`, every notification, the error enum, the envelopes and the capture-journal line. TypeScript types are generated by `json-schema-to-typescript` (`packages/rpc-schema/src/build.mjs` → `generated/types.ts`, `generated/names.json`); Rust types by `typify` 0.8 in `crates/plur1bus-rpc/build.rs` (into `OUT_DIR`, `$defs` rewritten to `definitions` for schemars 0.8). The TypeScript server validates params with ajv, and **also validates every result** before sending it (`rpc/server.ts`: a result that violates the schema is logged and answered with `E_INTERNAL reason=result-schema`). `packages/config-schema/schema/config.schema.json` plays the same role for configuration (ADR-013).
- **Contract fixtures** (`packages/rpc-schema/fixtures/`): one valid request/response pair per method, every error code once, every notification once; the TypeScript server tests and the Rust client tests (`crates/plur1bus-rpc`) read the same files.
- **Workspace package resolution** (rulings R12, R14): `rpc-schema`, `config-schema` and `module-api` export `{ "source": "./src/index.ts", "types": "./src/index.ts", "default": "./dist/index.js" }`; `scripts/test-package.mjs` runs Node with `--conditions=source`, so cross-package tests always run against source, never a stale `dist/`. Production resolution (`default`) is unchanged.
- **CLI `--json`** (ruling R13) prints the raw `serde_json::Value` returned by the RPC call, never a re-serialised typed struct: `typify` drops unknown keys on open result types and drops empty optionals, so a typed round trip would silently change the documented shape. Typed structs are used only to read fields. **R13 amended (2a-H2, ADR-016 §8):** every `--json` document now has exactly one key spliced on top of that raw value, `"schema": "<command>/<major>"` (dotted command path, e.g. `memory.list/1`, `memory.proposals.accept/1`; every failure document is `error/1`), inserted by a single `document()` helper (`crates/plur1bus/src/output.rs`) so `Out::ok`/`Out::fail` are the only call sites that touch the envelope. No RPC method result may declare a top-level `schema` property (enforced by a schema test) so the two can never collide; `config schema --json`'s value is `{ schema, tier, jsonSchema }` rather than splicing into the JSON Schema value itself, since a JSON Schema must not carry a foreign top-level key (ruling G15). `core run`'s ready line is the core process's own output, not a CLI document, and is exempt.

### 3. RPC transport and protocol

- **JSON-RPC 2.0, NDJSON**: one UTF-8 JSON value per line, at most 4 MiB per line (`MAX_LINE_BYTES` in `packages/module-api/src/framing.ts`, `MAX_LINE` in `crates/plur1bus-rpc/src/client.rs`, the Rust read is bounded to `MAX_LINE + 1` bytes). An over-long line is answered with `E_INVALID_PARAMS reason=line-too-long` and the connection is closed. One connection per client; notifications arrive on the same connection after `events.subscribe`.
- **Address**: POSIX `run/core.sock`; Windows `\\.\pipe\plur1bus-<first 16 hex of sha256(lower-cased home)>-core` (`packages/core/src/paths.ts` `coreAddress`; the Rust CLI derives the identical name, T11 ruling: `--home`/`PLUR1BUS_HOME` are absolutised and lexically normalised like Node's `path.resolve` on both sides).
- **Handshake `core.auth`**: the first request on every connection is `core.auth { token }`. Its result is `{ contract, rpc, instanceId, pid, capabilities? }`: the engine contract version (`1.6.0` at the pinned commit, `d32771c5`) and the RPC schema version (`x-rpc-version`, `1.1.0`, plan 2a-H2). Any other method before a successful `core.auth` is answered `E_UNAUTHORIZED reason=auth-required`; a wrong token or malformed `core.auth` params get an error and the connection is closed; a connection that has not authenticated within 30 s is closed (`authIdleMs`). `core.status` repeats `contract` and `rpc`. **2a-H2 (ADR-016 §3, ruling G2):** `capabilities` (`buildCapabilities`, `packages/rpc-schema/src/index.ts`) is now attached to the `core.auth` result — `{ methods, notifications, extensionPoints: {}, features }`, `methods`/`notifications` derived from the schema's own `x-stability`/`x-since`/`x-deprecated` annotations, never a hand-kept list; `features` is `CORE_FEATURES` (`packages/core/src/capabilities.ts`) sorted, currently `["events.harness", "memory.ops", "memory.proposals"]`. Both clients' `supports(method)` (`crates/plur1bus-rpc/src/client.rs`, `packages/module-api/src/client.ts`) answer `true` when `capabilities` is absent (an older core) and otherwise check `capabilities.methods` — this is how the CLI answers `E_NOT_AVAILABLE reason=core-lacks-method` against an old core instead of crashing (Review Focus 5). G2 also records that the supervisor handshake gets the same `Capabilities` `$def` only when the supervisor exists (2a-H3); H2 has no second handshake to extend.
- **Version check** is the client's job: both clients (`crates/plur1bus-rpc` `SUPPORTED_RPC_MAJOR = 1`, `packages/module-api/src/client.ts`) read `rpc` from the `core.auth` result, compare the major **before** deserialising the rest (a future major may have a shape this client cannot read), and refuse with `E_RPC_VERSION reason=major-mismatch`.
- **Closed error enum** (`$defs/ErrorCode`), now 15 codes: `E_UNAUTHORIZED`, `E_RPC_VERSION`, `E_NOT_AVAILABLE`, `E_CORE_UNAVAILABLE`, `E_INVALID_PARAMS`, `E_AGENT_UNKNOWN`, `E_CONFIG_INVALID`, `E_MODULE_UNKNOWN`, `E_INTERNAL`, `E_LOCKED`, and, added in 2a-H2 for the memory-op surface (ruling G7): **`E_NOT_FOUND`, `E_DENIED`, `E_APPROVAL_REQUIRED`, `E_CONFLICT`, `E_STORAGE`**. The code travels in `error.data.error` with optional `reason` and `detail`; the numeric JSON-RPC `code` is `-32602` for invalid params, `-32600` for an invalid request, `-32700` for a parse error, `-32601` for an unknown method (reported as `E_INTERNAL reason=method-not-found`) and `-32000` otherwise for every other code including the five new ones (`packages/core/src/rpc/errors.ts`). `RpcError` refuses to construct a code outside the enum, so no method can invent one without a schema change. `error.data` also gained an optional `ids: { [k]: string }` (2a-H2): the engine's non-secret `MemoryOpError.detail` map, copied onto the error only when it has at least one string-valued entry (`mapMemoryOpError`, `packages/core/src/memory-ops.ts`), and threaded through to `RpcError::ids()` (`crates/plur1bus-rpc/src/error.rs`) and the CLI's `--json` error document (`rpc_error_extra`, `crates/plur1bus/src/output.rs`) — this is how a half-failed shared-copy refresh's `sourceId`/`sharedId`/`staleSharedId` reach the person who has to finish it by hand (Review Focus 3).
- **RPC 1.2.0 adds a second server (2a-H3a, ruling S2).** The schema's single method/notification namespace now carries `x-server: "core" | "supervisor"` on every entry (`packages/rpc-schema/schema/rpc.schema.json`); `buildCapabilities(features, server)` (TS, `packages/rpc-schema/src/index.ts`) and `capabilities(server, features)` (Rust, `crates/plur1bus-rpc/src/capabilities.rs`) filter by it, so `core.auth`'s `capabilities` lists only core methods/notifications and the new `supervisor.auth`'s lists only the supervisor's. The supervisor serves `supervisor.auth` (token → `{rpc, instanceId, pid, capabilities}`, `SUPERVISOR_FEATURES = ["adoption", "lifelines"]`), `daemon.status` (`{supervisor: ProcessState, children: ChildStatus[]}`), `daemon.start` and `daemon.stop`; the core additionally serves **`core.adopt { nonce }`** (`x-server: "core"`, per S2 — the call a supervisor makes *on* the core, not `daemon.adopt` as the design spec's prose named it), which authenticates against `run/supervisor.token` (`timingSafeEqual`, case-insensitive hex) and, on success, makes the calling connection the core's lifeline (`packages/core/src/core.ts` `adopt()`, `orphan-watch.ts` `watchConnection`). `core.status`'s result became the shared, named `$defs/CoreStatus` (also returned by `core.adopt`), and gained three optional fields this plan adds: **`deprecationsUsed: string[]`** (ADR-016 §5, `RpcServer.deprecationsUsed()`, sorted, populated the first time a deprecated method or notification name is used, surfaced by `1staid check`'s `api.deprecations`); **`models: { embedder, reranker }`** (`$defs/ModelStatus`, Task 13, E4 contract 1.8.0 — see the warm-up deviation below); and **`sharedMemory: SharedMemoryStatus`** (Task 14, E4). A child's own shape, `$defs/ChildStatus`, is new: `{ role, process: ProcessState, instanceId, pid, adopted, restarts, lastExit, nextRestartAt }`, rendered by the Rust `ChildState::to_json()` (`crates/plur1bus/src/supervisor/state.rs`) and validated against the schema by both `crates/plur1bus`'s and `packages/rpc-schema`'s test suites. Both clients' `supports(method)` now check membership against the handshake's own `x-server`-filtered `capabilities.methods`, so a CLI command against an old or capability-less peer answers `E_NOT_AVAILABLE` for that one method (ADR-016 §3 restated for the second server).
- **Memory ops are served, not stubbed (2a-H2).** The paragraph this replaces described `memory.list|show|forget|correct|share|state` answering `E_NOT_AVAILABLE reason=engine-pr-E1` until engine PR E1 landed; that PR is in at the pinned commit, and `packages/core/src/memory-ops.ts`'s `buildMemoryOpMethods` now serves all ten MemoryOps methods (the original six plus `memory.propose`, `memory.proposals.list|accept|reject`, D31) from `Engine.memory`, spread into the RPC method table in place of the old stub. Every handler runs the same `op()` wrapper in order: refuse if the core `isStopping()` (`E_CORE_UNAVAILABLE reason=core-stopping`); `requireAgent` (`E_AGENT_UNKNOWN reason=not-registered`, moved here from `rpc/methods.ts` so the two modules don't import each other); derive the principal with `callerToPrincipal` and, on a degraded identity, refuse writes with `E_DENIED reason=principal-invalid` before the engine is called while reads proceed and carry `degraded` (ruling G8, extending the recall-only rule of R18 in §4 to the whole memory-op surface); for `memory.list`, refuse `topic` and `since` both present or both absent, or `until` without `since`, with `E_INVALID_PARAMS reason=topic-xor-since` (ruling G9) before the engine is called; call the engine under `AGENT_CONTEXT_CLI`; project the result onto exactly the schema's keys (`projectCard`/`projectProposal`), copying optional `score`/`sharedBy`/`sourceId` only when the engine sets them so a foreign `sharedBy` such as `"Anna.Main"` still validates (Review Focus 1); on a throw, `mapMemoryOpError` runs the G7 table (recognising a `MemoryOpError` by `name` and a known `code`, never by importing an engine internal) and, if it returns null, the error is rethrown as `E_INTERNAL handler-threw`. Accepting a proposal is worth naming here too: the engine refreshes the recipient's shared copy under a **new id** (the accept result's `id`, which also becomes the proposal's `resultId`), so a copy id taken before an accept is stale afterward — confirmed end to end by the 2a-H2 system test (`tests/system/memory-ops.test.ts`).
- **Back-pressure**: if a connection's pending writes exceed 16 MiB (`MAX_PENDING_BYTES`), the core logs a warning and destroys that connection — a stalled local client cannot exhaust the core's memory (T6 ruling).
- **Client timeouts** (`crates/plur1bus-rpc/src/client.rs`): socket connect and the whole `core.auth` handshake run under `connect_timeout` (300 ms); later calls under `call_timeout` (an idle read timeout; default 30 s, set per command by the CLI, e.g. `core.recall.hardBudgetMs` + 400 ms for `memory recall`). After a timeout, an I/O error, an over-long line or EOF the client marks itself **poisoned** and refuses further calls until reconnected, because the stream position is unknown. A missing socket fails at once (ENOENT), which is how the CLI answers "core absent" in well under 300 ms.
- **Shutdown drains memory ops before closing sockets (2a-H2, ruling G17).** `stop()`'s order is now: set state `stopping` → abort the shutdown signal → `engine.close({ budgetMs })` → `RpcServer.drain({ methods: MEMORY_OP_METHODS, budgetMs })`, which tracks every in-flight dispatch of a listed method and resolves once each has written its reply or the remaining budget runs out → `server.close({ graceMs: 1000 })`, which stops accepting, `end()`s every connection (never `destroy()` right after a `write()` — the PR #2 Windows rule) and arms an unref'd `destroy()` timer for the grace period → lock release → run files (`packages/core/src/core.ts`, `packages/core/src/rpc/server.ts`). A memory op already dispatched when `stop()` begins gets its result; one sent after `isStopping()` flips answers `E_CORE_UNAVAILABLE reason=core-stopping` at once.

**Notifications (2a-H2 replaces the H1 verbatim-forward model, ADR-016 §6).** `$defs/notifications` is now harness-owned: `core.state { process }` (unchanged), `agent.activity { agentId, activity }` (unchanged), and nine new schemas the core maps engine events onto (`packages/core/src/events-map.ts` `mapEngineEvent`) — `recall.completed`, `recall.degraded`, `recall.block-clipped`, `recall.block-dropped`, `job.run`, `memory.proposal`, plus the not-yet-emitted-by-the-engine `dream.completed`, `acl.denied`, `embedding.identity.changed` (ruling G11: minimal, experimental schemas, mapped when the engine starts emitting them, no invented payload fields). `mapEngineEvent` returns `null` — logged at debug and never sent — for an unknown name, a non-object payload, a missing or wrongly typed required field, or an `agentId`/`sharerAgentId`/`sharedBy` combination the schema rejects; `memory.proposal` sets `agentId` to the sharer and an `audience: [sharerAgentId, proposerAgentId]` so both sides of a proposal see it under an `events.subscribe { agentId }` filter (ruling G12). The old verbatim `engine.event { name, agentId?, payload }` notification still exists, unchanged in shape, but is now `deprecated` (`x-deprecated { since: "1.1.0", removeAfter: "2027-03-26", replacement: "harness event notifications: recall.completed, recall.degraded, recall.block-clipped, recall.block-dropped, job.run, memory.proposal (ADR-016 §6)" }`) and delivered **only** to a subscription that names it explicitly in `events.subscribe { names }` (ruling G13 — opt-in, so a no-filter subscriber gets the mapped notifications and never the raw engine payload); subscribing to it, or calling any deprecated method, logs one warning per process. `events.subscribe { names?, agentId? }` still filters by notification method name and, for an audience-bearing notification, by membership in the audience instead of the `params.agentId` match; one delivery per connection.

### 4. Authentication and transport security

- **Token**: 32 random bytes (`crypto.randomBytes(32)`), hex-encoded (64 characters; the schema enforces the length on `core.auth`), generated fresh at every core start and written to `run/core.token` with mode `0600`. The core compares it with `crypto.timingSafeEqual` after an equal-length check (`rpc/server.ts` `tokenMatches`). Socket permissions plus the token make the caller `trust: "proved"`.
- **POSIX**: `run/` is created `0700` and re-`chmod`ed `0700` at listen; the socket is `chmod 0600` after `listen`. An existing socket file is probed first: if something answers, the core refuses (`address in use`); only a dead (stale) socket is unlinked.
- **Windows, as built in 2a-H3a (Task 10; ruling S11).** The **supervisor's** pipe is created in Rust (`crates/plur1bus/src/supervisor/pipe_windows.rs`) with an explicit security descriptor `D:P(A;;GA;;;<user SID>)(A;;GA;;;SY)` (`crates/plur1bus-rpc/src/win.rs` `SecurityDescriptor::from_sddl`), `FILE_FLAG_FIRST_PIPE_INSTANCE` on the first instance, and every instance overlapped; closing a connection runs `CancelIoEx` before `DisconnectNamedPipe`, and `daemon.stop`'s drain (`FlushFileBuffers`) is bounded at 2 s before it cancels. The **core's** Node-created pipe deliberately keeps Node's default DACL (full control for SYSTEM/Administrators/creator-owner, read-only for Everyone/Anonymous) — deviation C2 below — mitigated two ways: (1) `securePath` (`packages/core/src/platform.ts` `createPlatformCapabilities`) now runs `icacls <p> /inheritance:r /grant:r *<SID>:(F) *S-1-5-18:(F)` (directories get `(OI)(CI)(F)` so files created later inherit it, ruling H3-R15) on `run/`, `run/core.token` and `run/core.pid`, returning `mechanism: "acl"` (the engine contract's closed union has no `"icacls"` value) or `{ applied: false, reason: "acl-tool-unavailable" }` on failure; (2) every RPC client (Rust and, via the supervisor's own connect calls, the health/adoption code) refuses a pipe whose `GetNamedPipeServerProcessId()` differs from the `run/{core,supervisor}.pid` it expects, before the token is even sent (`Client::handshake`'s `check_server_pid`, `E_UNAUTHORIZED reason="pipe-server-mismatch"`; client opens also carry `SECURITY_IDENTIFICATION` so a squatting pipe cannot impersonate the real server first). `1staid check`'s `windows.pipe-acl` row runs the same DACL walk (`win::pipe_dacl_report`/`writable_by_others`) read-only, and `crates/plur1bus-rpc/src/acl.rs` (`writable_by_others`, `run_writable_by_others`) implements the platform-neutral decision logic, unit-tested on every OS. Reads on every Windows `Client`/pipe now carry a real deadline via overlapped I/O (`win::overlapped_op`, `OverlappedPipe`) instead of the H1/2a-H2 "no deadline yet" gap. **Still true from H1/2a-H2:** the supervisor's own writes to a client have no deadline (`INFINITE`; documented limit, unchanged by this plan). **Not verified in this plan** (no Windows runner in the implementer's environment; verified only by `windows-2025` CI once the branch runs there): the exact interaction of `GetSecurityInfo` on a read-only pipe client handle, `FlushFileBuffers` cancellation on an overlapped pipe, and whether Task Scheduler's `RestartOnFailure` restarts a non-zero *exit code* or only a launch failure (§10 below).
- **Principal on the CLI path**: the CLI sends only `CallerIdentity { channel: "cli", accountId: <hostname>, userId: <OS user> }` (`crates/plur1bus/src/identity.rs`); every params object is closed (`additionalProperties: false`), so a client cannot supply `trust`, `origin`, `background` or `incognito`. The core derives the engine `Principal` (`packages/core/src/principal.ts`): `user:v1:sha256(JSON.stringify([channel, accountId, userId]))`, `workspace-dir:v1:<realpath of agents/<id>/workspace>`, `trust: "proved"`, `AgentContext { origin: "user", background: false }`, and `incognito: false` set explicitly on captures. **Identity degrade (ruling R18):** an identity that is empty, longer than 128 characters or contains control characters does not fail the call; the core uses `trust: "inferred"` without a user principal (agent-private memory) and reports `degraded { reason: "principal-invalid", capability: "identity" }` on recall. The schema therefore carries no `maxLength` on `accountId`/`userId`; the 128 limit (the engine's `INPUT_LIMITS`) lives in the core only.

### 5. The core lock: `node:sqlite` `BEGIN EXCLUSIVE`, not `flock`

The core holds `state/core.lock` for its lifetime (`packages/core/src/lock.ts`). The file is a SQLite database: the core opens it with `node:sqlite` (`DatabaseSync`), sets `PRAGMA busy_timeout=0; PRAGMA locking_mode=EXCLUSIVE`, runs `BEGIN EXCLUSIVE`, and records `{ pid, instance, at }` in a `holder` table inside the open transaction. An open EXCLUSIVE transaction is an `fcntl` (POSIX) / `LockFileEx` (Windows) lock held by the kernel for the process: a second core's `BEGIN EXCLUSIVE` fails immediately (busy timeout 0) and becomes `E_LOCKED reason=core-lock-held`; when the holder dies — including `SIGKILL` — the OS releases the lock. `release()` rolls back and closes. Verified: Node 24.21 during the plan's H1 pre-check, and permanently by `packages/core/test/lock.test.ts` ("refuses a second holder in another process and frees on SIGKILL") and `core.test.ts` (a second `createCore().start()` on the same home rejects with `E_LOCKED`).

Why not `flock`, as the spec says: Node has no `flock` API; the options were a native addon (a new prebuild matrix on five targets for one system call) or shelling out to a helper whose lifetime is not the core's. `node:sqlite` ships inside Node ≥ 24, already on the harness's dependency floor, and gives the same property — the lock dies with the process, "two cores on one LanceDB" is excluded by the OS, not by discipline.

**`E_LOCKED` (H1 addition to the spec's error enum).** The spec's closed enum had no code for "another core already holds this installation". Reusing `E_CORE_UNAVAILABLE` would have said the opposite of the truth (a core *is* running), and `E_INTERNAL` would have hidden an expected, user-actionable state. `E_LOCKED` is added to `$defs/ErrorCode`; the core process exits with code 3 when it is refused (`packages/core/src/bin.ts`), and the CLI maps `E_LOCKED` to exit code 3 too (`crates/plur1bus/src/output.rs`). A refused core never touches the running core's `run/core.token` or `run/core.pid`.

**Engine contract major is enforced, not just read (2a-H2).** `SUPPORTED_CONTRACT_MAJOR = 1` and `assertEngineContract` (`packages/core/src/engine.ts`) run immediately after the engine binds, inside `core.ts`'s start `try` block, so an unsupported major goes through the same start-failure cleanup as any other start error. A contract whose major isn't 1, or whose string doesn't parse as semver, throws `E_RPC_VERSION reason=engine-contract-major`; `bin.ts` maps that to process exit code **4** (ruling G20) — a fourth, distinct exit code alongside `E_LOCKED`'s 3, because "the engine moved to a contract this core cannot speak" is a different, non-retryable condition from "another core holds the lock".

### 6. Why `contract`/`rpc` travel in `core.auth`, not in every response envelope

The spec (§6.2) says every response envelope carries `contract` and `rpc`. JSON-RPC 2.0 defines the response object's members exactly (`jsonrpc`, `result` or `error`, `id`); strict clients reject extra members, and the harness's own `$defs/Response` is closed (`additionalProperties: false`) so that the schema stays a faithful JSON-RPC 2.0 description. Putting the versions inside every `result` would pollute every method's result type. The purpose — a client learns both versions before it relies on any shape and refuses an unknown major — is met by the mandatory first call: `core.auth` returns `contract` and `rpc`, `core.status` repeats them, and a connection cannot issue any other call before `core.auth`.

### 7. Captures under core loss (the journal)

When the core cannot be reached, `memory add` does not fail: the CLI appends a `JournalLine` (schema `$defs/JournalLine`: `v`, `id`, `at`, `agentId`, `sessionKey`, `caller`, `messages` — the caller identity, not a principal; the core derives the principal at replay exactly as for a live call) to `state/journal/<agentId>.jsonl` and reports `degraded { reason: "core-unavailable", capability: "capture" }` with `journaled: true`; `memory recall` answers `degraded { reason: "core-unavailable", capability: "recall" }` with exit code 0 — missing memory is a visible state, not a command failure. The core replays the journal at start, before it opens the socket:

- **Ruling R20**: a line leaves the journal only if its capture resolved without a `reason` and `stored + skipped > 0`; any reason, zero counts or a rejected `done` keeps it (logged, retried next start, counted as `journalBacklog` in `core.status`). Replay first renames `<agent>.jsonl` to `<agent>.jsonl.replaying-<pid>`, so a concurrent CLI append lands in a fresh file; kept lines are appended back, each with its own newline, so a later append can never glue onto a kept torn tail; leftover `*.replaying-*` files from a crashed replay are processed first; each file is processed in isolation (a failed rename skips that file for this start). Criterion: "no journal line lost". Cost: a poison line is retried every start until fixed by hand, and a crash between append-back and delete gives at-least-once reprocessing, which the engine's capture dedup absorbs.
- **Ruling R19** (capture semantics): a capture's abort signal is the core's own shutdown signal only — never the client connection and never the `waitMs` timer. `memory.capture` with `wait: true` races `done` against `waitMs` (default 60 s, `core.capture.waitMs`) and answers `{ id, acceptedAt, pending: true }` if the timer wins; the capture keeps running. A client disconnect never aborts a capture. Cost: a capture can outlive its request until core shutdown.

### 10. Supervision (2a-H3a)

This section records how the supervisor built in 2a-H3a resolves the spec §6.4 gaps the plan's rulings S3–S9, S14 and S17 were written against, plus the durability bugs the plan's kill soak found and the model warm-up it shipped.

#### 10.1 Identity, the token, and lifelines (S3, S4)

`run/supervisor.token` is both "the nonce a fresh start writes" (spec) and the supervisor's own RPC bearer token: 32 random bytes as lower-case hex, written fresh at every `supervise` start with mode `0600` (`crates/plur1bus/src/supervisor/mod.rs`, `fresh_token`, `getrandom` 0.3). A spawned child's lifeline is its **stdin pipe**, held open by the supervisor's `Monitor` (`supervisor::child::Monitor`, `Lifeline::Stdin`); an adopted child's lifeline is **the authenticated connection `core.adopt` succeeded on** (`Lifeline::Connection`). Losing either — stdin EOF/error, or that connection closing — orphans the core (`packages/core/src/orphan-watch.ts` on the core side); a later successful `core.adopt` replaces the previous source (`orphan-watch.ts` `watchConnection`).

#### 10.2 Health, hangs and termination (S6, S8)

The health thread polls `core.status` every `healthIntervalMs × scale` with a 2 s deadline; three consecutive failures mark the child `degraded("unresponsive")`, and one success restores whatever state the core itself reports (`process.state`). "Hung" is defined as no successful poll for `max(30 s, 3 × healthInterval) × scale` of monotonic time (`Instant`, never wall time) — the `3 ×` floor is a 2a-H3a addition beyond the spec's bare "30 s", because a literal 30 s would make every healthy core between polls look hung whenever `healthIntervalMs` is configured above 10 s. A hung child is escalated: `core.shutdown` on a fresh connection (any OS), `SIGTERM` after 2 s × scale (unix only), `SIGKILL`/`TerminateProcess` after 10 s × scale more (`supervisor::child::Monitor`'s waiter thread). The supervisor never signals a PID it has not confirmed is the actual peer at that moment: on unix this is `SO_PEERCRED`/`LOCAL_PEERPID` (`plur1bus-rpc::transport::Stream::peer_pid`) checked via a fresh connect immediately before each signal (macOS and other unix, per-signal re-check), or pinned once through a `pidfd` opened at probe time (Linux, `crates/plur1bus/src/supervisor/adopt.rs` `Peer::open`, no re-check needed — a pidfd cannot be reused for a different process); on Windows it is a process handle opened with `OpenProcess` while the pid was known to be the pipe's server (`Peer`, `TerminateProcess`), with "cannot tell" (treated as alive) when `OpenProcess` itself fails. `run/core.pid` is `<pid> <instanceId>\n`; a mismatch on either field marks a found process `Foreign`, never signalled by the socket-server pid alone.

#### 10.3 Exit classification, crash reasons and backoff (S9, ruling H3-R3)

`crates/plur1bus/src/supervisor/state.rs`'s `CrashReason` enum is the vocabulary the whole plan uses for "why did the core stop", both in `daemon.status`'s `lastExit.reason` and in `1staid check`'s `core.state`/`supervisor.state`: **`lock-held`**, **`config-invalid`**, **`engine-contract`**, **`ready-timeout`**, **`adopted-exit`**, and **`none`** (a clean, requested stop). `classify_exit(code, signal, requested)` maps: a requested stop always wins → `stopped` with reason `none`; otherwise exit 2 → fatal `config-invalid` (an invalid `config.json`, never retried without `daemon start`); exit 4 → fatal `engine-contract` (the pinned engine's contract major, or since Task 13 minor, is unsupported by this core — S18 below — never retried without `daemon start`); exit 3 (`E_LOCKED`) → retryable `lock-held`; anything else (including a bare signal) → retryable with no specific reason, except that the supervisor itself assigns `ready-timeout` when its own readiness wait (60 s × scale, with a 10 s floor below scale 1 — see the next paragraph) is what killed the child, and `adopted-exit` when an *adopted* core (one the supervisor did not spawn) goes away on its own with no lifeline loss recorded as the cause.

**Ready-timeout floors (2a-H3b-b fix, 2026-09-28).** `supervisor::child::ready_timeout(kind, scale, core_floor)` is 60 s × scale, but never below `MODULE_READY_FLOOR` (10 s) for a module and `CORE_READY_FLOOR` (10 s) for the core. At scale 1 (production; the scale is a test seam) the timeout is 60 s and neither floor ever applies. At the tests' scale 0.02 the bare value was 1.2 s, too little for a Node core to secure `run/` and start on a loaded Windows runner: the core was killed as `ready-timeout` and respawned, and tests asserting `restarts == 0`, one `started` event or an unchanged core pid failed on a different test each run. A test of the core's ready timeout itself (a core that never listens) drops the core floor with the test seam `PLUR1BUS_SUPERVISOR_NO_CORE_READY_FLOOR=1` (honoured only with `PLUR1BUS_ALLOW_TEST_INTERNALS=1`), so it still sees 60 s × scale. `config.set`'s restart wait uses the same floored value.

`Backoff` (`state.rs`) is the exit → next-restart-delay/give-up policy: delays double 1, 2, 4, 8, 16, 32, 60, 60… seconds (× scale), reset to 1 s once the child has been `ready` for a full `600 s × scale` window with no new exit. **Ruling H3-R13** (a fix-round finding, not the plan's original text): a `lock-held` exit backs off exactly like any other exit **but never counts toward the 5-exits-in-10-minutes give-up rule** (`Backoff::on_lock_held_exit`, distinct from `on_exit`). Without this, a core that is simply slow to listen (still holding `state/core.lock` from a prior generation, or racing a hand-started `core run`) would exhaust the sticky give-up budget — reached in about 1 s at scale 0.02 — before the supervisor's next start-up probe (`probe_and_adopt`) ever got a chance to find it `Serving` and adopt it instead of respawning. The cost accepted: a lock holder that never listens and never dies causes one spawn (which exits 3) at most every 60 s × scale, forever, each logged — cheaper than a supervisor that gives up on a core still coming up. A real crash still gives up permanently after 5 exits within the window (sticky, cleared only by `daemon start`'s `Backoff::reset()`), pinned by `crates/plur1bus/tests/system/kill-soak.test.ts`'s `S16` subtest and `state.rs`'s property tests.

#### 10.4 A missing `core.js` keeps the supervisor up (ruling H3-R11)

Spec §6.4 does not say what happens if the thing the supervisor is told to spawn does not exist (for example, before `setup`/2a-H3b-4 has installed a runtime). The first cut of Task 6 had the supervisor exit 1 in that case; the fix round reversed this, because under a service manager with `Restart=on-failure` that just loops the exit every second, which is worse than the alternative: `run_inner` builds the `Monitor` lazily (`supervisor::child::mark_unspawnable`), and a missing `core.js` shows the child as `Crashed { reason: "config-invalid" }` with `restart_at` cleared and `nextRestartAt`/`pid` both `null` — visible and quiet, not retried, until a `daemon start` (which re-runs `core_spec` and spawns as soon as the file exists) or the file simply appears and the next `daemon start`/restart finds it.

#### 10.5 Run files: `run/supervisor.lock`, stale files, and `*.tmp` (ruling H3-R9)

Beyond the spec's "probe the address, then write the token, then bind" sequence, 2a-H3a added an exclusive `run/supervisor.lock` (`std::fs::File::try_lock`, no new dependency) taken *before* the address probe, closing a real race: two processes starting at once can both find a dead address and each proceed to overwrite the other's fresh token or unlink the other's fresh socket. The loser of the lock probes the winner (up to 3 s) for its pid, prints `supervisor already running (pid N)` to stderr, and exits 3 (Review Focus 1, `a_second_supervisor_on_the_same_home_exits_3`). **The lock file is never removed** — removing it would reopen the same race on the next start — so `1staid check`'s `run.stale-files` row must treat `run/supervisor.lock` as expected, not stale, and never reports it. The same expectation extends to any `*.tmp` file a rename-based atomic write leaves behind after a crash mid-write (config, tokens); `1staid check` does not flag those either. What `run.stale-files` *does* flag: `core.pid`/`supervisor.pid` present but naming a dead pid, and `core.sock`/`supervisor.sock` present but nothing answering — both expected after a power loss, both cleared automatically by the next `supervise` start (a stale socket file is unlinked once probing confirms nothing is listening on it), and both reported `warn` before that start and `ok` after (Review Focus 3).

#### 10.6 Stop: a hard deadline, and the OS service unit values (S16 hand-off, Task 8)

`daemon.stop { budgetMs? }` (default 10 s, range 0–120 000 ms, S16's soak uses this to bound outages) is a **hard deadline** from the moment the stop request is accepted, not a sequence of independent waits: `Monitor::stop` computes `deadline = now + budget + stop_grace` once, and every subsequent wait (for `core.shutdown` delivery, for the process to exit, for a post-kill reap) is clamped to what remains of that deadline, not to its own fixed timeout — this is what makes `daemon.stop`'s advertised budget an upper bound on wall time rather than an aspiration (`crates/plur1bus/tests/supervisor_children.rs` `daemon_stop_is_bounded_by_the_budget_for_a_hung_core`). This deadline is why the OS service units' own stop-timeout values are set well above the RPC-level maximum: `TimeoutStopSec` (systemd) and `ExitTimeOut` (launchd) are **150 s** — the 120 s maximum `daemon.stop budgetMs` plus a further hard-stop grace plus a 25 s margin — so the OS never forcibly kills the supervisor mid-graceful-stop while it is still legitimately draining a child within a budget the RPC caller itself chose. Task Scheduler has no equivalent graceful-stop setting; its `/End` terminates directly, which is why `service uninstall` on Windows now calls `daemon.stop` first and falls back to `/End` only if that does not answer (Task 10).

#### 10.7 Deviations accepted for this plan (beyond the table below)

- **No `PR_SET_PDEATHSIG` / Job Object `KILL_ON_JOB_CLOSE` (ruling S5, controller ruling C1).** The spec names both as backstops that kill an orphaned child when the supervisor dies. Both were rejected outright: they contradict D11 and acceptance criterion 3 ("the core survives a supervisor crash and is adopted by the next one") by definition — a backstop that kills the child on supervisor death makes adoption impossible. The core's own grace timer (`supervisor.graceMs`) is the backstop for an orphan whose new supervisor never arrives in time; a hung orphan (accepts a connection but never answers) is caught by the *next* supervisor's start-up probe, which terminates it before adopting or spawning fresh (§10.2). Recorded as a permanent ADR-012 deviation, not merely deferred.
- **`KillMode=process` (systemd) / `AbandonProcessGroup=true` (launchd), Task 8's own addition beyond the plan's literal service-unit values, for the same D11/C1 reason:** the default `KillMode=control-group` (systemd) would have systemd kill the core *together with* a crashed or stopped supervisor, since both share a process group by default — again making adoption impossible. `RestartPreventExitStatus=2 3` (systemd) stops the OS from looping a restart on a usage error (2) or "another supervisor already owns this home" (3, the single-instance-lock refusal of §10.5) — those are not transient failures a restart would fix.
- **launchd has no "don't restart on this exit status" equivalent to systemd's `RestartPreventExitStatus` — closed for the non-transient cases by 2a-H3b-a (B16), a genuine gap left for the rest.** `KeepAlive = { SuccessfulExit = false }` restarts on *any* non-zero exit; before this plan that included exit 2 (a usage error) and exit 3 (lost the single-instance race), looping every `ThrottleInterval = 5` seconds indefinitely. `crates/plur1bus/src/supervisor/mod.rs`'s `exit_code(code, manager)` now remaps 2 and 3 to 0 **only** when the process environment carries `PLUR1BUS_SERVICE_MANAGER=launchd` (`service/launchd.rs`'s rendered plist always writes that variable first in `EnvironmentVariables`, ahead of any caller-supplied entry) — so launchd's own `KeepAlive` sees a clean exit and does not restart the supervisor, while `fail()` still writes `exiting 0 instead of <code> so launchd does not restart a non-transient failure` to stderr and `logs/supervisor.log` before it does, and every other `(code, manager)` pair (systemd, no manager, or launchd with any other exit code, including 1 and 70) passes through unchanged — clap's own exit 2 for a CLI usage error is untouched, since it happens before `supervisor::run` is ever called. The gap this leaves, unchanged from before: **a real launchd misconfiguration now exits 0 silently**, visible only in `supervisor.stderr`/`logs/supervisor.log`, never in `launchctl print`'s own exit-status field — detecting *that* (as opposed to merely not looping on it) is explicitly left to 2a-H3b-b's `1staid repair` (a launchd-restart-loop check is named in that plan's outline), not solved here.
- **Windows Task Scheduler's `RestartOnFailure` semantics are still unverified** for a process that exits with a non-zero *code* versus one that simply fails to *launch* — sources disagree, and no implementer of this plan or 2a-H3a had a Windows runner. The CI system job (`windows-2025`, gated `service_real::the_os_restarts_a_killed_supervisor`) is the empirical answer; **as of this 2a-H3b-a record, it had still not been observed to run** (no CI access from this plan's implementer environment either — this record could not fetch or quote a `windows-2025` run). If it turns out `RestartOnFailure` only covers launch failures, a future plan needs either a wrapper task or a second, repetition-based trigger; nothing in 2a-H3b-a depends on the answer, since `exit_code`'s remap above is launchd-only and schtasks carries no equivalent mapping.
- **A Windows console window can flash briefly at Task Scheduler logon** even with `release_own_console()`'s `FreeConsole()` call (Task 10, checkpoint 5c) — that call only closes a console the supervisor does not share with an interactive shell; it cannot prevent one being briefly created at process start. Not fixable from user-mode without hiding the whole process, which is out of scope.
- **A `%` in the binary path or `--home` is refused outright for Task Scheduler** (`ServiceError::PathHasPercent`, reason `path-percent`) rather than escaped: Task Scheduler expands `%VAR%` in both the command and its arguments with no literal-percent escape, so a path containing one cannot be represented safely.
- **`PLUR1BUS_NODE` must name `node.exe`/`node` directly, never a shell shim (`.cmd`, a wrapper script).** With a shim, the OS-reported child pid is the shim's, not the eventual `node.exe`'s; the supervisor's identity checks (§10.2: hello `pid` must equal both the socket-server pid and, for a spawned child, the OS process handle it holds) then never match, and the child never becomes `ready`. This is a documented operational constraint, not a bug to fix — the same requirement already existed for `core run` before 2a-H3a, and the Windows pipe-server-pid check (§4) now catches the mismatch even earlier, before the token is sent.
- **The supervisor's own writes to a connected client have no deadline** (`INFINITE` on Windows, unbounded on unix) — a client that stops reading its socket/pipe can hold one server-side connection thread open indefinitely. This predates 2a-H3a (present since the H1 RPC server) and is recorded here as a known limit still not addressed, tracked for a future plan if it becomes a real problem (the supervisor's own connections are all short-lived RPC calls in practice).

#### 10.8 Two data-loss bugs the kill soak (criterion 2, Task 12) found and fixed

1. **A dead supervisor's stdio pipes crashed the core's own graceful stop (EPIPE).** An orphaned core's grace-expiry stop path logs through `console.error`, which after a `SIGKILL`ed supervisor writes to a now-reader-less pipe and throws `EPIPE`; the resulting unhandled `error` event on the stream crashed the process mid-stop, leaving `run/core.sock`, `core.pid` and `core.token` behind with no "core stopped" line ever written. Fixed in `packages/core/src/bin.ts`: every stdio stream's `error` event is now swallowed (`stream.on("error", () => {})`) for both `stdout` and `stderr`, on the reasoning that losing a log sink must never be allowed to abort a shutdown — the core's own log file remains the record of what happened.
2. **A capture the core's own stop aborted was answered as if it had succeeded, and the fact was silently lost.** `memory.capture` accepted just before the core began stopping was cancelled by the stop's abort signal, but the engine's own "not captured" outcome (`{ stored: 0, skipped: 1, reason: "not_captured" }`, or `{ stored: 0, skipped: 0 }`) was returned to the caller as a normal (non-error) result — so the CLI printed it as a plain, non-degraded reply and never journaled it (the journal fallback only triggers on an RPC *error*). Fixed in `packages/core/src/rpc/methods.ts`: `memory.capture` now throws `E_CORE_UNAVAILABLE reason=core-stopping` in every case where the stop's abort touched the call before anything was actually stored — arriving after `isStopping()` is already true, aborted before `stored > 0`, or a post-abort rejection — and the CLI (`crates/plur1bus/src/commands/memory.rs`) journals that error exactly as it already journals an unreachable core. **Ruling H3-R21** extends the same refusal to `memory.recall` on a stopping core (previously it could answer `degraded { reason: "engine-closed" }`, a shape a caller could mistake for a normal, if degraded, answer): a stopping core now refuses both memory ops the same way, `core-stopping`, so "the core is going away" is never confused with "the core answered, just imperfectly."

#### 10.10 Model warm-up, its measured numbers, and where it lives (spec §6.3, ruling C4)

The core now calls `engine.models.warm({ signal })` once, right after it becomes ready (`packages/core/src/warmup.ts` `startWarmup`), in the background — `process` stays `ready` throughout (ruling S7/C4: the design spec's own `core.status.degraded = { reason: "models-warming" }` does not exist as a top-level field; the model-derived degraded state lives at `core.status.engine.degraded`, distinct from process health, exactly as ADR-012 §3 already separated "is the socket serving" from "is the engine's own state fully healthy"). `engine.ready` is `true` only once `engine.degraded` is `null`; `engine.models` (`$defs/ModelStatus`, §3 above) reports the embedder's and reranker's own `state`/`warming`/`checkedAt`/`error` independently, so a client can show partial readiness rather than a single boolean. `1staid check`'s `models.warm` row (inserted right after `core.state`, ruling H3-R5's fixed check-id ordering) is `ok` when nothing is degraded, `warn` (with `detail.capability`) while `models-warming`, and `fail` (with `detail = { capability, error }` and a hint pointing at `logs/core.log`) on `model-failed`.

Measured numbers (Task 13, this 2-core sandbox unless noted):
- **B8 (core ready, flat embedder, no real models):** ~563–599 ms from `core run`/`supervise` start to the socket serving; the flat-embedder path never has a model to warm, so "models warm" reports 75–77 ms after ready (there is nothing real to wait for).
- **B11 (`core.status` p95, the health-poll-cost bound):** 0.32 ms, well inside the 5 ms budget.
- **Reference hardware vs. CI (ruling H3-R26):** the 400 ms (`timing.totalMs`) and 600 ms (CLI wall time) recall targets are the baseline on reference hardware, where `tests/system/two-session-recall.test.ts` asserts them (`PLUR1BUS_CI_RECALL_HARD_MS` unset; AGENTS.md shows the command). Shared CI runners are not reference hardware: the nightly sets `PLUR1BUS_CI_RECALL_HARD_MS=2000`, which raises the test home's `core.recall.hardBudgetMs` and turns the targets into diagnostics and `::warning::` lines, while both measured recalls must still answer `degraded: null`. The macOS shared runner on 4eeddb4 is why: first recall wall 988 ms, `timing.totalMs` 574, models warm 12.6 s after ready — over target on runner speed alone, while ubuntu passed the strict targets.
- **Real-model nightly** (`nightly.yml`, real embedder + reranker): models warm **4.5–4.9 s** after the core reports ready; the **first real recall** answered in **292 ms (ubuntu)** / **314 ms (macOS)**, both inside the 400 ms soft budget and both with `exceededBudget: false`. The nightly run on this plan's branch was nonetheless red, on a `degraded { capability: "recall", reason: "aborted" }` flag the first recall carried despite its reported latency being within budget.

**Root cause and fix (rulings H3-R22–H3-R24).** `timing.totalMs` (the number checked against the 400 ms/600 ms budgets) times only the recall's own measured phases; it excludes real, un-timed work that precedes them — the scheduler's queueing wait, the engine's "neo prelude" (which runs its own `embedQuery`), and the first LanceDB table open. On the very first recall against real models, that untimed prefix was long enough that the core's *wall-clock* 600 ms hard abort fired before the timed phases even started, so the recall came back `degraded { reason: "aborted" }` while `timing.totalMs` still read a small, in-budget number — the two clocks disagreed about when the recall "started." `startWarmup` (§ above) only warmed the models themselves (`engine.models.warm()`), never the recall *path* itself, so this cold-start cost was paid in full by whichever real recall happened to run first, including the one the nightly measures.

The fix, built in this plan (`packages/core/src/warmup.ts`, `core.ts`) rather than deferred: once `models.warm()` reports the embedder ready, the core runs one **side-effect-free recall-path warm-up pass per registered agent**, as the CLI principal, before it lets `engine.ready` go true — `engine.degraded` stays `{ capability: "recall", reason: "models-warming" }` for that whole pass (ruling **H3-R22**). The pass deliberately does **not** call `engine.recall` itself: a user-origin recall has side effects (it presents due reminders and nudges, and records activity/mood/neo/dream-echo state to disk), and warming must never touch any of that. Instead (ruling **H3-R23**, a same-day correction to H3-R22's first cut) it runs, per agent, one `engine.memory.list({ topic, limit: 1 })` (exercises query embedding, the table open and a vector search — the same cold-path costs a real recall would pay) plus **one** `engine.embedding.rerank` call for the whole pass when the reranker is enabled (not one per agent — a remote reranker bills per call) — read-only, no `recall.*` events forwarded, and pinned by a test that snapshots the whole home directory except `logs/`, `run/` and `state/lancedb` to prove the warm-up left every agent's on-disk state untouched. `tests/system/two-session-recall.test.ts` now asserts the **CLI's own wall-clock time** for the first measured real recall is under 600 ms, printed next to `timing.totalMs`, specifically to catch the gap between the two clocks that let the original bug through unnoticed by the budget assertion alone.

**Still open:** the engine's own "neo prelude" is warmed by the pass above (since the pass calls the real recall-adjacent path), but the *phase timer* inside `timing.totalMs` still starts after the prelude rather than before it — so the untimed-prefix gap this section describes is narrowed, not eliminated at the measurement level, and a future engine change (a warm-only recall option, or moving the phase timer to start before the prelude) is recorded as an engine follow-up rather than fixed here. The nightly re-run against this fix was pending at the time of this record.

Engine-side follow-up recorded for the next engine plan (not fixed in this plan, and not a 2a-H3a/2a-H3b bug): **capture latency grows roughly linearly with the number of LanceDB fragments** a table accumulates, because every `memory add` writes one fragment and a query scans all of them; compaction (`table.optimize()`/equivalent) currently runs only inside the engine's own `consolidate-daily` job, never opportunistically. This was found by the kill soak's own latency measurements (Task 12: `memory add`/`memory recall` grew past their per-call budgets at roughly 100–150 facts on one agent with the flat embedder) and is why the soak spreads its facts round-robin across several agents rather than one (ruling H3-R19) instead of the design spec's implied single-agent load. Measuring this with the real embedder, and periodic compaction outside `consolidate-daily`, are both open items for a future engine plan (tentatively "E5").

#### 10.11 Journal replay runs before the socket listens — closed by 2a-H3b-a (B2)

The core's journal replay (ADR-012 §7, unchanged in mechanism by this plan) still runs to completion **before** the RPC socket starts serving. Task 15 made replay durable against a kill mid-replay for the *replay-time* half of the problem — every replayed line carries a stable `runId` (`journal:<line id>`, unchanged across restarts and across a partially-replayed `.jsonl.replaying-<pid>` file), and the engine's own `duplicate-turn` capture outcome removes a line a previous, interrupted replay had already stored. Closing the gap fully needed one more piece, landed after Task 15 as a review follow-up (**`a161a76`**): the *live-capture* half. `memory add`'s CLI now builds the journal line (and so its id) **before** sending the live `memory.capture`, and sends that same `runId: journal:<id>` on the live call, not only on the journal-fallback replay (`crates/plur1bus/src/commands/memory.rs`) — so a core that stored the turn but died before its RPC reply reached the CLI is replayed with the exact same `runId` the live call already used, and the engine answers that replay `duplicate-turn` (stored once), instead of the replay minting a *different* id for what is actually the same turn. Together these two pieces get "no fact captured twice" down to the kill-soak's own runs (0 duplicates in Task 15's report).

**One window remains, closed on the harness side but still open at the pinned engine (ruling H3-R24).** The engine's own replay-duplicate guard was found to record a turn as "seen" **after** the row is durably stored, with a gap of roughly 300 ms between store and record; a SIGKILL landing inside that gap makes the *next* replay see no record yet, so it stores the same turn a second time — a real, if narrow, duplicate the harness's `runId` plumbing cannot prevent, because the engine's own bookkeeping is what raced the kill. The fix (recording the guard once the row has settled, not before) ships as **engine PR E4.1**; until the harness pins a commit that includes it, `tests/system/kill-soak.test.ts` tolerates *exactly* this one case and no other: a duplicate is accepted only when the soak's own logs show the killed core (by pid) logged `journal: replay start { id, pid }` for that line before the SIGKILL and never went on to log `journal: replayed` for it (`packages/core/src/journal.ts`); every other duplicate — including one where the killed core did log `journal: replayed` before dying, meaning the engine's own guard should have caught it — fails the soak. The soak also sets `logs.keep` high enough (20) that the log evidence this check depends on cannot itself be rotated away mid-run.

**Closed by 2a-H3b-a (owner decision B2, confirmed 2026-09-27): the core now starts serving RPC before the replay finishes**, rather than leaving that window unreachable. §10.12 below records the mechanism (`startJournalReplay`, RPC 1.3.0's `CoreStatus.journalReplay`, the bounded stop wait) and the one remaining tolerance this reopens for the kill soak (H3-R24, still not fully closed as of this record — see §10.12).

#### 10.12 2a-H3b-a: replay while serving, module processes, config ownership, launchd (implementation record)

Plan 2a-H3b-a (this repository @ `feat/m1b-2a-h3b-a`, `1ba26c5` at this record, engine @ `72b6697f` since Task 1 (was `d0842424`), contract 1.8.0) is the plan that closes §10.11's open design question, moves `config.json` ownership onto the supervisor (ADR-013 §5, recorded there in full), gives the supervisor a second kind of child (modules, D14, `docs/module-guide.md`), fixes the launchd gap in §10.7, and adds `admin.*` over RPC (B15, recorded in ADR-016). This subsection covers the process-model and RPC-contract pieces; ADR-013 covers configuration in full and `docs/module-guide.md` covers the module manifest and runtime in full.

**B2 — replay while serving, and its deviation from the design spec's own apply order.** The core now calls `server.listen()` and reports `ready` (or `orphaned`, if the lifeline was lost during the engine start) *before* `startJournalReplay` begins; the journal drains in the background instead of blocking readiness (§10.11). RPC 1.3.0 adds `$defs/JournalReplayStatus` (closed, experimental, `x-since: "1.3.0"`) and `CoreStatus.journalReplay: { state: "empty"|"replaying"|"done"|"aborted"|"failed", replayed, kept, passes, pendingRemoval, finishedAt }`; `1staid check`'s `check_journal_backlog` reports `warn` with `replaying: <replayed> replayed, <left> left` while a replay is in progress, `left = max(core journalBacklog, files on disk) − pendingRemoval` saturating at 0. **Deviation from spec §6.3's implied apply order**: the design spec's own ordering (replay, *then* serve) is not followed; `ready` now happens first, and replay is a background concern the client discovers through `journalReplay`, not a precondition for the core answering at all. The reasoning is exactly §10.11's own "open design question" text: a client that needs already-consolidated data during a long backlog can now get it (`memory.recall` runs concurrently with replay; `memory.list`/`memory.show` too), at the cost of a short window where a fact the replay has not yet reached is invisible to a read that would otherwise have waited for it. `stop()` gained a bounded "journal replay" wait — `min(5000, budgetMs / 2)` — between the shutdown signal and `engine close`, so a stop always keeps at least half its budget for the engine regardless of a running replay; past that wait the replay is `abandon()`ed (state forced to `aborted`, its logger detached, `onDone` suppressed, and the file it was mid-way through is left exactly as it is, with no lines removed and no append-back) rather than left to write to a closed log. The abort itself acts **only between lines** — the capture already in flight keeps its own 60 s timeout and is allowed to finish — which is what makes a graceful stop's "no line lost, no line duplicated" guarantee hold without depending on engine PR E4.1 (next paragraph): a graceful stop never aborts a capture mid-flight, so the pre-E4.1 duplicate window described below simply does not occur on that path.

**H3-R24's kill-during-replay tolerance is closed by Task 1 of this plan.** §10.11 recorded the one duplicate `tests/system/kill-soak.test.ts` tolerated: a core SIGKILLed while a line is mid-replay could, before engine PR E4.1, store that turn twice, because the engine's own replay-duplicate guard recorded a turn as "seen" roughly 300 ms *after* the row was durably stored. Task 1 repins the engine to `72b6697f9f5739049e1336ad2be2882a87fe36f0` (E4.1, the merge of engine PR #195, verified at that commit: the guard now calls `onRowsSettled`, contract unchanged at 1.8.0) and removes the soak's tolerance in the same commit: `tests/system/kill-soak.test.ts` now asserts `replayedTwice` is empty with no exception, and the bookkeeping the tolerance needed (`killsDuringReplay`, `coreLogRecords`, the `sigkills`/`journalLine` maps, `logs.keep`) is gone along with it. Before the repin, the tightened assertion was run three times against the old pin (seed 3748478939, matching H3-R24's reproducing seed) and failed every time with exactly one journaled fact stored twice, confirming the assertion was RED for the right reason; after the repin, the same three runs (that seed plus two unseeded) pass with `replayedTwice` empty each time. The commit `72b6697f9f5739049e1336ad2be2882a87fe36f0` also merges engine PR #196 (E4.2, verified-path shared memory on macOS/Windows, an ancestor of the E4.1 merge commit): the core's `sharedMemoryStatus` projection already accepted `"verified-path"` as a valid `SharedMemoryStatus.mode` (added ahead of this engine landing it), so no core change was needed for E4.2 to keep working. `packages/rpc-schema/schema/rpc.schema.json`'s `SharedMemoryStatus` description, which still called "verified-path" reserved and not yet produced, was corrected in the final review fix wave (description only, no version change).

**Module processes (B9–B12), spec §6.4.** A module is a second kind of supervised child, alongside the core, sharing the same `Slot`/`Monitor`/backoff/adoption machinery (`supervisor::state::{Role, RoleKind}`, `Slot::new(role, scale)`; `supervisor::child::{module_spec, module_plan}`; `supervisor::adopt::probe_module`). It runs `node <module-dir>/<entry> --home <home> --module <name> --lifeline stdin --instance <id>` (omitting `--lifeline stdin` when the manifest sets `lifeline: false`, ruling H3B-R25-3), authenticates over its own control endpoint with `module.auth` (`x-server: "module"`, RPC 1.3.0, no version bump; `Endpoint::Module` in `plur1bus-rpc`), and is monitored by `module.status`/`module.watch`/the `module.state` notification exactly as the core is monitored by `core.status`/`daemon.status`. **B12, the API-version identity check**: `wait_ready` and `probe_and_adopt` both check a module's hello (`module.name`, `module.apiVersion`) against its on-disk manifest; a mismatch on the spawn path is killed and backed off as `CrashReason::ManifestInvalid`, and on the probe path the found process is `Foreign` and terminated through its pinned peer (`module.shutdown`, then SIGTERM/kill) rather than adopted — never signalled by the socket-server pid alone, the same rule §10.2 already applies to the core. **New `CrashReason` members**: `ManifestInvalid` (`manifest-invalid` — an invalid manifest, a manifest-name/identity mismatch, or a module left out of the dependency-resolved start order) and `ApiVersionUnsupported` (`api-version-unsupported` — the manifest's `apiVersion` is outside the window `current_api_version`/`current_api_version − 1` supports, closing ADR-016 §"Server obligations": the supervisor loads a module of the current or the previous manifest `apiVersion` side by side, verified by `module_api_versions_run_side_by_side`). **New stopped reasons** (`ChildStatus.process.reason` when `state: "stopped"`, never retried on their own): `disabled` (`modules.<name>.enabled == false`), `scope-agent-unsupported` (`scope: "agent"`, not started in 2a per B10), `stopped-by-request` (`module stop`, until `start`/`restart`/a supervisor restart), and `needs-unavailable` (below). A module's exit-code classification differs from the core's in one place only (ruling H3B-R13/P13): exit 2 is `manifest-invalid`, not `config-invalid` — the core's own exit 2 keeps its long-standing meaning (§10.3).

**`needs-unavailable` — held-back needs, transitively (rulings H3B-R25-4, H3B-R28).** A module whose `needs` names a module that is disabled, agent-scoped, unsupported, manifest-invalid, or itself `needs-unavailable`, is never spawned: it is shown `stopped` with reason `needs-unavailable` and an `errors` line naming the chain (`"needs X, which is not started (<why>)"`). The computation (`supervisor::modules::ModulesView`/`held_reason`) walks `start_order` — already topological — in one pass, so the hold propagates transitively without a fixed-point loop. **H3B-R28 extends the same mechanism to a module a person stopped by hand**: `module stop <name>` also counts as a held need for that module's dependents, so `fixture-b`, which needs `fixture`, becomes `needs-unavailable` the moment `fixture` is stopped by request and is released the moment `fixture` is started again — `fixture` itself can still be started directly regardless of its own held state. This is evaluated fresh on every reconcile (a module install, uninstall, config change, or explicit `start`/`stop`/`restart`), not only once at supervisor start.

**Restart jobs and `restartPending` (B7, B8), spec §6.1's live-apply/restart-execution steps.** A `RestartJob` carries a `RestartPlan` (`{ live: string[], core: bool, modules: string[] }`, ADR-013 §3) and runs on the supervisor's main thread, queued ahead of `daemon.start`/a due restart. **B7 — the core learns it needs a core-class restart two ways**: (1) `config.set`/a valid hand edit whose plan names `restart.core` pushes a job at once, queued under the same config-mutex hold that installed the change (so it precedes any job the *old* core's own `status().config.restartPending` could independently cause), with the wait for the new core happening after the mutex is released (ruling H3B-R6); (2) a hand edit the watcher applies without anyone waiting on it relies on the core's own `config.status.restartPending` (computed from `restartPlan(builtWith, current())`, cached per accepted change so `core.status` stays cheap) being polled by the health loop, which pushes exactly one job per generation once it sees `true`. **B8 — a restart job never counts toward give-up**: `Monitor::restart_requested(budget)` records its exit as `Requested` (`lastExit.reason: "none"`), so `Backoff` never touches its exit-in-10-minutes counter regardless of how many core-class restarts a burst of `config.set` calls triggers; a child that was `Crashed` (fatal) or had already given up is `reset()` first so a restart can still bring it back. A module restart job coalesces the same way as a config-triggered core restart: several queued jobs drain into one run (`run_restart_jobs`), and a core (or module) already running since after the oldest queued job is skipped rather than restarted a second time for a request that no longer applies (`state::restart_already_done`/`crashed_for_good`). **One deadline, the grace reserved for the core (ruling H3B-R25-1)**: `daemon.stop` still spends one shared budget-plus-grace deadline across every slot (§10.6, unchanged in kind), but modules and the core no longer share it identically — each module gets `stop_until(left, budget_end)` and is killed at the end of the plain *budget* if it has not stopped, while the core additionally gets the *grace* as its own reserve (`stop_until(max(left, grace/2), budget_end + grace)`), so a hung module cannot itself starve the core down to a `budgetMs: 0` SIGTERM: the core is asked with time still left and killed only at the end of the grace, not the budget. With no modules present the core still gets the full budget (unchanged from 2a-H3a).

**`CrashReason::GaveUp` (`gave-up`, ruling H3B-R26).** A give-up (five exits within the sticky 10-minute window, §10.3) now sets `process.reason: "gave-up"` for the core and for a module alike, distinct from `lastExit.reason` (which keeps the exit's own reason, e.g. `"none"` for exit 0). `$defs/CrashReason` is a new, additive, `x-since: "1.3.0"` enum documenting the whole vocabulary (`config-invalid`, `manifest-invalid`, `api-version-unsupported`, `engine-contract`, `lock-held`, `ready-timeout`, `adopted-exit`, `gave-up`, `none`); the fields stay plain strings, so this is additive under ADR-016 §2, not a breaking change to an existing closed enum. `1staid check` reports `"crashed: gave up after repeated exits (last exit code N)"`.

**B18 — an invalid `config.json` is fatal, and the first valid file re-arms (ruling H3B-R19/H3B-R19 as adopted).** The supervisor validates every file it reads — at its own start, on every watcher poll, and on every `config.set`/hand edit. An invalid file at start, or an invalid hand edit while a core is running, leaves `ConfigState.running: None` with `rejected` set (`{ errors, at }`, and the rejected bytes backed up to `config.json.rejected-<ms>`); the core is treated as `config-invalid` (fatal, not retried) rather than started against a broken configuration. **Re-arming is scoped, not blanket**: the core is only re-armed by the *first* valid file that follows a rejection — `running` was `None`, or `rejected` was set — never by every subsequent configuration change (an early cut of this ruling re-armed on every change, which broke an unrelated fatal-crash test by restarting a core that was fatal for an unrelated reason; `rearm_core()` now runs only from that specific transition). A fix can arrive as a `config set`, as a hand edit, or by reverting the file's bytes back to what is already running (`poll_locked`'s `applied_hash` path). `1staid check`'s `config.valid` row fails on a `rejected` file, with the hint "the supervisor runs the last valid configuration; fix config.json or use `plur1bus config set`" and, while nothing has ever run, no `config set` suggestion.

**B4 — the file watcher polls; it never `notify`s.** Per the supervisor's dependency budget (no `notify`, no async runtime), `supervisor::config::poll_file` runs on a plain timer (`spawn_watcher`, every `1000 ms × scale`), keyed on mtime+length first and SHA-256 only on a mismatch, so an unchanged file costs one `stat`. The watcher never rewrites the file itself.

**B5 — `revision`.** `plur1bus-config::revision(&Config)` is a content hash (independent of key order) that both `config.get`'s result and `config.watch`'s snapshot/pushes carry; `config.set { ifRevision }` and `E_CONFLICT`'s `ids.currentRevision` (ADR-013 §1's pre-existing `d17` ruling) both key on it, so a client can preview against a known revision and have its apply refused, not silently overwritten, if the file moved under it.

**B6 — CLI routing, with a fallback for an older supervisor.** `commands::config::route` decides `Direct` (write the file itself, exactly as the CLI did through 2a-H3a) versus `Supervisor` (call `config.get|set` over RPC) by: no recorded token, a dead recorded pid, or a refused connection → `Direct`; a supervisor that answers `supervisor.auth` → `Supervisor`, *unless* its handshake capabilities don't list `config.set` (an older supervisor from before this plan) → `Direct`, so a partially-upgraded install still lets the CLI write the file the old way rather than silently doing nothing; any other RPC failure while a supervisor is running → `E_NOT_AVAILABLE reason=supervisor-unresponsive`, exit 1 — a genuinely broken supervisor is reported, not silently bypassed. **Ruling H3B-R22 — the CLI's deadline covers the restart wait it may trigger**: `config set`/`agent create|remove` (which also route through `apply`) use `SUPERVISOR_CALL_TIMEOUT = RESTART_WAIT_MAX + 10 s`, where `RESTART_WAIT_MAX = DEFAULT_STOP_BUDGET (10 s) + the 60 s × scale ready timeout` — never a timeout shorter than the wait the supervisor's own `config.set` may take waiting for a restarted core to become ready, so a slow-but-successful restart is reported as such rather than as a false `supervisor-unresponsive` after the CLI gave up early.

**Offline module operations hold `run/supervisor.lock` (fix round, Task 10 review).** `module install`/`module uninstall` run offline (no supervisor answering) take the same exclusive `run/supervisor.lock` file (§10.5) the supervisor itself takes before it probes the address — via the same `try_lock` — for the whole staged mutation. If the lock is held (a supervisor is starting or stopping concurrently), the offline command refuses at once with `E_NOT_AVAILABLE reason=supervisor-running`, exit 1, and changes nothing; a supervisor that itself tries to start while an offline install/uninstall holds the lock gets `WouldBlock`, rather than the two racing to write the same module directory. **Final review I1**: that supervisor no longer exits 3 unconditionally. `already_running` probes the address for up to 3 s; only a supervisor that actually answers gives exit 3 (0 under launchd, B16). If nobody answered, it tries the lock once more and continues as the supervisor when it wins; otherwise it exits **1**, a transient code launchd's `KeepAlive{SuccessfulExit:false}` retries after its throttle interval. Without this, a launchd start (login, or a restart after a crash) that coincided with an offline `module install` exited 3→0 and stayed down silently. Any future ruling that makes another process hold `run/supervisor.lock` must re-check this exit mapping (`tests/supervisor.rs` `a_supervisor_under_launchd_that_finds_the_lock_held_by_an_offline_install_exits_1`, `a_supervisor_that_finds_the_lock_released_during_its_probe_wait_starts`).

**Windows: supervisor writes to a connected client still have no deadline (ruling H3B-R18) — this is why the never-reading-subscriber test is unix-only.** §10.7 already recorded this as a standing limit ("the supervisor's own writes to a connected client have no deadline… tracked for a future plan if it becomes a real problem"). 2a-H3b-a's `config.watch`/`module.watch` subscription queues (`supervisor::subscribers`, one `sync_channel(64)` and its own writer thread per subscriber) turn this from a theoretical limit into one with an actual, tested consequence on unix: `tests/config_service.rs`'s `a_subscriber_that_never_reads_is_dropped_and_set_stays_fast` proves that a subscriber whose queue fills (its socket buffer never drained) is *dropped* — its connection closed, the drop logged — rather than blocking every future `config.set`/`config.changed` on a client that stopped reading. On Windows the equivalent write still has no deadline (`INFINITE`), and there is no cross-platform way to force a write to fail fast enough to test the same drop path deterministically without one, so the test is `#[cfg(unix)]`/`{ skip: process.platform === "win32" }`; the *behaviour* (a full queue drops the subscriber) is not unix-only, only its regression test is.

**launchd (B16) — see the updated §10.7 above** for the fix itself (`exit_code`, `PLUR1BUS_SERVICE_MANAGER=launchd`) and the RestartOnFailure evidence status.

**Windows: what 2a-H3b-a has not run on Windows (final review M8).** Every piece below compiles on Windows and is written to the PR #2 Windows rules, but has no passing Windows run yet; the first `windows-2025` CI leg of this branch is its first evidence. #### 10.13 2a-H3b-b: setup, update --check, repair, the operations skill, release, and the Windows `run/` ACL landing (implementation record)

Plan 2a-H3b-b (this repository @ `main`, `049b9a3` at this record, PRs #17–#46; engine repinned by its Task 1 to `b0e149b8`, E4.3, contract 1.9.0) is the plan named in §8/§10.12's "still deferred" lists: the installer (`setup`), the updater's read-only half (`update --check`), `1staid repair`, the bundled operations skill, and the release/signing pipeline. This subsection records the process-model- and supervision-relevant pieces; the installer's own file layout is recorded in `docs/module-guide.md` §12, and the wizard's use-class question in ADR-006.

**The Windows `run/` ACL (HB5) lands as designed in §11's amendment, not merely proposed.** `supervisor::mod.rs`'s `secure_run_dir` calls `SetNamedSecurityInfoW` (`plur1bus_rpc::win::set_path_dacl`, `plur1bus_rpc::acl::run_dir_sddl`: `D:P(A;OICI;FA;;;<user SID>)(A;OICI;FA;;;SY)`) on `run/` immediately after `create_private_dir(run)` and before the supervisor spawns, adopts or probes any child; success sets every spawned child's environment to `PLUR1BUS_RUN_ACL=inherited` (`supervisor::child::RUN_ACL_ENV`), failure is logged and children get no such variable. `createSecurePath` (`packages/module-api/src/secure-path.ts`) reads that variable: with it set and the path `run/` or directly inside it, it returns `{ applied: true, mechanism: "acl" }` with no tool spawned; anything else — an unsupervised `core run`, a module started by hand, any other path — takes the pre-existing `icacls` path unchanged. The defence-in-depth check moved to Rust as planned: `plur1bus_rpc::win::file_dacl_report`/`acl::run_writable_by_others` read the DACL natively, and `1staid check`'s `run.permissions` row now covers every `module-*.token`/`.pid` file, not just the core's and the supervisor's own (`crates/plur1bus/src/commands/firstaid.rs`, test `run_permissions_covers_module_tokens`). `MODULE_READY_FLOOR`/`CORE_READY_FLOOR` (both 10 s) are recorded in full in §10.3 above, as part of the same Windows work, not repeated here. **Deviation found during implementation, not in the ruling text**: `1staid repair`'s `run.permissions.fix` step does not rewrite a token/pid file's DACL — Windows real-world testing (a physical Windows 11 box, not the CI runner) found `SetNamedSecurityInfoW` on an already-secured file returning `ERROR_ACCESS_DENIED` under ordinary user rights; the fix instead resets the file to *inherit* `run/`'s own DACL (`plur1bus_rpc::win::inherit_path_dacl`, needing only `READ_CONTROL | WRITE_DAC`, which the owning user always holds on their own file) — `crates/plur1bus/src/repair/safe.rs`'s `fix_run_permissions`, PR #34. **Evidence**: PRs #27 (Task 2, the ACL itself) and #34 (Task 7, the repair step) both ran green on the `windows-2025` CI leg, and a separate real-hardware Windows run (a physical Windows 11 box reached over SSH, outside CI) exercised the full `setup`/`daemon start`/`1staid check`/`1staid repair` path and found one genuine product bug the GitHub runner's timing never exposed — recorded next, since it is a Windows-specific fix of this same plan, not an ACL fix.

**`pid_alive` on Windows now excludes an exited process whose handle Defender still holds (PR #46).** `crates/plur1bus/src/commands/firstaid.rs`'s `pid_alive` opens the process with `PROCESS_SYNCHRONIZE` and counts it alive only when `WaitForSingleObject(h, 0) == WAIT_TIMEOUT`; before this fix, `OpenProcess` succeeding (which a security product can make true well after the process has exited, by keeping a handle open) was itself read as "alive". This is shared by `commands::config`'s own liveness check (`config.rs`'s `route`), so the same fix reaches the config-routing fallback described in §10.12's B6, not only `1staid check`. This is the first Windows finding of this plan's implementation that the `windows-2025` CI runner itself did not surface — it took a real machine, under a real antivirus, to reproduce.

**Installer process boundary: no installer crate in the supervisor (HB6).** `crates/plur1bus/src/install/` is a module of the `plur1bus` binary, not a separate crate, but the spec §4 dependency budget still applies to it in spirit: `scripts/lint-hygiene.mjs` (run by `pnpm lint`) refuses the strings `ureq`, `flate2`, `tar::`, `zip::`, `minisign_verify`, `install::fetch` and `install::archive` anywhere outside `install/` itself, so a future change cannot casually pull the installer's HTTP client, archive handling or signature verification into `supervisor/`. `install/mod.rs`'s own header states the boundary in prose: reached only from `setup`, `update` and `1staid repair`, never from `supervisor/`.

**Targets and the zigbuild deviation from HB7.** `crates/plur1bus/src/install/targets.rs`'s `Target` enum has exactly the five required targets (`Target::ALL`); `Target::current()` returns `None` on macOS x64 (best-effort, not built, Q2), unit-tested (`current_target_is_some_on_ci_hosts`). `.github/workflows/harness-release.yml`'s `binary` job zigbuilds only `linux-x64`/`linux-arm64` (`cargo zigbuild --target <triple>.2.28`, the glibc 2.28 floor) and builds `darwin-arm64`, `win-x64` and `win-arm64` natively on their own runners (`macos-15`, `windows-2025`, `windows-11-arm`) — recorded as a deviation from the spec's "`cargo-zigbuild` for the five targets" below.

**`harness-release.yml` and the one-liner's signature limit (HB19).** The workflow (`workflow_call` for D78's `release.yml`, `workflow_dispatch` for a manual dry run) has five jobs: `meta` (version/channel), `payload` (one core payload per target), `binary` (one `plur1bus` binary per target, zigbuilt or native per the deviation above), `sign-macos` (Developer ID codesign plus notarisation, gated on the `macos-signing` environment's owner-approval reviewer), and `native` (assembles `release-native.json`, the `native` object D78's `release.yml` merges into `release.json` and signs). `scripts/install/install.sh`/`install.ps1` fetch `{channel}.json`, take `native.binary[<target>].{url,sha256}`, verify the downloaded binary's SHA-256 **before running anything**, then exec `plur1bus setup "$@"` — they never check the feed's own minisign signature, because a bare `curl | sh` target has no signing tool available; that check is `update --check`'s job (HB10), over HTTPS the same feed already came over. Recorded as a permanent, known limit (deviation table below), not a gap to close later.

**Repair's pinned-peer termination (`unit.terminate-hung`, HB16).** When no supervisor answers and a core's or a module's socket accepts a connection but does not answer its handshake or a `*.status` call within `HUNG_TIMEOUT` (2 s, `crates/plur1bus/src/repair/risky.rs`), the plan reports a high-risk step that terminates the hung process **through the pinned peer** `adopt::probe_child` already opens for identity (a `pidfd` on Linux, a process handle opened while the pid was known to own the socket/pipe on Windows, a fresh `SO_PEERCRED`/`LOCAL_PEERPID` re-check on macOS and the BSDs — the same non-negotiable rule §10.2 states for the supervisor's own signalling: never signal a pid confirmed only by the socket-server pid), then removes its run files. `store.migrate` (`admin.migrate` over the core) and the two report-only steps below share the same file.

**§10.7's launchd gap is now detected, not merely not-looped-on (HB17).** §10.7 above recorded that a real launchd misconfiguration exits 0 silently and left *detecting* that state to this plan's `1staid repair`. It is built as two log-based, OS-neutral checks (`crates/plur1bus/src/repair/risky.rs`): `service.silent-exit` fires when the last `logs/supervisor.log` record is `exiting 0 instead of <code>` and no supervisor answers; `service.restart-loop` fires when at least `LOOP_MIN_STARTS` (5) `supervisor started` records fall within the latest `LOOP_WINDOW_MS` (10 minutes) and no supervisor answers. Both steps are `action: "report"`, `risk: "none"` — repair surfaces the loop for a person to act on, it does not guess at a fix — and, being log-based rather than launchd-specific, the same two checks also catch a systemd or Task Scheduler restart loop with the identical evidence shape.

The zigbuild target split (HB7) and the one-liner's signature limit (HB19) are added to the "Deviations from the spec" table below.

#### 10.14 X1: extensions from file (implementation record)

Plan X1 (`docs/superpowers/plans/2026-09-28-x1-extensions-from-file.md`, integration branch `feat/x1-extensions`; user-facing description in `docs/extensions.md`) adds the `.p1x` package pipeline and the `skill`, `plugin` and `ext` commands. This subsection records the process-model and supervision decisions and the rulings taken while building it.

**The worker process boundary (X1-R2).** The extensions spec §10.2 puts `ext.*` on the supervisor, and §4's dependency budget forbids `zip`, `flate2` and `minisign_verify` there (the supervisor has no heavy dependencies and no reason to crash). Parsing untrusted ZIPs in it would add both, so **the supervisor never touches package bytes**. `ext.inspect` and the staging half of `ext.install` run in a child, `plur1bus ext __worker inspect|stage` (`std::env::current_exe()`, a hidden command; `crates/plur1bus/src/ext/worker.rs`). The child prints exactly one JSON line, `{ok:true,result}` or `{ok:false,error:{code,reason,message,data}}`; a deadline of 60 s (inspect) and 300 s (stage) kills it, and a crash, an overrun, an unparseable answer or a reason outside its known list becomes `E_INTERNAL reason=worker-failed`. A crashing parser fails the call and nothing else. A crashed or timed-out stage also discards the inspection (X1-C20: a crash on a package is itself suspicious), so the package is inspected again; answered refusals keep it. The supervisor then commits (renames, state, index, config) in-process under one process-wide `try_lock` mutex (a second mutation is `E_CONFLICT reason=busy`; the module queue's own `busy` keeps its meaning). On stop the supervisor calls `worker::stop_all`, which kills running workers and refuses new ones. The offline CLI calls the same functions in-process.

`plur1bus-ext` **audits and never extracts** (X1-R3): its own central-directory parser checks every rule and streams each entry once to hash it, with no write. The worker extracts with the shared `install::archive::extract` into staging, then walks the staged tree (symlinks, special files, extra or missing files, hash and size mismatch), so ⟂EXT 1's single extractor holds and the time-of-check gap is closed. The audit hashes at inspection (X1-R7), so a hash mismatch, a lying size and a deflate bomb are refused before the person confirms.

**The lint rule.** `scripts/lint-hygiene.mjs` classifies every file under `crates/plur1bus/src/ext/` as supervisor-safe (`mod, paths, state, index, overlays, host, worker, record, commit, lifecycle, remove, list`) or worker-only (`inspect, stage`); an unclassified file fails the lint. The supervisor-safe files, and `crates/plur1bus/src/supervisor/**`, must not match `plur1bus_ext::(zipaudit|verify|pack|normalise)`, `install::archive`, `zip::`, `flate2` or `minisign_verify`, including grouped imports. Package bytes reach the supervisor-side code only as an opaque file, moved by rename (X1-C22: the spool into the cache, the cache into the trash and back; a copy only across devices; the cache and the trash never both hold a package).

**Start-time overlays.** At supervisor start (`supervisor/ext.rs`) `ext::recover` runs first (it re-hashes every enabled packaged module against `extensions/state.json`); the overlays (revoked, tampered, incompatible) are then computed for packaged modules and computed again after every ext mutation, and a module whose overlay changed is reconciled. A failing module is `stopped` with reason `ext-revoked`, `ext-tampered` or `ext-incompatible`, evaluated after `disabled` so its dependents become `needs-unavailable`, and `module.start`/`module.restart` answer `E_NOT_AVAILABLE` with the same reason. The start-up re-hash covers enabled modules only (X1-C21); a disabled one is re-hashed at enable. An unreadable `state.json` holds back every packaged module known from the cache manifests as `ext-tampered`, fail closed (X1-C23; a packaged module whose cache files are also gone looks local, which `1staid check extensions.consistency` reports).

**Exit codes (X1-C26).** `plur1bus module` keeps exit 1 for `supervisor-running` and `supervisor-not-running`. The extension commands exit 2 for every `E_NOT_AVAILABLE` and `E_APPROVAL_REQUIRED` (G18), 3 for `E_LOCKED`, 1 otherwise, so `supervisor-running` exits 2 there. `supervisor-lacks-method` (the running supervisor predates `ext.*`) is a CLI-only reason and exit 2.

**Test seams** (all gated by `PLUR1BUS_ALLOW_TEST_INTERNALS=1`, listed in `AGENTS.md`): `PLUR1BUS_TEST_EXT_PUBKEYS`, `PLUR1BUS_TEST_EXT_REVOCATIONS`, `PLUR1BUS_TEST_EXT_FAIL_AT` (`<step>` or `kill:<point>`), `PLUR1BUS_TEST_EXT_INSPECT_TTL_MS`, `PLUR1BUS_TEST_HARNESS_VERSION`, `PLUR1BUS_TEST_EXT_WORKER_ARGS` (`<op>:<args>` separated by `;`), `PLUR1BUS_TEST_EXT_WORKER_DEADLINE_MS` (`<op>:<ms>`) and the hidden worker arguments `--sleep-ms` and `--crash`.

### 11. Container mode (amendment 2026-09-27, owner decision D77)

The desktop app now ships the harness as a container image (spec D77; `docs/superpowers/specs/2026-09-27-desktop-app-design.md` DS1, DS14–DS23, §6.15), and the same image runs on a VPS. Process model B is unchanged *inside* the image; what changes is who plays the role of the OS service manager, and a few commands that do not make sense in a container.

- **One container for supervisor, core and modules.** They are never split across containers: the `run/*.sock` endpoints with their peer-pid identity checks (§10.2), lifelines and adoption (spec §6.4), the `node:sqlite` `BEGIN EXCLUSIVE` core lock (§5, an `fcntl` lock that excludes only within one kernel) and the single LanceDB/ONNX handle (T7) all require one kernel and one PID namespace. Only the streamed Chromium (D74 b) and optional sidecars (SearXNG) run in separate containers, and they talk to the harness over its authenticated interfaces, never over `run/`.
- **PID 1 is `plur1bus init`**, a new mode of the same binary: it reaps orphans (`waitpid(-1)`), forwards SIGTERM/SIGINT as `daemon.stop { budgetMs: 120000 }`, and respawns `plur1bus supervise` with the §10.3 backoff (five crashes in 10 minutes → `init` exits non-zero so the runtime surfaces it). tini was rejected: it exits when its single child exits, so a supervisor crash would stop the container and kill the core, contradicting acceptance criterion 3 (the core survives a supervisor crash and is adopted). With `init` respawning the supervisor, the orphaned core is adopted exactly as under launchd/systemd (§10.7's reasoning against `PR_SET_PDEATHSIG` applies unchanged).
- **The OS service manager is replaced by the container runtime and the desktop app.** Docker: `restart: unless-stopped`, `stop-timeout 150` (the §10.6 value: 120 s maximum `daemon.stop` budget plus grace and margin). Apple `container` has no restart policy and a 5 s default stop timeout, so the app passes `stop -t 150` and restarts a dead container itself while it runs. `service install|uninstall` and `update` answer `E_NOT_AVAILABLE reason=container-managed` when `PLUR1BUS_CONTAINER=1`; upgrades are image-digest swaps done by the app (spec DS21).
- **State root** is `PLUR1BUS_HOME=/var/lib/plur1bus` on a named volume, never a host bind mount (SQLite WAL and the core lock need a local file system seen by one kernel). `run/` lives there as before; nothing in `run/` is reachable from the host.
- **The host CLI forwards.** A host `plur1bus` configured for container mode answers `--help`/`--version` locally (T1 unchanged) and forwards every other command through the runtime's `exec`, passing `--json` output and the exit code through untouched (R13 holds end to end). T1/T2 are not claimed for forwarded commands; their latency is measured and reported.
- **API binding.** Inside the container the HTTP API binds the container's own interface; the runtime publishes it on host loopback only, so "no listening TCP port except the harness API, loopback-bound by default" (ADR-001) still holds on the host. *Amended 2026-10-02 (desktop spec C8, DS16):* with `remote.publish` = `network` a second, TLS-only listener is published on the host interface the person chose; the plain-`http` listener stays loopback-only, since the harness cannot tell the two apart by source address in container mode. The `local` and `tailnet` levels (the default) publish nothing beyond loopback. `Tailscale-User-*` headers are not trusted in container mode (requests arrive from the runtime's gateway).
- **Unchanged:** `daemon status|start|stop|restart` (inside), `1staid check` (gains a `container` section), config ownership (ADR-013 §5), the module lifecycle, the journal, exit codes 2/3/4. The launchd exit-code remap (§10.7, B16) is irrelevant in the container and stays launchd-only.
- **Upgrades (D78)** are image swaps driven by the app, never an in-place update inside the container. Two new container-mode pieces of the same binary serve them: the hidden `plur1bus state snapshot|verify|restore` (runs in a throwaway container with no core, copies the stopped state volume and checks it against a SHA-256 manifest), and `plur1bus admin smoke` (core RPC `admin.smoke`: store integrity, model load, and a capture → recall → purge round trip on the reserved agent `__smoke`), which with `1staid check` forms the post-upgrade health gate. Config migrations stay the supervisor's (ADR-013 §5); store migrations stay `admin migrate`. A failed gate restores the snapshot and the previous image.
- **Native installs remain supported** (spec §6.5, now the secondary path); everything in §1–§10 continues to describe them. Their `plur1bus update` (M8) follows the same D78 sequence on the state root.
- **Windows ACL follow-up (owner 2026-09-27, desktop spec DS36; tracked as `2026-09-27-m1b-2a-h3b-config-modules-setup-repair.md` item H3b-b-7; container mode unaffected either way) — landed in 2a-H3b-b (§10.13 above).** The per-module `icacls` spawn (§10.4's `MODULE_READY_FLOOR`, ~1 s per module on Windows) is replaced by one in-process `SetNamedSecurityInfoW` call on `run/` at supervisor start, through `windows-sys` (already a dependency, `Win32_Security_Authorization` feature — no new crate), before any module listens; token and pid files then inherit the restrictive ACL from creation, and `icacls` is no longer called per module. Node's own default named-pipe DACL (the core's pipe, §10.2/S11) is unaffected and needs no change: it is already the deliberately permissive-but-read-only default (full control SYSTEM/Administrators/creator-owner, read-only Everyone/Anonymous), which upstream Node declines to change by default (`nodejs/node#47086`) and which `pipe_dacl_report` already verifies.

| Spec says | H1 does | Reason |
|---|---|---|
| §6.2 closed enum of nine codes | Adds `E_LOCKED` | No existing code states "another core holds this installation" truthfully (§5). |

## Consequences

- **Easier:** restarting or replacing a module without touching the core, now proven end to end by a real module (the fixture, D14, module-guide.md) that starts, backs off, is adopted and is reconfigured without any change to the core; third-party add-ons with the same shape as first-party ones; a CLI that answers in milliseconds and stays useful when the core or the supervisor is down; one schema edit changes both languages, and the fixtures fail the build on drift; a second core on the same home is impossible, not merely discouraged; a config change now states, and enforces, exactly what it restarts (ADR-013 §3–§5), down to a single module.
- **Harder:** two toolchains in CI (Cargo and pnpm) and two failure surfaces; every new method needs a schema edit, `pnpm gen`, fixtures and `pnpm docs:gen`; RAM grows by 30–50 MB per running module process; the supervisor's lifeline/adoption/backoff code is now exercised by two kinds of child (core and module) sharing one scheduler, verified so far only by the Linux sandbox plus compile-checks on Windows and macOS pending their CI legs; the supervisor's own writes to a client still have no deadline on any platform, now with an observed consequence (a full subscription queue drops the subscriber, §10.12) rather than a purely theoretical one.
- **Revisit when:** RAM per module becomes a user complaint (build the in-process module host for trusted modules); the engine publishes the npm prerelease (switch the pin); a client needs versions on every response (it does not today — they are per connection); the engine adds LanceDB compaction outside `consolidate-daily` (§10.10) or an earlier-starting phase timer for the neo prelude (§10.10); the Windows `RestartOnFailure` question (§10.7) is finally answered by an observed `windows-2025` CI run; the harness adopts `RecallQuery.warmOnly` (HB2 — this would raise the engine floor past 1.8.0 and is left for the next core plan); or the embedding use-class question (ADR-006, HB11) actually selects a different model instead of every install being forced to E5-small/BGE-v2-m3 regardless of answer (O5, D54/M3).

## Alternatives considered

- **Process model A (single process, hot reload)** and **C (worker threads)**: rejected, see the table in §1.
- **One language (TypeScript for the CLI too)**: rejected by D7 — a Node CLI pays Node start-up on every command (B1 < 100 ms p95 is not reliably reachable) and puts Node on the recovery path of a broken Node installation.
- **Hand-written types on both sides**: rejected; drift between the Rust client and the TypeScript server is the most likely class of bug in a two-language system.
- **`contract`/`rpc` in every result**: rejected, pollutes every result type (§6).
- **`flock` through a native addon, or a PID file**: the addon adds a prebuild matrix for one call; a PID file is discipline, not exclusion (stale PIDs, PID reuse).
- **HTTP on loopback instead of a Unix socket / named pipe**: rejected for the local control path — a port is reachable by every local user and needs its own auth story; filesystem permissions on the socket are free on POSIX.
