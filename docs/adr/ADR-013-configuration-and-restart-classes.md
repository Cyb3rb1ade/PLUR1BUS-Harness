# ADR-013: Configuration and restart classes

**Status:** Accepted (2026-09-24, owner decisions D3 and D5; reserved namespaces per D15, D16, D18; implementation record of plan H1 added 2026-09-25; implementation record of plan 2a-H2 added 2026-09-26) · **Date:** 2026-09-24 / 2026-09-25 / 2026-09-26 · **Deciders:** Christian (owner) · **Inputs:** `docs/superpowers/specs/2026-09-24-m1b-2a-core-daemon-cli-design.md` §2 (D3, D5, D15, D16, D18), §6.1 · `docs/superpowers/plans/2026-09-24-m1b-2a-h1-harness-foundation.md` Tasks 3, 12, 13, 16 · the H1 implementation ledger (rulings R10, R22, the T5, T11 and T12 rulings, the H1 interim of a CLI-owned `config.json`) · owner decision D29 (setup asks only `basic`) and `docs/superpowers/plans/2026-09-26-m1b-2a-h2-memory-surface-and-api-stability.md` ("Global Constraints" and rulings G4, G6, G16; lands on `main` via docs PR #3) · Source of record: this repository @ `53acbb3` (`feat/m1b-2a-h2`); engine @ `d32771c5` (contract 1.6.0). Companion: ADR-012 (process model, RPC), `docs/config-engine-keys.md` and `docs/config.md` (both generated).

## Context

D3: "a config change restarts only what it must" and "individual modules restart without restarting the whole". D5: one state root per user (`~/.plur1bus/`, `%LOCALAPPDATA%\PLUR1BUS`, overridable by `PLUR1BUS_HOME`) and **one** `config.json` with `$schema` and `schemaVersion`. Under process model B (ADR-012) the configuration is read by a Rust supervisor/CLI and a TypeScript core, so both languages must agree on the schema, the defaults and the consequence of every change. The engine brings its own configuration (55 keys at `d32771c5` — 54 at H1's `eaaf168f`, plus `chatModels` added in engine 7.16.4, ruling G6 — measured by `scripts/gen-engine-keys.mjs`), most of which it reads once, at `createEngine()`; the harness cannot make such a key live without an engine change. D29 (2026-09-25) additionally asks that `setup` offer a `basic` question set before the full schema; that interactive flow is 2a-H3 work (ruling G4), but every key needs a tier value now so the resolver and the CLI can exist ahead of it.

## Decision

**One `config.json` per installation, validated by one JSON Schema (`packages/config-schema/schema/config.schema.json`) that both languages load; every key carries a restart class `x-restart: live | module:<name> | core` and, since 2a-H2, a presentation tier `x-tier: basic | advanced` (D29), both resolved by the nearest ancestor that declares one; a change is validated, previewed as a restart plan computed by a recursive tree diff, applied atomically, and then — once the supervisor exists — announced as `config.changed` and executed in dependency order. There is exactly one writer of the file: in H1 and 2a-H2 the CLI through `crates/plur1bus-config`, from 2a-H3 the supervisor.**

### 1. The file

- **Location**: `<home>/config.json`, where `<home>` is `--home`, else `PLUR1BUS_HOME`, else `~/.plur1bus` (POSIX) or `%LOCALAPPDATA%\PLUR1BUS` (Windows). Both sides absolutise and lexically normalise the path like Node's `path.resolve` (T11 ruling), so the CLI and the core derive the same file, socket and pipe name.
- **Shape**: a closed top-level object (`additionalProperties: false`) with `$schema` (the schema's `$id`, `https://plur1bus.dev/schema/config/1/config.schema.json`, written into defaults) and `schemaVersion` (`const: 1`, required).
- **Defaults** come from the schema's `default` keywords only — one source. TypeScript produces them by validating `{ $schema, schemaVersion: 1 }` with ajv `useDefaults` (`packages/config-schema/src/index.ts` `defaults()`); Rust by walking the same `default` keywords (`crates/plur1bus-config/src/lib.rs` `fill_defaults`, `defaults()`), and `load()` fills defaults before validating so both sides see one shape. A missing `config.json` is created from defaults by whichever side loads it first (TS `loadConfig`, Rust `load`).
- **Validation**: ajv 8 (draft 2020-12, `strict`, `allErrors`, `ajv-formats`) in TypeScript; the `jsonschema` crate in Rust, against the identical file (`SCHEMA_JSON = include_str!(…/config.schema.json)`).
- **Parity contract**: `packages/config-schema/fixtures/defaults.json` is generated by `pnpm gen` from the TypeScript `defaults()`; the TypeScript test (`test/defaults-fixture.test.ts`) and the Rust test (`crates/plur1bus-config/tests/config.rs`) both assert equality with it. `fixtures/restart-plan-cases.json` does the same for restart plans (§3). A schema change that makes the two languages disagree fails both test suites.
- **Migrations**: `migrate()` applies registered `vN → vN+1` functions (`MIGRATIONS`, empty for version 1). When a migration applies, the TypeScript loader writes the original bytes to `config.json.bak-<fromVersion>` and then writes the migrated file atomically (`packages/core/src/config-load.ts`). The Rust loader does not migrate yet — no migration exists; the supervisor (2a-H3, ruling G1) adds it next to the first `schemaVersion: 2`.
- **Atomic write**: temp file `config.json.tmp-<pid>` with mode `0600`, then `rename` over the original (TS `writeConfigAtomic`, Rust `write_atomic`, which also removes the temp file on failure). A reader never sees a half-written file.

### 2. Namespaces and their classes (schema version 1)

| Key / namespace | Class | Notes |

| `logs.maxBytes`, `logs.keep` | live | Defaults 20 MiB, 5; consumed by 2a-H3 rotation (ruling G1). |

Reserved namespaces carry `x-reserved: "M2 (Dnn)"` and accept any content today, so M2 can fill them without a schema-version bump and a user's early entries survive validation. No `module:<name>` key exists yet (no modules in 2a); the class is implemented and tested in the resolver.

### 2a. Presentation tiers: `x-tier` (D29, 2a-H2)

Every key that carries `x-restart` now also carries `x-tier: basic | advanced`, resolved the same way (`tierOf` in TypeScript, `tier_of` in Rust — `packages/config-schema/src/index.ts`, `crates/plur1bus-config/src/lib.rs`): walk the dotted key from the root through `properties`; the nearest ancestor that declares `x-tier` wins; a key the schema does not describe keeps its deepest described ancestor's tier, and the root default is `advanced` (the conservative choice, mirroring the restart-class resolver exactly). D29's concrete `basic` set is an M3 decision; ruling G16 fixes a **provisional** `basic` set for 2a-H2 so every key has a value today: `agents` (the registry and display names), `embedding.useClass` (the ADR-006 setup question), `providers` and `modelRoles` (model and login). Every other key — `$schema`, `schemaVersion`, every `core.*`/`supervisor.*`/`logs.*` key, `embedding.acceptedNcLicence[At]`, `engine` (and so all 55 pass-through keys under it, §7), `oauth`, `decision` — is `advanced`. Re-tiering later is a presentation change, not an API change: moving a key between `basic` and `advanced` is a minor release, never a `schemaVersion` bump.

- **`filterSchemaByTier(schema, tier)` / `filter_schema_by_tier`** keep a node whole when its own `x-tier` matches the requested tier; an unannotated container (a bare object with no `x-tier` of its own) recurses through `properties`, kept only if at least one child survives, with `properties`/`required` reduced to the surviving keys. This is what `config schema --tier basic|advanced` (Task 11) returns, and what the generated `docs/config.md` mirrors row for row (§7).
- **`filterConfigByTier(config, tier)` / `filter_config_by_tier`** walk an actual configuration value against the same schema-driven decisions, so `config get --tier basic` shows only the basic slice of a real `config.json`, not just the schema.
- **Fixture parity**: `packages/config-schema/fixtures/tier-cases.json` pins the resolver and filter outputs for both languages, the same pattern ADR-013 already used for `restart-plan-cases.json`.
- **`setup` (D29, deferred to 2a-H3, ruling G4)**: the spec's "`setup` asks only `basic`" interactive flow is not built in 2a-H2 — `setup` is still a stub (ADR-012 §8) — but it will consume exactly the `tierOf`/`filterSchemaByTier`/`filterConfigByTier` resolver this ADR now records, so no re-design is needed when it lands.

### 3. Restart classes and the restart plan

- **Classes**: `live` — applied by the process that uses the key, without a restart (log level, budgets, timeouts, the agent registry; from M2 provider profiles and keys); `module:<name>` — restarts that module only; `core` — restarts the core (embedding identity, `stateDir`-like keys, every engine key the engine reads in `createEngine()`).
- **Resolution** (`restartClassOf` in TS, `restart_class_of` in Rust): walk the dotted key from the root through `properties`, or through an object-valued `additionalProperties` for open maps; the **nearest ancestor that declares `x-restart` wins**; a key the schema does not describe keeps the class of its deepest described ancestor, and the default at the root is `core` — the conservative choice. So `agents.bernd.displayName` is `live` (from `agents`), and `engine.recall.softBudgetMs` is `core` (from `engine`; its `additionalProperties` is `true`, not a schema, so the walk stops there).
- **The plan** (`restartPlan` / `restart_plan`) is `{ changed: string[], restart: { live: string[], core: boolean, modules: string[] } }`. `changed` comes from a **recursive tree diff (ruling R10)**: at each level, for every key in the union of both sides, recurse if both values are plain objects, otherwise report the full dotted path if the values differ. Adding or removing an open-map entry is therefore reported once, at the entry (`agents.bernd`), symmetrically. Leaf equality matches `JSON.stringify` equality in both languages; the Rust side compares numbers by value so `1` and `1.0` are equal as in JavaScript (T12 ruling). Parity is asserted by both test suites against `fixtures/restart-plan-cases.json` (seven cases: a live leaf, a core key, adding, removing and renaming an agent, a first entry in an empty reserved map, two classes at once); the numeric-representation case (`400` vs `400.0`, and exact comparison of integers above 2^53) is a Rust-only unit test in `crates/plur1bus-config/tests/config.rs`, since JSON fixtures parsed by JavaScript cannot express the difference.

### 4. The apply sequence

Target sequence (2a-H3, supervisor-owned; ruling G1):

1. **Validate** the resulting whole configuration against the schema; an invalid value is rejected with the reason, the file untouched, the running configuration unchanged.
2. **Preview**: compute the restart plan and show the consequence ("changes `mcp.port` → restarts module mcp"). `config set` applies only after confirmation or `--yes`; `config set --dry-run` prints the plan and changes nothing.
3. **Write atomically** (temp + `rename`; on a migration, a backup `config.json.bak-<schemaVersion>` first).
4. **Emit `config.changed { diff, restartPlan }`.**
5. **Subscribers apply `live` keys** themselves.
6. **Execute the restart plan in dependency order** — modules before the core when both are affected, the core first when modules depend on the new core state — and report the result and its duration.

H1 implements steps 1–3 in the CLI (`crates/plur1bus/src/commands/config.rs` over `plur1bus-config`): `config get [key]` prints the value and its class; `config set <key> <value>` parses `<value>` as JSON and falls back to a literal string (so a JSON-looking string cannot be set as a string — documented behaviour), validates, prints the plan, asks on a TTY or requires `--yes` otherwise (without `--yes` in a non-interactive shell it exits 2 with `applied: false` and the plan), and writes atomically; `--dry-run` prints the plan only; `config schema` prints the schema (2a-H2 adds `--tier` to both, §2a). Steps 4–6 need the supervisor and arrive in 2a-H3 (ruling G1); in H1 and 2a-H2 the CLI's human output says so for core changes ("restarts core: yes (H1: takes effect at the next `plur1bus core run`)").

### 5. One owner

- **2a-H3 (ruling G1)**: the supervisor owns `config.json` and exposes `config.get|set|watch`; core and modules load their configuration from the supervisor at start and subscribe to `config.changed`. Direct file edits are detected by a watcher, validated and treated like a `set`; an invalid edit is rejected with the reason and the running configuration stays the last valid one.
- **H1/2a-H2 (interim, deviation from the spec)**: there is no supervisor, so the CLI is the owner and writes through `crates/plur1bus-config` — the same crate the supervisor will run, so the code moves, it is not rewritten. The core reads the file itself (`packages/core/src/config-load.ts`); it writes only in two cases, both before any other writer could race it at start: creating a missing file from defaults, and persisting a migration (none exist in version 1).

### 6. What "live" means in H1

The class is a property of the key; *applying* a live key is the subscriber's job, and the H1 core has no `config.changed` to subscribe to. What the H1 core actually does (verified in `packages/core/src/core.ts`, `agents.ts`, `rpc/methods.ts`):

- **`agents.*` is applied live**: the agent registry re-reads `config.json` whenever its mtime changes (on every registry access), scaffolds newly added agents (`agents/<id>/SOUL.md`, `USER.md`, `persona-voice.md`, `workspace/`), and on an invalid edit logs once and keeps the last valid configuration.
- **Every other key is read once, at core start**: `core.logLevel`, `core.recall.*`, `core.capture.waitMs` and `core.shutdownBudgetMs` take effect at the next core start in H1 and 2a-H2, although their class is `live`. 2a-H3's `config.changed` subscription (ruling G1) makes them live without changing their class.
- **Engine backlog (for plan 2a-E)**: `core.recall.softBudgetMs` and `core.recall.capChars` are also written into the engine's construction-time config (`recall.softBudgetMs`, `recall.globalInjectMaxChars`), and the engine ignores the per-call `RecallQuery.budget` at `eaaf168f`; until engine PR E5 they are effectively `core` for the engine's share of the work. `core.recall.hardBudgetMs` is harness-side (an `AbortSignal.timeout` per call) and is genuinely per call once the core re-reads configuration.

### 7. Engine keys: pass-through under `engine.*`

- `engine` is an open object (`additionalProperties: true`) of class `core` and, since 2a-H2, tier `advanced` (§2a — nothing under `engine` overrides it, so all engine keys inherit `advanced` through the same nearest-ancestor walk `x-restart` uses): every engine key is reachable as `engine.<key>` and restarts the core, until the engine declares per key whether it is read at construction or live (`readAt: construction|live`, engine PR E5). The engine has **55** configuration keys at `d32771c5` (ruling G6, 2a-H2 — 54 at H1's `eaaf168f`, ruling R22; `chatModels` was added in engine 7.16.4). `docs/config-engine-keys.md`, generated from the pinned engine's plugin manifest by `scripts/gen-engine-keys.mjs` (which asserts the count and, since 2a-H2, prints a `Tier` column — `advanced` on every row), lists each key with its type, default, class, tier and whether the harness owns it. `docs/config.md` (new, 2a-H2, `scripts/gen-docs.mjs`, checked by `pnpm docs:check`) walks the whole config schema in declaration order and renders one table row per `x-tier`-annotated node without recursing into it — so `engine` is a single `advanced` row there, pointing at `docs/config-engine-keys.md`, exactly mirroring what `config schema --tier advanced` returns rather than expanding into all 55 pass-through keys.
- **Harness-owned engine keys** are set by `packages/core/src/engine-config.ts`, the single translation between harness configuration and the engine's key names, *after* the user's `engine.*` values so a user cannot override them (T5 ruling): `baseDbPath` (`<home>/state/lancedb`, or `engine.baseDbPathOverride` — testing/advanced only, the one engine key the schema declares), `autoRecall: false`, `autoCapture: false`, `embedding.provider: "local-transformers"`, `reranker.enabled: true`, `reranker.provider: "local-transformers"`, `recall.softBudgetMs` and `recall.globalInjectMaxChars` (from `core.recall.*`), `recall.decisionTrace.enabled: true`. Model defaults (`intfloat/multilingual-e5-small`, 384 dimensions; `woxpas-ai/bge-reranker-v2-m3-onnx`; cache `<home>/models`) are defaults the user's `engine.embedding.local.*` / `engine.reranker.local.*` override.
- **Naming**: harness keys use harness language (`core.recall.capChars`, not `recall.globalInjectMaxChars`); the translation lives only in `engine-config.ts` until E5 lets it shrink.

## Deviations from the spec, and why

| Spec §6.1 says | H1 does | Reason |
|---|---|---|
| The supervisor owns `config.json`; `config.get|set|watch` over RPC | The CLI owns it through `plur1bus-config`; the core reads the file | No supervisor in H1; the crate is the supervisor's future code (§5). |
| `config.changed` → subscribers apply live keys → supervisor restarts in dependency order | Validate, preview, atomic write only; only `agents.*` is applied live (mtime reload); other keys take effect at the next core start | Steps 4–6 need the supervisor (§4, §6). |
| "each of the 56 engine keys" | 54 keys | Measured at `eaaf168f` (R22); spec and schema description corrected. |

## Consequences

- **Easier:** a user or an agent can ask "what does this change restart?" before applying it (`--dry-run`, or the class shown by `config get`); a module author declares a key's class once, in the schema; unknown or engine keys default to the safe class; both languages compute the same defaults and the same plan, enforced by fixtures; M2 namespaces exist before M2.
- **Harder:** every new key needs a class decision and, for a `module:` key, a module name that matches the manifest; making an engine key live needs an engine change (E5), not a harness change; until 2a-H3, "live" keys other than `agents.*` need a core restart, which the CLI output does not yet state for `live` keys.
- **Revisit when:** E5 lands (derive `engine.*` classes from the engine's `readAt` instead of the blanket `core`); the first `schemaVersion: 2` (add the Rust migration path and its fixture); M3 decides D29's concrete `basic` set (replace the provisional G16 list); 2a-H3 lands (supervisor ownership, `config.changed`, watcher, restart execution, the interactive `setup` flow).

## Alternatives considered

- **One file per module or per process**: rejected by D5 ("one `config.json`"); it also makes a cross-cutting change non-atomic and scatters the restart consequence over several files.
- **TOML or YAML**: rejected; JSON Schema validates JSON natively in both languages, `$schema` gives editor completion, and there is no second parser to keep in step.
- **Environment variables as the primary configuration**: rejected; no schema, no preview, no restart plan. `PLUR1BUS_HOME` is the only environment input, and it selects the file.
- **Restart everything on any change**: rejected by D3.
- **A restart class per leaf only, no inheritance**: rejected; open maps (`agents`, `engine`, reserved namespaces) have no fixed leaves, and a forgotten annotation would silently default to something other than the enclosing namespace's class.
- **A flatten-and-compare diff** (the plan's first version) and a two-pass heuristic: rejected by R10 — the first failed its own test, the second reported additions and removals asymmetrically.
