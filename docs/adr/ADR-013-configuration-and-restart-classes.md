# ADR-013: Configuration and restart classes

**Status:** Accepted (2026-09-24, owner decisions D3 and D5; reserved namespaces per D15, D16, D18; implementation record of plan H1 added 2026-09-25) · **Date:** 2026-09-24 / 2026-09-25 · **Deciders:** Christian (owner) · **Inputs:** `docs/superpowers/specs/2026-09-24-m1b-2a-core-daemon-cli-design.md` §2 (D3, D5, D15, D16, D18), §6.1 · `docs/superpowers/plans/2026-09-24-m1b-2a-h1-harness-foundation.md` Tasks 3, 12, 13, 16 · the H1 implementation ledger (rulings R10, R22, the T5, T11 and T12 rulings, the H1 interim of a CLI-owned `config.json`) · Source of record: this repository @ `93f11ca` (`feat/m1b-2a-h1`); engine @ `eaaf168f`. Companion: ADR-012 (process model, RPC), `docs/config-engine-keys.md` (generated).

## Context

D3: "a config change restarts only what it must" and "individual modules restart without restarting the whole". D5: one state root per user (`~/.plur1bus/`, `%LOCALAPPDATA%\PLUR1BUS`, overridable by `PLUR1BUS_HOME`) and **one** `config.json` with `$schema` and `schemaVersion`. Under process model B (ADR-012) the configuration is read by a Rust supervisor/CLI and a TypeScript core, so both languages must agree on the schema, the defaults and the consequence of every change. The engine brings its own configuration (54 keys at `eaaf168f`, measured by `scripts/gen-engine-keys.mjs`), most of which it reads once, at `createEngine()`; the harness cannot make such a key live without an engine change.

## Decision

**One `config.json` per installation, validated by one JSON Schema (`packages/config-schema/schema/config.schema.json`) that both languages load; every key carries a restart class `x-restart: live | module:<name> | core`, resolved by the nearest ancestor that declares one; a change is validated, previewed as a restart plan computed by a recursive tree diff, applied atomically, and then — once the supervisor exists — announced as `config.changed` and executed in dependency order. There is exactly one writer of the file: in H1 the CLI through `crates/plur1bus-config`, from H2 the supervisor.**

### 1. The file

- **Location**: `<home>/config.json`, where `<home>` is `--home`, else `PLUR1BUS_HOME`, else `~/.plur1bus` (POSIX) or `%LOCALAPPDATA%\PLUR1BUS` (Windows). Both sides absolutise and lexically normalise the path like Node's `path.resolve` (T11 ruling), so the CLI and the core derive the same file, socket and pipe name.
- **Shape**: a closed top-level object (`additionalProperties: false`) with `$schema` (the schema's `$id`, `https://plur1bus.dev/schema/config/1/config.schema.json`, written into defaults) and `schemaVersion` (`const: 1`, required).
- **Defaults** come from the schema's `default` keywords only — one source. TypeScript produces them by validating `{ $schema, schemaVersion: 1 }` with ajv `useDefaults` (`packages/config-schema/src/index.ts` `defaults()`); Rust by walking the same `default` keywords (`crates/plur1bus-config/src/lib.rs` `fill_defaults`, `defaults()`), and `load()` fills defaults before validating so both sides see one shape. A missing `config.json` is created from defaults by whichever side loads it first (TS `loadConfig`, Rust `load`).
- **Validation**: ajv 8 (draft 2020-12, `strict`, `allErrors`, `ajv-formats`) in TypeScript; the `jsonschema` crate in Rust, against the identical file (`SCHEMA_JSON = include_str!(…/config.schema.json)`).
- **Parity contract**: `packages/config-schema/fixtures/defaults.json` is generated by `pnpm gen` from the TypeScript `defaults()`; the TypeScript test (`test/defaults-fixture.test.ts`) and the Rust test (`crates/plur1bus-config/tests/config.rs`) both assert equality with it. `fixtures/restart-plan-cases.json` does the same for restart plans (§3). A schema change that makes the two languages disagree fails both test suites.
- **Migrations**: `migrate()` applies registered `vN → vN+1` functions (`MIGRATIONS`, empty for version 1). When a migration applies, the TypeScript loader writes the original bytes to `config.json.bak-<fromVersion>` and then writes the migrated file atomically (`packages/core/src/config-load.ts`). The Rust loader does not migrate yet — no migration exists; the supervisor (H2) adds it next to the first `schemaVersion: 2`.
- **Atomic write**: temp file `config.json.tmp-<pid>` with mode `0600`, then `rename` over the original (TS `writeConfigAtomic`, Rust `write_atomic`, which also removes the temp file on failure). A reader never sees a half-written file.

### 2. Namespaces and their classes (schema version 1)

| Key / namespace | Class | Notes |
|---|---|---|
| `$schema` | live | Editor hint only. |
| `schemaVersion` | core | `const 1`. |
| `core.logLevel` | live | `debug`/`info`/`warn`/`error`, default `info`. |
| `core.recall.softBudgetMs`, `hardBudgetMs`, `capChars` | live | Defaults 400, 600, 17 000. See §6 for what "live" means in H1. |
| `core.capture.waitMs` | live | Default 60 000 (ruling R19, ADR-012 §7). |
| `core.shutdownBudgetMs` | live | Default 30 000. |
| `supervisor.graceMs`, `supervisor.healthIntervalMs` | live | Defaults 60 000, 5 000; consumed by the H2 supervisor. |
| `logs.maxBytes`, `logs.keep` | live | Defaults 20 MiB, 5; consumed by H2 rotation. |
| `agents.<agentId>` | live | Open map; ids match `^[a-z0-9][a-z0-9_-]{0,63}$`; entries `{ createdAt?, displayName? }`. The agent registry (D13, agent ≡ persona). |
| `embedding.useClass`, `acceptedNcLicence`, `acceptedNcLicenceAt` | core | Embedding identity (ADR-006). |
| `engine.*` | core | Engine pass-through, §7. |
| `providers.*` | live | Reserved, M2 (D15), open object. |
| `oauth.*` | live | Reserved, M2 (D16), open object. |
| `decision.*` | live | Reserved, M2 (D18), open object. |
| `modelRoles.<role>` | live | Reserved, M2 (D15, D18); role names restricted to `chat`, `reasoning`, `capture`, `dream`, `embedding`, `rerank`, `decision`; values are strings. |

Reserved namespaces carry `x-reserved: "M2 (Dnn)"` and accept any content today, so M2 can fill them without a schema-version bump and a user's early entries survive validation. No `module:<name>` key exists yet (no modules in 2a); the class is implemented and tested in the resolver.

### 3. Restart classes and the restart plan

- **Classes**: `live` — applied by the process that uses the key, without a restart (log level, budgets, timeouts, the agent registry; from M2 provider profiles and keys); `module:<name>` — restarts that module only; `core` — restarts the core (embedding identity, `stateDir`-like keys, every engine key the engine reads in `createEngine()`).
- **Resolution** (`restartClassOf` in TS, `restart_class_of` in Rust): walk the dotted key from the root through `properties`, or through an object-valued `additionalProperties` for open maps; the **nearest ancestor that declares `x-restart` wins**; a key the schema does not describe keeps the class of its deepest described ancestor, and the default at the root is `core` — the conservative choice. So `agents.bernd.displayName` is `live` (from `agents`), and `engine.recall.softBudgetMs` is `core` (from `engine`; its `additionalProperties` is `true`, not a schema, so the walk stops there).
- **The plan** (`restartPlan` / `restart_plan`) is `{ changed: string[], restart: { live: string[], core: boolean, modules: string[] } }`. `changed` comes from a **recursive tree diff (ruling R10)**: at each level, for every key in the union of both sides, recurse if both values are plain objects, otherwise report the full dotted path if the values differ. Adding or removing an open-map entry is therefore reported once, at the entry (`agents.bernd`), symmetrically. Leaf equality matches `JSON.stringify` equality in both languages; the Rust side compares numbers by value so `1` and `1.0` are equal as in JavaScript (T12 ruling). Parity is asserted by both test suites against `fixtures/restart-plan-cases.json` (seven cases: a live leaf, a core key, adding, removing and renaming an agent, a first entry in an empty reserved map, two classes at once); the numeric-representation case (`400` vs `400.0`, and exact comparison of integers above 2^53) is a Rust-only unit test in `crates/plur1bus-config/tests/config.rs`, since JSON fixtures parsed by JavaScript cannot express the difference.

### 4. The apply sequence

Target sequence (H2, supervisor-owned):

1. **Validate** the resulting whole configuration against the schema; an invalid value is rejected with the reason, the file untouched, the running configuration unchanged.
2. **Preview**: compute the restart plan and show the consequence ("changes `mcp.port` → restarts module mcp"). `config set` applies only after confirmation or `--yes`; `config set --dry-run` prints the plan and changes nothing.
3. **Write atomically** (temp + `rename`; on a migration, a backup `config.json.bak-<schemaVersion>` first).
4. **Emit `config.changed { diff, restartPlan }`.**
5. **Subscribers apply `live` keys** themselves.
6. **Execute the restart plan in dependency order** — modules before the core when both are affected, the core first when modules depend on the new core state — and report the result and its duration.

H1 implements steps 1–3 in the CLI (`crates/plur1bus/src/commands/config.rs` over `plur1bus-config`): `config get [key]` prints the value and its class; `config set <key> <value>` parses `<value>` as JSON and falls back to a literal string (so a JSON-looking string cannot be set as a string — documented behaviour), validates, prints the plan, asks on a TTY or requires `--yes` otherwise (without `--yes` in a non-interactive shell it exits 2 with `applied: false` and the plan), and writes atomically; `--dry-run` prints the plan only; `config schema` prints the schema. Steps 4–6 need the supervisor and arrive in H2; in H1 the CLI's human output says so for core changes ("restarts core: yes (H1: takes effect at the next `plur1bus core run`)").

### 5. One owner

- **H2**: the supervisor owns `config.json` and exposes `config.get|set|watch`; core and modules load their configuration from the supervisor at start and subscribe to `config.changed`. Direct file edits are detected by a watcher, validated and treated like a `set`; an invalid edit is rejected with the reason and the running configuration stays the last valid one.
- **H1 (interim, deviation from the spec)**: there is no supervisor, so the CLI is the owner and writes through `crates/plur1bus-config` — the same crate the supervisor will run, so the code moves, it is not rewritten. The core reads the file itself (`packages/core/src/config-load.ts`); it writes only in two cases, both before any other writer could race it at start: creating a missing file from defaults, and persisting a migration (none exist in version 1).

### 6. What "live" means in H1

The class is a property of the key; *applying* a live key is the subscriber's job, and the H1 core has no `config.changed` to subscribe to. What the H1 core actually does (verified in `packages/core/src/core.ts`, `agents.ts`, `rpc/methods.ts`):

- **`agents.*` is applied live**: the agent registry re-reads `config.json` whenever its mtime changes (on every registry access), scaffolds newly added agents (`agents/<id>/SOUL.md`, `USER.md`, `persona-voice.md`, `workspace/`), and on an invalid edit logs once and keeps the last valid configuration.
- **Every other key is read once, at core start**: `core.logLevel`, `core.recall.*`, `core.capture.waitMs` and `core.shutdownBudgetMs` take effect at the next core start in H1, although their class is `live`. H2's `config.changed` subscription makes them live without changing their class.
- **Engine backlog (for plan 2a-E)**: `core.recall.softBudgetMs` and `core.recall.capChars` are also written into the engine's construction-time config (`recall.softBudgetMs`, `recall.globalInjectMaxChars`), and the engine ignores the per-call `RecallQuery.budget` at `eaaf168f`; until engine PR E5 they are effectively `core` for the engine's share of the work. `core.recall.hardBudgetMs` is harness-side (an `AbortSignal.timeout` per call) and is genuinely per call once the core re-reads configuration.

### 7. Engine keys: pass-through under `engine.*`

- `engine` is an open object (`additionalProperties: true`) of class `core`: every engine key is reachable as `engine.<key>` and restarts the core, until the engine declares per key whether it is read at construction or live (`readAt: construction|live`, engine PR E5). The engine has **54** configuration keys at `eaaf168f` (ruling R22; earlier documents said 56). `docs/config-engine-keys.md`, generated from the pinned engine's plugin manifest by `scripts/gen-engine-keys.mjs` (which asserts the count), lists each key with its type, default, class and whether the harness owns it.
- **Harness-owned engine keys** are set by `packages/core/src/engine-config.ts`, the single translation between harness configuration and the engine's key names, *after* the user's `engine.*` values so a user cannot override them (T5 ruling): `baseDbPath` (`<home>/state/lancedb`, or `engine.baseDbPathOverride` — testing/advanced only, the one engine key the schema declares), `autoRecall: false`, `autoCapture: false`, `embedding.provider: "local-transformers"`, `reranker.enabled: true`, `reranker.provider: "local-transformers"`, `recall.softBudgetMs` and `recall.globalInjectMaxChars` (from `core.recall.*`), `recall.decisionTrace.enabled: true`. Model defaults (`intfloat/multilingual-e5-small`, 384 dimensions; `woxpas-ai/bge-reranker-v2-m3-onnx`; cache `<home>/models`) are defaults the user's `engine.embedding.local.*` / `engine.reranker.local.*` override.
- **Naming**: harness keys use harness language (`core.recall.capChars`, not `recall.globalInjectMaxChars`); the translation lives only in `engine-config.ts` until E5 lets it shrink.

## Deviations from the spec, and why

| Spec §6.1 says | H1 does | Reason |
|---|---|---|
| The supervisor owns `config.json`; `config.get|set|watch` over RPC | The CLI owns it through `plur1bus-config`; the core reads the file | No supervisor in H1; the crate is the supervisor's future code (§5). |
| `config.changed` → subscribers apply live keys → supervisor restarts in dependency order | Validate, preview, atomic write only; only `agents.*` is applied live (mtime reload); other keys take effect at the next core start | Steps 4–6 need the supervisor (§4, §6). |
| "each of the 56 engine keys" | 54 keys | Measured at `eaaf168f` (R22); spec and schema description corrected. |

## Consequences

- **Easier:** a user or an agent can ask "what does this change restart?" before applying it (`--dry-run`, or the class shown by `config get`); a module author declares a key's class once, in the schema; unknown or engine keys default to the safe class; both languages compute the same defaults and the same plan, enforced by fixtures; M2 namespaces exist before M2.
- **Harder:** every new key needs a class decision and, for a `module:` key, a module name that matches the manifest; making an engine key live needs an engine change (E5), not a harness change; until H2, "live" keys other than `agents.*` need a core restart, which the CLI output does not yet state for `live` keys.
- **Revisit when:** E5 lands (derive `engine.*` classes from the engine's `readAt` instead of the blanket `core`); the first `schemaVersion: 2` (add the Rust migration path and its fixture); H2 lands (supervisor ownership, `config.changed`, watcher, restart execution).

## Alternatives considered

- **One file per module or per process**: rejected by D5 ("one `config.json`"); it also makes a cross-cutting change non-atomic and scatters the restart consequence over several files.
- **TOML or YAML**: rejected; JSON Schema validates JSON natively in both languages, `$schema` gives editor completion, and there is no second parser to keep in step.
- **Environment variables as the primary configuration**: rejected; no schema, no preview, no restart plan. `PLUR1BUS_HOME` is the only environment input, and it selects the file.
- **Restart everything on any change**: rejected by D3.
- **A restart class per leaf only, no inheritance**: rejected; open maps (`agents`, `engine`, reserved namespaces) have no fixed leaves, and a forgotten annotation would silently default to something other than the enclosing namespace's class.
- **A flatten-and-compare diff** (the plan's first version) and a two-pass heuristic: rejected by R10 — the first failed its own test, the second reported additions and removals asymmetrically.
