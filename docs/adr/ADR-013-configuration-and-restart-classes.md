## Context

D3: "a config change restarts only what it must" and "individual modules restart without restarting the whole". D5: one state root per user (`~/.plur1bus/`, `%LOCALAPPDATA%\PLUR1BUS`, overridable by `PLUR1BUS_HOME`) and **one** `config.json` with `$schema` and `schemaVersion`. Under process model B (ADR-012) the configuration is read by a Rust supervisor/CLI and a TypeScript core, so both languages must agree on the schema, the defaults and the consequence of every change. The engine brings its own configuration (55 keys at `d32771c5` — 54 at H1's `eaaf168f`, plus `chatModels` added in engine 7.16.4, ruling G6 — measured by `scripts/gen-engine-keys.mjs`), most of which it reads once, at `createEngine()`; the harness cannot make such a key live without an engine change. D29 (2026-09-25) additionally asks that `setup` offer a `basic` question set before the full schema; that interactive flow is 2a-H3b work (ruling G4), but every key needs a tier value now so the resolver and the CLI can exist ahead of it.

## Decision

**One `config.json` per installation, validated by one JSON Schema (`packages/config-schema/schema/config.schema.json`) that both languages load; every key carries a restart class `x-restart: live | module:<name> | core` and, since 2a-H2, a presentation tier `x-tier: basic | advanced` (D29), both resolved by the nearest ancestor that declares one; a change is validated, previewed as a restart plan computed by a recursive tree diff, applied atomically, and — since 2a-H3b-a — announced as `config.changed` and executed in dependency order by the process that now owns the file. There is exactly one writer of the file: in H1 through 2a-H3a the CLI through `crates/plur1bus-config`; since 2a-H3b-a, the supervisor (§5, §8).**

### 1. The file

- **Location**: `<home>/config.json`, where `<home>` is `--home`, else `PLUR1BUS_HOME`, else `~/.plur1bus` (POSIX) or `%LOCALAPPDATA%\PLUR1BUS` (Windows). Both sides absolutise and lexically normalise the path like Node's `path.resolve` (T11 ruling), so the CLI and the core derive the same file, socket and pipe name.
- **Shape**: a closed top-level object (`additionalProperties: false`) with `$schema` (the schema's `$id`, `https://plur1bus.dev/schema/config/1/config.schema.json`, written into defaults) and `schemaVersion` (`const: 1`, required).
- **Defaults** come from the schema's `default` keywords only — one source. TypeScript produces them by validating `{ $schema, schemaVersion: 1 }` with ajv `useDefaults` (`packages/config-schema/src/index.ts` `defaults()`); Rust by walking the same `default` keywords (`crates/plur1bus-config/src/lib.rs` `fill_defaults`, `defaults()`), and `load()` fills defaults before validating so both sides see one shape. A missing `config.json` is created from defaults by whichever side loads it first (TS `loadConfig`, Rust `load`).
- **Validation**: ajv 8 (draft 2020-12, `strict`, `allErrors`, `ajv-formats`) in TypeScript; the `jsonschema` crate in Rust, against the identical file (`SCHEMA_JSON = include_str!(…/config.schema.json)`).
- **Parity contract**: `packages/config-schema/fixtures/defaults.json` is generated by `pnpm gen` from the TypeScript `defaults()`; the TypeScript test (`test/defaults-fixture.test.ts`) and the Rust test (`crates/plur1bus-config/tests/config.rs`) both assert equality with it. `fixtures/restart-plan-cases.json` does the same for restart plans (§3). A schema change that makes the two languages disagree fails both test suites.
- **Migrations**: `migrate()` applies registered `vN → vN+1` functions (`MIGRATIONS`, empty for version 1). When a migration applies, the TypeScript loader writes the original bytes to `config.json.bak-<fromVersion>` and then writes the migrated file atomically (`packages/core/src/config-load.ts`). The Rust loader does not migrate yet — no migration exists; the supervisor (2a-H3b, ruling G1) adds it next to the first `schemaVersion: 2`.
- **Atomic write**: temp file `config.json.tmp-<pid>` with mode `0600`, then `rename` over the original (TS `writeConfigAtomic`, Rust `write_atomic`, which also removes the temp file on failure). A reader never sees a half-written file.

### 2a. Presentation tiers: `x-tier` (D29, 2a-H2)

Every key that carries `x-restart` now also carries `x-tier: basic | advanced`, resolved the same way (`tierOf` in TypeScript, `tier_of` in Rust — `packages/config-schema/src/index.ts`, `crates/plur1bus-config/src/lib.rs`): walk the dotted key from the root through `properties`; the nearest ancestor that declares `x-tier` wins; a key the schema does not describe keeps its deepest described ancestor's tier, and the root default is `advanced` (the conservative choice, mirroring the restart-class resolver exactly). D29's concrete `basic` set is an M3 decision; ruling G16 fixes a **provisional** `basic` set for 2a-H2 so every key has a value today: `agents` (the registry and display names), `embedding.useClass` (the ADR-006 setup question), `providers` and `modelRoles` (model and login). Every other key — `$schema`, `schemaVersion`, every `core.*`/`supervisor.*`/`logs.*` key, `embedding.acceptedNcLicence[At]`, `engine` (and so all 55 pass-through keys under it, §7), `oauth`, `decision` — is `advanced`. Re-tiering later is a presentation change, not an API change: moving a key between `basic` and `advanced` is a minor release, never a `schemaVersion` bump.

- **`filterSchemaByTier(schema, tier)` / `filter_schema_by_tier`** keep a node whole when its own `x-tier` matches the requested tier; an unannotated container (a bare object with no `x-tier` of its own) recurses through `properties`, kept only if at least one child survives, with `properties`/`required` reduced to the surviving keys. This is what `config schema --tier basic|advanced` (Task 11) returns, and what the generated `docs/config.md` mirrors row for row (§7).
- **`filterConfigByTier(config, tier)` / `filter_config_by_tier`** walk an actual configuration value against the same schema-driven decisions, so `config get --tier basic` shows only the basic slice of a real `config.json`, not just the schema.
- **Fixture parity**: `packages/config-schema/fixtures/tier-cases.json` pins the resolver and filter outputs for both languages, the same pattern ADR-013 already used for `restart-plan-cases.json`.
- **`setup` (D29, closed in 2a-H3b-b, ruling HB11).** The spec's "`setup` asks only `basic`" interactive flow is built exactly on the resolver this ADR already recorded: `crates/plur1bus/src/install/setup.rs`'s `basic_tier_keys` walks a schema already run through `filter_schema_by_tier(schema, Tier::Basic)` and returns its leaf keys, and `setup_asks_only_basic_tier_questions` asserts every one of them has a prompt in `PROMPTS`. At this pin that is exactly two keys — `agents` (the first agent's name) and `embedding.useClass` (the ADR-006 use-class question) — matching G16's provisional `basic` set below unchanged.

### 3. Restart classes and the restart plan

- **Classes**: `live` — applied by the process that uses the key, without a restart (log level, budgets, timeouts, the agent registry; from M2 provider profiles and keys); `module:<name>` — restarts that module only; `core` — restarts the core (embedding identity, `stateDir`-like keys, every engine key the engine reads in `createEngine()`).
- **Resolution** (`restartClassOf` in TS, `restart_class_of` in Rust): walk the dotted key from the root through `properties`, or through an object-valued `additionalProperties` for open maps; the **nearest ancestor that declares `x-restart` wins**; a key the schema does not describe keeps the class of its deepest described ancestor, and the default at the root is `core` — the conservative choice. So `agents.bernd.displayName` is `live` (from `agents`), and `engine.recall.softBudgetMs` is `core` (from `engine`; its `additionalProperties` is `true`, not a schema, so the walk stops there).
- **The plan** (`restartPlan` / `restart_plan`) is `{ changed: string[], restart: { live: string[], core: boolean, modules: string[] } }`. `changed` comes from a **recursive tree diff (ruling R10)**: at each level, for every key in the union of both sides, recurse if both values are plain objects, otherwise report the full dotted path if the values differ. Adding or removing an open-map entry is therefore reported once, at the entry (`agents.bernd`), symmetrically. Leaf equality matches `JSON.stringify` equality in both languages; the Rust side compares numbers by value so `1` and `1.0` are equal as in JavaScript (T12 ruling). Parity is asserted by both test suites against `fixtures/restart-plan-cases.json` (seven cases: a live leaf, a core key, adding, removing and renaming an agent, a first entry in an empty reserved map, two classes at once); the numeric-representation case (`400` vs `400.0`, and exact comparison of integers above 2^53) is a Rust-only unit test in `crates/plur1bus-config/tests/config.rs`, since JSON fixtures parsed by JavaScript cannot express the difference.

### 4. The apply sequence

Sequence (all six steps closed in 2a-H3b-a; §8 records the implementation):

1. **Validate** the resulting whole configuration against the schema; an invalid value is rejected with the reason, the file untouched, the running configuration unchanged.
2. **Preview**: compute the restart plan and show the consequence ("changes `mcp.port` → restarts module mcp"). `config set` applies only after confirmation or `--yes`; `config set --dry-run` prints the plan and changes nothing.
3. **Write atomically** (temp + `rename`; on a migration, a backup `config.json.bak-<schemaVersion>` first).
4. **Emit `config.changed { diff, restartPlan }`.**
5. **Subscribers apply `live` keys** themselves.
6. **Execute the restart plan in dependency order** — modules before the core when both are affected, the core first when modules depend on the new core state — and report the result and its duration.

H1 implemented steps 1–3 in the CLI (`crates/plur1bus/src/commands/config.rs` over `plur1bus-config`): `config get [key]` prints the value and its class; `config set <key> <value>` parses `<value>` as JSON and falls back to a literal string (so a JSON-looking string cannot be set as a string — documented behaviour), validates, prints the plan, asks on a TTY or requires `--yes` otherwise (without `--yes` in a non-interactive shell it exits 2 with `applied: false` and the plan), and writes atomically; `--dry-run` prints the plan only; `config schema` prints the schema (2a-H2 adds `--tier` to both, §2a). Steps 4–6 needed the supervisor and arrived in 2a-H3b-a (ruling G1, §8): `config set`/a hand-edit-applying watcher poll now runs all six steps for real, and the CLI (`config get|set`) is a thin client of them when a supervisor answers (§5).

### 5. One owner

- **2a-H3b-a (ruling G1), landed**: the supervisor owns `config.json` and exposes `config.get|set|watch`; the core and every module load their configuration from the supervisor at start (over a `config.watch` connection, `@plur1bus/module-api`'s `watchSupervisorConfig`, shared by the core and the module runtime) and stay subscribed to `config.changed`. Direct file edits are detected by the polling watcher (§2's `modules.<name>` row, §8), validated and treated like a `set`; an invalid edit is rejected with the reason (backed up to `config.json.rejected-<ms>`) and the running configuration stays the last valid one (B18, ADR-012 §10.12). A core or module that cannot reach any supervisor — none installed, or an older one that does not yet serve `config.set` (ADR-012 §10.12's B6 CLI-routing fallback covers the CLI's own equivalent case) — falls back to reading `config.json` directly, logs that it did, and keeps re-watching with backoff. **That fallback never writes the file (final review M4)**: a supervised core reads it with `readConfigFile` (the defaults when it is missing, a migration applied in memory only), not `loadConfig`, which creates or rewrites it. The same holds for the CLI's readers: `module list`, `admin obsidian *` (which asks the supervisor for the running configuration first, so it sees the last valid one over a rejected hand edit), `memory *` and `dreams *` read through `plur1bus_config::read`, which returns the defaults for a missing file without creating it. Only the supervisor, and the commands that write the configuration (`config set`, `agent create|remove`, directly only when no supervisor answers), write `config.json`; `config get` and `agent list` offline still create the defaults under `--home`, the H1 behaviour kept for compatibility (`tests/cli.rs` asserts it for `config get`).
- **H1 through 2a-H3a (interim, deviation from the spec while it lasted)**: there was no supervisor, so the CLI was the owner and wrote through `crates/plur1bus-config` — the same crate the supervisor now runs, so the code moved, it was not rewritten. The core read the file itself (`packages/core/src/config-load.ts`); it wrote only in two cases, both before any other writer could race it at start: creating a missing file from defaults, and persisting a migration (none exist in version 1). `packages/core/src/config-load.ts`'s file-reading path still exists and is exercised today, but only as the fallback described above, not as the core's primary source.

### 6. What "live" meant before 2a-H3b-a, and what it means now (§8 records the mechanism)

The class is a property of the key; *applying* a live key is the subscriber's job. Through 2a-H3a the core had no `config.changed` to subscribe to, so most `live` keys were live only in name:

- **`agents.*` was already applied live**: the agent registry re-read `config.json` whenever its mtime changed (on every registry access), scaffolded newly added agents (`agents/<id>/SOUL.md`, `USER.md`, `persona-voice.md`, `workspace/`), and on an invalid edit logged once and kept the last valid configuration. This mtime-poll path still exists and still runs for an unsupervised core, or a supervised one that fell back to the file (§5); a supervised core instead applies agent changes through `config.watch`.
- **Every other key was read once, at core start**: `core.logLevel`, `core.recall.*`, `core.capture.waitMs` and `core.shutdownBudgetMs` took effect only at the next core start through 2a-H3a, although their class was already `live`. **Closed in 2a-H3b-a** (§8): `core.logLevel` (`setLevel`), `logs.maxBytes`/`logs.keep` (`setRotation`) and `supervisor.graceMs` (`OrphanWatch.setGraceMs`) now apply from the config source's live-applier list the moment `config.watch` delivers a change, no restart needed, on both the core and — for its own copies of `logs.*` and `supervisor.*` — the supervisor. `core.recall.*` and `core.capture.waitMs` are read per call/per capture already (§7 below), so nothing further was needed for them once the core's own configuration snapshot is itself live.
- **Engine backlog, closed in 2a-H3b-b (ruling HB3).** `core.recall.softBudgetMs` and `core.recall.capChars` are also written into the engine's construction-time config (`recall.softBudgetMs`, `recall.globalInjectMaxChars`); engine PR E5 (the pinned engine is now `b0e149b8`, contract 1.9.0) ships a host-neutral `engine-config.schema.json` with a `readAt: "construction" | "live"` flag per top-level key, and `recall.*` stays `"construction"` there — the engine still ignores the per-call `RecallQuery.budget`, confirmed again at this pin (Task 1 of 2a-H3b-b, `docs/config-engine-keys.md`). Rather than leave the class saying `live` while the engine behaves as `core`, §2's table now reclassifies both keys `core` outright: a `config set` of either genuinely restarts the core, matching what was already true of the engine's own reading of them. `core.recall.hardBudgetMs` is harness-side (an `AbortSignal.timeout` per call) and stays `live`, genuinely per call.

### 7. Engine keys: pass-through under `engine.*`

- `engine` is an open object (`additionalProperties: true`) of class `core` and, since 2a-H2, tier `advanced` (§2a — nothing under `engine` overrides it, so all engine keys inherit `advanced` through the same nearest-ancestor walk `x-restart` uses): every engine key is reachable as `engine.<key>` and restarts the core. **Engine PR E5 (2a-H3b-b, pinned engine `b0e149b8`, contract 1.9.0) ships the `readAt: "construction" | "live"` flag per key this row used to wait for**, closing the "Revisit when: E5 lands" item below: `scripts/gen-engine-keys.mjs` now reads every key's `readAt` from the engine's own host-neutral `engine-config.schema.json` and throws if one is ever `"live"` instead of silently keeping it `core` — the mechanism the open item asked for exists, even though at this pin every one of the 55 keys is still `readAt: "construction"`, so every `engine.<key>` remains class `core` in practice; the day the engine marks one `"live"`, this generator fails the build rather than misclassifying it. The engine has **55** configuration keys at `b0e149b8` — unchanged in count since `72b6697f`/contract 1.8.0 (ruling G6, 2a-H2, established the count at 54→55 when `chatModels` was added; E5 added no further keys). `docs/config-engine-keys.md`, generated from the pinned engine's own `engine-config.schema.json` by `scripts/gen-engine-keys.mjs` (which asserts the count and, since 2a-H2, prints a `Tier` column — `advanced` on every row), lists each key with its type, default, class, tier and whether the harness owns it. `docs/config.md` (new, 2a-H2, `scripts/gen-docs.mjs`, checked by `pnpm docs:check`) walks the whole config schema in declaration order and renders one table row per `x-tier`-annotated node without recursing into it — so `engine` is a single `advanced` row there, pointing at `docs/config-engine-keys.md`, exactly mirroring what `config schema --tier advanced` returns rather than expanding into all 55 pass-through keys.
- **Harness-owned engine keys** are set by `packages/core/src/engine-config.ts`, the single translation between harness configuration and the engine's key names, *after* the user's `engine.*` values so a user cannot override them (T5 ruling): `baseDbPath` (`<home>/state/lancedb`, or `engine.baseDbPathOverride` — testing/advanced only, the one engine key the schema declares), `autoRecall: false`, `autoCapture: false`, `embedding.provider: "local-transformers"`, `reranker.enabled: true`, `reranker.provider: "local-transformers"`, `recall.softBudgetMs` and `recall.globalInjectMaxChars` (from `core.recall.*`), `recall.decisionTrace.enabled: true`. Model defaults (`intfloat/multilingual-e5-small`, 384 dimensions; `woxpas-ai/bge-reranker-v2-m3-onnx`; cache `<home>/models`) are defaults the user's `engine.embedding.local.*` / `engine.reranker.local.*` override.
- **Naming**: harness keys use harness language (`core.recall.capChars`, not `recall.globalInjectMaxChars`); the translation lives only in `engine-config.ts` until E5 lets it shrink.

### 8. Implementation record (2a-H3b-a): the supervisor becomes the owner

Plan 2a-H3b-a (this repository @ `feat/m1b-2a-h3b-a`, `1ba26c5` at this record; engine @ `72b6697f` since Task 1 (was `d0842424`), contract 1.8.0) is the plan that builds §4's steps 4–6 and moves ownership per §5. ADR-012 §10.12 records the RPC-contract and process-model side (`config.get|set|watch`, `x-server: "supervisor"`, RPC 1.3.0, no version bump); this section records the configuration-specific mechanics.

**The watcher polls; it never `notify`s (ruling B4).** `supervisor::config::poll_file` runs on a plain timer, ticking every `1000 ms × scale` (`spawn_watcher`/`spawn_guarded`), keyed on mtime+length first and a SHA-256 comparison only on a mismatch — the supervisor's dependency budget (ADR-012's global constraints: no `notify`, no async runtime) rules out a filesystem-event watcher. The watcher never rewrites the file itself; every write, including the atomic rename, comes from `config.set` or a direct hand edit.

**`revision` (ruling B5).** `plur1bus-config::revision(&Config)` is a content hash, independent of key order (`revision_is_independent_of_key_order`), that both `config.get`'s result and every `config.watch` snapshot/push carry. `config.set { ifRevision }` compares against it; a stale revision is `E_CONFLICT` with `ids.currentRevision` (the pre-existing §1 `d17` ruling's shape, now actually reachable through a live RPC round trip rather than only a CLI-internal race). This is what lets a client preview a plan against a known revision and have its apply refused — never silently overwritten — if the file moved under it between preview and apply.

**Reply ordering and subscription queues.** Every reply on a connection that has subscribed to `config.watch` (or, since modules, `module.watch`) goes through that subscription's own queue, never straight to the socket, so a reply can never overtake a notification queued ahead of it or be overtaken by one queued behind it. Each subscriber gets its own bounded queue and writer thread (`supervisor::subscribers`); a queue that fills (a client that stops reading) drops that subscriber and closes its connection, logged — the concrete consequence of the standing "supervisor writes to a client have no deadline" limit, recorded in ADR-012 §10.12 alongside why its regression test is unix-only.

**A hand edit is applied like a `set` (ruling B18, ADR-012 §10.12 for the fatal/re-arm semantics in full).** The watcher validates every file it reads; a valid change goes through the same live-apply/restart-plan path a `config.set` would, and an invalid one is rejected with the file backed up and the running configuration kept. §5 already covers the direction that matters most for restart classes: an edit that changes a `module:<name>` key restarts only that module (criterion 4), never the core, exactly like a `config.set` of the same key.

**`config.set` never overwrites an unseen hand edit.** `set` re-polls the file under the config lock before applying: a pending valid edit it had not yet noticed is installed first (so a stale `ifRevision` correctly conflicts, and a revision-less `set` builds on top of it rather than discarding it), and a pending invalid edit is recorded as rejected before the new value is even considered. This closes a race that would otherwise let a `config.set` clobber a file someone had just hand-edited a moment earlier, between the watcher's last poll and the `set` call.

**Live appliers, one per key, on both processes that can hold a live configuration.** The core's `config-source.ts` and the supervisor's own `config.rs` both maintain a short table of "this key changed → call this" appliers (§6 above lists the core's own); each accepted change logs `configuration changed` at info and `live keys applied` at debug. A key with no live applier registered anywhere still reaches `restartPlan`'s `live` bucket correctly (it is simply a no-op live key, same as before this plan, for example the reserved namespaces) — the applier table is additive machinery on top of the restart-class resolver, not a replacement for it.

**CLI routing and its deadline (rulings B6, H3B-R22, ADR-012 §10.12 for the full rule).** `config get|set` route to the supervisor when one answers and lists `config.set` in its handshake capabilities, and fall back to writing the file directly otherwise — including against an older, partially-upgraded supervisor that does not yet serve `config.set`, so an upgrade of the CLI ahead of the supervisor never silently no-ops a `config set`. The CLI's own timeout for a routed `config set`/`agent create|remove` (`SUPERVISOR_CALL_TIMEOUT`) is sized to outlast the *supervisor's own* worst-case wait for a triggered core restart (`RESTART_WAIT_MAX = 10 s stop budget + 60 s × scale ready timeout`, plus a further 10 s margin), so a slow-but-successful core restart is reported as such, not as a false "supervisor unresponsive."

**`modules.<name>` (§2, ruling B13) and `config schema`/`config get --tier`.** The new namespace's `enabled` key and every module-declared key both resolve through the ordinary nearest-ancestor `x-restart`/`x-tier` walk (§2a is unchanged in mechanism); what is new is that a module's *own* `configSchema` (its manifest, `docs/module-guide.md`) is checked in addition to the harness schema — `modules/mod.rs`'s `config_errors` validates only the sections that actually changed, so installing a second module later can never retroactively invalidate an unrelated `config.set` of the first.

Everything about the module lifecycle itself that this ownership move enables — `enabled` stopping and starting a module, `needs-unavailable` propagating a held-back dependency, and the module CLI commands — is recorded in `docs/module-guide.md` and, for the supervisor's own state machine, in ADR-012 §10.12.

## Consequences

- **Easier:** a user or an agent can ask "what does this change restart?" before applying it (`--dry-run`, or the class shown by `config get`); a module author declares a key's class once, in the schema, and its own `configSchema` on top (2a-H3b-a, §8); unknown or engine keys default to the safe class; both languages compute the same defaults and the same plan, enforced by fixtures; M2 namespaces exist before M2; since 2a-H3b-a, a config change genuinely restarts only what it must, down to one module, closing D3's own requirement in full.
- **Harder:** every new key needs a class decision and, for a `module:` key, a module name that matches the manifest; making an engine key live needs an engine change (E5), not a harness change; a module author must additionally decide what belongs in the manifest's `configSchema` versus a plain harness-schema key.
- **Revisit when:** the engine ever marks an `engine.*` key `readAt: "live"` (the generator built in 2a-H3b-b fails loudly rather than misclassifying it, but nothing yet derives a non-`core` class from that flag); the first `schemaVersion: 2` (add the Rust migration path and its fixture); M3 decides D29's concrete `basic` set (replace the provisional G16 list `setup` consumes as-is today).

## Alternatives considered

- **One file per module or per process**: rejected by D5 ("one `config.json`"); it also makes a cross-cutting change non-atomic and scatters the restart consequence over several files.
- **TOML or YAML**: rejected; JSON Schema validates JSON natively in both languages, `$schema` gives editor completion, and there is no second parser to keep in step.
- **Environment variables as the primary configuration**: rejected; no schema, no preview, no restart plan. `PLUR1BUS_HOME` is the only environment input, and it selects the file.
- **Restart everything on any change**: rejected by D3.
- **A restart class per leaf only, no inheritance**: rejected; open maps (`agents`, `engine`, reserved namespaces) have no fixed leaves, and a forgotten annotation would silently default to something other than the enclosing namespace's class.
- **A flatten-and-compare diff** (the plan's first version) and a two-pass heuristic: rejected by R10 — the first failed its own test, the second reported additions and removals asymmetrically.
