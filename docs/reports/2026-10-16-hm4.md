# HM4 implementation evidence — 2026-10-16

Base: fresh `origin/main` at `3859b949bf96fcfbf060b0a4b3033d73139a5145`, separate `codex/hm4-existing-harness` branch. Phase 1/2 performance work remains in open draft PRs #537/#538. No production performance optimization or Hermes/catalog release is claimed here.

## Behavior

- Python provider/client attach to a running full Harness with an approved personal token, never a full-profile core-token fallback. Normal existing-full `bind` and explicit `bind --existing` both use this path. No daemon launch or importer.
- Normal account/token store, expiry and revocation; server-enforced one-agent/method allowlist and current rights on every call. No subscriptions, cross-agent sharing, configuration, secrets or shutdown. Approved host authority includes Hermes' mapped users within its one agent.
- Owner-only provisioning utility refuses old cores without `hermes.scoped-client`, creates/validates the agent and writes an owner-only credential without printing it. Requires an HM4-capable host runtime first; Host-Addons rollout is an owner task.
- Host → full setup runs in a snapshot/stop/child-setup/health/commit-or-rollback transaction. State/store are never copied or renamed. Existing service registration retained; no new OS unit in the child. Afterward every recorded Hermes credential must authenticate for its agent.
- Dry-run is read-only. Interrupted snapshots are preserved and require explicit `setup --recover-profile`; there is no automatic reboot/daemon-start recovery hook.
- Catalog preparation under `hosts/hermes/catalog/`; no submission, no moving SHA passed off as pinned, no updater. Owner supplies the stable SHA, verified artifact hash and catalog-compatible vendored source layout.
