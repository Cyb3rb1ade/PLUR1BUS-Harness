# Configuration key reference

Generated by `scripts/gen-docs.mjs` from `packages/config-schema/schema/config.schema.json` — do not edit by hand; run `pnpm docs:gen`.

Every declared member is listed, including schema-backed map values (`*`) and array items (`[]`). Restart, tier and sensitivity columns include inherited annotations. Supported Engine credentials and URLs have Harness-owned `x-value-schema` metadata: it describes sensitivity without changing opaque pass-through validation or the Engine contract. Other [engine keys](../config-engine-keys.md) are documented separately; arbitrary reserved values have no additional declared members here.

`x-sensitive: true` identifies fields containing literal secrets or reference forms, including objects of such values. Literals are masked; matching safe references stay readable. `x-url-credentials: true` identifies endpoint URLs whose userinfo and all query values must be masked while retaining their host and path. The Engine reminder webhook is entirely sensitive because its path may carry a credential. The Telegram callback URL is an endpoint: its authentication secret is carried separately in `channels.telegram.webhook.secret`.

`x-secret-reference` marks a reference subschema directly, or links a field to a schema-owned local definition. Matching safe references remain readable in every view and are preserved in regular backups without reading their targets. A pasted-key-like reference is masked and registered as a literal, with a value-free warning. Reference names never enter the text registry merely because their field is sensitive. See [reference safety](../secrets.md#reference-names-and-pasted-keys). `x-value-schema` also protects retired OTLP diagnostic fields without accepting them as valid configuration. See [configuration disclosure](../config-disclosure.md).

TypeScript validation returns optional, value-free `warnings` for endpoint userinfo and points to the sibling secret-reference field when available. It adds no error and does not rewrite the URL. Warning-free validation retains its previous result shape. SH2 consumers apply these declarations to public views, diagnostics, exports and configuration-value registration in logs.
