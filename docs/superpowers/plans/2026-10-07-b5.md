# B5: audit log with a hash chain

Package b5, branch `feat/audit-hash-chain`. Authorities: D111 log schema (`docs/log-schema.md`, audit stream), D109
(`audit.read`, `audit_integrity`), `docs/rbac.md`. Code: `packages/core/src/audit/**`.

## Problem

`logs/audit.log` is append-only by convention only. Four writers (Rust CLI, RBAC sink, identity, secrets) append
unchained lines; editing, deleting or truncating lines is undetectable.

## Design

- New file family `logs/audit.chain.jsonl` (+ rotated `audit.chain.<000001>.jsonl`, + `audit.chain.anchor`), owned by
  the core. `logs/audit.log` and its writers are untouched (RULING A: the legacy file has non-TS writers that cannot
  join a chain in this PR). The RBAC default sink tees into the chain.
- Line = the five audit v1 keys plus `seq` and `prev`: `{at,actor,action,target,detail,seq,prev}`. `prev` is the
  lowercase hex SHA-256 over the exact bytes of the previous line (without `\n`/`\r\n`); the first line uses 64 zeros.
- Anchor file `{v,seq,hash,file}`, written atomically (temp + rename, fsync) after every line, holds the last hash.
  Truncation at the end leaves the anchor ahead of the file and is reported. A crash between line and anchor leaves
  the anchor exactly one line behind: reported as `anchor-lag` (still ok), more is `anchor-mismatch`.
- Rotation at `maxBytes` (default 8 MiB): rename active to the next index, the new active file continues with the old
  last hash. Verify walks the rotated files by index, then the active file; an index gap is a finding.
- Writers serialise through a lock directory next to the file (`mkdir`, stale by age and dead pid, bounded wait).
- `audit.verify` (experimental, 1.5.0, read-only): rule `audit.read` (Owner, Admin). Streams in chunks, bounded memory,
  findings capped. CLI `plur1bus audit verify` forwards only; exit 1 when `ok` is false.
