# M1b-2a-H3b-b — Engine 1.9.0, Windows `run/` ACL, `setup`, `update --check`, `1staid repair`, operations skill, release and exit — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Scope note.** This is the full plan for the 2a-H3b-b outline (items H3b-b-1 … H3b-b-7) at the end of `docs/superpowers/plans/2026-09-27-m1b-2a-h3b-config-modules-setup-repair.md`, plus the E5 final review's harness follow-ups at the engine re-pin to contract 1.9.0 (review item m8). It has 12 tasks. It ends milestone M1b-2a (spec §12). Skill and plugin enable/disable/install belong to the parallel spec on `docs/extensions-ecosystem` and are **not** planned here. This plan only marks where its module install path must stay compatible with that spec (§ "Extension-ecosystem compatibility").

**Goal:** A person installs the harness with one command. `plur1bus setup` downloads the pinned Node runtime and the core payload, verifies their hashes, writes the config, copies the skills, registers the service, starts the supervisor and runs `1staid check`. `update --check` says what a release would change and which units would restart. `1staid repair` shows a plan and fixes what `check` finds. An agent can run the installation from the shipped `plur1bus-ops` skill. A release workflow builds the five targets. On Windows, `run/` gets its ACL once, at supervisor start. The core runs on engine contract 1.9.0.

**Architecture:** One new Rust area, `crates/plur1bus/src/install/`, does the installer work: targets, pins, a verified download, safe extraction and the install manifest. `setup`, `update --check` and `1staid repair` share it. None of it runs inside the supervisor. `setup` is an ordered list of steps with fixed ids, the same way `1staid check` is a list of checks. Repair turns failing checks into a plan of steps and prints the plan before it changes anything. The Windows ACL change moves the `run/` DACL from per-file `icacls` spawns in every Node process to one `SetNamedSecurityInfoW` call in the supervisor, with inheritable ACEs. The supervisor then checks each child's run files natively.

**Tech Stack:** Same as 2a-H3b-a: Node 24.21, TypeScript 5.9, `node:test`, Rust 1.95, clap 4, serde_json, jsonschema 0.26, sha2 0.10, windows-sys 0.59, assert_cmd. **New Rust dependencies (Task 3 only, installer and CLI paths only, ruling HB6):** `ureq` 3 (`default-features = false`, features `rustls`, `platform-verifier`), `flate2` 1 (`rust_backend`), `tar` 0.4, `zip` 2 (`default-features = false`, feature `deflate`), `minisign-verify` 0.2. **New TypeScript dependencies:** none. ## Review Focus

Five inputs the spec implies but no acceptance criterion names. Each is pinned by a test in the owning task.

1. **`setup` killed mid-download or mid-extract** (Ctrl-C, closed laptop lid): no runtime or core under its final name, no stray `*.tmp-*` after the next run, and a re-run completes without asking again. → Task 4 `a_killed_setup_leaves_no_half_installed_runtime_and_a_rerun_completes`.
2. **A home path with spaces and non-ASCII** (`/tmp/p1b A/Jürgen`, `C:\Users\A B\AppData\Local\PLUR1BUS`): the runtime path, the service unit and the spawned core all work. → Task 4 `setup_under_a_home_with_spaces_and_non_ascii_works`.
3. **`1staid repair` while the daemon runs and serves:** a live socket, token or pid file is never "stale", even when the check found a stale sibling. → Task 7 `repair_never_removes_a_live_endpoint`.
4. **`update --check` offline, against a malformed manifest or a 50 MB response:** a clear error, exit 1, nothing written, and the call ends within its 30 s deadline. → Task 5 `offline_malformed_or_oversized_manifests_fail_cleanly_and_write_nothing`.
5. **Windows: `run/`'s ACL cannot be set** (FAT or network volume, `ERROR_NOT_SUPPORTED`): children must not get `PLUR1BUS_RUN_ACL=inherited`. They fall back to per-file `securePath`, so security is never weaker than today. → Task 2 `when_the_run_acl_cannot_be_set_children_fall_back_to_secure_path`.

## Extension-ecosystem compatibility (⟂EXT)

The `docs/extensions-ecosystem` spec (not yet written) will add skill and plugin enable/disable/install. This plan fixes these points so that spec extends them instead of building a second path. Task 12 records them in `docs/module-guide.md` §"Install paths":

1. **One verified extractor.** Every package that comes from outside the binary (the Node archive, a core payload, a module package, a skill bundle) goes through `install::archive::verify_and_extract(archive, sha256, into, strip)`. The ecosystem spec must not add a second extractor or download client.
2. **Refusal vocabulary is stable.** `modules::install::InstallError::reason()` strings (`not-a-directory`, `manifest-invalid`, `symlink`, `special-file`, `entry-outside`, `reserved-name`, `socket-path-too-long`) plus this plan's `digest-mismatch`, `archive-unsafe-entry`, `archive-unsupported` and `download-too-large` are the reasons a plugin install reports. They may be extended, never renamed.
3. **One commit path for modules.** Setup's `modules.bundled` step installs through `modules::install::{stage, commit}` (staging `modules/<name>.tmp-<pid>`, the `run/supervisor.lock` rule for offline installs, supervisor-first when one answers). A plugin that is a module uses the same path.
4. **The install manifest has a slot per unit.** `manifest.json` `modules[]` and `skills[]` entries carry `{ name, version, source: "bundled"|"local"|"catalog", sha256 }`. `"catalog"` is reserved for the ecosystem spec and is unused here.
5. **Skill layout.** `<home>/skills/<name>/` with `SKILL.md`. Third-party skills are verified against a `CHECKSUMS` file before the copy. Enable/disable is the ecosystem spec's and must not move the directory layout.
