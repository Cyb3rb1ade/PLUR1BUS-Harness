## 1. Goal

A person on macOS, Windows or Linux runs one installer ("weiter, weiter, fertig") and gets a working PLUR1BUS: the harness itself runs in **containers** that the app brings along, starts at login and keeps running, and the PLUR1BUS web UI opens in a native window, already paired and logged in. To the person it looks like a closed, self-contained installation. The app detects **Apple `container`** (macOS 26+, Apple silicon) and **Docker-compatible runtimes** (Docker Desktop, Docker Engine incl. rootless, Podman, OrbStack, Colima) and works with either; it never bundles Docker Desktop. As a secondary mode the window can instead attach to a harness on another host (a VPS reached over Tailscale). A tray icon shows the harness state. The app stores its credential only in the OS keychain and updates itself from signed releases. Later milestones add the D74 browser panel (CEF, with a D73 egress profile per panel, driven by agents through a loopback CDP token proxy), onboarding for computer use (D62), push-to-talk (D45), native notifications and WebMCP bridging (D55).

The shell is still **optional as a UI**: the SPA served by the harness is the only required UI (ADR-004 amendment), and the same container image runs without the app on a VPS (§6.15.11). On the desktop the app has two roles that stay strictly apart: (1) **runtime controller** — it installs, starts, stops, upgrades and watches the harness containers through the container runtime, like an OS service manager would; (2) **client of the harness API**, like the SPA and the CLI, with **no policy layer of its own**. Every decision about who may do what stays in the harness's `authorize()` chokepoint (ADR-007). The shell can take things away (for example, refusing to show a panel without a sandbox). It never grants anything the harness has not granted.

## 2. Decisions carried in, and decisions this spec makes

Carried in, binding: **D74** (Tauri + `tauri-apps/cef-rs`, a collapsible panel that detaches and re-attaches, streamed Chromium without a shell, a CDP token proxy on loopback, the `browser` skill; **amended 2026-09-27**, DS37: the in-app panel is native on every OS — WebView2 on Windows, CEF on macOS and Linux — and the streamed container Chromium serves only windowless cases), **D73** (egress profiles, wireproxy, SOCKS5, fail closed), **D72** (Tailscale publishing, the supervisor's port registry 18700–18799), **D62** (computer use through `cua-driver`, off by default, OS permissions belong to the person, a visible indicator and a kill switch), **D55** (WebMCP in both directions through `@plur1bus/webmcp`), **D35** (remote access only through the M3 API, TLS, device pairing, a revocable token per device, no vendor relay), **D8** (targets macOS arm64, Windows x64/arm64, Linux x64/arm64), **§6.5** (the `plur1bus setup` installer, which asks only the D29 `basic` questions), **D45/D44** (voice, the microphone button), **D47** (attachments), **D52** (no harness-native Anthropic OAuth, no reading another client's credentials), the **ADR-004 amendment** (optional client, no own policy layer, after M3), and **D77** (owner 2026-09-27, overruling this spec's original DS1: the desktop app brings the harness as containers, container distribution first on macOS, Linux and Windows, one installer that feels like a closed installation, split into one or two containers where things could affect each other, and Apple `container` and Docker must both be detected and both work), and **D78** (owner 2026-09-27: consumers get only versioned, tested releases with human-readable notes, updates never break the installation — backup, health gate and automatic rollback — and no daily firehose of upstream changes; §6.16).

Decisions this spec makes (numbered **DS**, so they do not collide with the core spec's D-rows or the plans' rulings):

| # | Decision | Why |
|---|---|---|
| DS1 | **Bundle the harness as containers; attach to a remote harness as the secondary mode** (D77, replaces "attach, never bundle"). The app contains no supervisor, core or Node runtime *in its own process*; it carries a pinned **harness container image** (and, from D3, a browser image) and runs it through the container runtime it finds (DS14). The first run installs, starts and pairs it on loopback without a question the person has to understand (§6.15.10). *Attach remote* (a VPS over Tailscale) and *attach to a native local harness* (installed with §6.5, for developers) remain available from the connection manager. | Owner decision D77: "Desktop-App bringt den Harness als Container mit … sieht aus wie eine geschlossene Installation." Containers give the closed-installation feel without the app hosting Node or the engine, keep the D6 process model intact inside the image (DS15, DS19), and make the desktop and the VPS run the **same artefact** (§6.15.11). The original concern — coupled release trains — is handled by DS21 and DS24: one version covers app and image, the app pins the image digest, the harness upgrade is a separate, guarded step after the app update (snapshot, health gate, rollback), and the app supports the previous image major, so a failed harness upgrade never needs an app rollback. |
| DS2 | **Tauri 2 stable first, the CEF runtime later.** D1 and D2 run on Tauri **2.12** with its default runtime (wry: WKWebView, WebView2, WebKitGTK). D3 moves the app to **Tauri 3 + `tauri-runtime-cef`**, but only after a gate: Tauri 3 has reached at least beta, `tauri-runtime-cef` has left alpha, and our smoke test passes on all five targets. A nightly canary job builds D1 against Tauri 3 alpha from D1 onward. **Amended 2026-09-27 (DS37):** the move to `tauri-runtime-cef` applies to **macOS and Linux** only; **Windows keeps the wry runtime (WebView2)** for the SPA and for the panel, so the Windows panel does not wait for the Tauri 3 gate (the runtime is picked per target at compile time). | The CEF runtime exists only for Tauri 3 alpha today (§4.1). A thin shell that has to ship cannot sit on an alpha. D1 code stays small so the 2→3 move is cheap. |
| DS3 | **The SPA is loaded from the harness origin**, in a webview in **incognito** mode (nothing kept on disk). It is not bundled into the app. | The SPA version always matches the harness it talks to. No cookie or local storage stays on disk after the app quits. |
| DS4 | **Credential = a D35 device token** of kind `desktop`, bound to one harness user (ADR-007: effective rights = role ∩ token scopes). It is kept **only in the OS keychain** (`keyring` 4.x native stores). It is never on disk in plain text and never visible to page JavaScript. *Boards (§13.6, 2026-09-28):* `DskB-Connections-*` state *No keychain* (GNOME/KDE only), Settings *Unlock secrets with …* names the store per OS (keychain, Credential Manager, login keyring, KDE Wallet). | D35 and ADR-007 are already decided. A desktop app with a person present needs no file fallback. |
| DS5 | **Webview login by one-time ticket.** The Rust side trades the device token for a single-use ticket (60 s, bound to the device). The webview opens `/auth/ticket#<ticket>`, and the SPA redeems it for a normal session cookie that is never persisted. The ticket travels in the URL fragment, so it never appears in server, proxy or `tailscale serve` logs. | This keeps the token out of the renderer (D55: "device token, never exposed to the agent") and reuses the SPA's cookie + CSRF model unchanged (ADR-004). |
| DS6 | **Remote transport: `https` with a certificate the OS trusts, or `http` only on loopback.** The recommended remote path is `tailscale serve` (D72, a valid `*.ts.net` certificate) in front of a harness API that stays on loopback. A self-signed harness with a pinned fingerprint (D35) is a named degradation: the webview cannot pin, so the app refuses such a connection and points to Tailscale or a real certificate. *Boards (§13.6, 2026-09-28):* `DskB-Connections-*` state *Add error* (plain http to a LAN address refused; self-signed refused; `tailscale serve` named). | Webviews have no cross-platform API to pin a certificate. A local TLS-terminating proxy would make the shell a network component. |
| DS7 | **IPC allow-list: capabilities per webview.** The bundled shell pages get the connection commands. The SPA webview gets a capability added at runtime, scoped to exactly the paired origin, with a closed list of `shell_*` commands. **Panel webviews get no IPC at all.** No Tauri `shell`, `fs` or `http` plugin is reachable from any webview. `withGlobalTauri: false`, `freezePrototype: true`. | Tauri 2 capabilities are the enforcement point (§4.5). The panel shows hostile content by definition. |
| DS8 | **No sandbox, no panel.** The CEF panel is enabled only where Chromium's process sandbox is active. **Amended 2026-09-27 (DS37):** this rule now governs the **CEF** panel on macOS and Linux only. Windows no longer uses CEF for the panel: it uses WebView2, whose renderers run in the Edge/Chromium process sandbox (§6.9), so the Windows exclusion is gone. The remaining exclusion is AppImages on systems that restrict unprivileged user namespaces (Ubuntu ≥ 23.10); what the panel shows there is open (§11 Q9) — the streamed container Chromium is no longer the in-app fallback (DS37). *History:* until this amendment, Windows (tauri-runtime-cef runs CEF unsandboxed there) and the restricted AppImage both showed the harness's streamed Chromium (D74 b) in the panel. | A browser panel that renders arbitrary pages without a renderer sandbox turns one renderer bug into code execution as the user (§4.1). |
| DS9 | **CDP only for panels, and always through the shell.** The CEF DevTools server stays **disabled** (`RemoteDebugging::Disabled`). The shell reaches each panel through CEF's in-process `send_dev_tools_message`. For a local harness, it exposes that through a WebSocket token proxy on `127.0.0.1` (port from the D72 registry). For a remote harness, it relays CDP over its authenticated device connection. The SPA webview is never a CDP target. **Amended 2026-09-27 (DS38):** on Windows the same holds for the WebView2 panel — the shell uses the in-process `CallDevToolsProtocolMethod`/`CallDevToolsProtocolMethodForSession` and `GetDevToolsProtocolEventReceiver` (`DevToolsProtocolEventReceived`) on the panel's `ICoreWebView2`, and never starts WebView2 with `--remote-debugging-port`. | D74 requires loopback plus a token. The in-process API avoids an open DevTools port, which CEF itself calls "reachable by every process on the machine … no authentication". A remote agent cannot reach the laptop's loopback. |
| DS10 | **Computer-use permissions go to `CuaDriver.app`, not to the PLUR1BUS app.** The shell only guides the person through granting them (deep links into System Settings, a live status re-check) and shows D62's indicator and kill switch in the tray. | Least privilege: an app that contains a web browser should not hold Accessibility or Screen Recording. `cua-driver` supports this bundle identity directly (§4.7). |
| DS11 | **Egress for a panel is resolved by the harness.** The shell asks for a panel's egress profile and receives a proxy URL (`socks5://127.0.0.1:<port>`) or a refusal. A request context with a proxy is never rebuilt as `direct` when the proxy fails. With a **remote** harness, only profiles the client itself can reach (`direct`, `socks5` to a host reachable from the client) are offered. `wireguard` panels need a local harness. | D73 fails closed. A WireGuard key is not handed to a laptop, and the shell does not run wireproxy (no second supervisor). |
| DS12 | **Separate update keys per channel** (`dev`, `beta`, `stable`; revised by D78), held by the owner. `dev` is internal (owner and CI only): dev builds embed only the dev key and are never offered to consumers. Release builds embed the `beta` and `stable` public keys; the person's channel choice (*Settings → Updates*, default `stable`) selects the feed **and** the key. Promotion from `beta` to `stable` re-signs the **identical** artefacts and image digests with the stable key; nothing is rebuilt. Private keys live only in GitHub Environments that require approval, never in the repo. Only the public keys are committed. *Boards (§13.6, 2026-09-28):* `DskB-Settings-*` *Updates*: channel *Stable \| Beta* only (C7 settled). | A leaked dev or beta key must not be able to push to stable users. Tauri cannot turn signature checks off (§4.4). Promoting unchanged bytes means `stable` runs exactly what `beta` tested. |
| DS13 | **The desktop app lives in `apps/desktop/`**, with its own Cargo workspace and lockfile, outside the root `crates/*` workspace. | The supervisor's dependency budget (no tokio, spec §4) and the root `cargo test --workspace` stay untouched. Tauri brings its own async stack. |
| DS14 | **Two runtime adapters, both first-class.** (a) **Apple `container`** through its CLI with `--format json` (there is no Docker-API socket and the XPC API is Swift-only, §4.10); minimum 1.0.0, tested against the 1.3 line. (b) **Docker Engine API** over a socket or named pipe (Rust `bollard`), which covers Docker Desktop, Docker Engine rootful and rootless, Podman's Docker-compatible service, OrbStack and Colima with one code path (§4.11). The app never shells out to a `docker` CLI and never requires one on `PATH`. Selection: exactly one usable runtime → use it; several → prefer the one already running; a tie on macOS 26+ → Apple `container` (free, a VM per container, no licence question). The choice is shown in the wizard and in *Settings → Runtime*; switching runtimes is a backup/restore, not a live move (volumes are runtime-specific). *Boards (§13.6, 2026-09-28):* `DskB-Install-*` *Runtime found* / *No runtime* (states ready, found · not running, no access, needs macOS 26, not found; probe list; "never switches runtime by itself"), `DskB-Settings-*` *Runtime* (switch = backup/restore); macOS 26 path undrawn (§13.3 G1). | Owner: "Apple Containers und Docker müssen erkannt werden und beide funktionieren." An Engine-API client reaches every Docker-compatible runtime without depending on which CLI happens to be installed; Apple's runtime has only a CLI we can call from Rust. |
| DS15 | **Two containers, not one and not more, plus optional sidecars each set to bundled/remote/off (DS25):** `plur1bus-harness` (supervisor, core, all modules including channel modules, wireproxy, the tsnet sidecar) and, from D3, `plur1bus-browser` (the D74 b streamed headless Chromium; **since 2026-09-27 for windowless cases only** — background agent tasks while the app is closed, a remote harness, headless — DS37). Optional sidecars `plur1bus-searxng` (D75) and, on Linux/Windows only, `plur1bus-model-runtime` (DS26), both off by default. No local-model container on macOS (DS26). The supervisor, core and modules are **never** split across containers. | §6.15.3 has the full answer. Short form: the core, supervisor and modules share Unix sockets in `run/`, the `node:sqlite` lock, peer-pid identity checks, lifelines and adoption, and the one LanceDB/ONNX handle (T7) — all of which need one kernel and one PID namespace. Chromium is the thing that can hurt the core: memory pressure against the recall budget, its own crash domain, untrusted web content, a 3–4-week security cadence. |
| DS16 | **Host ↔ container interface is narrow.** The harness API is published on **host loopback only** (`127.0.0.1:<port>`, port chosen by the app from 18700–18799). The host reaches nothing else: no core or supervisor socket leaves the container; the host `plur1bus` CLI forwards through `exec` (§6.15.5). **No container ever gets the runtime's socket.** No host directory is mounted by default; Obsidian vaults and a backup folder are explicit, per-item bind mounts the person adds (§6.15.6). | Unix sockets do not cross a VM boundary (virtiofs), and a runtime socket inside a container is root on the host. Loopback publishing is supported by both runtimes (§4.10, §4.11). Pairing trust comes from the ability to `exec` into the container, never from "arrived on loopback" (§6.2). |
| DS17 | **Host bridge for host-only capabilities.** The app dials **into** the harness over the published API port with its device token (WebSocket, the D51 b node-bridge protocol) and offers named capabilities only: `host.keyUnlock` (D1), `host.notify`, `host.localModel`, `host.filePick` (D2), `host.computerUse` (D4). Each capability is named in the device's grant (`host.keyUnlock` only through the CLI at pairing time, which the API and SPA cannot extend, because in container mode a peer-address check is meaningless), enabled by the person in the app, and then authorized per call by the harness's `authorize()` and its D30 approvals. The bridge carries requests, not ambient power: no shell, no file-system browsing, no arbitrary HTTP. *Boards (§13.6, 2026-09-28):* `DskB-Settings-*` *Runtime → Unlock secrets with …* switch (`host.keyUnlock`) with the secrets state in words; `DskB-Sidecars-*` model runtime *Remote · Ollama on this Mac, through the app* (`host.localModel`, D2). | Some things cannot live in a Linux container (§6.15.4). Reusing the D51 b outbound bridge means one protocol for "a paired device lends a capability", whether the harness runs in a container on the same Mac or on a VPS. |
| DS18 | **State lives on named volumes, never on host bind mounts.** `plur1bus-state` holds the state root (`PLUR1BUS_HOME=/var/lib/plur1bus`: `config.json`, stores, LanceDB, `run/`, logs, installed modules); `plur1bus-models` holds downloaded ONNX models. Both runtimes keep named volumes inside the VM's own ext4 (Apple: a sparse ext4 image per volume; Docker Desktop: inside its VM; Linux: a host directory on a native file system). | SQLite WAL needs shared memory on one host and "does not work over a network filesystem" (§4.13); a virtiofs bind mount is the host-to-VM share, slower and with host-side locking semantics we do not control. LanceDB and the `node:sqlite` core lock (ADR-012 §5) stay on a local ext4. Models on their own volume survive a state reset and an image upgrade. |
| DS19 | **PID 1 is `plur1bus init`, not tini; the runtime plus the app replace the OS service manager.** `plur1bus init` (a new mode of the same Rust binary) reaps zombies, forwards signals, and **respawns `plur1bus supervise`** with the ADR-012 backoff, so a supervisor crash leaves the core running and adopted exactly as on a native install. Restart of the whole container: Docker `--restart unless-stopped`; Apple `container` has no restart policy (§4.10), so the app's controller restarts it. `service install` and `update` answer `E_NOT_AVAILABLE reason=container-managed` inside the image. | tini exits when its one child exits, which would turn every supervisor crash into a container restart and kill the core — breaking ADR-012 acceptance 3 (core survives a supervisor crash and is adopted). ADR-012 amendment §11 records the rest. |
| DS20 | **One trust chain: signed app → pinned image digests.** Each app release embeds `bundle.json` (image references by digest per arch, min/max runtime versions, the recommended Apple `container` pkg URL and SHA-256). The app pulls **by digest** or loads a bundled OCI tarball and checks its digest against `bundle.json` before creating anything. Images are multi-arch (`linux/arm64`, `linux/amd64`), built natively per arch, signed keyless with cosign in CI, and carry an SBOM and build provenance for anyone verifying them outside the app (VPS). | The app's own signature and the Tauri updater signature already protect `bundle.json`; digest pinning then gives integrity without a cosign verifier in the app. cosign and SBOM serve the VPS/compose path and audits. |
| DS21 | **Harness upgrades by digest, with a checksummed snapshot, migrations, a health gate and automatic rollback** (revised by D78). One PLUR1BUS release = one version for the app **and** the harness image (DS24). The person approves the release once ("Jetzt"); the app updates itself, then upgrades the harness without a second question: stop (150 s) → cold snapshot of `plur1bus-state` into `plur1bus-state-pre-<from>` with a SHA-256 manifest, verified → new container on the same volumes → config and store migrations → **health gate** (`ready`, compatible `/api/v1/meta`, `1staid check` without `fail`, `admin smoke` recall test) → keep the previous container stopped as `-previous`. Any failure → stop the new container, verify and restore the snapshot, start `-previous`, and tell the person which step failed. One snapshot and one previous image are kept for manual rollback. §6.15.8. *Boards (§13.6, 2026-09-28):* `DskB-Update-*` *Progress* (8 steps), *Done*, *Rolled back*, *Restore failed*; `DskB-Settings-*` *Version*, *Rollback* confirm. | An upgrade may migrate stores, so rollback needs the pre-upgrade data, and a failed upgrade must not strand the person (owner, D78: not "after every update it no longer works"). A health gate that exercises recall catches a harness that starts but cannot remember. Volume clones work the same on every runtime and do not need M8's backup/restore. The app supports the current and the previous image major, so a harness rollback never needs an app rollback. |
| DS22 | **Native installer (§6.5) stays, demoted to secondary.** Container distribution is the primary desktop path; `plur1bus setup` remains for developers, for hosts where no container runtime is wanted, and as the reference implementation of the process model. The VPS path is the **same image** with a `compose.yaml` (Docker, Podman) and Podman quadlet units (§6.15.11). | One artefact everywhere reduces the support matrix; the native path is cheap to keep because it is what the image runs inside anyway. The owner's own VPS keeps using the OpenClaw plugin and is unaffected. |
| DS23 | **CI: the Docker path is tested for real, the Apple path by contract plus a self-hosted or manual run.** GitHub's arm64 macOS runners cannot run Apple `container` ("Nested-virtualization is not supported", §4.15). The Apple adapter is tested against a fake `container` CLI replaying recorded 1.3.x JSON, and end to end on a self-hosted macOS 26 runner (owner's Mac, label `macos-26-container`, manual dispatch, never required) or as a recorded manual check on every release. | An adapter that is only unit-tested against invented output would drift; recorded fixtures plus a real run per release is the strongest check available without nested virtualization. |
| DS24 | **Release and update policy (D78).** Consumers receive only **versioned, tested releases**, never `main` or daily commits: SemVer with a product meaning (patch = fixes only and never a store or config migration; minor = features, forward migrations allowed; major = the only place for a breaking change, always with a migration note); channels `stable` (default) and `beta` (opt-in); a predictable rhythm (a stable minor every **4 weeks**, patches as needed, a security fix out of band); short **release notes in German and English written for users**, shown before anything is installed, with the choice **Jetzt / Später / Überspringen** and a *Version halten* switch; security fixes marked as such. A release reaches `stable` only through the CI release gate (full matrix, kill soak, upgrade tests from the previous two releases on synthetic data fixtures) and a canary period on `beta` (7 days for a minor or major, 48 h for a patch). Images and bundles are cosign-signed with SBOM and provenance (DS20). Auto-update is **off** by default; whether patches may install automatically is owner question §11 Q8. §6.16. *Boards (§13.6, 2026-09-28):* `DskB-Update-*` *Minor*, *Security* (re-offered after 7 days), *Major* (migration note), de/en toggle, *Version halten* link; `DskB-Settings-*` *Updates* (auto patches on, quiet hours 03:00–05:00, hold), `V2Modules` card (C6 settled). | Owner, D78: no OpenClaw-style breakage after updates, and no Hermes-style firehose ("jeden Tag 800 Git-Changes … als Konsument kann man das gar nicht mehr nachvollziehen"). §6.16.6 contrasts both explicitly. |
| DS25 | **Every optional sidecar gets the same three settings: bundled, remote, or off** (owner 2026-09-27). ## 3. Non-goals

- A second policy layer, a local account system, or any cache of harness data outside the webview's memory.
- Running the harness in the app process, or a mobile app (milestones §7). The harness runs in containers the app controls (DS1), never inside the Tauri process.
- Bundling, installing or silently upgrading **Docker Desktop, OrbStack or Podman Desktop's own bundled Docker/Podman engine**. All have licence terms we do not control (§4.11) or are simply not ours to repackage; the app only detects them, or (Windows/Linux, DS27) downloads and runs the vendor's own official installer with a verified checksum, where the person sees and accepts the vendor's own licence. It *does* bundle **Apple `container`** directly (Apache-2.0, DS27: the signed pkg ships inside the app, the person confirms with their admin password, no separate download) and may *point to* Docker Engine, Podman or Colima on Linux.
- Giving any container the container runtime's socket, host networking, `--privileged`, or a mount of the person's home directory.
- A local-model container **on macOS**: both Apple `container`'s and Docker Desktop's Linux VM have no access to the Mac's GPU/Metal (§4.17), so large models stay on the host there and are reached through the host bridge (DS17, §6.15.4). On Linux and Windows a GPU-backed `plur1bus-model-runtime` sidecar is supported instead (DS26).
- macOS x64 (D8 drops it) and Linux musl builds.
- Telemetry. The updater's request to a static manifest is the only automatic network call the shell makes, and it can be turned off.
- ~~Computer use on a laptop driven by a harness on **another host**.~~ **Lifted 2026-09-29 by core spec D108** (owner): the desktop dials out to the person's own harness over their own network; consent, indicator, stop control and scopes per `docs/superpowers/specs/2026-09-28-basics-quality-bar-design.md` §D108; lands in D4.
- Imitating other clients. The panel keeps CEF's default user agent. The shell does no fingerprint evasion, and it never offers a claude.ai sign-in (D52).

## 4. Evidence (researched 2026-09-27)

### 4.1 Tauri and the CEF runtime

- **Tauri 2.12.0** is the current stable release (crates.io, 2026-09-26). **Tauri 3.0.0-alpha.3** was published the same day. The 3.x alpha line started on 2026-09-13.
- **`tauri-runtime-cef` 3.0.0-alpha.4** (2026-09-26; alpha.0 on 2026-09-13) is a complete Tauri runtime ("Tauri runtime interface for Chromium Embedded Framework"). It replaces wry and depends on `tauri ^3.0.0-alpha.3` and `cef =152.3.0` (CEF 152.0.6). Nothing exists for Tauri 2.
- From its source (alpha.4):
  - It supports several webviews, each with its own profile (`data_store_identifier`, "giving the same isolation `data_directory` does") and its own proxy (`WebviewAttributes::proxy_url`, applied to that webview's request context).
  - It has a runtime-wide `ProxyConfig` and a WebRTC policy that includes `DisableNonProxiedUdp`.
  - `RemoteDebugging` is `Disabled` by default. The docs say a port "is reachable by every process on the machine, and the protocol has no authentication". A `Pipe` mode exists.
  - Each webview has `send_dev_tools_message` plus a message observer.
  - A `DowngradePolicy` handles rolling back to an older CEF.
- **Sandbox, quoted from `src/sandbox.rs`:**
  - "Windows currently runs unsandboxed, whatever the policy says." Since Chromium M138, the sandbox entry point needs CEF's prebuilt `bootstrap.exe` host, which loads the app as a DLL, and "a Tauri application is built as an executable".
  - Linux deb/rpm install the setuid `chrome-sandbox`. An AppImage cannot (its payload is mounted `nosuid`), so it depends on unprivileged user namespaces, "which Ubuntu 23.10 and later restrict through AppArmor".
  - macOS always keeps the sandbox.
- **`cef-rs`** (`tauri-apps/cef-rs`, Apache-2.0 OR MIT) lists x86_64 and ARM64 on Windows, Linux and macOS. `cef-dll-sys` 154.2.0 ships bindings for `aarch64-pc-windows-msvc`, `aarch64-unknown-linux-gnu`, `aarch64-apple-darwin` and the x64 triples. It also ships the `download-cef`, `export-cef-dir` and `bundle-cef-app` helpers. The `cef` crate reached 154.2.0+154.0.28 on 2026-09-27.
- **What we could not find:** any upstream statement that `tauri-runtime-cef` is tested on Windows arm64. Bindings and CEF binaries exist for it, but runtime evidence does not.

### 4.2 CEF size and update cadence

### 4.10 Apple `container` (researched 2026-09-27)

- **What it is.** `apple/container` (Apache-2.0, Swift) runs "Linux containers as lightweight virtual machines on your Mac"; it consumes OCI images and pushes/pulls standard registries. It is built on `apple/containerization` (Apache-2.0), where "each Linux container runs in its own dedicated lightweight virtual machine" with an optimised kernel and `vminitd` as the guest init (gRPC over vsock), and Rosetta 2 for amd64 images. Both READMEs: **Apple silicon only, macOS 26**; the container README says stability is guaranteed only within patch versions until 1.0.
- **Versions.** 1.0 shipped in summer 2026 (coverage dated 2026-07-06). The newest release on 2026-09-27 is **1.3.1 (2026-08-29)**, a security release (six advisories in Containerization, among them path traversal through OCI descriptors and an image-layout symlink read of host files) that moves to Containerization **0.42.0**. Other 1.x notes: a TOML config file replacing UserDefaults, a reduced default capability set, a volume `journal` option, host-only networks, `container machine`, and Kata kernel 3.28–3.32. **Consequence:** `bundle.json` carries a minimum `container` version and the app refuses older ones with a named upgrade.
- **Install and service.** A signed `.pkg` from the GitHub releases that "requires admin password" (installs into `/usr/local`). `container system start` starts the services "and (optionally) installs a default kernel" (`--enable-kernel-install`); `container system kernel set --tar|--binary|--recommended` installs one explicitly. The services are a launch agent `container-apiserver` plus XPC helpers (`container-core-images`, `container-network-vmnet`, `container-runtime-linux` per container) using Virtualization.framework, vmnet, XPC, launchd and the Keychain. **Detection:** `container system version --format json` ("version information for the CLI and, if available, the API server") and `container system status`. The API is XPC and Swift-only; there is **no Docker-API socket**.
- **Images.** `container image pull --platform os/arch`, `image load --input <tar>` ("a tar archive created by `image save`"), `image save -o`. The reference does not say whether `name@sha256:` references are accepted → a D1 spike checks it, and the fallback is pull-by-tag followed by a digest comparison (§6.15.9).
- **Mounts.** Bind mounts are **virtiofs** (`type=bind`, alias `virtiofs`). Named volumes are **ext4 disk images** (`~/Library/Application Support/com.apple.container/volumes/<name>/volume.img`), sparse, up to 512 GiB by default, journal `ordered` by default (`writeback`, `journal` selectable), and give "better I/O performance than a bind mount". Anonymous volumes are not removed by `--rm`. The volumes page says a named volume or a bind mount *can* be shared between containers ("You can't share a `tmpfs` mount between containers, unlike a bind mount or a named volume") but says nothing about fsync, durability or file locking (re-read 2026-09-27). With one VM per container, a shared volume would still be seen by **two kernels**, so neither Unix sockets nor `fcntl` locks nor SQLite's WAL shared memory would work across it — our design never shares a volume between containers (DS18).
- **Networking.** Every container gets its own IP on a vmnet network (default `192.168.64.1/24`), "always reachable by that IP from the host and from other containers on the same network". `-p [host-ip:]host-port:container-port[/proto]`, including `127.0.0.1:` and `[::1]:`. `container network create [--internal] [--subnet]` needs **macOS 26**; on macOS 15 there is one default network and no container-to-container traffic. `run --network` takes **one** network. Name resolution between containers needs a DNS domain (`sudo container system dns create <domain>`), and bare hostnames on custom networks do not resolve. Reaching a host service needs `sudo container system dns create <name> --localhost <ip>` with the service bound to 127.0.0.1 — an **admin step**, which is why local models go through the host bridge instead (§6.15.4). No `--network host`.
- **Lifecycle and limits.** `--init` exists ("forwards signals and reaps processes"), `-m/--memory`, `-c/--cpus` (defaults **1 GiB, 4 CPUs**), `--read-only`, `--cap-add`, `--ulimit`, `--tmpfs`, `stop -t` (default **5 s**), `logs -f -n`, `exec -i -t -u -e`, `inspect` (JSON), `list --all --format json`. **No `--restart` flag and no autostart:** tracking issue #2142 (open) collects #158, #286, draft PR #1201 and PR #1258 (last activity 2026-06-22) with "no maintainer response". **No Compose.** No health checks, no `--privileged`. Memory: "memory pages freed … are not relinquished to the host" (technical overview; "partial" ballooning), so every container gets an explicit memory cap and the browser container is stopped when idle. A 2026-05-02 field report (pre-1.0, 0.12) adds: ~1 s cold start, slow small-file I/O on bind mounts, and container DNS hiccups after sleep/wake fixed by `container system stop && start`.

### 4.11 Docker-compatible runtimes (researched 2026-09-27)

- **Docker Desktop licence** (Docker docs, updated 2026-09-03): free for small businesses ("fewer than 250 employees AND less than $10 million in annual revenue"), personal use, education and non-commercial open-source projects; larger commercial use and government need Pro, Team or Business. Docker Engine and Moby are unaffected. → **We never bundle or install Docker Desktop**; the wizard names the licence when it points to it.
- **OrbStack** (pricing page read 2026-09-27): free only for "personal, non-commercial use"; commercial use is Pro at $8/user/month. It ships a Docker engine and Compose, creates a Docker context `orbstack`, and may symlink `/var/run/docker.sock`.
- **Colima** (MIT): Docker, containerd or Incus on macOS and Linux, VM backends `vz` (Virtualization.framework, Rosetta) and QEMU; socket `~/.colima/default/docker.sock` plus a Docker context.
- **Podman** Docker compatibility (Podman Desktop docs): the compatible API is served at `/var/run/docker.sock` on macOS (the "Third-Party Docker Tool Compatibility" setting, on by default) and `npipe:////./pipe/docker_engine` on Windows; on Linux and Windows tools are pointed at Podman through `DOCKER_HOST`. Compose is a separate extension. Rootless is the default for `podman machine`.
- **Docker Engine rootless** (Docker docs): daemon and containers run without root in a user namespace; needs `newuidmap`/`newgidmap` and 65 536 subordinate ids; `dockerd-rootless-setuptool.sh install` creates a `systemd --user` service and a context `rootless`; clients use `DOCKER_HOST=unix:///run/user/<uid>/docker.sock`.
- **Docker Desktop on Windows** (docs, 2026-09-07): WSL 2 backend needs WSL ≥ 2.1.5 on Windows 10 22H2 (19045) or Windows 11 23H2 (22631)+, SLAT, 8 GB RAM, virtualization on; per-user install needs no admin (Hyper-V backend does). Arm64 is "Early Access".
- **Restart policies** (Docker docs, 2026-08-16): `no`, `on-failure[:max]`, `always`, `unless-stopped`; a policy applies only after the container ran 10 s; a manual stop suspends it until the daemon or the container restarts; Docker advises against combining restart policies with host process managers.
- **Socket candidates the D1 detector probes** (to be confirmed per runtime in the Task 5 report, not asserted here): `DOCKER_HOST`; the current Docker context (`~/.docker/contexts`); `/var/run/docker.sock`; `$XDG_RUNTIME_DIR/docker.sock` (rootless); `$XDG_RUNTIME_DIR/podman/podman.sock`; macOS `~/.docker/run/docker.sock`, `~/.orbstack/run/docker.sock`, `~/.colima/default/docker.sock`; Windows `npipe:////./pipe/docker_engine`, `npipe:////./pipe/podman-machine-default`. Every candidate is confirmed with `GET /_ping` and `GET /version` (the reply names the engine, so Podman and OrbStack are told apart from Docker for diagnostics only; behaviour does not branch on it).

### 4.12 WSL 2 as a Windows fallback (researched 2026-09-27)

- A custom distribution is a tar root file system: `wsl --import <Distro> <InstallLocation> <tar>` (docs 2024-07-16), or since WSL 2.4.4 a `.wsl` file (a renamed `.tar.gz`) installed by double-click or `wsl --install --from-file` with `/etc/wsl-distribution.conf` for first-run behaviour; systemd is opt-in through `/etc/wsl.conf [boot] systemd=true` (docs 2025-09-12).
- Networking (docs 2025-08-06): in NAT mode Windows reaches a Linux service at `localhost:<port>`; mirrored mode (Windows 11 22H2+) also lets Linux reach Windows services on `localhost`.
- **Assessment.** A WSL distro built from our image is Microsoft's own mechanism and needs no third-party runtime, but it is **not a container**: every WSL 2 distro shares one VM and kernel with the person's other distros, memory is capped only globally (`.wslconfig`), and there is no restart policy. It is therefore a **D2 fallback** when neither Docker Desktop nor Podman is present, not the primary Windows path (§6.15.10).

### 4.13 Storage semantics for SQLite and LanceDB

- SQLite: "All processes using a database must be on the same host computer; WAL does not work over a network filesystem", because the wal-index lives in shared memory (sqlite.org/wal.html, read 2026-09-27).
- Docker Desktop: "Named volumes … are created inside the VM's own filesystem, so they are as fast as on a Linux machine"; bind mounts cross the host–VM boundary (Docker blog 2022-01-24, updated 2022-10-03; virtiofs is the macOS share since then). Apple `container` says the same for its volumes (§4.10).
- **Field evidence from the two projects the owner compares us with** (issues read 2026-09-27; the pages show no absolute date):
  - NousResearch/hermes-agent #110847: on Podman (applehv machine, macOS), a WAL `state.db` on a **virtiofs bind mount** reported "database disk image is malformed" within about one minute of concurrent writers; the same workload on an **ext4 named volume** ran clean for 30 minutes (235 857 rows, zero integrity errors). The main file copied without `-wal`/`-shm` passed `integrity_check`: the damage was in WAL/shared-memory coordination. Closed as duplicate of #110848.
  - NousResearch/hermes-agent #68545: SQLite's `checkpoint_fullfsync` relies on macOS `F_FULLFSYNC`, "fundamentally unavailable to a Linux process", so inside a Linux container on a macOS virtiofs mount the durability barrier never applies; the project moved to a configurable `journal_mode=DELETE`.
  - openclaw/openclaw #139214 (OpenClaw 2026.6.11): on Docker Desktop for macOS a SQLite state database in the container's **writable overlayfs layer** corrupted "reliably within approximately one minute"; a fresh database on the same mount hung under concurrent writes, which the reporter attributes to broken POSIX advisory locking.
- Consequence (DS18): LanceDB, the stores, `run/` and the `node:sqlite` core lock stay on a named volume, i.e. a local ext4 seen by exactly one kernel — never on a virtiofs bind mount and never in the container's writable layer (the read-only root file system, §6.15.7, makes the second impossible by construction). Vault bind mounts carry Markdown files only; `1staid check` fails when the state root or a store path sits on virtiofs, FUSE or overlayfs (`statfs` magic numbers), and the core refuses to open a store there.

### 4.17 GPU access for containerised model runtimes (researched 2026-09-27)

- **Apple `container`: no GPU passthrough.** The maintainers state directly, on the project's own repository (`apple/container` discussion #62, 2025-06-09, re-read 2026-09-27): "we do not currently support this." The thread names the technical reason (Apple's GPU stack has no IOMMU path suitable for standard passthrough) and the design reason (one VM per container). No release since — up to and including 1.3.1, §4.10 — has added it. **Consequence for DS26:** a large model in an Apple-`container` container is CPU-only, full stop; there is no GPU escape hatch to verify away.
- **Docker Desktop and Apple `container` on macOS both run containers inside a Linux VM with no Metal access.** This is the same VM boundary §4.10 and §3 already describe for volumes and mounts; it applies equally to GPU access, since Metal is a host (XNU/AppleGPU) framework the guest Linux kernel cannot see. Podman's `libkrun`/`krunkit` machine backend is the one macOS path with any GPU story (experimental Vulkan passthrough, at a real performance cost) — already named by the owner and not contradicted by anything found.
- **Linux: NVIDIA Container Toolkit's CDI mode.** CDI ("Container Device Interface") support landed in NVIDIA Container Toolkit **1.12.0** ("As of the v1.12.0 release the NVIDIA Container Toolkit includes support for generating Container Device Interface (CDI) specifications", NVIDIA docs, CDI support page, read 2026-09-27). **Podman is CDI-native since 4.1.0** — a GPU is requested with `--device nvidia.com/gpu=all` directly. **Docker does not speak CDI natively**; the NVIDIA Container Runtime instead runs in a `cdi` mode that injects the same CDI devices for it. Both paths are driven by the same `nvidia-ctk` tooling and the same generated CDI spec, so one adapter code path covers Docker and Podman on Linux.
- **Windows: Docker Desktop's WSL 2 backend supports NVIDIA GPUs.** Docker's own docs (`docs.docker.com/desktop/features/gpu`, read 2026-09-27): "Docker Desktop for Windows supports NVIDIA GPU Paravirtualization (GPU-PV)... allowing containers to access GPU resources," requiring an NVIDIA GPU, a WSL2-capable NVIDIA driver on the host (not inside WSL), and the WSL 2 backend. NVIDIA's own CUDA-on-WSL guide describes the same paravirtualized path from the driver side. **Consequence for DS26:** the Linux/Windows sidecar is a real, verified option, not a hopeful one; only macOS is a hard no.

### 4.18 Host-to-container file-change notifications over virtiofs (researched 2026-09-27)

- **Docker Desktop for Mac: inotify events are not reliably delivered across a virtiofs bind mount.** `docker/for-mac` issue #7246 (reported against Docker Desktop 4.29.0, 2024; re-read 2026-09-27, still open, no maintainer fix recorded): "While other events (CREATE, ATTRIB, MODIFY, possibly others) are correctly propagated from the host, the DELETE event is not triggered for files and nested directories at all." A host-side delete inside a virtiofs-shared folder silently never reaches the container's inotify watchers.
- **The same class of failure appears independently on the Virtualization.framework backend Apple `container` itself uses.** `containers/podman` issue #22343, "cannot receive inotify on shared directories when using AppleHV" (AppleHV = Virtualization.framework, the same host virtualization layer `apple/container` builds on, §4.10): host-side changes to a virtiofs-shared directory generate no inotify events inside the guest at all, not just a missing event type.
- **Consequence (DS16, §6.15.4, §6.15.6):** the Obsidian bridge cannot assume host file-change notifications reach the container over a virtiofs bind mount, on either Docker Desktop or Apple `container`. It detects changes by **polling** (an mtime scan on an interval) instead, and never depends on inotify for a bind-mounted vault. This is unrelated to the state-root question (§4.13): the vault holds plain Markdown files with atomic temp+rename writes from our own bridge, so the durability risk that keeps `plur1bus-state` off virtiofs does not apply to a vault mount — only the *notification* path is unreliable there.

### 4.19 MSIX, the Microsoft Store, and Docker/WSL detection from a packaged app (researched 2026-09-27)

- **Full-trust MSIX keeps normal process, pipe and socket access; only AppContainer is constrained.** Microsoft's own MSIX containerization overview (`learn.microsoft.com/windows/msix/msix-containerization-overview`, read 2026-09-27) distinguishes the two models: a **full-trust** (Desktop Bridge) MSIX app "runs with the same permissions as a standard desktop app," with package identity and *selective* file/registry virtualization (user-profile and package-install paths are affected; system paths and, by omission, named pipes and sockets are not) — the stronger sandboxing (blocked system paths, no ambient IPC) applies only to the separate **AppContainer** model, which we do not use. A full-trust MSIX is therefore no different from an unpackaged Win32 app for DS14's purposes: probing `\\.\pipe\docker_engine` / `\\.\pipe\podman-machine-default`, reading `~/.docker/contexts`, and spawning nothing (the Docker path is API-only, DS14) all work unchanged.
- **Docker Desktop itself is the existence proof.** Docker Desktop for Windows is published on the Microsoft Store (`apps.microsoft.com/detail/xp8cbj40xlbwkx`; Docker's own announcement, `docker.com/blog/docker-desktop-on-microsoft-store/`, read 2026-09-27) and, once installed from there, drives the same WSL 2 backend and the same named pipe it does when installed directly — a full-trust MSIX distributing exactly the kind of runtime our app needs to detect. Docker's post states updates are then Store-managed ("The Microsoft Store handles all update processes automatically"), including enterprise delivery through Intune, "similar to `winget install`."
- **Store policy requires Store-only updates for a Store-distributed product**, so a Store build cannot keep its own self-updater active. Microsoft's Store Policies (`learn.microsoft.com/windows/apps/publish/store-policies`, read 2026-09-27) §10.2.5 requires products submitted for Store ingestion to be "installed and updated only through the Store," and §10.2.2 separately bars dynamic code inclusion that changes the app's functionality outside what was reviewed — a `tauri-plugin-updater` fetching and applying its own signed update on a Store-installed copy would run against both. **Consequence for DS32:** the Store build compiles with the updater plugin disabled; the app's *content* is otherwise identical, and the harness image's own D78 upgrade path is untouched (it lives inside the container, not the app package).
- **Store submission re-signs the package**, which is exactly the SmartScreen-avoidance property DS31 wants: a package submitted through Partner Center is signed by the Store at ingestion regardless of whether the developer also signs it, so a Store listing carries Microsoft's own signature and reputation rather than needing an EV/OV certificate or SignPath at all for that channel (Microsoft's code-signing options overview, `learn.microsoft.com/windows/apps/package-and-deploy/code-signing-options`, read 2026-09-27, lists Store signing alongside Trusted Signing/Artifact Signing and a third-party certificate as the available options for a Windows app).

### 4.20 Flatpak sandboxing and reaching a host Docker/Podman socket (researched 2026-09-27)

- **The Flatpak portal model does not cover arbitrary Unix domain sockets.** The Flatpak sandbox-permissions docs (`docs.flatpak.org/en/latest/sandbox-permissions.html`, read 2026-09-27) describe D-Bus name allow-listing (`--talk-name`, for D-Bus session/system services), filesystem holes (`--filesystem`), and device/portal access, but name no portal for a raw socket file such as Docker's or Podman's. `flatpak-spawn(1)` (read 2026-09-27) instead lets a sandboxed app run a command **on the host** (`flatpak-spawn --host <cmd>`), which is the documented escape hatch for "talk to a host service that has no portal."
- **The practical pattern, confirmed by real Flatpak apps that already do this** (Fedora Discussion "how do flatpaks (e.g. PyCharm Pro) access podman sockets?", read 2026-09-27; a `flathub/com.jetbrains.IntelliJ-IDEA-Ultimate` issue on the same problem): a `--filesystem` hole to the **specific socket path** (e.g. `--filesystem=xdg-run/podman:ro` for `$XDG_RUNTIME_DIR/podman/podman.sock`, or the equivalent Docker/OrbStack/Colima path from §4.11's candidate list), not `--filesystem=host`; TCP to the socket "doesn't work" per the same thread, so it has to be the Unix socket itself. Flatseal ("Other files") is the manual equivalent of adding the same override.
- **Consequence (DS34):** the Flatpak manifest declares a `--filesystem` override per detected runtime's socket path (added at build time for the common ones, or requested at first run via a `flatpak-spawn --host` probe plus a documented manual Flatseal step for an uncommon one), and any command that must run against the host's own service manager (the Linux installer's `systemctl --user enable --now podman.socket` one-click, §6.15.10) runs through `flatpak-spawn --host` rather than a bundled `systemctl`.

### 4.21 GitHub Releases limits (researched 2026-09-27)

GitHub's own release documentation (`docs.github.com/en/repositories/releasing-projects-on-github/about-releases`, read 2026-09-27): each release asset must be under **2 GiB**, a release may hold up to **1,000 assets**, and GitHub states **no limit on total release size or download bandwidth**. **Consequence (DS28):** GitHub Releases is a free, effectively uncapped CDN for the app bundles and `bundle.json`/`release.json`; none of the D1 artefacts (§6.15.9's ≤350 MB/≤700 MB image budgets, or a five-target app release) approaches the 2 GiB per-asset ceiling.

### 4.22 Windows named-pipe default security descriptor (researched 2026-09-27)

`nodejs/node` issue #47086 (read 2026-09-27): Node's `net` module (through libuv's `CreateNamedPipe` call) uses Windows' **default** security descriptor when no explicit one is given, which the issue documents as granting "full control to the LocalSystem account, administrators, and the creator owner" and, separately, "read access to members of the Everyone group and the anonymous account." Node maintainers have not changed this default (a fix would need a libuv change first) but do expose `readableAll`/`writableAll: false` on `server.listen()` for a caller that wants to opt out of the `Everyone`-readable grant. **Consequence (DS36):** this is exactly the shape S11 already chose deliberately for the core's own pipe ("full control for SYSTEM, Administrators and the creator owner, read-only for Everyone and Anonymous") rather than an oversight, so the Windows ACL follow-up leaves it unchanged and scopes itself to `run/`'s file-level ACL and the module-spawn latency instead.

### 4.23 WebView2 as an agent-driven panel, Tauri multi-webview, CEF on Windows (researched 2026-09-27)

For DS37–DS39. Every fact was read on 2026-09-27; URLs in §12.

- **WebView2 CDP, in-process.** `ICoreWebView2::CallDevToolsProtocolMethod(methodName, parametersAsJson, handler)` "runs an asynchronous DevToolsProtocol method"; for "available methods" it points to the generic DevTools Protocol viewer (tip-of-tree) and lists **no excluded domain**. It returns `E_INVALIDARG` for an unknown method. It warns: "Even though WebView2 dispatches the CDP messages in the order called, CDP method calls may be processed out of order." `GetDevToolsProtocolEventReceiver(eventName)` subscribes to events. `ICoreWebView2_11::CallDevToolsProtocolMethodForSession(sessionId, …)` reaches other targets (cross-origin iframes, workers) after `Target.attachToTarget` or `Target.setAutoAttach` with `flatten: true`; an empty `sessionId` means the top page. Microsoft's CDP how-to page states no limitations and says nothing about the `Input` domain or debugging ports.
- **WebView2 CDP coverage for what the agent needs — what we could and could not verify.** `Page.navigate`, `Page.captureScreenshot`, `DOM.*`, `Runtime.evaluate` and `Network.*` are ordinary CDP methods; nothing in Microsoft's reference excludes them, but we found **no Microsoft page that lists them as tested**, so the D3 spike (below) calls each one. **`Input.dispatchKeyEvent` works and yields trusted events**: webdriverio's Tauri service routes WebView2 keyboard input through `CallDevToolsProtocolMethod` for exactly that reason ("trusted keyboard events", `isTrusted: true`, the same mechanism msedgedriver and Playwright use), with two caveats it documents — CDP key events carry no frame parameter (keys follow focus, so input inside an iframe needs focus placed there first) and it did not cover pointer events. **Gap, unresolved upstream:** WebView2Feedback #1278 reports that `Input.dispatchKeyEvent` for Ctrl+F produces no effect and no error — browser-level accelerators are not triggered through CDP input; the issue ends without a fix. This does not contradict DS37 (an agent types into pages, it does not need browser accelerators; find-in-page is done with `DOM`/`Runtime`), but the `browser` skill must not rely on accelerators on Windows. **`Input.dispatchMouseEvent` on WebView2: no source found either way** — the D3 spike must prove it (click, drag, wheel) before DS37's Windows half is considered verified.
- **Playwright with WebView2.** Playwright's WebView2 page documents only the port path: start WebView2 with `--remote-debugging-port=9222` (through `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` or `AdditionalBrowserArguments` on `EnsureCoreWebView2Async`), then `chromium.connectOverCDP('http://localhost:9222')`; it warns that instances share one user data folder by default and gives no security note. Microsoft Learn's Playwright page only links there.
- **Why a debugging port is unacceptable in release builds.** Chrome's own blog (Chrome 136): `--remote-debugging-port`/`-pipe` are no longer honoured on the default data directory because attackers use remote debugging to extract cookies; the protection is a non-default data directory. The DevTools endpoint itself stays unauthenticated. `tauri-runtime-cef` says the same of CEF's port (§4.1: "reachable by every process on the machine, and the protocol has no authentication").
- **WebView2 user data and profiles.** A user data folder (UDF) holds cookies, cache, permissions, history; one UDF per session; several UDFs mean separate browser processes and more resources; profiles are the lighter isolation within one UDF. Tauri: `WebviewBuilder::data_directory` sets the webview's data directory, and "Webview instances with different browser arguments must also have different data directories"; `incognito` needs WebView2 Runtime ≥ 101.0.1210.39; `on_navigation` can cancel a navigation, `on_download` can refuse a download.
- **WebView2 servicing.** Evergreen: "The WebView2 Runtime updates automatically without requiring any action from you. It receives the same Microsoft Edge updates" as Edge Stable. Fixed Version: "you control the timing of updates … The WebView2 Runtime on the client isn't automatically updated" (over 250 MB per Microsoft). Evergreen offline: the *Standalone Installer* "installs the Evergreen WebView2 Runtime in offline environments". MSIX via App Installer can declare the runtime as an external dependency. Tauri's `webviewInstallMode`: `downloadBootstrapper` (default, needs internet, 0 MB), `embedBootstrapper` (~1.8 MB, needs internet), **`offlineInstaller` (~127 MB, no internet, "recommended for offline environments")**, `fixedVersion` (~180 MB, "manage the release patches yourself"), `skip`; Tauri notes the runtime ships as part of Windows 10 (April 2018 or later) and Windows 11.
- **Tauri 2 multi-webview.** Tauri **2.12.0** (released 2026-09-26) is current. `WebviewBuilder` — the child-webview API behind `Window::add_child` — is documented "Available on crate feature `unstable` only"; the crate's `unstable` feature forwards to `tauri-runtime-wry/unstable`, and the `multiwebview` example requires it. So multi-webview is **still unstable** on 2026-09-27. 2.12.0 itself fixes multi-webview issues relevant to us: channel IPC queue entries are now bound to the webview that created them ("Queued channel payloads and large invoke responses can no longer be read by other webviews"), `Window::is_focused` in multi-webview mode on Windows, and focus on Alt-Tab under `unstable` — i.e. **2.12.0 is the minimum** for a hostile child webview beside the SPA. On Windows, `PlatformWebview::controller()` and `environment()` (via `Webview::with_webview`) return the `ICoreWebView2Controller` and `ICoreWebView2Environment` (source, `crates/tauri/src/webview/mod.rs`, tag `tauri-v2.12.0`), which is what DS38 needs to reach `ICoreWebView2`.
- **CEF sandbox on Windows in cef-rs / `tauri-runtime-cef`.** `cef-rs`'s README: with its `sandbox` feature, the bundler "will build the DLL (cdylib) target instead of the executable (bin) target, and copy that with a renamed `bootstrap.exe`" — so `cef-rs` has a Windows sandbox path. `tauri-runtime-cef` is still 3.0.0-alpha.4 (2026-09-26) with no newer release; its alpha.4 notes say nothing about the sandbox, and we found no change to the §4.1 finding ("Windows currently runs unsandboxed"). Since DS37 moves Windows to WebView2, this no longer blocks anything; it only matters if Windows ever moves to CEF.

## 6. Design

### 6.1 Relationship to the daemon

A connection has one of three kinds: **`bundled`** (the default; the harness containers this app controls, §6.15), **`local`** (a native harness installed with §6.5 on this computer, attach only) and **`remote`** (attach only). Only `bundled` connections involve the runtime controller.

- **Bundled.** The app knows the published URL (`http://127.0.0.1:<port>`) because it chose the port; it reads nothing from the container's file system. Readiness is `GET /api/v1/meta` on that URL plus `exec plur1bus daemon status --json` inside the container (the same single source of process health as on a native install, spec §6.4). Lifecycles are **joined on purpose**: the app starts the harness at login (§6.8), shows its state in the tray, and offers *Stop harness* / *Start harness*. **Quitting the window never stops the harness**; *Quit PLUR1BUS* in the tray asks whether to stop the harness too (default: keep it running). Uninstalling the app offers to remove the containers and, separately and with a second confirmation, the volumes (data).
- **Discovery (native local, attach mode).** The shell reads `<state root>/run/api.json` (D5 root: `PLUR1BUS_HOME`, `~/.plur1bus`, `%LOCALAPPDATA%\PLUR1BUS`). The file holds `{ url, pid, instanceId, installationId, apiVersion }` and is written by the harness API server at bind time (`instanceId` changes with every start; `installationId` is stable for the installation). It contains no secret. The shell **never reads `run/*.token`** (those are core/supervisor RPC credentials, ADR-012). A stale file (dead pid, refused connection) counts as "no local harness".
- **Compatibility.** The shell reads `GET /api/v1/meta` (unauthenticated) → `{ apiVersion, installationId, capabilities }` and feature-detects what it needs, following ADR-016 §3 (capabilities, not version sniffing): `desktop.sessionTicket`, later `panel.cdp`, `egress.resolve`, `computerUse`. A different API major is refused with a message naming both versions.
- **No harness yet.** The first-run wizard (§6.15.10) creates the bundled harness. The former D2 "Install here" action (download and run `plur1bus setup`) is dropped: the native installer stays available from the docs for people who want it (DS22), but the app does not drive it.
- **Updates.** The app updates itself (§6.11). A bundled harness is upgraded by the app by image digest (DS21, §6.15.8); `plur1bus update` inside the container refuses (`E_NOT_AVAILABLE reason=container-managed`). A native local harness keeps updating through `plur1bus update` (M8); the app never touches it. Both follow the D78 release policy (§6.16).

### 6.2 Connections and authentication

A **connection** is `{ id (UUIDv7), name, kind: bundled|local|remote, origin, installationId, deviceId, tokenHint (last 4) }`; a `bundled` connection also carries `{ runtime: apple|docker, runtimeEndpoint, containerName, imageDigest }` (no secret). Connections are stored in `connections.json` in the app config directory, written atomically with mode `0600`, and hold no secret. One connection is bound to one harness user. Switching user means switching connection. Before any authenticated call, the shell compares `/meta`'s `installationId` with the stored one. If they differ (a different harness now answers at that address), it sends no token and asks the person to pair again.

**Origin rules:**
- `https://host[:port]`, or `http://127.0.0.1|[::1]|localhost[:port]`.
- No userinfo, path, query or fragment.
- The origin is shown as punycode when it is IDN.
- `http` to any other host is refused (DS6).

**Pairing (D35):**
0. *Bundled, automatic.* Right after the first start, the controller runs `plur1bus device pair --json --kind desktop --name "<hostname> desktop" --scope ui.session,events.read,bridge.serve --grant host.keyUnlock` **inside the harness container** through the runtime's `exec` (Apple `container exec`, Docker `POST /containers/{id}/exec`), with fixed arguments, and redeems the code over the published loopback URL exactly as in flow 1. Trust comes from the ability to `exec` into a container owned by this OS user, which only that user (or an administrator) has. The person sees no code. The first harness user is created by the same exec step (`plur1bus user create --owner --json`, M3 naming), so the SPA opens logged in as the owner.
1. *Local, one click (native attach).* The shell runs `plur1bus device pair --json --kind desktop --name "<hostname> desktop"` with fixed arguments. The binary path comes from the known install location, never from input. The CLI authenticates to the core over its local socket, as it does for every command. The shell redeems the returned code at `POST /api/v1/devices/redeem` and receives `{ deviceId, token }`. If the CLI has no local principal that may pair devices (M3 decides this), the shell falls back to flow 2. Pairing trust never comes from "the request arrived on loopback": behind `tailscale serve`, every remote request arrives on loopback too (§4.8).
2. *Code flow.* The person enters the origin and an 8-character code. They get the code from `plur1bus device pair` on the host, or from *My area → Devices* in the SPA on any logged-in device. D2 adds `plur1bus://pair?origin=…&code=…`, which only pre-fills this form (§6.9).
3. The token goes **straight from the HTTP response into the keychain**: service `app.plur1bus.desktop` (bundle id, DS33), account = connection id. The token is held in memory as a `SecretString` (zeroized on drop, `Debug` prints `***`). The harness stores only a hash (D35).
4. **Revocation.** Any `401 E_AUTH reason=device-revoked` from the harness deletes the keychain entry and returns the shell to the pairing screen for that connection.
5. **Linux without Secret Service.** The token is kept in memory for the session only. A banner explains that the app must be paired again after a restart. There is no plain-text or passphrase fallback in track D (DS4).

**Webview session (DS5).** At every SPA open, the shell calls `POST /api/v1/auth/session-ticket` with `Authorization: Bearer <device token>` and gets `{ ticket, expiresAt }` (single use, 60 s, bound to `deviceId`). It then navigates the incognito `spa` webview to `<origin>/auth/ticket#t=<ticket>`. That page POSTs the ticket to `/api/v1/auth/ticket/redeem`, receives the session cookie (`HttpOnly`, `SameSite=Lax`, `Secure` on TLS, no `Expires`) and the CSRF token, and replaces the URL so the fragment is gone. Everything the SPA does afterwards goes through ADR-004 as for any browser. The **Rust side** uses the device token for its own calls only: `/events` for tray and notifications, ticket issue, and later panel registration.

**Device scopes** (named for M3's scope list): `ui.session`, `events.read`, `bridge.serve` (bundled connections only: the device may offer host-bridge capabilities, DS17; each capability is additionally named in the grant), and from D3 on `panel.serve` (the device may serve CDP for panels to the harness). The harness applies role ∩ scopes. The shell never asks for scopes it does not use.

### 6.4 The native panel (D3)

**Engine per OS (DS37, amended 2026-09-27):** a second webview in the app window — **WebView2 on Windows** (wry runtime; a Tauri 2 child webview behind the `unstable` feature, or wry directly, §4.23 and the D3 spike), **CEF on macOS and Linux** (`tauri-runtime-cef`). Everything below applies to both unless marked. The panel is never the SPA webview, and the SPA is never a CDP target.


- **Layout.** The panel is a second webview in the main window: a right-hand side panel that can be resized and collapsed, and detached into its own window. Re-attaching moves the same webview back, so its state is kept. The panel's tab strip, address bar and handover banner are drawn by the SPA as ordinary DOM. The SPA calls `shell_panel_*` commands (DS7) to open, navigate, resize, detach and attach. The page content itself is never in the SPA's DOM.
- **Profiles.** Each panel gets `data_store_identifier = panel-<egressProfileId>` (CEF) or its own WebView2 user data folder `…/panel-<egressProfileId>` via `data_directory` (Windows), so every egress profile has its own cookie jar and cache, and **no panel profile ever shares storage with the `spa` or `shell` webviews** (§6.9). Logins made through one egress path never appear on another. A panel can be marked *ephemeral*; its profile is then deleted when it closes.
- **Egress (DS11).**
  1. The shell calls `POST /api/v1/egress/resolve { profile, for: "panel" }` → `{ proxyUrl }`, or `E_NOT_AVAILABLE reason=tunnel-down|not-client-reachable`.
  2. `proxyUrl` goes into `WebviewAttributes::proxy_url` (CEF). On Windows the proxy is a WebView2 browser argument, and Tauri requires webviews with different browser arguments to use different data directories (§4.23), which the per-profile folder above already gives; the D3 spike verifies the exact argument and that SOCKS5 host-name resolution goes to the proxy. For `socks5://`, Chromium sends host names to the proxy, so DNS does not bypass the tunnel.
  3. As long as any non-direct panel profile exists, the runtime-wide WebRTC policy is `DisableNonProxiedUdp` (CEF); on Windows the equivalent WebView2 setting is a D3 spike item, and a proxied panel stays disabled on Windows until it is proven.
  4. A proxy that dies makes requests fail. The shell shows the tunnel state from `/events` and never rebuilds the context as `direct`.
- **Schemes.** A panel may load only `https:` and `http:` (never `file:`, `chrome:`, `devtools:`, `data:` at top level, `plur1bus:`, `ipc:` or `tauri:`). Downloads go to a per-profile quarantine directory. Keeping or opening a download needs a harness approval when an agent started it, and a click when the person did.
- **Support window (CEF).** The panel refuses to load pages when its CEF is more than **60 days** behind the newest stable major on the update feed, and says why. This is enforced by the shell from its release metadata, with no network probe. The SPA keeps working.
- **WebView2 runtime (Windows).** Evergreen, serviced by Microsoft (DS39); the panel refuses to load pages below the minimum runtime version the release declares, and says why.
- **States.** The panel shows the design brief's states: *loading*, *agent-driving* (with *Take over* / *Stop*, §6.5), *error*, *login-required* (handover, §6.5).
- **Where there is no panel.** When the app is closed, on a remote harness with no app attached (an attached app still serves its panel over the DS9 relay), or headless, agent browser tasks run in the `plur1bus-browser` container (§6.15.3), which arrives in D3; the `browser` tool is engine-agnostic and works against WebView2, CEF or the container (DS37). The restricted-AppImage case (DS8) is open (§11 Q9). *History:* until 2026-09-27 the SPA showed the streamed container Chromium in the panel's place on Windows and on a restricted AppImage.

### 6.5 CDP token proxy and the `browser` skill (D3)

- **Transport.** The shell opens a CDP session per panel in-process: CEF `send_dev_tools_message` plus an observer (macOS, Linux); WebView2 `CallDevToolsProtocolMethod`/`…ForSession` plus `GetDevToolsProtocolEventReceiver` (Windows, DS38), with calls serialised per session because WebView2 may process CDP calls out of order (§4.23). No DevTools server or `--remote-debugging-port` is opened on either engine. `Target.*` stays denied to the harness; the shell alone uses `Target.setAutoAttach` internally to reach panel iframes.
- **Engine gaps the skill must respect (Windows, §4.23).** CDP key events do not trigger browser accelerators in WebView2 (WebView2Feedback #1278); key events carry no frame parameter (focus first); `Input.dispatchMouseEvent` is unverified until the D3 spike.
- **Local harness.** A WebSocket server on `127.0.0.1:<port>` (port leased from the D72 registry through `ports.lease`). Path `/cdp/<panelId>`. The client authenticates with a 32-byte random token in `Authorization: Bearer`. A request with an `Origin` header, or with a `Host` other than `127.0.0.1:<port>`, is rejected (no browser page, no DNS rebinding). The token and port go to the harness over the device connection (`panel.register`). They are never written to a file.
- **Remote harness.** The harness sends CDP frames over the shell's authenticated `/ws` connection (dialled outward, like the D51 node bridge). The shell forwards them to the named panel.
- **Filter (both paths).** Only panel targets are reachable. A method allow-list by domain applies:
  - allowed: `Page`, `DOM`, `Accessibility`, `Runtime`, `Input`, `Network` read and `Emulation` subset;
  - denied: `Browser`, `Target`, `SystemInfo`, `Storage`, `Tracing`, `IO`, `Network.getAllCookies`, and `Page.setInterceptFileChooserDialog` unless the harness attached an approval;
  - events outside the panel's session are dropped.
- **Visibility.** While an agent drives a panel, the panel shows a persistent "Agent is using this panel" bar with *Take over* and *Stop*. *Stop* closes the CDP session at once.
- **Skill.** The `browser` skill (harness side, D74) calls a handover when it meets a login or a CAPTCHA. The shell then pauses the CDP session and gives the panel to the person until they press *Done*. Credentials the person types stay in the panel profile. Page text reaches agents only as tool output, sanitised and marked untrusted (D55, D62 rule: page content is data, never instructions).

### 6.6 Computer-use onboarding (D4)

This shows only when the harness is local and D62 is enabled for at least one agent.

- **macOS.**
  1. Check that `CuaDriver.app` is installed (link to its upstream installer otherwise).
  2. Read the grant state from the driver's diagnose command.
  3. Explain the two grants in plain language.
  4. Open *Privacy & Security → Accessibility* and then *→ Screen & System Audio Recording* through `x-apple.systempreferences:` links.
  5. Re-check every 2 s while the window is focused.
  6. Name the known flapping issue (§4.7) with the re-toggle fix.
- **Windows.** UI Automation needs no grant. The screen shows only D62's safety summary.
- **Linux.** Wayland asks for consent through the desktop portal when a session starts. The shell explains the prompt before it appears. X11 needs no grant.
- **Every OS.** While a computer-use session runs, the tray icon changes and the menu offers *Stop computer use*, which calls the harness's kill switch. The PLUR1BUS app itself never requests either grant (DS10).

### 6.7 WebMCP (D55)

- **Provider direction.** The SPA registers its own tools when the webview offers `document.modelContext`. That behaviour belongs to the SPA and is unchanged in the shell. System webviews do not offer it today, so this adds nothing in D1/D2.
- **Consumer direction (D4, panel only).**
  1. If the embedded Chromium exposes WebMCP natively, the shell reads page tools over the panel's CDP session.
  2. Otherwise, it installs a small main-world shim with `Page.addScriptToEvaluateOnNewDocument`. The shim defines `document.modelContext.registerTool` and reports registrations through a `Runtime.addBinding` binding, so the panel gets no Tauri IPC.
  3. Descriptors go through `pageToolsToMcp(origin, tools)` (`@plur1bus/webmcp`: names limited to `[A-Za-z0-9_.-]` and 128 characters, always `untrustedContentHint`), then to the harness browser bridge. The bridge applies `isOriginAllowed` and the D30 approval to every call.
  4. `execute` results pass through `normalizePageToolResult`.
  5. A hostile page can call the binding with anything. Each payload is capped at 64 KiB, and a page may register at most 64 tools.

### 6.8 Native integration details (D2)

- **Tray.** On Linux the tray needs an AppIndicator host (GNOME: extension). When none is found, the app keeps its window in the taskbar and says so once.
- **Global shortcut and push-to-talk.** No default binding: the person chooses one. On Wayland there is no global shortcut (§4.6). Push-to-talk then works while the window is focused, plus a tray item. The GlobalShortcuts portal is a later option.
- **Microphone.** The macOS Info.plist carries `NSMicrophoneUsageDescription`. Webview media requests are granted only for the connection's origin.
- **Autostart** (moved to D1 by D77) starts the app minimised to the tray and, for a `bundled` connection, starts the runtime (`container system start` when `container system status` says it is stopped; Docker Desktop/OrbStack/Colima are started by their own login items, and the app waits up to 120 s for the socket) and then the harness containers. It is on by default for a bundled harness, because the harness used to be an OS service that started at login (§6.5); the toggle is in the tray and in settings. It never starts a `local` (native) harness — that one has its own OS service.

### 6.9 Security model

- **Trust zones.**
  - The Rust core is trusted.
  - The bundled shell pages are trusted code with no remote content.
  - The SPA is trusted for its own origin, because it is served by the harness the person paired.
  - Panel pages are **hostile**.
  - Deep links and anything on the command line are **untrusted input**.
- **IPC allow-list (DS7).**
  - `shell-ui` → `connections_list|add|remove|rename`, `pair_local`, `pair_code`, `open_connection`, `app_info`, `update_check|install|later|skip`, `update_settings` (channel, hold, automatic patches), and for the runtime controller `runtime_detect`, `bundle_install` (wizard: acquire image, create volumes and containers, start, auto-pair), `harness_start|stop|status|logs_tail`, `harness_upgrade|rollback`. None of them takes a free-form command, image reference, mount path or port from the page: images come from `bundle.json`, ports from the controller, and bind mounts (D2) from a native folder picker in Rust.
  - `spa-bridge` (runtime `add_capability`, `remote.urls = [<exact origin>/*]`, `webviews: ["spa"]`) → `shell_info`; in D2 `shell_notify_prefs`, `shell_ptt_bind`; in D3 `shell_panel_open|navigate|close|detach|attach|resize|handover_done`.
  - Every command checks, again, the calling webview's label and current top-level origin (defence in depth for the Linux iframe caveat, §4.5), and validates its input against a closed serde struct (`deny_unknown_fields`).
- **Navigation.** The `spa` webview may navigate only within its origin. Other links open in the system browser (D3: optionally in the panel). `window.open` of foreign origins is blocked.
- **CSP.**
  - Shell pages: `default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data:; connect-src ipc: http://ipc.localhost; object-src 'none'; base-uri 'none'; frame-ancestors 'none'; form-action 'none'`.
  - The SPA's CSP is the harness's (ADR-004, nonce-based, `frame-ancestors 'none'`).
- **No Node, no plugins with ambient power.** Tauri has no Node runtime. The app does not include `tauri-plugin-shell`, `-fs` or `-http` at all. Subprocesses are spawned from Rust with fixed argument vectors only: the Apple `container` CLI (absolute path resolved once from its install location and re-checked against its code signature, never from `PATH` alone), `plur1bus device pair` for a native local harness, and `open`/`installer` for the Apple `container` pkg the person confirmed. The Docker path spawns nothing: it speaks the Engine API.
- **The runtime is a privileged neighbour.** Whoever controls the runtime controls the harness (exec, volumes). The app therefore talks only to the runtime endpoint it detected and the person confirmed, shows that endpoint in *Settings → Runtime*, and never forwards runtime access to the SPA, an agent or a container.
- **Remote content isolation.** Panels have no IPC, no CDP towards the SPA, their own profiles, and no access to the device token or the session cookie. No shell code parses page text for commands. Page-originated strings shown in native UI (window titles, notification text) are truncated and shown as plain text only.
- **Browser panel rules (owner 2026-09-27, DS37; both engines).**
  - **No Tauri IPC, no capabilities.** The panel webview (label `panel-*`) appears in no capability file and no runtime `add_capability`; no capability ever lists a remote origin for it (`remote.urls` is never set for a panel), so a panel page cannot call any command, including `shell_panel_*`, which only `spa` may call. Every command re-checks the calling webview's label (above), so a panel is rejected even if a capability were misconfigured. Tauri ≥ 2.12.0 is required because 2.12.0 binds channel IPC queue entries to the webview that created them (§4.23).
  - **Separate profile.** Its own user data folder (Windows) or `data_store_identifier` (CEF) per egress profile, never the `spa`/`shell` store: no shared cookies, storage, cache or permissions with the app's own webviews.
  - **Downloads and file pickers through a policy.** Downloads land in the per-profile quarantine (§6.4) through `on_download` (WebView2) / CEF's download handler; keeping or opening one needs a harness approval when an agent started it and a click when the person did. File-chooser dialogs are intercepted: the person picks through the native picker, an agent only with a harness approval (`Page.setInterceptFileChooserDialog`, §6.5), and never from the app's data or state folders.
  - **Navigation limited to `http:`/`https:`.** Enforced in `on_navigation` / CEF's request handler for top-level and frame navigations, plus new-window requests; `file:` is refused, so the panel has no path to app data, the WebView2 UDF, logs or the keychain export.
  - **No debugging port** (DS9, DS38).
- **Deep links.**
  - `plur1bus://pair?origin&code` pre-fills the pairing form. The person must confirm with the origin displayed prominently. It never replaces an existing connection and never pairs on its own.
  - `plur1bus://open?path=` accepts only a relative path matching the SPA route allow-list, on the active connection.
  - Everything else is ignored and logged without its arguments.
  - Links arriving through the command line are treated the same way.
- **Updater (§6.11)** signatures are always checked, with one key per channel (DS12).
- **Logs.** App log directory, size-rotated. Tokens, tickets, cookies, `Authorization` headers and every URL's query and fragment are redacted by a single formatter with a test. Page content and page URLs from panels are never logged.
- **OS sandboxing.**
  - *macOS:* hardened runtime and notarisation. **No App Sandbox**: the controller runs the `container` CLI and talks to runtime sockets outside the app container, local pairing runs `plur1bus`, and CEF under the App Sandbox is not supported by the runtime. CEF helpers carry only the entitlements Chromium needs for JIT. No `disable-library-validation`.
  - *Windows:* per-user NSIS install without admin (`installMode: currentUser`). WebView2's own renderer sandbox, for the SPA and, since 2026-09-27, the panel (DS37); Evergreen runtime serviced by Microsoft (DS39). *History:* before DS37 there was no Windows panel until CEF's sandbox worked (DS8). MSIX/AppContainer is not planned for the direct channel.
  - *Linux:* deb/rpm install `chrome-sandbox` setuid (D3). AppImage gets the panel only when the runtime finds a working sandbox. Flatpak is an open question (§11).

### 6.11 Updates

- **Channels (DS12, D78).** `dev` is internal: CI builds of `main` for the owner, OS-unsigned (macOS ad-hoc), dev key, prerelease tag `desktop-dev`, never offered in a release build. Consumers see `beta` (opt-in) and `stable` (default). Each channel's feed is a static, minisign-signed `release.json` attached to a GitHub release (`v<semver>-beta.<n>` for beta, `v<semver>` for stable), next to the Tauri `latest.json`. In D1, `beta` and `stable` exist but carry **OS-unsigned** builds (the D1 dev/beta period); OS signing arrives in D2 (§11 Q1).
- **What an update is (DS24).** One version covers the app, `bundle.json` and the harness image digests. `release.json` = `{ version, channel, kind: major|minor|patch, security: bool, date, notes: { de, en }, migrationNote?: { de, en }, minFromVersion, bundle: <bundle.json digest>, tauri: <latest.json digest> }`, verified with the channel key before anything is shown. The app never updates from a branch, a commit or a tag outside the feed.
- **Checks.** At start (with an off switch) and on demand, never more than once every 6 hours. No identifiers are sent. An update is offered only when its version is higher than the running one and the running version is ≥ `minFromVersion` (otherwise the notes name the intermediate release to install first). The flow and its UI are §6.16.
- **Key custody.** The owner generates the three keys (`dev`, `beta`, `stable`) offline, keeps them in a password manager, and stores them in the GitHub Environments `desktop-dev`, `desktop-beta` and `desktop-release` (required reviewer: the owner). Rotation ships a release, signed with the old key, whose config carries the new public key. The key-loss procedure is documented in `docs/desktop.md`: users must reinstall once.
- **CEF duty (D3+).** A Chromium security fix is shipped to `stable` as a security patch release (§6.16.5) within **14 days** of the matching `cef` crate release. The panel's 60-day support window (§6.4) is the fail-safe.

### 6.12 CI, secrets, reproducibility

- **Workflows.**
  - `desktop.yml`: path filter `apps/desktop/**` plus nightly. Matrix `macos-15` (aarch64-apple-darwin), `windows-2025` (x86_64-pc-windows-msvc), `windows-11-arm` (aarch64-pc-windows-msvc), `ubuntu-24.04`, `ubuntu-24.04-arm`. Steps: fmt, clippy `-D warnings`, `cargo test --locked`, the TS tests of the shell pages, unsigned bundles as artefacts.
  - `container.yml` (D77): builds the harness image per arch natively, size gate, cosign signing and SBOM attestation on release, `docker run` smoke on both arches, and the real Docker/Podman end-to-end scenarios (§6.15.12).
  - `release.yml` (D78): on a `v<semver>-beta.<n>` tag from the release workflow only; runs the release gate (§6.16.4: matrix, kill soak, upgrade tests, notes lint, `release.json` schema), then signs with the beta key and publishes. `release-promote.yml`: manual, environment `desktop-release`, re-signs a beta's artefacts with the stable key after the canary period. `desktop-dev` builds stay a dispatch of `desktop-release.yml` with the dev key. Signing jobs run only in their approved Environment.
  - The **canary** job (nightly, from D1): build against Tauri 3 alpha + `tauri-runtime-cef` on all five targets. It is allowed to fail and is reported in the D-milestone test report.
- **Secrets are owner-held, never in the repo.** Only the release workflow sees `APPLE_CERTIFICATE`, `APPLE_CERTIFICATE_PASSWORD`, `APPLE_API_ISSUER`, `APPLE_API_KEY` and the `.p8` content, `TAURI_SIGNING_PRIVATE_KEY[_PASSWORD]` per channel, the Windows signing credentials (SignPath API token, or an OIDC federated identity where the chosen service supports it) and the Linux GPG key. Pull requests from forks run `pull_request` (never `pull_request_target`) and get no secret. Actions are pinned by commit SHA. `scripts/lint-hygiene.mjs` gains a check that fails when `*.p12`, `*.p8`, `*.key`, `*.pem`, `*.keystore` or a minisign secret-key header is tracked.
- **Reproducibility.**
  - Inputs are pinned: `rust-toolchain.toml`, `cargo --locked`, `pnpm --frozen-lockfile`, and in D3 the CEF version plus the SHA-1 from CEF's index and our own recorded SHA-256.
  - Build settings: `SOURCE_DATE_EPOCH` = commit time, `--remap-path-prefix`.
  - Outputs: a CycloneDX SBOM per target and GitHub build-provenance attestations for every artefact.
  - A nightly job builds the unsigned Linux x64 bundle twice and compares hashes. It is advisory until it has been stable for 14 days, then a gate. Signed artefacts are not expected to be bit-identical (signatures and notarisation tickets).

#### 6.15.2 Detection

1. **Apple** (macOS only): resolve `container` at `/usr/local/bin/container` (the pkg's location), verify its code signature, run `container system version --format json`; parse CLI and API-server versions. `container system status` decides whether the services must be started. A CLI below the minimum is "found, too old".
2. **Docker-compatible**: walk the §4.11 candidates in order, first `DOCKER_HOST`, then the current Docker context, then the fixed socket paths and pipes; each candidate must answer `/_ping` and `/version` within 2 s and report `Os: linux` (a Windows-containers engine is "found, wrong mode"). Rootful sockets that answer "permission denied" are reported as such with the fix (add the user to `docker` — which is root-equivalent, so the wizard recommends rootless or Podman first).
3. The result is a list of `{ runtime, endpoint, version, state: ready|stopped|too-old|no-access|wrong-mode }`, shown as is; DS14's rule picks the default. Detection runs at first start, when the person opens *Settings → Runtime*, and when the chosen runtime stops answering for more than 60 s (it never switches runtime silently).

#### 6.15.3 One container or two — the answer

**Recommendation: two containers by default in the long run (harness + browser from D3), one in D1, plus optional sidecars; never split the harness itself.**

| Candidate | Verdict | Why |
|---|---|---|
| (a) `plur1bus-harness`: supervisor + core + all modules (HTTP API, channels, MCP, scheduler, decision service, D70), wireproxy, tsnet | **One container, not divisible** | These processes share `run/*.sock` Unix sockets with peer-pid identity checks (ADR-012 §10.2), lifelines (pipes) and adoption (§6.4), the `node:sqlite` `BEGIN EXCLUSIVE` core lock whose exclusion is an `fcntl` lock inside one kernel (ADR-012 §5), and the single LanceDB/ONNX handle (T7). Across two containers pids are in different namespaces (the peer-pid checks and adoption stop working), and sockets and locks would have to cross a shared volume: on Apple every container is its own VM, so a shared volume is seen by two kernels and neither a Unix socket nor an `fcntl` lock nor SQLite's WAL shared memory crosses it (§4.10, §4.13); on Docker it would work only while both containers share one kernel, which is not something the design may depend on. Splitting would break ADR-012, not refine it. Channel modules (Telegram etc.) are ordinary core clients and belong here. |
| (b) `plur1bus-browser`: streamed headless Chromium (D74 b) with a small CDP/screencast server — **windowless cases only since 2026-09-27** (background tasks while the app is closed, a remote harness, headless; the in-app panel is native, DS37) | **Separate container (D3)** | *Memory pressure:* Chromium grows to gigabytes under real pages; in the same cgroup/VM it competes with the core's recall budget (400 ms soft / 600 ms hard) and makes the core a candidate for the OOM killer. A separate memory cap contains it. *Crash domain:* a renderer or GPU-process crash, or an OOM, ends the browser, not the harness. *Security boundary:* it renders untrusted content; on Apple it gets its own VM and kernel, on Docker its own namespaces, cgroup and seccomp profile, and it holds none of the harness's secrets or volumes. *Update cadence:* Chromium ships security fixes every 3–4 weeks (§4.2's CEF cadence mirrors it); the browser image is rebuilt and upgraded without touching the harness image or its data. *Cost:* on Apple a second VM with memory that is not returned to the host (§4.10) → cap 2 GiB by default, started on demand and stopped after 15 min idle. |
| (c1) SearXNG (D75) | **Bundled / remote / off** (DS25), off by default | Python stack with its own cadence, parses untrusted result pages, not needed by most people. *Bundled* runs `plur1bus-searxng` on the harness network, as before. *Remote* (the common case, owner 2026-09-27: his instance runs on his NAS) points at a URL — scheme, host, port, e.g. a Tailscale MagicDNS name or a `100.x` address — and reaches it through the configured egress path: tsnet inside `plur1bus-harness` for a tailnet address, or the host's own tailnet client for anything else the harness's egress profile can reach. *Off* disables the skill. A settings-page **connection test** probes the configured endpoint through the same egress path before saving. |
| (c2) Local model runtime | **Bundled (Linux/Windows, GPU-capable) / remote (host-native, all platforms) / off** (DS25, DS26) | ONNX embedding/reranker and the sherpa-onnx voice fallback stay in the core everywhere (CPU-sized by design, D34/D45) — this row is about large chat LLMs only. **Linux (Docker/Podman)** and **Windows (Docker Desktop/WSL2)** support a `plur1bus-model-runtime` sidecar with real GPU access (NVIDIA CDI on Linux, WSL2 CUDA paravirtualization on Windows, §4.17) or CPU-only without a GPU. **macOS** has no GPU path in a container (§4.17): large models run natively on the host (Ollama, LM Studio, MLX) and are reached as *remote* through `host.localModel` (DS17, D51 b); a bundled CPU-only container is an **opt-in fallback for small models only**, never the default there. *Remote* also covers any model server the person already runs, on any platform, reached the same way as SearXNG's remote mode. |

**Things that could affect each other, and where each lands:** memory pressure (Chromium, models) vs the core's latency budget → separate browser container with a cap, models on the host; crash domains → browser separate, harness processes already isolated by the supervisor inside; untrusted web content → browser separate, no secrets, no volumes, egress through the harness's proxy; update cadence → browser image separate. Nothing in the harness container needs isolating from the rest of the harness that the supervisor's process model does not already provide.

**How the two talk (D3):** the harness drives the browser over CDP behind a per-start token (D74). Docker: a user-defined network `plur1bus` plus an `--internal` network `plur1bus-internal`; the browser joins only the internal one and reaches the web only through the harness's egress proxy (D73, fail-closed by construction), and the harness reaches it by DNS name `plur1bus-browser`. Apple: one network per container and no bare-name DNS without an admin-created domain (§4.10), so both join network `plur1bus`; the controller reads the browser's IP from `container inspect` after start and hands `{endpoint, token}` to the harness through the host bridge (`browser.attach`), and Chromium is started with the harness proxy as its only proxy (policy-enforced, not network-enforced — a named Apple degradation, re-checked each `container` release). The token reaches the browser as a read-only single-file bind mount written by the app.

Alternative: host `tailscaled` with `tailscale serve` → the published loopback port. In container mode the harness does not trust `Tailscale-User-*` headers (requests arrive from the runtime's gateway, not 127.0.0.1); tsnet delivers identity in-process instead |
| WireGuard/SOCKS (D73) | harness container | wireproxy is userspace (no root, no routes) and runs as a supervised child inside, as designed. For D3 panels on the host the controller publishes the per-profile proxy ports to host loopback, which is a recreate (decided in D3) |

**Host bridge protocol (DS17).** The app opens `ws://127.0.0.1:<port>/ws` (loopback; `wss://` for a remote harness if the bridge is ever used there) with its device token and sends `bridge.hello { capabilities: [...] }`, listing only capabilities the person enabled. The harness answers with the capabilities it accepts, per its scope check (`bridge.serve` + the capability name). Every request (`bridge.call { capability, op, args, callId }`) is authorized by `authorize()` and subject to D30 approvals on the harness side; the app additionally enforces its own per-capability off switch and shows a tray indicator while `host.computerUse` is active. The bridge reconnects with the same backoff as the tray's event stream (1 s → 30 s). No capability carries a generic "run this" operation.

#### 6.15.5 Host ↔ container interface

- **API port.** Inside the container the HTTP API module binds `0.0.0.0:18700` of the container's own network namespace (it is not reachable from anywhere else unless published); the controller publishes it as `127.0.0.1:<host port>` only, the host port being the first free one in 18700–18799. ADR-001's "no listening TCP port except the harness API, loopback-bound by default" holds on the host. On Apple the container IP is also reachable from the host and from other containers on the same network (§4.10); the API requires authentication for everything but `/api/v1/meta` anyway, so this changes reachability for local processes only, not trust.
- **CLI.** The installer puts the native `plur1bus` binary on the host (`~/.local/bin` on macOS and Linux, `%LOCALAPPDATA%\PLUR1BUS\bin` on Windows; the wizard offers to add it to `PATH`, per user, and never writes to a system directory). With `~/.config/plur1bus/target.json` (`{ "mode": "container", "runtime": …, "container": "plur1bus-harness" }`, written by the app, no secret) the CLI answers `--help`/`--version` locally (T1 unchanged) and forwards every other command as `exec -i plur1bus-harness plur1bus <args>`, streaming stdio and the exit code. `--json` documents pass through byte for byte. The forward costs one `exec`; its latency is measured and reported in D1, and T1/T2 are not claimed for forwarded commands.
- **Nothing else crosses.** No runtime socket in any container, no `--network host`, no `--privileged`, no home-directory mount, no device passthrough.

#### 6.15.6 Volumes, state root, bind mounts, backups

- `plur1bus-state` → `/var/lib/plur1bus` = `PLUR1BUS_HOME` (D5's state root, in-container path). Contains `config.json`, stores, LanceDB, journal, `run/`, logs, installed modules (`<home>/modules/`, so `module install` survives image upgrades), the encrypted secret file.
- `plur1bus-models` → `/var/lib/plur1bus-models`, the engine's model cache (first run downloads the default embedding/reranker models with the existing licence gate, D34/ADR-006; roughly 600 MB per AGENTS.md).
- Apple volumes are sparse ext4 images with `ordered` journaling (default kept: `writeback` would weaken crash consistency for LanceDB and SQLite); size cap 64 GiB for state and 32 GiB for models at create time, changeable later only by migration (named in the D1 test report).
- **Backups.** A running volume image is not a consistent backup. D1: the upgrade snapshot (DS21). M8's `backup` (stores first, then config, users, sessions, dream ledger) writes into an optional person-added bind mount `…/PLUR1BUS Backups` (D2), which is the thing Time Machine / File History / a Linux backup tool should copy.
- **Environment passed at create:** `TZ` and `LANG` from the host (scheduler, dreaming and UI dates must match the person's clock), `PLUR1BUS_CONTAINER=1`, `PLUR1BUS_HOME`. Never a secret.

#### 6.15.7 Inside the harness container

- **Entrypoint:** `plur1bus init` as PID 1 (DS19): `waitpid(-1)` reaping, SIGTERM/SIGINT → `daemon.stop { budgetMs: 120000 }` then exit, supervisor respawn with the ADR-012 backoff (five crashes in 10 min → the container exits non-zero so the runtime or controller surfaces it, instead of looping inside).
- **The service manager is replaced**, not emulated: Docker `--restart unless-stopped` and `--stop-timeout 150`; Apple: the controller passes `stop -t 150` and runs the restart watch (poll `container list --all --format json` every 5 s while the app runs; restart with 1 s → 60 s backoff; five failures in 10 min → tray shows `crashed` with the last exit code and log tail). With Apple and the app not running, nothing restarts a dead container until the next login — acceptable because inside it `init` and the supervisor already restart everything short of the VM itself.
- **Unchanged inside:** `daemon status`, `1staid check`, `config`, `module`, `admin`, the journal, adoption. `service install|uninstall` and `update` answer `E_NOT_AVAILABLE reason=container-managed`; `1staid check` gains a `container` section (runtime-reported memory limit, volume free space, `secrets-locked`, image digest).
- **Hardening:** user `10001:10001`, read-only root file system with `tmpfs /tmp`, all capabilities dropped (Docker `--cap-drop ALL --security-opt no-new-privileges`; Apple keeps its reduced default set and gets no `--cap-add`), `--pids-limit 1024` on Docker. Resources: memory **3 GiB** by default (Apple's 1 GiB default is too small for the core with models), one slider 2–16 GiB in the wizard's *Advanced* view, CPUs `min(4, host cores)`. The wizard warns when the host has less than 8 GB RAM or when Docker Desktop's VM is smaller than the chosen limit plus 1 GiB.
- **Sleep/wake:** on wake the controller re-checks `/api/v1/meta`; only if it fails for 30 s on Apple does it run `container system stop && start` (the known post-sleep DNS issue, §4.10) and restart the containers.

#### 6.15.8 Upgrades, health gate and rollback (DS21, D78)

The person approves a release once (§6.16: *Jetzt*, or an allowed automatic patch). The app then updates itself with the Tauri updater and restarts; the new app sees that its `bundle.json` digest differs from the running container's and that `upgrades.json` (app config directory, no secret) holds a `pending` entry for this version, and continues without asking again. Every step is shown in the tray and in a progress page; the harness is unreachable from the stop (step 2) until the gate passes, and the notes say so ("Dauer etwa 2–5 Minuten").

1. **Pre-flight, harness still running.** Acquire the new image next to the old one (pull by digest, or load the bundled tarball) and verify its digest against `bundle.json`. Check free space (state volume used × 1.2 plus the image). Run `1staid check --json` on the **old** harness: a `fail` row stops the upgrade before anything changes, with that row shown ("PLUR1BUS hat schon vor dem Update ein Problem: …").
2. **Stop** gracefully (`daemon.stop`, 150 s runtime timeout).
3. **Checksummed snapshot.** A throwaway container from the **old** image, `--network none`, read-only root, mounts `plur1bus-state` read-only and a fresh volume `plur1bus-state-pre-<from>`, and runs `plur1bus state snapshot --src /src --dst /dst --json` (a new hidden container-mode command): it copies every file preserving modes and times, writes `MANIFEST.sha256` (sorted path, size, mode, SHA-256) and `SNAPSHOT.json` (`from`, `createdAt`, `fileCount`, `bytes`, `manifestSha256`), then **re-reads the copy** and compares it with the manifest (`state verify`). The app records `manifestSha256` in `upgrades.json`. Only after a verified snapshot is the snapshot of the previous upgrade removed. The `plur1bus-models` volume is not snapshotted (re-downloadable, and models are versioned by file name).
4. **Swap containers.** Rename the old container to `plur1bus-harness-previous` (kept, stopped). Create the new one with the same volumes, bind mounts, port and environment plus `PLUR1BUS_UPGRADE_FROM=<from>`, and start it.
5. **Migrations.** Config: the supervisor applies the `config.json` schema migrations `vN → vN+1` on load and writes `config.json.bak-<schemaVersion>`, as on a native install (core spec §4). Stores: the controller reads `engine.storeSchema { current, required }` from `1staid check --json` and, when they differ, runs `exec plur1bus admin migrate --from <current> --to <required> --yes --json`. A **patch** release never migrates (DS24); the release gate fails a patch whose upgrade fixtures show a schema change.
6. **Health gate** (all within 300 s, else failure): `ready`; `/api/v1/meta` reports the new version and a supported API major; the device token still authenticates (`GET /api/v1/auth/whoami` or M3's equivalent); `1staid check --json` has no `fail` row; **`admin smoke --json`** (new core RPC `admin.smoke`, CLI-only, never a WebMCP tool) returns `ok`: `PRAGMA quick_check` on every SQLite store, every LanceDB table opens, the embedding and reranker models load, then a synthetic fact is captured for the reserved agent `__smoke` (never listed, exported or dreamed), recalled at rank 1 within the hard recall budget, forgotten and purged, leaving no row behind.
7. **Success.** Clear `pending`, tray green, one notification "PLUR1BUS <to> ist installiert" with a link to the notes. `-previous` and the snapshot stay until the next successful upgrade (manual rollback, step 9).
8. **Failure at any step from 4 on → automatic rollback.** Collect a diagnostic (failed step, exit code, the last 200 log lines through the redacting formatter). Stop and remove the new container. Verify the snapshot against `MANIFEST.sha256` again, then restore it into a fresh `plur1bus-state` with `plur1bus state restore` in a throwaway container from the **previous** image; the failed state volume is kept as `plur1bus-state-failed-<to>` for diagnosis until the next upgrade. Rename `-previous` back, start it, and run the same health gate on the old version. Tell the person in plain words what happened: "Das Update auf <to> ist beim Schritt „Datenmigration“ fehlgeschlagen. PLUR1BUS läuft wieder mit <from>; deine Daten sind auf dem Stand von vor dem Update." with *Details kopieren* (the redacted diagnostic, for an issue). The failed version is marked *skipped* and is not offered again; the next release is. If the rollback's own health gate fails, the tray shows `Wiederherstellung fehlgeschlagen` and points to the manual recovery page in `docs/desktop.md`; nothing is ever deleted in that state (snapshot, failed volume and both containers are kept).
9. **Manual rollback.** *Settings → Version → Zurück zu <from>* exists while `-previous` and the snapshot exist; it shows the snapshot's time, warns that everything since then is lost, and runs step 8's restore path.

An **app** update that fails leaves the harness untouched (the Tauri updater replaces the app bundle atomically per OS; the harness upgrade only starts after the new app runs). Because the app supports the current and the previous image major (`bundle.json` range), a harness rollback never needs an app rollback.

#### 6.15.9 Image build, signing, SBOM, size

- **Images:** `plur1bus-harness` (D1) and `plur1bus-browser` (D3), `linux/arm64` and `linux/amd64`, one manifest list each. Base: the official Node 24 Debian slim image pinned by digest (glibc: LanceDB and onnxruntime prebuilds; musl stays out, D8). The Dockerfile only **assembles** artefacts built natively on `ubuntu-24.04` / `ubuntu-24.04-arm` by the normal release jobs (the Rust `plur1bus` binary, the bundled core and first-party modules, the skill) — no cross-compilation under QEMU, in line with milestones §5.2's "never in Docker" rule for arm64 builds.
- **Tags:** `<registry>/plur1bus-harness:<semver>` and `:<semver>-<sha>`; the app and compose file reference **digests**, `stable` exists for humans only. **Registry (§11 Q6, decided 2026-09-27):** not public for now; the images become **publicly pullable on GHCR** (`ghcr.io/cyb3rb1ade/plur1bus-harness`) from the project's first release on. Until then, D1 tests pull-by-digest against a private/local registry (plan `2026-09-27-desktop-app-d1.md` DR17) and the offline installer variant is the default install path.
- **Supply chain:** cosign keyless signing from the release workflow (GitHub OIDC, `id-token: write`), a CycloneDX SBOM per arch attached as a cosign attestation, and build provenance. The docs give the one-line `cosign verify` for VPS users with the workflow identity and the GitHub OIDC issuer.
- **Size budget (targets, gated in CI at +10 %):** harness image ≤ 350 MB compressed per arch (Node runtime, core, modules, native prebuilds; **no models** — they download into `plur1bus-models` on first run); browser image ≤ 700 MB compressed; the offline installer adds one harness tarball to the app bundle. D1 measures and records the real numbers.

### 6.16 Release and update policy (D78)

This section answers the owner's third point directly: updates must not break the installation (OpenClaw), and a consumer must not be exposed to a daily stream of upstream changes they cannot follow (Hermes). It applies to **every** install path: the desktop bundle, a native install's `plur1bus update` (M8) and a VPS running `compose.yaml`.

#### 6.16.1 What a consumer receives

- **Only versioned releases.** A release is a git tag `v<semver>` whose artefacts (app per target, `bundle.json`, harness image digests per arch, `release.json`, notes) were built once by the release workflow and passed the release gate (§6.16.4). Nothing a consumer installs is built from `main`, a branch or a nightly; the `dev` channel exists for the owner and CI only (DS12).
- **Channels.** `stable` (default) and `beta` (opt-in in *Settings → Updates*). A beta is `v<semver>-beta.<n>` and becomes stable **unchanged**: promotion re-signs the same bytes and digests with the stable key. Leaving `beta` never downgrades; the app waits until `stable` reaches the installed version.
- **SemVer with a product meaning.** *Patch* (`x.y.Z`): fixes only, **no store or config migration**, so rolling a patch back is always lossless; *minor* (`x.Y.0`): new features, forward migrations allowed, the previous minor's data still restores from the snapshot; *major* (`X.0.0`): the only place a breaking change may appear (removed command or setting, API major, a migration that cannot be reversed), always with a migration note. The harness API's own versioning (ADR-016) is unchanged; this is the product version the person sees.
- **Signed and inspectable.** App bundles are OS-signed (from D2, DS31) and updater-signed (DS12); images are cosign-signed with an SBOM and build provenance (DS20, §6.15.9); `release.json` is minisign-signed with the channel key.
- **Where the bytes and the pointer to them live (DS28).** App bundles, `bundle.json` and `release.json` sit on **GitHub Releases**; harness/browser images sit on **GHCR** (§6.15.9) — both a free CDN with no bandwidth cap (§4.21). The Tauri updater and `plur1bus update` never read a GitHub URL directly: they fetch the small, per-channel manifest at `https://updates.plur1bus.app/{channel}.json` (§6.16.7), which names the current GitHub Releases asset and GHCR digests for that channel. Moving hosting later — a different GitHub org, a different registry — is a new manifest, not a client update.

#### 6.16.2 Release notes

- Every release has `release-notes/<version>.de.md` and `release-notes/<version>.en.md`, **written for users**: what is new, what got better, what was fixed, what to know before updating, in plain sentences — not a commit list. Fixed headings (`Neu` / `Verbessert` / `Behoben` / `Sicherheit` / `Vor dem Update wichtig`, and the English equivalents); at most 25 lines per language for a minor and 10 for a patch; a **security** release says so in its first line and names the severity without exploit detail.
- A major release adds a **migration note** per language: what changes for the person, what the upgrade does automatically, what they may have to do, and whether rollback is possible.
- A CI lint (`scripts/release-notes-lint.mjs`) fails the release when either language is missing, headings or length are off, a line looks like a commit subject (`feat:`, `fix(…)`, a 7–40-character hex hash, a PR number without text), or a major has no migration note. The developer changelog (`CHANGELOG.md`, Conventional Commits) remains, for developers.

#### 6.16.3 The update dialog

- When a newer release exists on the person's channel, the tray shows a dot and the SPA a banner; nothing installs by itself (default). Opening it shows version, date, the notes in the UI language, the security marker, and for a major the migration note, followed by three buttons: **Jetzt** (install now; §6.15.8 runs), **Später** (remind at the next app start or after 24 h, whichever is later), **Überspringen** (never offer this version again; the next one will be). A security release offered as *Später* or *Überspringen* is offered again after 7 days, still skippable.
- **Version halten** (*Settings → Updates*): no update is offered until the switch is turned off; the tray shows "Version gehalten" so a held version is never forgotten. Holding also stops automatic patches.
- **Automatic patch updates are ON by default for new installations** (owner 2026-09-27, decides §11 Q8). *Nur Patch-Updates automatisch* installs a patch during the configured quiet hours (default 03:00–05:00 local, only when the app is running and no agent run is active; the notes are still shown afterwards) — always through the same snapshot → health gate → automatic-rollback path §6.15.8 already runs for *Jetzt*, so an unattended patch can never leave a worse installation than it found. The setting stays visible and can be turned off (existing installs that opted out are never re-opted-in by an update). Minor and major releases always need *Jetzt*, never automatic.
- **Where the same policy reaches the other paths:** a native install's `plur1bus update` (M8) reads the same signed `release.json` feed, shows the notes on the terminal, needs confirmation (or `--yes`), and uses the same snapshot → migrate → health gate → rollback sequence on the state root. A VPS gets the notes on the GitHub release page and a digest per release; `deploy/upgrade.sh` (D2) runs the same sequence for compose.

#### 6.16.4 Release gate in CI

A tag becomes a `beta` release only when all of these are green, and `stable` only after the canary period:

1. **Full test matrix** on the five targets (milestones §5.2), the system tests including the **kill soak** (200 turns; the nightly's 1 000-turn run green on the release commit), `desktop.yml` on the five targets, `container.yml` (image build, size gate, `cosign verify`, SBOM present, smoke on both arches).
2. **Upgrade tests from the previous two releases** (N−1 and N−2, and from the last release of the previous major when it is a major) on **synthetic data fixtures**: `tests/upgrade/workload.mjs` builds a state with synthetic agents, memories, sessions, config changes and the fixture module against the old release's image; CI stores the resulting state volumes as release assets (`upgrade-fixture-<version>-<arch>.tar.zst`, synthetic only). The gate restores each into a volume, runs the **real controller upgrade path** (Docker adapter, §6.15.8) to the candidate, and asserts the health gate plus content checks (each synthetic fact recalled, config values kept, module still installed, the device token still valid). It then injects a failing migration and asserts the automatic rollback restores the old version with a matching manifest. For a patch, it also asserts that no schema version changed.
3. **Apple `container`**: the recorded manual or self-hosted run (DS23) of the install and upgrade scenario on macOS 26 is attached to the release before promotion to `stable`.
4. **Release notes lint** (§6.16.2) and the `release.json` schema check.
5. **Canary on `beta`**: 7 days for a minor or major, 48 h for a patch, with no open issue labelled `regression` against the beta. A security patch may shorten its canary to 24 h with the owner's recorded approval; it still passes items 1–4.

Promotion to `stable` is a manual workflow (`release-promote.yml`, environment `desktop-release`, owner approval) that re-signs the beta's artefacts and `release.json` with the stable key and moves no bytes.

#### 6.16.5 Cadence and support

- A **stable minor every 4 weeks** on a published calendar (beta cut one week before), **patch releases** only when there is something to fix, **security fixes** out of band as soon as they pass the gate. A month with nothing worth releasing ships nothing; there is no "release because it is Tuesday". The owner may change the rhythm (2–4 weeks) in `docs/releasing.md` without a spec change.
- **Support:** the latest minor gets patches; the previous minor gets security patches for 4 weeks after its successor. The app supports the current and the previous harness image major (DS21).
- The engine pin (AGENTS.md: exact commit) and every dependency move only inside this rhythm; the consumer never sees an upstream change except as part of a release and its notes.

#### 6.16.6 How this differs from OpenClaw and Hermes

- **OpenClaw — "after every update it no longer works".** Here an update cannot leave a broken installation behind: it only starts from a healthy harness (pre-flight), keeps a verified snapshot, migrates explicitly, must pass a health gate that exercises recall, and **rolls back automatically** to the previous image and data when anything fails, telling the person which step failed. Before any of that, every release has been upgraded in CI from the previous two releases with synthetic data, soaked, and run on `beta` for a week. Breaking changes are confined to majors with a migration note. Field evidence from both projects (§4.13) also shaped where data lives: never on a virtiofs bind mount or in a writable container layer.
- **Hermes — "800 git changes a day that a consumer cannot follow".** Here a consumer never updates from git: they receive a tagged release on a predictable rhythm, with a short German/English note written for them, and decide *Jetzt / Später / Überspringen* or hold the version. Security fixes are marked. The volume of development on `main` is invisible to them until it is released.

#### 6.16.7 Update hosting: GitHub Releases/GHCR for bytes, the owner's own domain for the pointer (DS28)

- **Bytes:** app bundles, `bundle.json` and `release.json` are **GitHub Releases** assets (per-file ceiling 2 GiB, up to 1 000 assets, no total-size or bandwidth cap, §4.21); harness and browser images are **GHCR** (`ghcr.io/cyb3rb1ade/plur1bus-harness`, `-browser`, §6.15.9), which also carries the cosign attestations and SBOM natively.
- **Pointer:** neither the Tauri updater nor `plur1bus update` reads a `github.com` URL directly. Both fetch `https://updates.plur1bus.app/{channel}.json` — a small, **minisign-signed** document (DS12's per-channel keys: `dev`/`beta`/`stable`) shaped like:
  ```json
  { "version": "0.1.3", "notes": { "de": "...", "en": "..." },
    "platforms": { "darwin-aarch64": { "url": "https://github.com/.../PLUR1BUS_0.1.3_aarch64.dmg.tar.gz", "signature": "..." }, "windows-x86_64": { "url": "...", "signature": "..." }, "...": "..." },
    "harnessImages": { "linux/arm64": "sha256:...", "linux/amd64": "sha256:..." } }
  ```
  which is the shape `tauri-plugin-updater`'s dynamic-endpoint mode already expects (§4.4) plus the `harnessImages` extension `bundle.json` reads.
- **Why the indirection, not a direct pointer to either.** Pointing straight at `github.com/.../releases/latest` ties every installed copy to today's GitHub org, repo name and asset-naming scheme; a rename, a fork, or ever moving off GitHub would silently orphan the update check for people who cannot be reached to tell otherwise. Pointing straight at the owner's own webspace (`plur1bus.app` serving the bundles itself) would trade GitHub's free, uncapped CDN for one the owner pays bandwidth for and has to keep available, with no benefit — the manifest, not the bytes, is the part that must be reachable and owner-controlled. The manifest is the **only** thing on `plur1bus.app`; everything it names can move (a different GitHub org, a different registry, even a different CDN entirely) by publishing a new signed manifest, with no client-side change and no re-pairing.
- **Verification stays double.** The Tauri updater's own signature check (DS12, §4.4) still verifies the downloaded app bundle against the channel's embedded public key regardless of where the manifest pointed it; `bundle.json`'s digest check (DS20) still verifies the harness image regardless of registry. The manifest signature protects the pointer; the artefact signature protects the payload — a compromised or wrong manifest can misdirect the fetch but cannot make an unsigned or wrongly-signed artefact install.
- **Same shape for a native install and the VPS.** `plur1bus update` (M8) and `deploy/upgrade.sh` (D2) read the same `{channel}.json`; a VPS operator who prefers to pin a GHCR digest by hand (no app to run the updater) still gets the same release notes from the manifest for the terminal or the compose comment.

## 8. Acceptance criteria for D1 (each is a test or a recorded manual check)

1. **Fresh install, Docker path (CI, Linux x64 and arm64; rootful Docker, rootless Docker, rootless Podman):** from a clean runtime, the wizard with defaults loads the offline tarball (and, in a second run, pulls by digest), creates `plur1bus-state`, `plur1bus-models` and the container with exactly the §6.15.7 flags, starts it, auto-pairs, and the SPA opens logged in as the owner, with no question beyond the three wizard clicks. The harness port is bound only on 127.0.0.1 (test inspects the runtime's port bindings and probes the host's non-loopback addresses). Afterwards the app's data and config directories contain no byte sequence equal to the device token (scan). The keychain entry exists (memory store in CI, real keychain smoke on macOS/Windows).
2. **Fresh install, Apple path:** the same scenario passes against the fake `container` CLI in CI, and for real on macOS 26 (self-hosted runner or recorded manual run per DS23), including the `container system start` step and a `container image load` of the offline tarball (or the recorded fallback if Apple's loader needs its own archive format).
3. **Detection:** with fixtures for each §4.11 candidate (and none), `runtime_detect` returns the right `{runtime, endpoint, state}` list; a Windows-containers engine is `wrong-mode`, a permission-denied socket is `no-access`, an old `container` CLI is `too-old`; DS14's default choice is applied and never switched silently.
4. **Supervision in the container:** killing `plur1bus supervise` inside the container leaves the core running and adopted by the respawned supervisor (ADR-012 acceptance 3, now in container mode); killing PID 1 restarts the container (Docker restart policy; Apple controller watch against the fake CLI). `plur1bus service install` and `plur1bus update` inside answer `E_NOT_AVAILABLE reason=container-managed`. `docker stop` / controller stop lets `daemon.stop` finish within 150 s.
5. **Upgrade and rollback (D78):** upgrading to a second image digest keeps data and the device token, writes a snapshot whose `MANIFEST.sha256` verifies, runs the config and store migrations, and passes the health gate including `admin smoke` (which leaves no `__smoke` row behind). For each injected failure — new image never `ready`, a migration exits non-zero, `1staid check` reports `fail`, `admin smoke` fails, a corrupted snapshot file before restore — the controller acts as §6.15.8 says: automatic rollback restores the snapshot and `-previous`, the old version passes its gate, the SPA works again, the failed version is marked skipped, and the person sees the failed step; with a corrupted snapshot, nothing is deleted and the tray shows `Wiederherstellung fehlgeschlagen`. A pre-flight `fail` on the old harness stops before any change.
5a. **Update dialog and policy (D78):** a signed `release.json` with de/en notes is shown before anything installs; *Später*, *Überspringen* and *Version halten* behave as §6.16.3 says (tests with an injected clock); a `release.json` with a bad signature, a lower version, or `minFromVersion` above the running version is not offered; automatic patch updates are on by default for a fresh install (an explicit off survives updates) and never apply a minor or major; switching from `beta` to `stable` never downgrades.
5b. **Release gate (D78):** `release-gate` fails on a missing or commit-log-style release note, on a patch whose upgrade fixture shows a schema change, and on an upgrade from N−1 or N−2 synthetic fixtures that loses a synthetic fact; it passes on the D1 release candidate. Promotion re-signs without rebuilding (digests identical before and after).
6. **Host CLI:** `plur1bus --help` on the host answers without touching the runtime; `plur1bus daemon status --json` on the host prints the container's document byte for byte and its exit code.
7. **Host bridge:** with `host.keyUnlock` granted, a harness restart reports `secrets-locked` until the app reconnects and then clears it; with the capability off, the harness stays locked and says so in `1staid check`; a bridge call for a capability not granted is refused by the harness.
8. **Remote pairing** (secondary mode) with `https://<host>` and a code opens the SPA logged in the same way. An `http://` origin that is not loopback is refused before any request is sent.
9. After `plur1bus device revoke`, the next shell request returns the app to the pairing screen and the keychain entry is gone.
10. The SPA webview can invoke `shell_info` and nothing else. Calls from another origin, from a navigated-away page, or to any other command are rejected. A link to another origin opens in the system browser.
11. After quitting and restarting, the SPA is logged in again through a fresh ticket without re-pairing, and no session cookie survived on disk. A ticket is refused on second use and after 60 s.
12. A **tampered update** (payload, signature, or `release.json`) is refused. A correctly signed `beta` update installs and restarts after *Jetzt*: automated on Linux and Windows, a recorded manual check on macOS; a key from another channel is refused.
13. `desktop.yml` builds and tests on all five targets; `container.yml` builds, signs, size-gates and smoke-tests the image on both arches. The Tauri 3 canary result is reported.
14. The shell pages pass axe-core WCAG 2.1 AA and full keyboard traversal. The screen-reader pass is recorded.
15. The log-redaction test passes: a planted token, ticket, cookie and URL fragment never reach the log file.

## 9. Data flow examples

- **Bundled first run (primary).** Installer → app start → wizard → `runtime_detect` (Apple `container` 1.3.x ready) → Resources (defaults) → `container image load` of the offline tarball, digest checked against `bundle.json` → `container volume create plur1bus-state|plur1bus-models` → `container network create plur1bus` → `container run -d --name plur1bus-harness --read-only --user 10001:10001 -m 3g -p 127.0.0.1:18700:18700 -v … <image>` → `/api/v1/meta` ok, `exec plur1bus daemon status --json` ready → `exec plur1bus user create --owner --json` → `exec plur1bus device pair --json --kind desktop` → `POST /devices/redeem` → token → keychain → host bridge `bridge.hello {host.keyUnlock}` → secrets unlocked → ticket → SPA logged in → tray green. On Docker the same steps go through the Engine API (`/images/load`, `/volumes/create`, `/networks/create`, `/containers/create` with `RestartPolicy: unless-stopped`, `StopTimeout: 150`, `/containers/{id}/start`, `/exec`).
- **Release update (D78).** Feed check → `release.json` verified with the channel key → tray dot → dialog with de/en notes → *Jetzt* → Tauri updater installs the app, restart → new `bundle.json` + `pending` → pull/load image → pre-flight `1staid check` → stop → `state snapshot` + verify → swap containers → config migration, `admin migrate` if needed → health gate (`ready`, `/meta`, token, `1staid check`, `admin smoke`) → green, notification. On failure: diagnostic → remove new → verify + `state restore` → start `-previous` → gate → message naming the failed step.
- **Native local first run (attach mode).** App start → `run/api.json` found → `GET /meta` ok → *Pair* → `plur1bus device pair --json` → code → `POST /devices/redeem` → token → keychain → `POST /auth/session-ticket` → webview `/auth/ticket#t=…` → SPA logged in → the Rust side subscribes to `/events` → the tray turns green.
- **VPS.** On the VPS: `tailscale serve` → `https://vps.tailnet.ts.net` → loopback harness API. `plur1bus device pair` on the VPS (over SSH) prints a code. In the app: *Add remote* → origin + code → the same redeem/ticket path. Nothing crosses the internet outside the tailnet. No vendor relay (D35).
- **Agent drives the panel (D3, local).** Skill → harness `panel.cdp` → token proxy `127.0.0.1:<leased port>/cdp/<id>` → method filter → `send_dev_tools_message` → the page. The panel bar shows "Agent is using this panel". The person presses *Stop* → the session closes.

### 13.7 Responsive rules (normative, from `RspRules`, 2026-09-28)

These rules are **binding** for every page of the web UI (SPA) and for the D1 shell pages. They are transcribed from `RspRules`; the example boards (§13.6) apply them. Where an older `V2*` board disagrees, the rule wins (e.g. settings nav 224, not 204). Open points: C22 (44 px outside compact).

1. **Units.** All sizes are logical px (CSS px). System scaling changes device pixels only, never the layout. The layout follows the **window's content width**.
2. **Minimums.** Text **12 px** · targets **44 px** (C22) · window **800 × 600** (the shell sets it as the minimum window size).
3. **Breakpoints** (content width, CSS px): **compact < 1024** (400–1023) — icon rail, one column, secondary panels as sheets; must work down to **400** (the 800 px minimum window at 200 % text zoom). **normal 1024–1600** (both bounds included) — full sidebar 256 + content; the reference layout of every V2 board (1440 × 900). **wide > 1600** (1601 and up) — never stretch text; add **one** column or panel where the pattern has one, otherwise centre the capped content. Below the normal width only 2-D content — graph, kanban board, wide tables — may scroll horizontally; text never does. Reference widths: 400 (minimum at 200 % zoom), 720 (a 1440 window at 200 %), 800 (minimum window), 960 (compact examples), 1440 (reference), 2560 (wide examples), 3840 (4K window).
4. **Per pattern.**

| Pattern (board) | compact < 1024 | normal 1024–1600 | wide > 1600 |
|---|---|---|---|
| Kanban (`V2Main`) | rail; 2 columns visible, horizontal snap scroll; actions → *More* | as today | up to 5 columns + *Activity* panel 400 |
| Chat (`V2Session`) | transcript full width; context behind a *Context* button (sheet) | transcript + context 320 | transcript ≤ 820 + context 400 (+ browser column when open) |
| List + detail (`V2Memory`) | list only; detail as a pushed pane with *Back* | list + detail | list + detail + *Sources* column |
| Settings (`V2Settings`) | *Sections* button opens the nav as a sheet; single column | nav 224 + content ≤ 880 | nav + content ≤ 880 + *Related & help* panel 360 |
| Graph (`V2Topology`) | graph fit-to-width with zoom (+ / − / Fit, 44 px); legend and palette in a bottom sheet | as today | graph + *Inspector* panel 400 for the selected node |
| Wizard (`V2Setup`) | step rail → "Step 2 of 6" progress bar + *Steps* sheet; cards one column | rail 320 + content | rail + content ≤ 960 + *Your choices* summary 360 |
| Embedded browser (`V2Browser`) | full-window overlay | split with draggable divider (each side ≥ 360, 44 px handle, 50/50) | transcript ≤ 820 · browser flexible · context 400 (may collapse to a tab) |
| Detached browser (own window) | — | own window; the session shows "Browser is in its own window · Bring back" | same |

5. **Collapse order** (what goes first as the window narrows): (1) **right panel → sheet** — context, inspector or activity become a header toggle; the panel opens as a sheet from the right (360, full width below 600); (2) **full sidebar → rail** — 256 → 64 px icon rail; the menu button opens it as a 288 px overlay; (3) **list + detail → push** — one pane, the detail replaces the list, with a 44 px *Back* top-left; (4) **browser split → overlay** — full-window overlay with *Back to chat*; (5) **kanban → snap scroll** — columns keep 300 px (min 280) and scroll horizontally with snap, two stay visible; (6) **header actions → More** — the primary action stays in the header, everything else moves into a *More* (…) menu.
6. **Maximum and minimum widths.** Reading text ≤ 72ch (~720) · chat transcript ≤ 820 · forms and settings content ≤ 880 · dialogs (update, confirm) ≤ 680, centred, height ≤ window − 48 · wizard content ≤ 960 · kanban column 300–360 (min 280) · right panel 360 normal, 400 wide · sheets 360, full width below 600 · browser split sides ≥ 360 each · minimum window 800 × 600 · compact must work down to 400.
7. **Text zoom 200 %.** Browser or system text zoom divides the CSS viewport and the layout reacts to CSS px: a 1440 px window becomes 720 CSS px → compact; the 800 px minimum becomes 400 → compact, and must still work.
8. **System scaling.** 100 / 150 / 200 / 250 % multiplies device pixels only: logical 1440 × 900 = 1440 × 900 / 2160 × 1350 / 2880 × 1800 / 3600 × 2250 device px; breakpoints and layout stay the same, only sharpness changes.
9. **Assets.** Icons are inline SVG, stroke ≥ 1.6 at 16–24 px, no detail that exists only as a 1-px line; app-icon rasters are exported per platform (§13.8). Rasters at 1× / 2× / 3× via `srcset` (avatars, screenshots, wallpapers; a 32 px avatar ships 32 · 64 · 96 px files). Borders may be 1 logical px (they snap to device pixels), but no information is carried only by a 1-px line; every state also has text. Segmented controls: 44 wide, ≥ 38 high inside a 44 px row.
10. **Sidebar and sheets.** *Full 256* — normal and wide; labels, count and percentage badges, pinned projects; glass background, identity glow only on the active item. *Rail 64* — compact; 44 px targets, labels as tooltip and `aria-label`; count badges kept, percentage badges dropped. *Overlay 288* — compact, opened by the rail's menu button over a scrim (light `rgba(14,14,18,.32)`, dark `rgba(0,0,0,.5)`); Esc, the close button or a click on the scrim closes it. *Right sheet* — secondary panels in compact: 360 from the right, full width below 600; same scrim and Esc. *Bottom sheet* — legends and palettes over 2-D content (graph); grab handle, 44 px close button.
11. **Shell pages** (as drawn in the desktop sections of `v3 · Glow`, same rules): wizard window normal ≤ 1100 × 800, wide ≤ 1280 × 860 centred, compact fills; wizard rail 292, *Your choices* 316, cards in two columns from 560 content width; update and `.p1x` dialogs `min(680, window − 48)` × `min(760, window − 48)`, min 320 wide; settings windows use a 256 sidebar (64 rail in compact), content ≤ 880 and a 400 panel in wide; connections use a 240 sidebar (256 in wide), a detail panel in wide, and turn the form into a full-window sheet in compact; below 600 the footer hint moves above the buttons and GNOME buttons fill the row.
12. **Conformance.** Each SPA page and shell page is checked at 400, 960, 1440 and 2560 CSS px and at 200 % text zoom of a 1440 window (M3 acceptance, D1 Task 19); `prefers-reduced-motion` stops every animation (§13.1).
